# A11yScan：通过补充界面状态并结合运行上下文，发现更多且更可信的 Android 可访问性问题

## 一页读懂

| 问题 | 本文回答 |
|---|---|
| 研究中心 | Android 可访问性测试：既扩大可检查的界面状态，又减少规则检测的误报。它不使用 LLM。 |
| 为什么与 UX 探索直接相关 | 同一个页面在打开菜单、填写表单或修改另一页面的数据后，会呈现不同控件与属性；只统计进入多少 Activity 会漏掉这些状态中的问题。 |
| 新增方法 | 解析 APK 以直接启动 Activity，先组合控件状态进行深度优先探索，再返回关键页面查找间接状态变化；结合静态资源树与运行控件树复核 ATF 可访问性警告。 |
| 输入与输出 | 输入 APK、运行时布局和截图；输出已探索场景、可访问性问题与被识别为误报的警告。需要反编译资源和程序信息，不能称为纯视觉黑盒。 |
| 主证据 | 100 个应用中，A11yScan 获得 952 个界面场景和 3,991 个保留问题，Xbot 分别为 460 和 2,321；平均耗时约 15.15 分钟，对照约 2.52 分钟。 |
| 最重要的边界 | 不是按视觉缺陷概率给页面排序的风险搜索，也不是任意重叠、截断、溢出的通用检测器。覆盖收益伴随更多运行时间。 |

## 一段话介绍

可访问性检查器需要先到达具体界面，才能检查文字对比度、触控区域大小和辅助标签。只进入一个 Android Activity 并不足够：打开抽屉菜单、输入内容，或在别处新增数据后返回，都会改变当前页面。A11yScan 先扩大这些界面状态的覆盖，再把检测规则放回实际上下文中解释，例如区分真正的低对比度文字与被折叠、遮挡或设计为不显示的元素。它的价值是把“怎样到达可检查的状态”和“当前警告是否成立”同时纳入可访问性测试，而不是用访问新页面的数量代替问题发现能力。论文发表于 **ICSE 2025 Research Track**，所读为作者主页提供的正式 IEEE 排版版，13 页。

## 关键术语与阅读前提

- **可访问性 accessibility**：让存在视觉、动作等障碍的用户也能使用软件，例如文字具有足够对比度、按钮具有读屏标签、触控目标足够大。它与一般 UX 有交集，但不能代替所有易用性评价。
- **[Activity 与界面状态](../glossary.md#activity)**：Activity 是 Android 界面组件。一个 Activity 内可以有菜单、弹窗、填表前后等多个状态，不能把它直接等同于一张截图。
- **UI scenario，界面场景**：本文主要指有特定控件及属性的界面状态，不是 ScenGen 那种高层业务测试场景。两篇使用同一个英文词时粒度不同。
- **Activity-dependent / Activity-sensitive**：前者是页面内直接操作产生的状态，例如打开菜单；后者是此前其他操作间接影响的状态，例如在分类管理页新增分类后，主页多出一项。
- **ATF，Accessibility Testing Framework**：Google 提供的可访问性检查组件。它提供规则，不独立负责探索整个应用。
- **[静态资源树与运行控件树](../glossary.md#view-hierarchy)**：前者来自反编译的布局资源，反映预定义结构；后者来自运行界面，反映当前实际控件及属性。比较它们用于解释警告，不代表静态定义总是正确。
- **[测试预言 oracle](../glossary.md#oracle)**：本文的判错依据主要是可访问性规则及其上下文修正，不是让模型凭截图自由判断。

## 动机

论文针对两种相互独立的错误（Sec.I，第1–2页）：

1. **未到达状态导致漏检。** 一个 Activity 已访问，并不意味着其中的抽屉、对话框和新增数据后的状态都已检查。原文 Fig.1 中，在分类页新增分类后返回主页，主页会出现新的可访问性问题；只扫描最初主页看不到它。
2. **脱离上下文套用规则导致误报。** 某个 TextView 在截图中呈现较低对比度，可能是折叠、遮挡或当前未启用；直接把截图颜色当成其实际可见文字颜色可能产生错误报告。品牌图标、装饰内容和选中状态也需要按相应规则的适用条件区分。

因此，“多访问一些 Activity”和“把规则放在每张截图上运行”都不足以单独解决问题。

## 贡献

按作者 Sec.I 贡献列表归纳，核心产物是**方法**：

- 用界面状态组合与关键状态重访扩大可访问性检查范围。
- 用静态资源、运行时层次和控件属性修正规则警告。
- 发布 A11yScan 和实验所用应用材料。

作者还报告了规则误报来源与人工核查结果，但公开实现、使用 100 个应用并不自动构成独立 benchmark 或通用测试 harness。作者“首次处理显著误报”的表述是论文主张，不能据此认定 2026 年仍无其他方法。

## 方法与核心技术

### 1. 直接启动组件，先把可探索入口打开

输入是 APK。工具分析 AndroidManifest.xml 与 Java 程序信息，提取 Intent 的 action、category、data、type 和基础类型额外参数，用 ADB 命令直接启动 Activity（Sec.III-A，第4页）。

这一步可以绕开通常导航中的某些入口障碍，但依赖对包内信息的分析。直接启动也不保证满足该页面的数据、登录或环境前提；作者在局限中承认这会限制覆盖。因此不应把这种方式当成自然用户路径一定可达的证明。

### 2. 初始探索不是只把每个按钮点一遍

启动页面后，自上而下深度优先操作可交互控件；文本输入按 inputType 随机生成。工具进一步考虑控件状态组合，例如一个输入框的空/非空、复选框的选中/未选中、开关的开/关，三项二元状态共有八种组合（原文例子，Sec.III-A，第5页）。滑动页面会继续滚动，以呈现屏幕外内容。

关键是同一页面、同一控件在不同组合下可能具有不同属性。覆盖单位由“进入组件”细化到“进入能够改变检查结果的状态”。不过论文未给出一般情形下组合爆炸的系统预算分配规则，也未证明穷举复杂应用的所有组合可行。

### 3. 返回关键页面，寻找由其他操作间接产生的变化

第一次探索形成状态转换图后，工具选择**出度至少为二**的关键状态，再以自下而上的深度优先顺序重访（Sec.III-A、Algorithm 1，第5页）。出度表示从该状态能去往多少不同路径；作者用它近似判断该处是否承载更多逻辑、容易被其他操作影响。

例如原文分类管理的操作完成后，返回主页检查新增分类造成的显示变化。这不是已知“此页面容易溢出”后的风险排序，而是以结构连接性为启发式，扩大对间接变化的观察。

去重使用运行布局中控件的 resource-id、class、package 信息及 MD5 标识。方法说明强调状态变化，但仅靠这些字段是否充分区分属性变化，论文未给出完整形式化状态等价关系；不能自行补成包含所有颜色、文本、业务数据的语义状态。

### 4. 先产生规则警告，再查警告是否适用于当前状态

ATF 为当前页面控件产生可访问性警告，后台监测应用 SUPERVISOR 同时获得运行信息。A11yScan 构建两类树（Sec.III-B，第6–8页）：

- **静态资源树**：反编译 XML 布局中的控件分组、层次和预设属性。
- **动态资源树**：运行时实际出现的控件、层次和状态；代码动态创建的控件主要依赖此树及相邻节点提供上下文。

它据此处理三类情况：

| 警告来源 | 具体检查什么 | 输出边界 |
|---|---|---|
| 外部依赖或无效元素 | 包名、图片路径、文字、大小、可见性等，辨认第三方内容及当前不适用的组件 | 过滤不应按该条规则报告的问题，不意味着所有第三方内容都不需要可访问性保障。 |
| 界面呈现问题 | 比较静态/动态树中的节点、位置和属性；对动态新增控件参考同父节点的兄弟元素 | 原本的低对比度警告可能不成立；这不等于遮挡本身一定没有 UX 问题。 |
| 特殊界面设计 | 结合控件组、selected 状态、输入提示与正文等判断 | 对具有争议的有意设计作分类与注释，由开发者决定是否修改，不能将设计意图自动等同于符合标准。 |

原文 Fig.5 的 TextView 示例中，工具先用文本和父级层次把两棵树的节点对应起来，再比较静态的黑色文字属性与运行树中灰色属性，借此识别可能由折叠等呈现造成的误报。**这里是对“低对比度警告”的复核，不是已经提供完整的遮挡缺陷验证方法。**

### 5. 对 UX 探索与视觉 oracle 的直接启发

可迁移的是**检查目标决定状态粒度**：如果目标是文字截断，输入前后的同一页、弹窗覆盖前后、字号或显示模式改变后都可能需要分别检查。与此同时，一个视觉候选应保留上下文及原因，不应因为静态结构和截图不一致就直接认定有 bug 或无 bug。

以上是基于论文方法的研究启发，不是作者已经验证的截断检测方案，也不是已确认的新颖性。本文本身没有根据视觉异常分数动态选择下一个动作。

## 实验：覆盖、检测与误报分别支持什么

### 数据和配置

- Dataset-1：100 个真实应用，F-Droid 与 Google Play 各 50 个，覆盖开源与闭源应用。
- Dataset-2：20 个来自 Themis、与 GPTDroid 部分实验材料相关的应用，专门用于有限的 Activity 覆盖比较。
- Android 9.0 模拟器，1080×1920；ApkTool 反编译资源，UIAutomator 与 ADB 获取布局、截图及执行动作。
- 正文未明确报告统一等时预算、随机重复次数、取均值/最好覆盖的完整协议；不能自行补写多次均值。

### RQ1：发现更多问题是否来自更多状态

Table II、第9页：

| 工具 | 平均 Activity 覆盖 | 界面场景总数 | 保留问题数 | 去除警告数 |
|---|---:|---:|---:|---:|
| Xbot | 68% | 460 | 2,321 | 471 |
| A11yScan | 75% | 952 | 3,991 | 1,070 |

Xbot 不具备相同的上下文误报识别模块，作者人工检查并剔除其警告；A11yScan 的剔除主要自动完成。因而两列真值处理方式不同，应保留这一实验条件。滚动产生的截图会拼接，同一页面的各段不重复计算成多个场景。

3,991/2,321 约为 1.72 倍，意味着保留问题数量更多。作者将 `(3991−2321)/3991=41.84%` 称为降低漏报率，**但分母是 A11yScan 找到的问题，不是独立标注的全量真值**，所以不能把它解释为对整个应用缺陷集合测得的召回提升。

平均单应用耗时正文为 **15.15 分钟 vs. 2.52 分钟**；引言写 15.16 分钟，存在轻微取值差异。约六倍时间意味着不能由上述数量直接断言单位时间缺陷发现效率更高。

### RQ2：场景覆盖与现有探索器的比较

同一 100 应用集合中，SceneDroid 获得 661 个场景、66% Activity 覆盖，A11yScan 为 952、75%（Table III，第9页）。这支持其补充间接变化状态的价值，但不能区分各策略的独立贡献，因为没有报告完整模块消融。

与 GPTDroid 的 **73% vs. 71%** 不是在同一实验环境下重新运行双方工具：作者运行 A11yScan 于 20 个可得应用，引用 GPTDroid 预印本的整体覆盖结果；原文承认工具不可得。因此应视为辅助背景比较，不能作为严格复现实验或统计等价证据。

### RQ3：所谓 90.56% 是哪一个准确率

1,070 个被分类为误报警告的来源为外部依赖/无效元素 564、呈现问题 371、特殊设计 135；约占全部 5,061 个初始警告的 21%。它不是以独立全量真值测得的通用误报率下降 21 个百分点。

用户研究抽取 20 个应用的 963 个警告，由三位接受可访问性培训的应用开发相关参与者核查；前两人独立标记，第三人处理分歧。A11yScan 标出 170 个误报，人工确认其中 154 个，`154/170≈90.59%`，正文报告 **90.56%**。应保留原报告和计数差异，而不能改写为全体 963 个结果的总体分类准确率或对全部真实误报的召回率。材料中已经突出工具给出的潜在真假标记，也可能影响独立判断。

正文 Table II/Fig.6 使用 1,070，第9页说明段落一处写 1,071；本笔记按表格与三类求和保留 1,070，并记录这一不一致。

## 局限

**作者承认（Sec.V，第11页）**：数据与环境依赖限制入口可达性；随机文本输入处理复杂功能不足；规则可能漏掉只有实际使用读屏等辅助技术时才能触发的问题；跨平台需要适配 Android 专属 API。

**我们的观察**：

- 探索和检测目标相关，但尚非基于缺陷风险或新发现反馈的自适应搜索；不能据此声称已解决 UX 导向探索。
- 需要 APK 内部资源和代码信息；复杂混合、动态绘制或资源缺失场景的适用性不能由 100 应用结果无限推广。
- 规则一致性、原始静态定义和用户偏好是三种不同依据。特别是“有意弱化”设计，仍可能影响障碍用户；开发者意图不能自动覆盖标准要求。
- 无全量可访问性真值、统一等时比较及模块消融；“多发现问题”“更快”“更准确”需要分别评价。
- 研究对象是可访问性警告，不是每条都具有开发者确认或修复记录的独立 bug。正文没有提供 3,991 条问题逐条提交、确认和修复的统计。

## 和我们课题的关系

### 与 UX testing 的关系

直接相关。它补充 UI-Lens 静态截图评测之外的两个环节：通过控件组合与跨页面操作暴露更多状态；用层次和运行状态解释视觉候选。对遮挡、重叠、溢出工作，最值得借鉴的是把“同一页面不同状态”作为检查单元，并区分“错误类型判错”和“界面本身有问题”。其对呈现误报的处理不能直接充当通用截断/遮挡 oracle。

### 与 GUI testing 的关系

代表**非 LLM 的测试目标感知场景探索 + 规则与上下文联合 oracle**。它说明即使研究主体是 LLM agent，也需要比较状态覆盖定义、既有图搜索及规则复核，而不能只与另一个通用 agent 比任务完成率。后续可考察风险排序或主动操作验证是否在相同预算下提高真实 UX 缺陷发现；这是待验证假设。
