# SUDFinder：直接渲染 Android 布局，比较设置变化前后的视觉关系

## 一页读懂

| 问题 | 本文的回答 |
| --- | --- |
| 研究什么 | 字体、语言、旋转和主题等系统设置变化后，页面是否出现颜色不协调、错位、间距异常或重叠裁切？ |
| 为什么旧方法不足 | 随机点击难以到达所有布局；“设置改完再改回来应一致”不能发现只在目标设置下出现、恢复后消失的问题；只看设置后的截图也容易把正常空状态和省略号当缺陷。 |
| 本文新增什么 | 先从真实设置相关显示问题归纳视觉关系，再抽取 APK 的 XML 布局、注入测试 Activity 直接渲染，比较设置变化前后的组件关系。模型主要负责填充布局中缺失的文字，不是最终裁判。 |
| 输入与输出 | 输入 Android APK、XML 布局、测试设置；输出违反颜色/对齐/间距/重叠关系的候选报告。实际可达性与真实影响需要人工复现确认。 |
| 主要证据 | 308 条历史问题实证；29 个应用实验，129 条报告中人工验证 98 条真问题，精确率 0.76，涉及 11 个应用；作者报告 67 条得到开发者确认、37 条已修复。 |
| 关键边界 | 主要检测 XML 定义的样式问题；直接渲染不等于真实业务页面可达，不能涵盖所有动态界面、功能语义或所有 UX 缺陷。 |

## 一段话介绍

当用户放大字体或切换语言、主题、横竖屏后，原本正常的 Android 页面可能出现文字裁切、元素错位和颜色不协调。本文认为，检测此类问题同时受“能否看到相关组件”与“如何判断设置变化是否合理”限制。SUDFinder 从 APK 中取得 XML 布局，给应用注入专门展示这些布局的测试 Activity，减少真实业务导航造成的覆盖障碍；再用模型补全运行时才有的文字，采集布局结构及像素显示范围，比较设置前后组件的颜色、对齐、距离和重叠关系。论文在 29 个应用中人工验证了 98 个此前未知问题，但也发现关系变化本身可能是合理适配。因此，它提供的是有特定适用边界的显示 oracle，而不是“视觉上不同就一定错误”的通用判断器。

## 关键术语与阅读前提

- **设置相关显示问题（SUD）**：Setting-Related UI Display bug，即系统设置改变后应用未正确适配而产生的显示问题。不是所有显示缺陷都由设置变化触发。
- **XML 布局**：Android 项目用来声明按钮、文字、容器及其大小、位置、颜色的配置文件。它描述初始界面，运行代码还可能修改它。此文处理 APK 内部配置，不能写成纯截图黑盒方法。
- **Activity**：Android 的页面承载组件。本文注入的测试 Activity 直接加载指定布局，绕过原页面通常需要的登录、导航或错误状态。
- **控件树边界与可见内容边界**：前者是组件布局框，后者是其中非透明像素的最小包围矩形。文字在框内左移时，布局框可能不变，但实际显示位置已经变化。
- **关系型 oracle**：判定正确与否的规则不直接给出整页标准截图，而约束设置前后两个组件之间应保持的关系。可理解为一种设置变换下的[蜕变判定](../glossary.md)：先有基准观察，再检查变换后的关系，而非要求所有像素不变。
- **精确率与召回率**：98/129 表示报告中有多少为真；没有所有真实缺陷的完整清单，就不能据此得到“全部问题找回了多少”的召回率。

## 动机

论文的 Signal-Android #11258 示例中，切换暗色主题后文字变白，但背景没有对应变化，导致提示难以阅读。问题不仅在于能否识别低对比：正常业务中还要进入特定页面或错误状态才能看到对应提示，随机点击未必触发。另一方面，改回浅色主题后页面恢复正常，使用“切换后恢复”的一致性规则也可能完全看不到异常（Sec. II-C，Fig. 1–4）。

由此产生两个独立问题：一是如何覆盖布局与组件；二是如何知道哪些适配变化应该一致。SUDFinder 对前者采用布局强制渲染，对后者采用从真实问题总结的视觉关系。这与让 LLM 自由探索全部页面、再凭常识找错的路线不同。

## 贡献

1. **实证贡献**：在原 218 条显示问题上补充 90 条，得到 308 条问题的分类、代码位置、功能影响与用户评价。这里是带数据与人工分析的实证研究，不是文献综述。
2. **方法贡献**：结合 XML 布局强制渲染、模型补充文本及关系判定的 SUDFinder。
3. **评价与资源**：公开实现、问题数据与实验材料，并在新应用上验证实用性。作者在 Sec. VI 明确提出标注数据可支持回归与评价，因此可记录为有特定任务范围的数据基准；不能当成端到端自由探索 benchmark。

## 方法

### 整体流程：覆盖布局，再检测适配关系

输入 APK → 抽取 GUI XML 布局 → 为布局注入测试 Activity → 给缺少运行时文本的控件补充内容 → 构建并执行测试应用 → 在默认及目标设置下采集布局/像素 → 必要时滚动收集新露出的组件 → 检查四种关系 → 生成候选报告。论文评价阶段再回到真实应用人工复现，确认问题是否实际存在（Sec. IV–V）。

工具没有先生成完整的自然语言用户任务，也没有把复杂业务流程规划作为主要创新；它有意绕过部分流程来覆盖布局。

### 1. 测试 Activity 怎样扩大可观察范围

测试 Activity 调用 `setContentView` 加载指定 XML。这样即使正常应用要登录、等待网络错误或通过深层菜单才能显示某段布局，也能先单独呈现它。论文同时检查屏幕能否横向/纵向滚动，执行滚动并收集新露出的组件，避免把大字体后移到屏幕之外的组件直接当作消失（Sec. IV-B）。

这是一种**针对内部配置的覆盖策略**，不是学习出更短点击路径。强制渲染会丢掉部分原页面运行时代码和状态，因此只是另一种有取舍的观察方式。

### 2. 模型补文字，而非直接判断最后的 bug

很多 TextView 的实际文字来自服务器，XML 中没有内容；若直接渲染为空，文字溢出等问题不会发生。SUDFinder 将应用名、XML 文件名和 XML 代码交给模型，要求只输出补充文字后的 XML，再重建测试应用（Fig. 11）。虽然作者使用 MLLM，展示的提示输入本身是这些文字和代码信息；不能擅自补写为“模型读取当前截图后填字”。

默认 GPT-4o，另比较 Qwen-VL、GLM-4.1V。模型生成的是合理的测试文本，不保证等于真实服务器返回内容；文本长度差异也会改变是否触发换行和裁切。

### 3. 将每个组件表示为可测量的对象

组件包含三个信息：控件树中的布局矩形、覆盖该框内非透明像素的最小矩形、两种最主要颜色。两种边界并存，是为了发现“布局框没变，内部文字却移位”的问题。颜色由图像颜色统计取得，不是让模型自由描述颜色（Sec. IV-C）。

### 4. 四种判定关系各自检查什么

| 关系 | 比较规则 | 能揭示的问题与边界 |
| --- | --- | --- |
| 颜色变化一致性 | 默认设置下颜色相同的两个组件，改变设置后是否仍保持相同颜色 | 发现部分组件未跟随主题适配；不是直接用 WCAG 对比度阈值判断所有文字是否可读。 |
| 对齐一致性 | 默认有左/右/顶/底/水平中心/垂直中心对齐的两组件，改变后是否完全失去对齐 | 依据实际可见内容矩形；排版合理重排也可能触发。 |
| 距离一致性 | 可见内容中心的水平或垂直距离变化是否超过阈值 | 默认阈值为屏幕宽/高的 10%；屏幕旋转等导致合理屏幕结构变化的设置需要区别处理。 |
| 重叠一致性 | 两组件改变前后的可见区域重叠关系是否不同 | 用于发现遮挡、容器与内容不协调等；不代表准确还原了被裁掉的不可见文字。 |

算法展示为遍历页面内组件对，比较默认与目标设置的关系。**并非“任何视觉变化都错”**，每条规则有自己的前提；但这些前提仍是经验启发式，可能不符合具体应用设计。

## 核心技术与研究价值

### 从历史问题推导规则，而不是将所有 UX 现象混成一个类别

308 条报告包含两大类：样式相关 T1（222 条）和语义相关 T2（86 条）。样式细分为颜色变化不一致 111、对齐不一致 63、距离不一致 36、包含/重叠不一致 34，另有两例其他样式；子类可交叉，不能将这些数量直接相加当独立总量。语义类包括元素应消失却仍显示、数据处理和翻译问题。SUDFinder 实现主要针对 T1，**分类覆盖 T2 不等于工具也检测 T2**（Sec. III、IV-A）。

历史问题中 188 条位于 XML、120 条位于应用代码。这是选择配置层方法的依据，也预告了它会漏掉代码动态生成状态。168 条影响功能、140 条主要影响非功能体验；仅 22 条表现为崩溃，因此只检查 crash 不足以评价显示问题检测。

### 关系变化仍需判断是否损害用户任务

Fig. 13 的 KeePassDX 示例中，大字体后 Username 与 Password 不再对齐，工具报警，但人工认为使用和视觉协调都未受破坏。这个反例表明：几何一致性是候选依据，不是用户影响的充分条件。若后续研究主动滚动、展开或点击，应明确想验证的是信息可达、可读或可操作，而不能把“恢复某条几何关系”直接当真实缺陷定义。

### 覆盖与 oracle 应分开比较

和随机探索相比，强制加载 XML 找到更多特定布局问题，但也漏掉只有运行代码才能生成的状态。和通用 MLLM 看图相比，关系型 oracle 引入了设置前后的参照，而通用模型基线只看目标设置下的单张图。两者不同的不只是“是否用模型”，还包括输入和可用证据。不能把实验简化成规则方法全面胜过 VLM。

## 实验

### 实证研究怎样形成问题基础

在旧数据 218 条 SUD 问题之外，作者从活跃 Android GitHub 项目筛选，937 个候选项目经报告规模和人工检查得到 58 个；85,479 条报告经关键词及状态过滤为 1,247 条候选，人工确认新增 90 条。两个作者分类、讨论到一致。数据补充截至论文提交时，未给出可直接当作 2026 全领域统计的固定截止日。

另选 15 个应用问题，在 AMT 获得 60 份有效回答，以五点量表询问功能及 UX 影响。平均 62.0% 和 59.4% 回答分别给出功能/UX 影响 4–5 分。这是对所选问题的主观评价，不是全部 Android 用户的普遍比例（Sec. III，Table III）。

### 检测实验的对象与配置

从 F-Droid 选择活跃、GitHub 星数较多、可安装且注入后能运行的应用，排除历史实证样本、游戏、演示/重复项目，最后 29 个，覆盖 13 类。实验使用 Pixel 7 模拟器、API 35、1440×2960 分辨率。

字体/显示大小使用三组：默认/默认、最大显示/默认字体、最大显示/最大字体；语言默认英语，目标西班牙语、印地语、阿拉伯语，包含从左到右和从右到左语言。论文亦分析主题和旋转问题，但没有把所有设置组合的遍历预算、完整运行时矩阵和总耗时统一列成可复算协议，不能声称穷尽设置组合。

### 主结果及开发者反馈

默认模型版本生成 129 条候选，人工在原应用中构建到达路径并检查真实视觉效果，确认 98 条真问题（精确率约 0.76），来自 11 个应用；其余 31 条误报。论文报告 67 条开发者确认、37 条修复/合并修复。**37 不应另加到 67 上得到 104 个，98 也不是所有 29 应用的真实缺陷总数。**

Table VI 按类型列出真阳性/报告数：颜色 15/22、对齐 46/60、距离 26/34、包含 11/13。对于原先找到的 98 条真问题，作者再进行三次独立重复，95 条每次检出，另 3 条取决于生成文本长度。不能将此改写成“整套新缺陷实验三次均值为 98”。

### 消融解释哪些模块有用

- **去掉模型填字**：60 真问题/83 报告，精确率 0.72；完整方法覆盖这 60 条并额外得到 38 条。说明测试内容是否充实会影响显示缺陷暴露。
- **替换为随机探索**：49/62，精确率 0.79。与完整方法交集 40 条，随机法独有 9 条，完整法独有 58 条。净计数差 49，不等于完整法在随机法基础上额外找到 49 个且不丢失任何问题。
- **替换填字模型**：Qwen 96/134（0.72），GLM 98/132（0.74）。不据此推断所有模型在所有 UI 任务上等价。

### 对照工具与直接看图基线

Table VI 中 SetDroid 10/12、dVermin 11/13、ITDroid 17/25。SetDroid 中有代码触发的 crash 和系统事件状态，SUDFinder 无法检测；dVermin 还有 SUDFinder 因内容边界恢复不足漏掉的问题。因此本文支持互补，不能说替代所有已有工具。由于各工具的探索覆盖和 oracle 不同，这也不是在完全相同截图上纯比较判错能力。

直接 MLLM 基线从随机探索的 174,000 张截图中按应用/设置采样 435 张独特状态截图，为模型提供 SUD 分类规则和当前截图。GPT-4o 报告精确率 24/273≈0.09，Qwen 44/208≈0.21，GLM 38/324≈0.12；分母是模型输出的问题报告，不是 435 张截图。示例中，模型将无数据空页误判为暗色模式内容缺失，将本就存在的省略号误判为放大字体引起的截断。**这不能支持“所有视觉大模型都不行”**：基线未给设置前后的完整对照，也不是 UI-Lens 等专门训练模型。

### 原文数字与机制中的待核对点

1. Sec. IV-B 介绍中写“文本关联 24 个问题”“测试 Activity 比随机方法多 35 个”；但 RQ6 与 Table VI 分别给出额外 38 个、净差 49 个及交集 40/独有 58。正文没有解释口径变化。本笔记保留两者，并以结果节完整计数解释实验，不混用。
2. Sec. II-C 对 dVermin/ITDroid 适用设置的个别表述混杂；有关工具边界以相关工作与实验配置为准，不能据该句称 ITDroid 只检测文本缩放。
3. 视觉边界定义仅包含布局框内非透明像素；其如何从渲染背景中稳定分离所有内容，以及跨滚动/设置匹配组件的完整实现细节，正文没有全部展开。实验已展示被裁掉内容无法准确恢复导致漏报，不能补猜为 OCR 自动还原完整原文。

## 局限

**作者承认的**：Sec. IV-A 不覆盖 T2 语义问题；布局注入不能保留全部动态代码；Sec. V 指出合理重排导致误报、不可见内容边界恢复不足导致漏报；Sec. VI-C 指出历史数据代表性、人工判断主观性、应用选择和模型非确定性。

**我们的观察**：排除注入后不能运行的应用使适用性取决于框架和可重建能力，不能直接泛化到 Compose、Flutter 或所有闭源商业应用；默认关系假设不保证符合设计意图；主动滚动能补观察，但正文没有证明它解决所有可滚动裁切误报。主要报告精确率和不同工具发现的问题集合，尚无完整真实问题清单可得总体召回率。

## 和我们课题的关系

### 与 UX testing 的关系

这是 UI-Lens 之外与遮挡、重叠、裁切直接相关的重要路线：用**设置前后关系**约束判断，而非只对单张图做缺陷识别。其滚动收集新增组件也表明，主动操作复核已有先例；因此“用滑动减少误报”本身不能直接宣称未被研究。可以进一步检验：在真实业务状态中，针对候选选择何种操作才能最有效证明信息可达或功能受损，以及怎样保留基准状态、避免误将合理重排当 bug。这些仍是需要比较现有工作的研究假设。

### 与 GUI testing 的关系

同时涉及定向覆盖与 oracle：布局注入选择更容易触发特定显示问题的状态，视觉关系提供判定依据。它也提供对照思路：自由探索、布局强制渲染与真实业务路径分别能发现哪些问题，哪些候选能在原应用中复现。应将生成测试状态、检测候选、人工复现和开发者确认四层结果分开统计。
