# GUITester：在定向导航中主动插入测试意图，并区分应用缺陷与智能体操作错误

## 一页读懂

| 问题 | 本文回答 |
|---|---|
| 研究中心 | 智能体能走到目标页，不代表会主动报告缺陷。本文研究任务内的探索性缺陷发现，而不是单纯提高导航成功率。 |
| 为什么重要 | 绕开失效按钮可能帮助完成任务，却掩盖产品问题；点击后没反应，也可能是点错坐标，不能一律报 bug。 |
| 核心方法 | 规划器插入替代路径、边界输入和状态验证；执行器操作后，监测器先发现异常，反思器再结合标注操作点的轨迹判断原因。 |
| 主要产物 | GUITestBench：12个 Android 应用中的26个已知真实缺陷扩展为143个任务；GUITester：四角色协作框架。 |
| 主结果 | 三次运行的 Pass@3 下，最好配置 F1 为48.90%，对应骨干的直接测试提示基线为33.35%；单次平均 F1 分别32.18%与22.95%。 |
| 与显示缺陷的边界 | 论文的 UX 主要指交互流程问题；作者明确尚未覆盖重叠、文字错位、标签截断，不能将其当作 UI-Lens 同任务的显示检测器。 |

## 一段话介绍

通用 GUI agent 通常以完成用户任务为目标。当按钮失效时，它可能寻找其他入口，或把界面没变化归因于自己点错，从而不报告真实问题。GUITester 保留自然语言导航任务，但在执行中加入有检查目的的操作：尝试同一功能的另一入口、输入边界数据、验证控件是否响应。每次操作后先判断是否出现异常，再回看带有实际点击位置的截图轨迹，区分应用缺陷与智能体错误。论文同时提供有真实缺陷和预期行为的交互式评测集合，支持把导航、触发、识别与报告分开观察。正式发表场合为 **Findings of ACL 2026，非 ACL 主会论文**；所读正式版共23页，含大量附录与案例。

## 关键术语与阅读前提

- **探索性测试 exploratory testing**：边操作、边观察、边调整检查方向。本文仍给定导航任务，因此不是完全无任务的全应用覆盖探索。
- **[测试意图 test intent](../glossary.md#test-spec)**：额外插入的检查目的。例如普通任务要求搜索产品，测试意图会要求输入空串或特殊字符，并观察反馈。
- **Goal-Oriented Masking，目标导向掩盖**：为了完成任务而绕开异常，使异常未被记录为缺陷。它是作者对行为现象的概括，不是训练阶段做了因果验证的结论。
- **Execution-Bias Attribution，执行偏差归因**：把产品失效误当作 agent 点错、动作类型不对等自身错误。
- **PEM，Planning Execution Module**：规划与执行模块，包含 Planner 和 Executor。
- **HRM，Hierarchical Reflection Module**：分层反思模块，包含先捕获异常的 Monitor 和后判断原因的 Reflector。
- **[测试预言 oracle](../glossary.md#oracle)**：工具运行时靠模型推断预期；评测时则由已知缺陷说明、触发规则和裁判模型判断检测是否正确。两者不能混为一谈。
- **Pass@1 / Pass@3**：本文前者是三次独立运行的分数平均，后者表示三次中至少一次检测成功。后者不代表一次运行的可靠性。

## 动机与原文案例

Fig.1、第2页的任务涉及清理已经完成的待办事项。点击清理后，已完成项目仍在列表中：

- 通用 agent 可能通过其他方式删除项目，最终完成任务，却不保留原按钮失效的证据。
- 另一个 agent 可能认为自己没有点到正确位置，继续尝试操作。
- 测试器应先保留前后界面的差异与实际动作，再判断是不是产品问题。

因此研究问题不只是“下一步点哪里”，还包括“为了检查什么而点击”“遇到异常时是否停下来确认”“看到异常后如何避免错误归因”。

## 贡献

按 Sec.1、第2页归纳：

1. 将任务成功偏向与异常归因不清作为探索测试的问题提出。
2. 建立 **GUITestBench benchmark**：可交互运行、包含真实已知缺陷和两类不同引导强度的任务。
3. 提出 **GUITester 方法**：主动插入测试意图，分离异常捕获与原因判断。

分类为 problem、benchmark、method。不能因为四角色协作就自动归为通用 harness，也不采信“首个探索性测试 benchmark”作为独立核实的排他结论。

## 方法与核心技术

### 1. 从用户目标生成导航子任务和检查子任务

输入包括自然语言目标、当前截图观察和历史上下文。Planner 生成子任务序列，每一项可以是推进任务的导航，也可以是探测潜在问题的检查（Sec.4.1，第4–5页；Appendix B/Fig.6，第11–12页）。

三种检查模式具有不同含义：

| 模式 | 原文例子 | 相比普通导航新增什么 |
|---|---|---|
| 替代路径 | 除菜单入口之外，尝试通过收藏图标进入收藏列表 | 检查另一个入口是否能到同一功能，增加可触达的交互路径。 |
| 边界条件 | 搜索框中输入空串或特殊字符 | 检查非典型输入，而不是只输能完成任务的合理关键词。 |
| 状态验证 | 点击新增文件夹按钮并确认是否打开创建界面 | 将“按钮应有反馈”明确变成检查目标。 |

这些意图穿插在正常任务中，论文没有给出基于布局缺陷概率、信息增益或 UX 风险分值的统一排序目标。因此它是**任务内的主动检查策略**，不是完整的风险驱动全局搜索算法。

### 2. 执行器负责动作，监测器避免把异常绕过去

Executor 使用已有 GUI 模型，将子任务和当前截图转换为点击、输入、滑动等动作。工具实际操作 Android 模拟器，再获得新截图。它不需要源代码或控件树来支撑所报告的视觉交互流程。

Monitor 结合当前子任务、前后观察和动作输出三种状态（Sec.4.2，第5页）：

- DONE：子任务完成，交给下一个任务。
- CONTINUE：尚需继续当前子任务。
- FAIL：发现无响应、结果不符合预期或跳转异常等，先暂停这一子任务并交给归因模块。

这里“暂停”是为了保留问题并分析，避免执行器立刻改走另一条路。FAIL 尚不等于确定 bug。

### 3. 在截图上标出操作点，再区分产品问题和操作错误

Reflector 回看当前子任务的交互轨迹及截图，把实际点击点画到图上，判断失败是否源自点错位置、动作类型或输入错误，还是应用没有按预期响应。它输出归因及给规划器的修正建议。

对导航操作的 agent 错误，可以纠正或重新规划；对于失败的测试意图，正文说明不让它持续阻塞主导航，允许从当前状态继续探索（Sec.4.2，第6页）。附录 Algorithm 1 给出在重试/步数约束下自纠与重规划的控制流程，但没有报告统一 MaxSteps 的具体数值。不能自行填入固定步数上限。

因此架构的关键不是“多了四个 agent”，而是**让主动试错、异常观察与原因解释承担不同职责**。异常标记与原因判断的分离，也防止执行器一边为任务成功找替代路线、一边决定是否应报告问题。

### 4. 完整案例：测试意图怎样改变实际探索

Appendix G.1/Fig.15、第13及20页中，任务执行到 Fox News 搜索功能时，工具插入特殊字符输入，观察到返回了与查询无关的内容。普通导航只用有意义的关键词，可能不触发这一状态。

这说明检查意图能够改变输入分布。不过“特殊字符应被禁止或返回空结果”的具体预期依赖搜索产品语义；论文未提供该案例的开发者确认记录。不能把模型认为不合理的返回结果直接升级为已确认 bug。

## GUITestBench：必须区分缺陷、任务与运行

### 来源与缺陷类型

Sec.3、第3–4页：从公开 GitHub issue 收集 **12个 Android 应用、26个真实缺陷**，再形成 **143个任务**。同一个缺陷可以对应多个任务，因此 143不是独立 bug 数，也不能把任务级结果称为26类全新缺陷的发现率。

作者分两层描述问题：

- UI 功能问题：某个组件的实现错误。
- UX 问题：跨操作的交互逻辑或任务流程异常，难归于单一坏组件。

具体模式为操作无响应 ONR、结果与预期不符 UTR、导航逻辑错误 NLE。这里的 UX 和本仓库关注的“遮挡、重叠、溢出”等显示缺陷不是同一分类口径。三模式交叉形成 UI-ONR、UI-UTR、UI-NLE、UX-UTR、UX-NLE 五项评价。

正文给单步触发62.24%、多步触发37.76%，这些比例与143任务整数更吻合，不能直接换算为26个独立缺陷的整数分布，原文分母没有充分解释。

### 两类任务故意控制探索难度

- **缺陷导向任务**：从人工复现轨迹生成较明确的动作级要求，主要看 agent 能否识别和报告。
- **探索导向任务**：从缺陷前后意图组合生成更高层任务，并筛选必须经过目标缺陷位置才能完成的任务，以同时测试导航、触发与识别。

Appendix A.1、第10页补充：候选任务会由 agent 实际尝试，仅保留能到达缺陷位置的任务。这有利于可执行性，但也意味着其“探索”是在已知缺陷附近人为构造的条件，不代表从任意应用主页自由搜索未知 bug 的实际分布。

### 运行时 oracle 与评测裁判严格分开

单操作缺陷的评测检查到达目标状态并执行精确触发动作；多操作缺陷由 Claude-4-Sonnet 接收**已知缺陷说明、前提、触发步骤、预期结果、参考图与执行轨迹**后判断（Sec.3.2、第4页；Appendix A.2/Table 3、第10–11和22页）。

GUITester 的 Monitor 没有这一完整已知缺陷答案，而是预测操作后应出现的状态。故不能把裁判规则当成工具运行时已获得的 oracle；也不能将对已知缺陷的轨迹判定当成对任意未知缺陷的可靠证明。

指标以任务为单位：Recall 是143任务中正确检测目标缺陷的比例；Precision 是报告缺陷的任务中正确检测目标缺陷的比例；F1 综合两者。论文未展示独立人工标注与模型裁判的一致性统计，单操作规则是否同时完整验证正确报告内容，也缺少细粒度协议说明。

## 实验

### 设置

- 六个开源骨干：GUI-Owl 7B/32B、MAI-UI 8B、UI-TARS 7B/72B/1.5-7B，以及 Mobile-Agent-V3 工作流。
- 基线增加统一的测试角色提示与缺陷检查表，不能说它们完全没有接受检测提示。
- GUITester 的 Planner 与 Reflector 用 Qwen3-VL-Plus，Monitor 用 GPT-4o，Executor 分别替换为三个 GUI 骨干；执行器温度0.1。
- 1080×2400 Android 模拟器，143任务，三次独立运行；Pass@1取平均，Pass@3按至少一次成功。
- 正文未报告完整 Android 版本、每任务时间/步数预算、API费用与模块调用成本，未报告逐模块消融或统计显著性检验；不能把多模块总体提升归因于某一个模块已经独立验证。

### 总体结果

Table 1、第6页，UI-TARS-1.5-7B 对应配置：

| 指标 | 加测试提示的骨干 | GUITester |
|---|---:|---:|
| Pass@1 Recall | 16.73% | 28.10% |
| Pass@1 F1 | 22.95% | 32.18% |
| Pass@3 Recall | 26.95% | 47.90% |
| Pass@3 F1 | 33.35% | 48.90% |

Pass@3 F1 相差 **15.55个百分点**，Pass@1相差9.23个百分点。48.90%不是单次检测准确率，也不是143个独立新缺陷中近半被发现。

同样 Pass@3 下，GUITester 在 UI-NLE 的 F1 为71.20%，但 UX-UTR仅12.50%、UX-NLE为26.10%。因此总体提升不能掩盖跨操作体验问题仍较难。Table 2 按任务粒度分组，也显示多动作问题的表现低于单动作问题。

正文用“显著提升”描述结果，但未给正式统计检验；本笔记将其理解为报告数值的明显差异。

### 真实发布版本案例及其证据边界

Sec.5.3及Appendix G展示 ESPN、Fox News、Booking.com、Harbor Freight、Pinterest 历史版本中的异常：按钮无响应、查询结果不符、返回后键盘未收起、产品链接跳错、关闭弹窗后菜单也被关闭。

它们说明工具能够给出有操作证据的候选问题，但未报告广泛应用集合上的候选总数、开发者确认/修复数及独立误报率。不能把这些示例写成已确认新 bug 发现统计。

## 局限

**作者承认（Sec.7，第9页；Appendix F，第13页）**：

1. 固定等待可能误报。附录 Zillow 例子中3秒缓冲不够，慢加载被当作异常；等待更久又会降低效率并错过瞬态问题。
2. 模型自己推断的预期可能错误。ESPN中 UFC 页面进入 MMA 被误认为跳错，暴露领域知识不足；正文对 UFC/MMA 的具体措辞不影响“错误预期导致误报”的主旨。
3. 导航模型动作空间限制可测交互。作者以股票图表缩放举例；这是论文对所考察模型的观察，不能外推为2026年所有 GUI agent 永远不支持缩放。
4. **未覆盖重叠、错位和截断等布局缺陷。** 它们被列为后续工作。

**我们的观察**：

- 26缺陷扩成143任务，任务间相关性强；与不同数据集上其他方法的准确率不能直接排名。
- 探索任务预先构造为必须经过缺陷位置，不能证明无目标发现未知 UX 问题的效率。
- 规划、监测与反思使用额外强模型，缺少成本匹配基线及消融，无法单独量化“插入意图”和“分离归因”的贡献。
- 干净无缺陷任务覆盖、模型裁判一致性与报告去重未充分说明，真实部署的误报率仍需额外评测。
- 特定页面元素消失是否违反设计，需要外部依据或重复验证；模型常识不是稳定的产品需求。

## 和我们课题的关系

### 与 UX testing 的关系

直接启发的是**让探索行为服务于检查目标，而非只到达页面**，以及把“候选异常”和“异常原因”分开判断。对显示类 UX 工作，可以考察任务中插入展开、滑动、键盘显示/关闭等检查动作，避免 agent 为完成任务主动绕过异常；这是基于方法的扩展假设。本文未验证截断、遮挡、重叠检测，不应替代 UI-Lens 或显示专用 oracle。

### 与 GUI testing 的关系

它明确区分任务完成与测试成功，为“探索—触发—判错”的分工提供直接研究样本。其 benchmark 还能启发分开评价：是否到达目标、是否执行触发动作、是否正确报告、是否把 agent 错误误归产品；但应补独立缺陷数、自然任务分布、干净样例及可靠真值，不能直接复制143任务得分作为通用质量证据。
