# Agent for User：让多个手机代理分别扮演用户，协调触发直播、通话等交互功能

## 一页读懂

| 问题 | 本文回答 |
|---|---|
| 与一般手机agent有何不同 | 不是一个用户独自完成任务，而是User1发出邀请、User2接收，必要时User3加入；必须协调设备和顺序。 |
| 新增什么 | 按用户分配虚拟设备与子任务，每设备一个LLM代理，用显式切换用户动作交接控制。 |
| 输入与输出 | 输入按User编号组织的任务；读取每设备控件树；输出跨设备GUI动作与任务完成结果。 |
| 判错从哪来 | 任务自动化主要负责触发交互。工业平台用日志检查crash，非崩溃交互失败主要由人工监控确认；不是模型独立判定所有bug。 |
| 主结果 | 24任务成功率75%、动作相似度85.9%；两位开发者比较耗时2.46 vs20.02分钟。工业3318任务完成70.09%，失败中人工识别26个bug。 |
| 边界 | 多agent不自动等于多用户测试；本文有明确不同用户设备。75%不是缺陷检出率，26个没有完整确认/修复分项。 |

## 一段话介绍

直播连麦或群组通话需要多台设备协作：一方发邀请，另一方必须在有效期内接受，普通单设备探索很难稳定触发这样的功能。本文从按用户编写的任务说明出发，分配虚拟手机，每台手机配一个GPT-4代理。代理读取自己设备的控件树，选择点击、输入、返回等动作；完成当前阶段后用切换用户命令把控制交给另一台设备。主要贡献是**自动执行跨用户任务**。工业缺陷发现建立在这个执行能力之上，尤其非崩溃错误仍由人工判断，不能把方法总结成自主生成完整多设备oracle。

## 关键术语与阅读前提

- **[多用户交互测试](../glossary.md#multi-user-interactive-testing)**：不同用户几乎实时交互，彼此操作和反馈有关。例如主叫发起通话后，被叫应收到邀请并能接听。
- **[多agent](../glossary.md#agents)**：本文每个agent对应一个用户和设备，不是对一个手机配置规划员、执行员等不同角色，也不是多个浏览器单纯并行增加覆盖。
- **虚拟设备池**：用服务器运行大量Android模拟环境，按需分配设备；论文称镜像物理设备配置，不能据此认为模拟器完整复现所有硬件缺陷。
- **[控件树](../glossary.md#view-hierarchy)**：表示当前界面的节点、文字、类型、可点击性和嵌套关系。本文主要给模型简化XML，不是将完整屏幕截图直接交给视觉模型。
- **[最长公共子序列LCS](../glossary.md#action-sequence-similarity)**：保留顺序、允许跳过不匹配动作，找生成序列与人工序列的共同部分。相似度衡量轨迹贴近程度，不等于功能验证完备性。

## 动机

作者分析TikTok内部7870条功能测试描述，经两作者独立标注、讨论与内部开发者裁决/复核，报告40.31%涉及多用户交互；这些描述用于一年52个开发周期。该比例是此内部任务集合的分布，不是所有手机应用的多用户比例（Sec.II-B，第2–3页）。

原文直播邀请案例显示两类困难（Fig.1–2，第1、3–4页）：不同屏幕或设备上目标用户可能需要滚动才可见；同时，被邀方必须在邀请发出后且过期前回应。只写“点击接收”或多个设备独立随机点击，不能保证交互按业务顺序触发。本文因此把设备分配、按用户拆任务、控制交接纳入自动化。

## 贡献

按作者Sec.I（第2页）：①识别多用户交互功能测试问题；②提出多agent LLM自动化方法；③在24任务、开发者时间实验及工业平台上评价。主要记`method`，包含问题经验，但不是以公开新benchmark或独立oracle为核心贡献。虚拟设备池是工业支撑能力，不应把5918设备写成每个实验都使用的设备数。

## 方法

### 1. 分配设备与子任务

输入采用类似 `User1: sends a voice call to User2; User2: accept the call` 的格式。正则识别 `User[1–9]`，统计不同用户并从池中随机分配相应设备。再按User编号切分各自的任务说明。根据内部先导经验先启动User1，而不是预先生成完整跨设备依赖图（Sec.III-A/B，第5页）。

设备池在395台ARM服务器上配置5918虚拟设备，每服务器64核ARMv8.2、128GB内存、1TBNVMe、1Gbps网络。模拟设备的CPU、存储、内存、屏幕及厂商服务配置；匹配Wi-Fi/蜂窝网络接口，并配置GMS/HMS等服务。作者引用既有负载研究说明同时承载能力，本文没有重新做5918台并行agent的扩展性消融（第4–5页）。

### 2. 把当前GUI压缩为模型可读信息

UIAutomator提取XML层级，保留 `resource_id`、`class`、`clickable`、`text`、`content_desc`。去除颜色、IME等无关属性，并深度优先简化只含单节点的嵌套布局容器，降低token和层级复杂度。该操作帮助语义理解，也可能遗漏视觉或布局异常；本文没有检验其显示信息保真性（Sec.III-B，第6页）。

### 3. 推断动作并交接控制

每个agent分别运行于线程，使用自己的LLM实例，避免混淆不同设备页面。提示给出分配任务、动作原语与当前简化界面，模型每轮输出一个动作，正则解析方括号格式，ADB执行后继续读界面。论文定义五类动作：`[tap] [element]`、`[input] [element] [value]`、`back`、`[switch] [user]`、`end task`。

其中switch是核心：主叫代理完成发起呼叫后切给被叫，后者观察自己的来电界面再接受。后续先后关系由执行中判断，而非所有agent无协调地持续同时点击。`end task`由模型判断本任务已完成且无需交互后发出。正文**没有在五类原语中列scroll**，尽管动机讨论了小屏幕滚动需要；不能自行补出滚动控制器或自动处理所有设备差异。

论文未详列失败动作的自动恢复上限、所有任务的统一步数/超时终止规则、switch错误的重调度机制，或隐式账户准备协议。不要把方法补写成具有完善重试与业务回滚的工作流系统。

### 4. 缺陷判定属于后续链路

在工业Fastbot平台，事件日志启发式识别crash；无法完成的非崩溃任务交给人工监控和内部系统定位功能问题（Sec.IV-C，第8–9页）。Fig.7的案例中一台手机发起通话，另一台没有出现应有来电，造成任务无法继续；**这是跨设备预期缺失，不是单屏文字遮挡**。单纯没有完成也可能是模型点错、界面不支持或响应过慢，所以没有把所有失败都算bug。

## 核心技术及失败例子

本文对“多用户”的限定包括多位用户、交互提示（通知/弹窗）、近实时回应。它明确不把普通用户提交预约、管理员审批的管理流程当成本研究核心，也区别于没有此类提示反馈的普通协同编辑（Sec.II-A，第2页）。综述引用时应保留这一范围，不替作者扩展为所有分布式业务。

TableI列24种任务，含直播邀请、群聊转让、视频通话、一起看、分享后转发等，多数2人、部分3人。原始描述含全局用户编号，agent因此知道自己的动作对象，但论文没有给完整共享消息字段、全局状态数据库或跨设备一致性断言机制（第3–6页）。

失败检查揭示自动化链路的三类边界（Fig.5，第7–8页）：①滚动评论需要约2秒内回应，模型推理结束时评论已消失；②分享链接要经过Facebook等第三方应用，跨应用往返复杂；③同屏两个“+”让模型点错后陷入错误路径。这些分别是时限、跨应用执行和控件歧义，不应归并成产品UX错误或oracle失败。

## 实验

### RQ1：任务能否完成、动作是否贴近人工

24条最常测任务来自上述内部集合，由两作者手动执行得到真值轨迹。TableI中动作列称任务所需总动作，而Sec.IV-A又报告平均每设备6.7动作；**两处统计口径不同/说明不足，不把6.7写为跨设备总动作均值**。LLM相关结果运行3次，正文未完整解释每次成功结果如何合并为百分比及波动（第7、9页）。

成功率分母是任务；动作相似度为 `2×LCS长度/(生成序列长度+真值序列长度)`，不是逐步严格精确率。基线AdbGPT加switch支持并用相同LLM配置；Monkey、Humanoid也启动对应数量设备，各工具预算2小时。正文该预算位于随机工具对比段，未清楚给所有LLM每任务的独立步数/耗时上限，不笼统写“每agent严格2小时”。

| TableII（第7页） | 任务成功率 | 动作相似度 |
|---|---:|---:|
| 本文 | 75.0% | 85.9% |
| AdbGPT | 29.2% | 55.6% |
| Monkey | 4.2% | 不计算 |
| Humanoid | 8.3% | 不计算 |

相对AdbGPT差值为45.8和30.3**个百分点**，不是相对提升45.8%。随机工具并非围绕指定任务设计，因此低成功率说明该目标下能力不足，不能直接外推成总体缺陷发现能力弱。论文没有拆掉设备交接、XML简化、用户拆分的消融，所以不能量化每项贡献。

### RQ2：与手写自动化脚本比较

两位至少3年经验的内部开发者，在安静独立环境为24任务编写工业脚本；计时从写脚本开始到设备上全自动完成。本文方法平均2.46分钟、手写20.02分钟，作者报告节省87%，Mann–Whitney U `p<.05`（第8页）。该比较衡量一次任务自动化准备/执行成本，不是持续回归总成本或缺陷修复耗时；设备池搭建、模型费用、长期维护未完整计入。

### RQ3：工业任务与bug来源

在2024年8–9月约一个月的部署中运行3318条任务，完成70.09%；在失败任务中人工识别26个交互bug。论文未给完整“报告—开发者确认—修复”计数和缺陷类别分项，因此只记人工识别26个，不写26个均修复。没有失败任务全量真值，不能由70.09%倒推误报率，也不能把26作为模型自主oracle准确率（第8–9页）。

上线触发条件为新功能描述或新版本回归。虚拟设备先承担多数任务，物理设备进一步发现硬件相关问题；本文没有测量虚拟/物理缺陷一致性的完整分母（Sec.V，第9页）。

## 局限

**作者承认**：时限敏感任务受LLM延迟限制，第三方跨应用与模糊控件困难（Sec.IV-A，第8页）；任务泄漏/人工标注/随机模型输出威胁，通过新标注、内部审阅和3次运行缓解（Sec.V-B，第9页）；更多应用适用性是讨论，未实际广泛验证。未来拟本地模型降低延迟、扩展跨应用交互（Sec.VII，第10页）。

**我们的观察**：主要是特定任务的执行，非独立多设备oracle；人工介入bug确认是重要条件；24常测任务偏已知场景，输入User编号约束明确；未报告交接模块消融、完整超时策略、LLM费用及不同硬件的具体成功分布。设备池规模不能替代方法规模实验。

## 和我们课题的关系

### 与 UX testing 的关系

截图候选、布局树复核和主动滑动通常关注一个页面，本文提示还可能需要观察**另一用户设备的反馈**：主叫操作后被叫是否收到内容。可借鉴显式设备/用户身份和交接记录，避免把不同设备截图混为同一状态。本文不检测遮挡、重叠、溢出，也没有自动滑动排除显示候选的可靠性证据。

### 与 GUI testing 的关系

补生成/执行中的多用户协调和回归入口。它与多个agent角色共同控制一台手机、以及多浏览器并行探索的目的不同。功能正确性需保留跨设备预期和人工/日志证据，不能只凭模型发出end task认定通过。
