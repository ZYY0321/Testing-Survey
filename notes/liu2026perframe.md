# PerFrame：从测试视频中定位加载起止帧，测量用户看到的 GUI 响应时间

## 一页读懂

| 问题 | 本文回答 |
|---|---|
| 研究中心 | 自动标注移动应用加载开始和结束的时间，为 GUI 性能比较与回归分析提供测量。不是自由探索或业务任务完成 Agent。 |
| 旧方法的困难 | 相邻画面不变可能是网络停滞，画面持续变化可能只是广告动画；外拍视频还受手部、反光和抖动干扰。单一图像相似度不能可靠区分。 |
| 核心新增 | SSIM 粗筛候选、多模态模型参照末帧判断、逐轮缩小采样区间，以及汇总各轮候选后的最终选择。 |
| 输入与输出 | 输入一段单次加载的内部录屏或外部拍摄视频；输出起止帧及其时间差。无需应用源码或内部插桩。 |
| 主要证据 | 美团测试平台 1,323 段人工标注视频；作者报告 61.6% 的预测在 5 帧误差内、85.6% 在 20 帧内，后者基线为 57.9%。统一按 30 FPS 分析。 |
| 工程代价 | 每段约两次小模型预判断、约五次主要 MLLM 调用；补贴 API 成本约 0.02 美元、离线分析约 3 分钟。 |
| 最重要边界 | 视频末帧仍未加载完时，直接以末帧作分析终点。这不表示页面在该帧完成加载，也不提供真实完成耗时。 |

## 一段话介绍

GUI 性能测试要知道用户触发操作后，页面什么时候真正呈现出主要内容。传统视觉方法常把“画面不再变化”当成加载结束，却会混淆分阶段加载、正常动效和弱网停滞。PerFrame 把已有测试视频交给离线分析流程：先从画面变化中筛出少量候选帧，再用多模态语言模型比较候选与末帧所示页面，逐轮缩小范围，最终给出加载关键帧。论文重点证明的是**视频标注接近人工结果的程度与工业处理效率**，并没有评价它发现了多少性能缺陷，也没有根据业务阈值自动判断页面是否“慢得不合格”。

## 关键术语与阅读前提

- **[帧、帧率与误差](../glossary.md#perframe-loading-boundaries)**：视频由连续静态图像组成，每张是一个帧。30 FPS 表示每秒 30 帧，5 帧约 0.167 秒，20 帧约 0.667 秒。这是单个帧位置误差的量级，不能直接当成完整加载时长的误差上限。
- **[加载起止帧](../glossary.md#perframe-loading-boundaries)**：起点对应交互触发加载的时间，终点对应主要内容完整呈现、可供交互的最早时刻。原文的一般起点定义与 Android 实现存在口径差异，后文单独说明。
- **[SSIM 与候选预筛](../glossary.md#perframe-semantic-refinement)**：Structural Similarity Index Measure，结构相似度，用一个分数表达两张图像的视觉相似程度。本文计算相邻帧 SSIM，利用变化曲线提出候选，不把这个分数直接当成加载完成判据。
- **内部录屏 / 外部拍摄**：前者由手机系统录制，可能占用设备资源；后者由外部摄像机拍手机，可以减少录屏软件对被测设备的影响，但会引入抖动、背景和光照变化。本文都支持。
- **多阶段加载**：页面先出现框架，再加载图片、文字、小图标等；最后一个“大变化”不一定就是最后一项必要内容完成。正常动画又可能在完成后持续播放。
- **[未完成加载的观察窗口](../glossary.md#perframe-incomplete-load)**：视频结束前仍在加载，只能说“截至录像结束尚未完成”；末帧是观察终点，不是实际完成时刻。

## 动机与贡献

作者基于美团实践指出：人工逐帧标注大量测试录像耗时；源码插桩又不适合没有源码的竞品比较。传统视觉方案虽可在外部观察，但常依赖画面相似度（Sec.1–2，第1–4页）。它会遇到四种具体障碍：

1. 外拍时手部、光照、抖动让画面持续变化，SSIM 不再只反映应用加载。
2. 先页面框架、再图片文字的多阶段加载，使“最后一次主要变化”漏掉重要小更新。
3. 视频、GIF、轮播或优惠动效本就不断变化，不能一直等待像素完全静止。
4. 弱网时空白页或转圈界面可能长时间不变，静止不等于已经加载成功。

Sec.1 的贡献是强调这个工业测量需求及旧方法限制，提出结合外拍、模型语义理解和渐进采样的 PerFrame，再用真实视频和部署案例评价。本仓库主记 `method`：有实现和企业数据评价，但正文没有提供可公开使用的新 benchmark 或通用 harness，也没有给出独立的缺陷发现研究。

## 方法与核心技术

### 1. 整体输入、输出与代码参与边界

输入是展示**单次应用或页面加载过程**的录像。测试操作在此前由工程师或自动执行系统完成，PerFrame 负责后续测量，不负责决定去哪些页面找 bug。视频可以来自内部录屏或外拍，统一转换为 30 FPS；输出关键帧编号，并可按 `(结束帧−开始帧)/30` 换算秒数（Sec.2.1、3，第2–7页）。

不需要应用源码、回调分析或 APK 插桩；模型接收的是视频中提取的页面图像。Android 开发者选项中的触摸坐标显示是起点检测的一项辅助，并不等于读取应用业务代码。论文不能直接解释“哪行代码导致慢”，也不检查 CPU、内存等内部性能根因。

### 2. 先处理录制环境与起点

**图像预处理。** 从视频随机抽一帧，让较小模型判断是内部录屏还是外拍并给置信度；对有把握的外拍视频，用开源工具去除手机屏幕外背景；提高候选图像分辨率，帮助后续模型比较细节。部署成本段还提到小模型判断操作系统。正文未给小模型名称、分类阈值、去背景及超分辨率工具的具体配置（Sec.3.6.2、4.4，第7、10页）。

**Android 起点。** 开启设备开发者模式的相关显示后，交互会产生屏幕坐标文字。工具对每一帧做 OCR（文字识别），再用正则匹配类似 `X:456` 的格式；第一次检测到的帧作为开始帧（Sec.3.6.1，第7页）。这依赖测试录像保留相关可见信号，不是从任意普通视频中都能无条件精确定位触摸。

起点需要保留一个口径疑点：Sec.2.1 把 start frame 定义为交互触发**第一次可见加载响应**的帧，Android 实现却使用**触摸坐标首次出现**的帧。触摸至可见响应之间可能有延迟，所以两者不能自动视为同一个指标。论文没有分别报告这段延迟以及对最终误差的影响；也没有展开非 Android 的等价起点实现。

### 3. 末帧先做完成性检查：决定能不能把它当参照

正常路径假设录像最后一帧是加载完毕的界面。末帧提供“最终应该长成什么样”的上下文，模型才能比较前面的候选，找出最早已经达到同类完成状态的帧。它是**分析参照帧**，不是人工评价真值本身（Sec.3.3，第6页）。

但弱网下录像结束时可能仍在转圈。框架先让 MLLM 检查末帧是否完全加载；如果判断尚未完成，就**直接把视频最后一帧标为分析结束帧并终止后续查找**（Sec.3.6.3，第7页）。这避免强行在前面挑出一个假完成点，却没有测出真实完成时间。

因此，使用该结果做性能报表时必须保留“未完成”的判断语义。本文没有给出独立超时策略或完整失败分类，也没有评价未完成样本的混淆矩阵；不把末帧输出包装为精确完成标签。

### 4. SSIM 粗筛：找到值得让模型看的位置

对相邻帧计算 SSIM，形成随时间变化的曲线。曲线斜率绝对值超过阈值的点被视为显著变化。潜在起点取变化前最近的稳定帧，潜在终点取变化后最先稳定的帧；外拍造成连续混乱波动时，把一定时间窗内连续变化合并成一个块，块附近稳定帧进入第一轮候选（Sec.3.2，第5–6页）。

这里保留 SSIM 的价值：低成本地缩小数百、数千帧的搜索空间。模型再判断这些变化是加载、动画还是干扰。正文没有给出斜率阈值、合并时间窗、稳定判定的全部数值或候选数量，不能直接照笔记复现出唯一参数。

### 5. 模型比较：判断内容完成，不要求所有像素停止变化

把本轮候选帧和末帧参照**拼成一张图**输入多模态模型，保留帧编号，减少多次调用及上下文丢失。模型先逐帧说明页面状态，再输出选中的帧与理由，以 JSON 的 `frame_analysis`、`target_frame`、`reason` 字段返回（Fig.4、Sec.3.3，第6页）。

提示中的完成标准包括：导航按钮完整、图像没有占位/空白、文字格式正确、交互元素样式正常、小图标已出现、布局与参照一致、没有加载指示或白色加载区。同时忽略完成后的局部文字颜色变化、同一区域小文字滚动、小弹出提示等。**这是一组从测试经验归纳的完成判定规则，不是通用的 UX 正确性标准。** 比如忽略某类小弹窗有助计时，却不能证明弹窗不遮挡业务入口。

本文“语义区分”的实质就在这里：整体图像仍有变化时，模型可以判断它只是动效；整体变化很小时，也可注意尚未出现的小图标或内容。它比较的是候选是否达到预期页面状态，而非单独判断哪一帧像素最稳定。

### 6. 迭代细化与最终候选选择

每轮选出最可能的关键帧后，在它附近缩小窗口，等间隔取新候选，再比较一次。粗位置逐步细化到邻近帧，也给后续判断纠正早期偏差的机会。正文没有给统一的窗口缩小公式、每轮样本数和精确停止阈值；部署中主要 MLLM 调用约五轮（Sec.3.4、4.4，第6、10页）。

最后并非直接采用最后一轮，而是汇总各轮选中的可疑帧，再做最终选择，作者称为 voting。Sec.3.5 的文字同时使用“各轮胜出帧投票”和“最终比较判断”的表述，Fig.5 显示将历史候选汇集后得到答案；**没有给出足以复现的完整计票或平票规则**，不将其补写成固定次数、严格多数表决的算法。消融比较特意保持总轮数相同，投票版少一次普通细化，把一轮留给最终选择（第7、9页）。

## 原文案例：商户页并非在第一次大变化时加载完

Fig.1 的录像长 750 帧，先是休闲玩乐列表页，存在局部文字闪动；第 510 帧用户点击商户，后续第 542、577 帧出现主要更新，直到第 723 帧才达到作者标示的完成状态，录像在第 750 帧结束（第2–3页）。按统一 30 FPS 和该示例编号换算，510 到 723 相差 213 帧，约 7.1 秒；这是示例推算，不是论文总体平均结果。

这个例子说明三个判别任务：点击前局部闪动不应算加载；商户图或页面框架出现还不表示所有必要元素完成；完成后到录像末尾也仍可能有轻微变化。因此，要把多阶段内容加载与正常页面动态区分开，并寻找**最早**满足完成条件的帧。

Fig.5 另用示意搜索过程展示细化：最初在大时间范围挑中 100 附近，后续候选集中到 140、125、123 一带，最终给出 123。该图说明从粗到细及复查历史候选，未附上这个示意例的完整逐轮图像或全部提示回复，不能当作已复现的真实视频追踪记录（第7页）。

## 实验与工程证据

### 数据、人工真值与比较设置

数据来自美团内部测试平台的员工和外包测试录像，**1,323 段视频，每段一次加载过程**，包含内部录屏、外拍、动态动画与弱网条件。加载时间中位数 3.24 秒、均值 5.21 秒。已有有经验工程师人工标注的起止帧作为评价真值（Sec.4.1，第7–8页）。

正文未公开应用数量、平台/设备细分、每类样本量、类别是否重叠，以及人工标注人数、一致性统计或分歧裁决细节。Sec.4.2 又使用“several hundred videos”的概括，与 4.1 的 1,323 描述不完全一致；以下以明确数据收集数量为主，不据此补出未报告的评测子集。

比较基线是参考文献[27] **Screencast-Based Analysis of User-Perceived GUI Responsiveness（2025）**：相邻帧 SSIM 加 Isolation Forest 异常检测，把首尾异常点作为边界。原方法通过显示触点和 Faster R-CNN 检测点击以切分视频；本次比较改用测试记录中的操作时间和随后片段，替代这一前处理。**基线并不是 GUIWatcher 本身**，GUIWatcher 是相关工作中另一项滞后分析研究（Sec.4.1.2、References，第8、11页）。

论文未报告主要 MLLM 的具体型号、温度、完整实验重复次数或置信区间；不能填入猜测的 GPT 版本。也未给单独的起帧/终帧准确率，或明确解释总体表如何合并两个边界的预测误差。因此保留“作者报告的关键帧预测误差”口径，不改写成“双边界同时命中率”或“时长误差准确率”。

### 指标：5 帧和 20 帧分别表示什么

Table 1 将预测相对人工关键帧的误差分为三档：≤5 帧为高精度，5–20 帧为可接受，>20 帧不可靠。Table 2 实际把前两档标为 0–5、6–20，避免 5 重叠；正文和摘要又出现 less than、no more than 等混用，本笔记以表格的包含端点口径为准（第8–9页）。

这些容差来自工程师对下游测量的需要；作者还说人工约有 10% 案例相差 5–20 帧，但没有给独立研究协议，不能把它当作严格建立的人类误差上限。对亚秒级性能回归而言，20 帧约 0.667 秒是否可接受，还取决于实际判定阈值。

### 整体与分场景结果

| 场景 | ≤5 帧：PerFrame / 基线 | ≤20 帧：PerFrame / 基线 |
|---|---:|---:|
| 总体 | 61.6% / 33.9% | **85.6% / 57.9%** |
| 内部录屏 | 65.5% / 52.3% | 90.3% / 79.6% |
| 外拍 | 61.0% / 25.2% | 82.1% / 39.9% |
| 动态动画 | 55.8% / 29.9% | 74.7% / 58.6% |
| 弱网 | 99.1% / 0.0% | 99.1% / 0.0% |

来源 Table 2，第9页。≤20 帧由前两档相加；不从这些比例反算精确人数。总体两个容差档的绝对提高恰好都是 **27.7 个百分点**，不是相对提高 27.7%。仍有 14.4% 超过 20 帧误差，动态动画一类为 25.3%，说明语义模型没有完全解决复杂动效。

**弱网 99.1% 需要单读**：框架发现末帧未完成时直接输出末帧，作者评价这一政策下与人工标签的接近程度；它不是自动找到真实完成时刻的 99.1% 成功率，也不是弱网性能缺陷检测精确率。没有独立未完成识别结果时，无法进一步分离语义判断与终止政策各自贡献。

### 消融：支持哪些设计

Table 3（第9页）均以 **≤20 帧比例**比较，不与上表 ≤5 帧混用：

| 配置 | 总体比例 | 较完整方法下降 |
|---|---:|---:|
| 完整 PerFrame | 85.6% | — |
| 不要求模型先分析再给答案 | 61.0% | 24.6 个百分点 |
| 第一轮改用等间隔采样，去掉 SSIM 预筛 | 70.1% | 15.5 个百分点 |
| 去掉多轮细化 | 53.4% | 32.2 个百分点 |
| 去掉最终汇总选择，直接取最后一轮 | 72.1% | 13.5 个百分点 |

几个细节帮助理解结果，而不是只记模块名字（Sec.4.3，第8–9页）：

- 要求解释候选页面状态后，作者观察单步选对最近关键帧的比例约 90%，去掉后约 70%；这是辅助分析数字，没有详细样本量，不等于总体85.6%的直接拆解。
- 相同初轮样本数下，SSIM 预筛约 99% 案例能取到距真值 100 帧内的候选，等间隔采样约 77%；所以预筛的作用是提供更好的起始邻域。
- 无细化时即使模型能理解画面，稀疏候选也可能离真值几十帧；精度不能仅靠一次语义判断获得。
- 投票与非投票版保持**总调用轮数相同**，支持最终复查有价值，而不是只因多花一次调用。
- 弱网列在去预筛、细化或投票后均仍是99.1%，与其提前检查并直接输出末帧的路径相符；不能用这一列证明后续模块对未完成加载都有效。

### 工业部署、时间与成本

作者称系统已接入美团平台，每天处理数千段视频，用于竞品加载性能比较、滞后分析及统计。一次跨地点、场景和启动方式的大规模比较中，数位工程师结合并行标注，在 24 小时内处理完数千段录像并出报告；旧流程要十多位测试人员各投入两个工作日，还需协调会议。报告因隐私未公开，也没有等条件对照的工时统计，不能据此计算一个精确的人效倍数（Sec.4.4，第9–10页）。

每段约两次小模型预判断，之后主要 MLLM 约五次。使用**公司补贴 API**估算每段约 0.02 美元、5,000 段约 100 美元，单段离线分析约三分钟。该成本不是公开市场报价，也不包含完整硬件、采集及人工复核成本；离线并行处理的部署证据不等于能够实时为每次 GUI 点击决定等待时长。

## 局限

**作者在方法和部署中承认的**：末帧可能尚未完成，必须另作检查；动态动画、低质量外拍仍是主要误差来源，少数错误来自模型判断能力；提出后续考虑训练等方式提升单次判断；实际测试报告因隐私无法披露（Sec.3.3、3.6.3、4.4，第6–7、9–10页）。论文没有单独的 Threats to Validity 章节，不把我们的批评写成作者完整列出的威胁。

**我们的观察**：

- 终点用最终页面作参照，依赖视频长度和最后状态；“还在加载就输出末帧”提供观察窗口结束时间，不能恢复窗口之外的真实完成时间。
- 起点在一般定义中是首可见响应，Android 实现却是坐标首次出现，可能混合触摸响应与页面加载两个量；分边界误差和时长误差也未单独报告。
- 效果是接近人工帧标签，不是检测性能 bug 的 precision/recall，更没有已确认/已修复缺陷计数。慢是否构成缺陷仍需阈值、对照版本或明确性能要求。
- 缺少模型具体版本、预筛参数、细化与最终选择的完整规则，无法只凭正文精确复现；未提供公开代码或数据链接，不声称 benchmark 已开放。
- 同一企业平台、分组规模和标注协议未充分展开，外推到其他应用与录制环境需进一步验证。“无需源码”也不自动意味着无需开发者设置、录制准备和人工复核。

## 和我们课题的关系

### 与 UX testing 的关系

这是直接研究**用户可见加载性能**的 UX 测量工作。对截图提出的截断、遮挡、重叠或溢出候选，判断页面是否已经完成加载，有助避免把尚未出现的文字、图片或临时占位当成稳定显示缺陷。其“低成本预筛→多帧语义比较→细化→最终复查”也可作为主动验证流程的参考。

但不能把加载完成检查直接用作布局缺陷判定：提示会忽略一些局部动态和小弹窗，异常布局还可能在参照末帧中一直存在。若最后状态本身有错，仅靠与它相似无法证明 UX 正确。把它用于截图采集时机或候选复核，需要另行验证，不属于本文已测结论。

### 与 GUI testing 的关系

它补的是 GUI 测试的**观测、测量和性能评价**环节，测试对象仍是通过界面触发的真实加载过程。测试执行器决定交互，PerFrame 为后续性能比较提供关键帧标注；它没有以覆盖率指导新页面探索，也不读取源码定位慢的根因。可与已有[GUIWatcher 笔记](liu2025guiwatcher.md)比较：本篇主要识别加载边界，GUIWatcher 关注用户可见 GUI 滞后；二者都利用录屏，但输出和评价对象不能合并。
