# OS-Oracle：合成错误操作数据，训练逐步判断 GUI agent 动作是否合理的模型

## 一页读懂

| 问题 | 本文的回答与边界 |
|---|---|
| 研究什么 | 给定用户目标、历史动作、当前截图和待执行动作，判断这一步是否有助于完成目标，并解释理由。判的是 **agent 的动作**，不是 APP 是否有产品缺陷。 |
| 旧方法哪里不够 | 成功轨迹也可能包含重复或错误动作，失败轨迹也并非每一步都错；用任务最终成败自动给每一步贴标签不可靠。现有训练数据和动作判断基准又常局限单个平台。 |
| 新增什么 | 从正常轨迹按四类规则合成错误操作，配模型生成的解释；训练监督微调加一致性强化学习的 7B critic；建立包含手机、桌面、网页的人工标注 OS-Critic Bench。 |
| 一次使用怎样发生 | 操作 agent 先提出动作，critic 结合上下文输出 Yes/No 和理由；判 No 时要求操作 agent 改写动作，最多重生成三次，再继续执行。 |
| 主要证据 | 738 条独立动作评价样本，其中手机 438 条；OS-Oracle-7B 手机 Accuracy/F1 为 70.78%/74.30%，整体为 68.02%/72.81%。接 UI-TARS 后主文 AndroidWorld 成功率 31.6%→33.2%，补充同项为 33.6%，二者不能混写。 |
| 能支持到哪里 | 支持定向错误负例和解释一致性训练改善动作判断；不能证明一般软件缺陷检测、UX 截断判定或真实应用故障注入已经解决。 |

## 一段话介绍

GUI agent 在长流程中可能点错目标、尚未选中输入框就输入、页面已经到底却继续滑动，或者任务尚未完成就结束。OS-Oracle 先用这些错误模式改写已有正确轨迹，形成“当前上下文—候选动作—对错—解释”的训练数据，再训练一个专门判断动作的多模态模型。它还另外收集模型提出的候选动作，由人判断动作是否合理，避免只在自己按规则造的负例上评价自己。论文的重点是 **GUI 动作 critic 的数据构造、训练及评测**。在软件测试中，它可帮助分析“操作器是否点错”，但不能替代依据需求判断“APP 保存结果是否错误”的测试预言。（主文 §1、§3–5，PDF pp.1–8）

## 关键术语与阅读前提

- **[GUI agent 与执行](../glossary.md#agents)**：根据目标和页面提出、执行点击等动作的系统。本文被辅助的操作 agent 与负责判断的 critic 是不同角色。
- **Critic（逐步评判器）**：输入当前任务上下文和一个候选动作，输出该动作是否合适。本文采用逐个判断，而非强迫在两个候选动作中选一个；两个候选都错时仍可分别拒绝。（§3.1，p.3）
- **[Grounding（动作定位）](../glossary.md#grounding)**：把“点始终忽略”落实到界面上的具体位置。动作类型正确而位置错误，仍可能导致任务失败。
- **Hard negative（困难负例）**：看起来接近合理操作、实际违反当前目标或状态的样本，例如点击同一弹窗中的另一个相似按钮；它不是在应用源码中植入的 bug。
- **SFT（监督微调）**：用带理由和对错标签的样本训练模型；**GRPO（组相对策略优化）**用多个输出之间的奖励差异继续训练。本文的 CP-GRPO 增加“解释和最终标签是否一致”的奖励。（§4，pp.5–6）
- **[真值、oracle 与指标](../glossary.md#truth)**：本篇真值是人工判动作是否有助于目标。动作 Accuracy/F1、任务成功率和应用缺陷检出率是不同对象；99.73% 的解释一致性也不是 99.73% 的正确率。

## 动机

作者归纳的失败包括不察觉局部状态变化、进入错误状态后不会恢复、结束时机不对和控件定位不准。直接训练更强操作模型需要大量在线交互与奖励设计，另一条路线是在动作执行前加 critic。困难在于：大量专家轨迹几乎只有正确操作，缺少有解释的错误操作；单凭最终成败反推逐步标签，又容易把“中途点错但最后成功”或“前面正确但最后失败”的步骤标反。（主文 §1、§3.2，pp.1、4）

Figure 1 的原文手机例子很清楚：用户要求始终忽略豆瓣更新，agent 却提议点“本次忽略”。critic 需要同时看任务和弹窗，才能解释为什么这个按钮不满足目标；应用弹窗本身可以完全正常。（p.2）

## 贡献

按主文贡献和具体产物归纳：

1. 构建跨平台动作判断训练集，先按已知错误模式造负例，再生成对应理由。
2. 以 Qwen2.5-VL-7B-Instruct 为底座，提出 SFT＋CP-GRPO 训练流程，使理由和最终判断更一致。
3. 构建独立人工标注的 OS-Critic Bench，评价不同模型逐步判动作的能力。
4. 检验作为在线执行前评判器、离线训练数据过滤器的用途。后两种用途评价的是任务执行收益，不是未知产品缺陷发现。

因此分类为 `method; benchmark`；有数据分析和对比实验，不自动将每一项常规实验都算一类独立实证贡献。

## 方法：从训练数据到一次在线判断

总体流程是：**正常轨迹→规则构造错误动作/上下文→生成和筛选理由→训练 critic→独立人工基准评价→可选地接入执行环路**。

1. 从已有轨迹抽取目标、截图和动作；保留动作历史作为记忆。这里的截图不是应用业务源码。
2. 按下一节四种错误类型改写动作或拼接异常上下文，得到负标签；原操作形成正样本。
3. 把历史、错误动作及已知错误类型/原因交给 GPT-4o，要求生成解释；若其判断与构造标签冲突则剔除。解释因此利用了造例时知道的错误信息，不是盲审得到的完全独立真值。
4. 模型先学解释与最终标签，再用正确性、格式和一致性奖励强化训练。
5. 在线使用时，操作模型先给下一动作，critic 输入目标、历史、当前图和候选动作，输出理由与 Yes/No。若拒绝，操作模型再生成，最多三次；这是一层外部执行控制，并非 critic 直接接管手机或修复 APP。（主文 §3–5；补充 §3、§5）

沿用 Figure 1：正常的目标是“始终忽略更新”→操作模型提出点击“本次忽略”→critic 指出目标不匹配并判 No→操作模型应改点“始终忽略”→外部环路再执行。若操作模型不能正确利用反馈，更准确的 critic 也未必显著改善最终完成率。

## 核心技术详解

### 1. 四种负例如何从正常轨迹构造

| 原文错误模式 | 实际构造 | 对测试研究应注意什么 |
|---|---|---|
| Operation Failure，操作失败 | 把输入动作放到选中输入框之前；重复某些点击；在滚动边界追加无效滑动 | 造的是错误操作或冗余操作，不是应用内部故障；无位移不自动说明产品 bug |
| Inefficient Error State Recovery，错误状态恢复低效 | 从相似观测的另一轨迹取后继状态，注入当前上下文；将非返回动作作负例 | 拼接状态可形成已知异常情境，但“只有返回才对”是较强构造假设，真实界面可能有其他合法恢复方法 |
| Mistimed Task Termination，结束时机错误 | 在成功轨迹后追加多余动作，或截断未完成轨迹后追加结束 | 需要可信的任务完成边界；不能据此获得应用是否符合需求的真值 |
| Inaccurate Element Localization，元素定位错误 | 用 OmniParser V2 检测可交互对象；有控件元数据时以 IoU>0.7 过滤检测框；按画面 2×2 分区采样其他目标 | 通过空间分区增加错误候选多样性；不同目标也可能产生等价合法操作，标签仍受构造假设影响 |

规则并非为实际 APP 自动改出可执行 bug；主要是改变训练样本里的动作/上下文。训练集由七种已有数据源汇合，手机部分包括 AndroidControl、AMEX、AITZ、GUI-Odyssey，网页和桌面另有对应来源。（§3.2–3.3，pp.4–5；补充 §1，p.1）

### 2. 为什么一致性不等于正确性

监督阶段同时学习理由与标签；强化阶段总奖励由标签正确性、输出格式和理由—标签一致性三项组成。权重分别为 0.9、0.05、0.05。一致性先用正/负词汇规则推断理由支持哪一结论，规则不能判断时交给 Qwen3-8B，再与输出 Yes/No 比较。（§4.2，pp.5–6）

例如理由说“这一步会走向无关页面”，结论却是 Yes，即解释和结论冲突。CP-GRPO 减少此类情况；如果理由和结论同时错误，仍然可以非常一致。论文的一致性得分依赖同一套代理判据，不能当人工证明的推理正确率。

### 3. 独立 benchmark 为什么不用“等于参考动作”评分

OS-Critic Bench 用另一组来源的任务和截图，让 Qwen2.5-VL-7B 产生候选动作，再由人判断。作者明确允许不同于原轨迹、但仍合理推进目标的动作，这比字符串匹配参考动作更符合 GUI 路径不唯一的特点。最终每项包含目标、历史、截图、候选动作、提示及人工二元标签，正负比例为 1:1。（主文 §5.1，p.6；补充 §2，p.1）

这套独立人工评测能缓解在固定规则负例上自证的问题，但规模只有 738 个动作情境；它不等于 738 个完整任务、独立应用或程序缺陷。

## 实验

### 数据与训练协议

| 项目 | 所读正式版本的设置 |
|---|---|
| 训练规模 | 主文以约 160k 正例＋150k 负例简称 310k；补充 Table 2 精确为 162,760＋150,667＝313,427，手机占约 58.32% |
| 独立评测 | 738 项：手机 438、桌面 152、网页 148；人工判动作是否合理，非产品缺陷标签 |
| 训练 | Qwen2.5-VL-7B-Instruct；SFT 一轮，CP-GRPO 三轮；rollout batch=512、group=16，KL系数 0.005 |
| 离线指标 | Accuracy 是动作对错预测与人工标签一致的比例；F1 衡量二元判别。正文未充分展开正类编码，跨实现引用需核对，不能称为“bug F1” |
| 在线协议 | UI-TARS-1.5-7B 或补充中的 Qwen2.5-VL-72B 提动作；判错后最多重生成三次；评价 AndroidWorld/OSWorld 任务成功率 |
| 未充分报告 | 本文所读部分未给完整在线任务抽样、重复运行/随机种子与置信区间，不补写为多次平均或显著性保证 |

### 主结果：动作判错与任务完成分开

主文 Table 1，p.7：

| 模型 | 手机 Accuracy / F1（%） | 整体 Accuracy / F1（%） |
|---|---|---|
| Qwen2.5-VL-7B | 58.45 / 65.79 | 58.27 / 66.23 |
| GPT-5 | 69.18 / 69.53 | 68.16 / 67.94 |
| Gemini-2.5-Pro | 68.26 / 70.11 | 67.62 / 70.16 |
| GUI-Critic-R1 | 59.13 / 66.54 | 59.49 / 68.76 |
| OS-Oracle-7B-SFT | 63.47 / 71.22 | 63.14 / 71.49 |
| OS-Oracle-7B | **70.78 / 74.30** | **68.02 / 72.81** |

结果支持专门训练改善本基准上的动作判断，并非所有指标都胜过所有闭源模型：例如 GPT-5 整体 Accuracy 68.16% 仍略高于 68.02%。它也没有测“发现多少 APP bug”。

主文 Figure 3，p.7：UI-TARS 在 AndroidWorld 从 31.6% 到 33.2%，提高 **1.6 个百分点**；OSWorld 从 29.2% 到 31.0%，提高 1.8 个百分点。GPT-4o critic 分别变成 30.2%、28.5%，显示更换通用判错器可能反而拖累执行。

**版本内数字不一致：** 补充 Table 5，p.8，将同一 UI-TARS＋OS-Oracle 的 AndroidWorld 值写成 **33.6%**。此处保留主文和补充各值，不擅自合并。补充还报告 Qwen2.5-VL-72B 在 AndroidWorld 22.4%→31.9%、OSWorld 5.0%→11.6%；支持反馈利用能力会影响在线收益，但不是跨不同 agent 的公平能力排名。

### 消融与数据过滤

| 实验 | 结果与它回答的问题 |
|---|---|
| 同规模负例来源比较（Table 3） | 固定 50k 正例并配 50k 负例；GPT 标负组整体 Accuracy/F1=55.42/67.33，规则合成负例组 60.03/69.37。支持定向合成在此设置更有用，不保证所有合成标签都正确 |
| 数据量（Figure 4） | SFT 整体 Accuracy 随规模总体提高，但最小组比未训练底座更低，部分中间组 F1 不单调；不能简化成数据越多必然每项更好 |
| 一致性奖励（Table 4） | 普通 GRPO Accuracy/一致性=66.53/80.89，CP-GRPO=68.02/99.73；收益主要体现在理由与标签一致，不等于判错接近100% |
| 过滤训练轨迹（Table 2） | 先生成 10k 手机操作样本；全量 SFT 后 AndroidWorld=12.07%，critic 过滤后=15.52%，原底座10.34%。作者用全量一轮、过滤子集两轮尽量平衡曝光，未证明完全相同 token/算力；3.45 是百分点差 |

所有数据均为论文报告。本笔记没有训练模型、运行 benchmark 或独立复核人工标签。

## 局限

### 作者讨论

补充 §4（p.2）指出：UI-TARS 利用反馈的能力会限制在线收益，强 critic 不自动带来更高任务成功；换更能利用反馈的 agent 后收益不同。论文没有单列覆盖全部局限的主文章节，不将下列观察归为作者原话。

### 我们根据机制与证据的观察

- 规则负例包括人为拼接状态和将非返回动作标错，可能过度约束合法恢复；GPT-4o 与规则冲突就剔除，也可能留下模型容易同意的样本。独立人工基准很重要，但还需更细的错误类型和真实执行验证。
- 当前图和历史未必足以知道隐藏状态、网络延迟或未显示业务结果。动作有帮助不代表结果必然正确，尤其难区分重复点击是冗余还是第一次操作根本没生效。
- 一致性奖励用词典/代理模型判断理由极性，能抑制自相矛盾，不能保证解释忠实或语义正确。
- 离线评测只有 738 项；在线收益、运行成本、重试失败去向及完整重复协议尚不足以支持稳定部署结论。主文/补充同项数字存在差异。
- 作者仓库的模型、训练数据和合成流水线曾仍列待发布；引用正式 CVPR 身份不等于声称全部代码资产已可运行。

## 和我们课题的关系

### 与 UX testing 的关系

对“截图提出截断候选→布局/滑动复核”的链条，本篇帮助拆出 **验证动作是否合理**：目标区域正确吗、已经到底了吗、重复滑动有无意义？它没有以截断/遮挡/溢出作为监督真值，不能用动作 Yes 直接证明没有 UX bug，也不能把动作 No 当成应用缺陷。可借的研究思路是从正常操作构造精确负例，并用独立人工评测检验动作验证器；是否改善截断判定仍需另测。

### 与 GUI testing 的关系

它为操作错误与应用错误的区分提供支撑，也展示“训练合成负例＋独立人工多解评价”的 benchmark 设计。与正常应用内注入 bug 不同，它主要改动作和上下文。若用于测试器，应额外建立应用需求/缺陷真值，并防止 critic 为完成目标而把异常直接绕过；这属于待验证改造，不是本文结论。
