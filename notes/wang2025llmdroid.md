# LLMDroid：在覆盖增长停滞时调用语言模型，为已有 GUI 探索器选择下一处功能

## 一段话介绍

Android 应用的 GUI 探索器可以很快点击和滑动，却可能反复访问已知页面。逐步询问 LLM 虽能理解功能，也会消耗等待时间与 API 费用。LLMDroid 将两者组合：通常由原探索器快速执行，模型同时把相似页面整理成功能摘要；当方法覆盖增长持续缓慢时，模型才选择下一处值得尝试的页面和功能。工具沿历史路径自行到达目标页，随后最多用五步模型指导执行目标，再交还原探索器继续探索。论文用覆盖率、模型交互次数和费用支持这种调用方式的价值，**不以缺陷检出率证明它更会判错**。

## 关键术语与阅读前提

- **[方法覆盖率与 Activity 覆盖率](../glossary.md#coverage)**：方法覆盖看应用中有多少程序方法至少执行过一次；Activity 覆盖看访问了多少 Android 界面组件。一个 Activity 可有多个页面状态，进入组件不代表测试了其中所有功能。
- **[APK 插桩](../glossary.md#program-analysis)**：修改应用安装包中的程序，加入记录执行情况的探针。本文用 AndroLog 记录方法覆盖，应用源码不可得仍可尝试；这不同于只看屏幕，也不同于让 LLM 理解程序内部业务逻辑。
- **[控件树与 HTML 描述](../glossary.md#view-hierarchy)**：从 Android 可访问性服务取运行时控件及父子关系，再转为类似 HTML 的文本交给模型；被测对象仍是 Android 应用，不是网页。
- **[页面簇 PageCluster 与 Dice 相似度](../glossary.md#llmdroid-pagecluster)**：把控件结构相近的页面状态归为一组，减少重复总结。页面簇不等于 Activity，也不等于语义完全相同的功能。
- **[覆盖停滞触发与后台总结](../glossary.md#llmdroid-coverage-trigger)**：模型在后台总结不必阻塞每次操作；是否暂停原探索器、请求定向引导，由近期覆盖增长判断。
- **[离线路径导航](../glossary.md#llmdroid-offline-navigation)**：利用已有运行轨迹在本地计算路线，再在真实应用中重放。“离线”指路径规划不调用 LLM，不是完全不运行应用。

## 动机与论文案例

作者指出两个不同障碍：已有随机、模型或学习式工具可能停留在少数页面；GPTDroid、DroidAgent 等逐步调用模型的方式则把 LLM 响应延迟带入每一次操作。本文希望保留传统工具的执行速度，仅在它难以继续扩大覆盖时借助模型语义判断（Sec.1，第2–3页）。

原文 Table 1 用网络工具 **Fing** 展示提示组织：页面结构中含网络选择等控件，模型把页面总结为网络监测与导航，随后可以输出“到 Page15 执行测速”这样的目标。这个例子说明目标由“页面 + 功能”组成，并非只让模型随意点击。**它是原文提示格式示例，不是一个已确认软件错误的案例**（第7页）。

另一个原文例子更能说明语义判断的风险：模型可能把“返回顶部”理解为前往新页面，实际操作只是把当前列表滚回顶部；或者推荐尚未点击的标签页按钮，却不知道该目标页已从另一条路线访问过。控件“没点过”与功能或页面“没测试过”并不相同（Sec.4.2，第16页）。

## 方法与核心技术

### 1. 运行信息：模型理解界面，插桩反馈执行覆盖

原探索器负责获取界面、抽取动作与执行动作。LLMDroid 额外取得应用名及简要说明，读取 Android AccessibilityService 暴露的控件树，并把它转换成 HTML 样式文本：可点击控件用 `button`，可勾选控件用 `checkbox`，可滚动控件用 `scroller`，输入框用 `input`，不可操作元素用 `p`。每个元素附本次引用编号、类型、resource-id、文字及 content-desc（面向辅助访问的文字说明），保留父子层级（Sec.3.1.2，第7–8页）。

这不是截图识别流程。模型虽然采用 GPT-4o，当前实现输入的是文字化控件结构；论文将引入视觉/多模态理解列为后续改进。信息不足的图标、自绘内容或无意义 ID 可能让模型遗漏功能。

方法覆盖由 AndroLog 在 APK 字节码中插桩后记录，采用方法级粒度以平衡开销与细致程度；作者同时提供可用源码时采用 JaCoCo 的实现（Sec.4.1，第11–12页）。覆盖计数影响何时请求引导，却不把具体未覆盖方法、回调路径或激活条件交给模型推理。因此它具有程序执行反馈，但不能归纳为源码路径分析方法。

### 2. 页面聚类：先决定哪些页面值得分别总结

工具逐次比较当前页面与每个已有簇的根页面。若两控件的类型、resource-id、支持动作、宽度和高度全部相同，就计为相同控件；两个页面的 Dice 相似度为 `2 × 相同控件数 / 两页控件总数之和`。选择相似度最高、且超过阈值的簇加入；都不满足则新建簇，并以当前页为根页面。默认阈值为 0.6（Sec.3.1.1，第5–6页；Sec.4.4，第18–19页）。

这样，内容刷新但结构相近的信息流页面通常不必反复请求模型。一开始只总结根页面；作者也认识到同簇其他页面仍可能有独特功能，所以在没有待处理模型请求的空闲时段，提取非根页面的独特控件，再补充总结。不能写成“一个簇永远只调用模型一次”，也不能称为已经解决语义重复检测。

### 3. 功能摘要与重要性排序：为后续目标选择准备信息

每个新页面的提示包含应用说明、当前页结构，以及此前最重要页面的摘要。模型需输出：不超过 30 词的页面概述、功能清单及其对应控件编号、页面在应用中的相对重要性排序。重要性以“可能打开新页面”或“属于当前页核心功能”为依据，并非发现错误的概率（Sec.3.1.2，第7–9页）。

总结时保留前 `P1=5` 个重要页面，每页最多展示前 `Q1=5` 个尚未测试的功能。功能是否“未测试”，实际由其对应控件在该页是否操作过来判断，不是用需求断言检查功能是否经过验证。模型将新页与已有前五页比较并更新排序；被挤出前五的页面仍在本地保留，以便目标选择阶段扩展为前十页。

摘要请求与原工具探索并发。降低等待的关键不仅是调用次数更少，还包括许多总结在后台完成，不会把每次模型响应都串到操作循环中。

### 4. 覆盖增长监控：什么时候中断原探索器

设 `c_i` 为执行第 i 个动作后的累计方法覆盖，单步相对增长为 `(c_i - c_(i-1)) / c_(i-1)`。维护最近 `W=80` 个增长率，只有窗口中的增长都低于动态阈值，才认为陷入低增长状态（Sec.3.1.3，第9页）。它不是遇到一次没有新覆盖就立即请求模型。

阈值从 0.05 开始，以历史增长率均值 G 为基准，按 `T_n = T_(n-1) × exp(g_n − G)` 更新，并设置 0.01 的下限：当前增长高于均值时提高阈值，低于均值时降低阈值。这使触发条件随应用与测试阶段调整。窗口 60、70、80、90、100 的控制实验没有清楚单调趋势，80 比 60/100 的覆盖高不到 1%；不能称为经过全面调优的唯一最佳参数。

### 5. 目标选择：从已知页面找到值得继续的未操作功能

低增长触发后，模型收到应用说明、前 `P2=10` 个重要页面的摘要、每页前 `Q2=5` 个未测试功能，输出目标页面及目标功能。与总结阶段不同，此时不必同时解析完整新页，因此可给更多页面选项。选择偏向导航或能开启新页面的功能（Sec.3.2.1，第10页）。

目标是在**已经知道的页面上寻找未操作入口**，希望进入未知区域；不是模型从完整源码中直接算出所有尚未覆盖页面。它也没有完全建模“不同入口通向同一页面”或“不同页面有同一个功能”，因此仍可能产生重复推荐。

### 6. 本地导航：重放已走过的路，而不是每一步问模型

导航先重启应用，从统一起点出发；在探索轨迹形成的界面转移图上，用 Dijkstra 算法选择到目标页的最短路径，逐步重放并检查实际页面是否与预期一致（Sec.3.2.2，第10–11页）。原文对转移方向的英文措辞不够规范，但明确指出动作不能随意反向撤销；不能据此假定任意界面跳转都能逆向执行。

为应对动态界面，模块允许三种处理：当前页与预期页足够相似便继续；若已直接到达路径中的后一节点，跳过中间步骤；最短路线失败则换用较新轨迹，并在每次失败后将匹配阈值降低 0.05。每个目标最多尝试三次导航，仍失败则让模型换页选目标；最多三轮目标都失败后，回原探索器自主探索。

这说明框架并不完全依赖模型执行长程导航；但也依赖过去的路径现在仍能重放。重启、弹窗、动态内容和服务端变化都可能影响它。

### 7. 目标功能执行：有限步模型操作后交还原工具

到目标页后，每步给模型应用说明、当前页 HTML、目标功能和已经执行的动作，问目标是否完成；若未完成，请它输出下一控件与动作，也可以生成输入文字。最多执行五步，随后结束引导并交还原探索器（Sec.3.2.3，第11页）。

模型说“目标完成”在这里是**探索调度条件**，不是功能测试通过的断言。即使没有进入新页面，框架也在当前页恢复自主探索，因为该页可能仍有值得尝试的操作。两阶段循环至分配的测试时间耗尽。产物主要是探索操作与覆盖结果，没有完整的需求到预期结果判定链条。

## 实验

### 数据与运行协议

Sec.4.1（第11–13页）从 Google Play 热榜及推荐相似应用收集候选，最终筛出 **14 个可正常插桩并运行的应用**。包括 Wish、Twitch、Wikipedia、Quora、Fing、Lefun Health、Red Bull TV、Time Planner、NewPipe、NHK WORLD-JAPAN、Renpho Health、Mood Tracker、CafeNovel、OceanEx。作者总体称其为流行闭源商业应用集合，但表中含 NewPipe、Wikipedia 等有开源实现的应用；本笔记保留具体名单，不将“14 个全部闭源”当严格事实。

候选筛选有兼容性限制：一些 APK 插桩成功后仍会在启动时崩溃。论文没有给初始候选总数或最终保留比例，不能把最后 14 个视为所有热门应用的无偏随机样本。

运行设备为 **Google Pixel 4 / Android 11**。需登录的应用先人工注册并登录。每种工具每应用运行 **60 分钟**，动作间隔统一设置 **3 秒**，每组合重复 **3 次，取最高覆盖值进行分析**；不是三次均值，也没有以置信区间呈现运行波动。Fastbot 服务运行在设备端，Droidbot/Humanoid 由电脑控制，实际操作速度仍有架构差异。

核心覆盖指标为方法级代码覆盖与 Activity 覆盖，先在应用间汇总；论文没有完整给出原生代码/第三方库剔除规则或 Activity 覆盖所有分母的操作细节。**不评价缺陷检测**：作者认为插桩可能制造崩溃，难与原应用错误区分，也援引已有研究讨论缺陷计数的不稳定性（第13页）。这里没有“发现、确认、修复了多少错误”的可填写数字。

### RQ1：增强不同探索器是否提高覆盖

三种底层工具分别代表模型式 Droidbot、深度学习式 Humanoid、强化学习增强的 Fastbot；另列 Monkey 作为参照。Table 3（第13页）已逐列核对：

| 底层工具 | 方法覆盖：原工具 → LLMDroid 增强 | 相对提高 | Activity 覆盖：原工具 → 增强 | 相对提高 |
|---|---:|---:|---:|---:|
| Droidbot | 9.21% → 11.69% | 26.90% | 15.90% → 22.46% | 41.29% |
| Humanoid | 11.05% → 13.40% | 21.29% | 19.16% → 23.66% | 23.51% |
| Fastbot | 11.36% → 14.80% | 30.30% | 24.40% → 30.05% | 23.13% |

Monkey 为方法覆盖 8.86%、Activity 覆盖 11.34%。三种工具相对提高幅度的平均值为方法覆盖 **26.16%**、Activity 覆盖 **29.31%**。例如 Fastbot 方法覆盖从 11.36% 到 14.80%，增加 **3.44 个百分点**，相对提高 30.30%；不是把应用代码覆盖提高到 30.30%。

14 应用 × 3 工具构成 42 个覆盖提高比例：7 个低于 10%，20 个超过 20%（Fig.2，第14页）。这反映收益分布，未提供独立统计显著性检验。

### RQ1 的过程分析：一次引导有效，究竟指什么

每应用小时平均触发引导次数分别为 Fastbot 9.17、Droidbot 6.42、Humanoid 6.17。**引导次数不是模型 API 总调用次数**，一次引导包含选目标及若干功能执行请求，另外还有后台总结。

有效性口径为：从本次引导开始到下一次低增长状态的覆盖增量，须超过“第一次引导时覆盖至最终覆盖的总增量”的 5%。因此“有效”不等于随便增加一点覆盖，更不是发现了 bug。这个阈值还利用最终结果作事后评价，不是实时调度阈值 T（Sec.4.2，第14–15页）。

按此定义，总体 **47.84%** 引导有效；Fastbot、Humanoid、Droidbot 分别为 42.48%、55.00%、48.24%。无效引导中，12.11% 未能导航到目标页；18.14% 进入新页但后续覆盖不足；69.75% 未进入新页。后两类包括新页过早退出、简单新页复用旧代码、控件语义误读、不同入口到相同页面、不同页面重复相同功能（第15–16页）。

这套分析说明“到新页”和“增加方法覆盖”也不完全一致。作者未给各 B1–B4 子类独立计数，不能把三大类比例分配成精确子类占比。

### RQ2：模型版本、实际调用、成本与逐步工具比较

这一组采用 LLMDroid-Fastbot，与 GPTDroid、DroidAgent 比较。模型为 `gpt-3.5-turbo-0125`、`gpt-4o-mini-2024-07-18`、`gpt-4o-2024-08-06`，费用采用 **2025 年 1 月实验时**输入/输出单价，不能用于推断 2026 年现行价格（Sec.4.3，第16页脚注2）。DroidAgent 的任务规划持续用 GPT-4o，表中 3.5/mini 指其任务执行模型，不能当成全流程单一模型；两种逐步基线未做执行也用 GPT-4o 的配置。

| 每应用小时均计，Table 4（第17页） | 方法覆盖 | Activity 覆盖 | API 美元 | 调用次数 | 调用总耗时 |
|---|---:|---:|---:|---:|---:|
| DroidAgent，3.5 执行 | 10.77% | 18.71% | 1.721 | 1761.00 | 2508.90 秒 |
| DroidAgent，4o mini 执行 | 10.89% | 18.05% | 1.086 | 1691.86 | 2762.24 秒 |

| GPTDroid，4o mini | 7.45% | 8.84% | 0.059 | 679.43 | 2131.72 秒 |

相对方法覆盖最高的逐步基线 10.89%，LLMDroid-4o 的 14.33% 相对提高 **31.59%**。mini 的覆盖为 4o 的约 **94%**，指 `13.47 / 14.33`，不是 94% 的覆盖提高收益；若只算超过原 Fastbot 11.36% 的部分，保留的是约 71% 收益。费用 0.033/0.494 约为 6.7%（第17–18页）。

Table 4 的成本与交互次数“改进率”采用的分母不宜直接理解成常规节省比例。例如费用从 0.059 美元降至 0.033 美元，按原费用作分母约节省 44.1%，表中却写 77.78%；这与按新费用作分母计算相符。上表保留可直接比较的绝对费用和次数，不将原表这些百分比转述为统一口径的降幅。

模型交互总耗时也不等于执行被阻塞的时间。后台总结与探索可重叠，LLMDroid 的 3.5、mini、4o 三配置实际阻塞时间分别为 **98、122、107 秒**，约占一小时 2.7%、3.4%、3.0%。相对原 Fastbot，仍执行约 94.4% 的动作数。本文没有分离“仅改并发”“仅改触发”“仅改摘要”的全面消融，不能将总收益全部归因于其中一个模块。

**两组实验不可混写。** RQ1 中 Fastbot+4o 为方法覆盖 14.80%、Activity 覆盖 30.05%；RQ2 则为 14.33% / 28.28%。第17页脚注4说明 RQ1 在 2024 年8月、RQ2 在 2025 年1月，同 APK 与设置下有三个应用结果持续下降，作者推测服务端变动。保留该说明，不将 14.80% 与 0.494 美元拼成同一次测量。

### RQ3：页面聚类阈值的影响

从上述集合随机取 **5 个应用**，用 Fastbot+GPT-4o 比较页面相似阈值 0.5、0.6、0.7、0.8，平均方法覆盖分别为 **20.72%、21.72%、20.60%、18.15%**。0.9 因调用频繁、成本过高未继续；较高阈值还会留下更多未完成摘要请求，影响引导阶段（Fig.4及Sec.4.4，第18–19页）。

这说明本组五应用中 0.6 是合理折中，不能证明对所有应用和未来模型都最优。21.72% 也不是 14 应用全量主结果，不能替代 RQ1 的 14.80%。

## 局限

### 作者承认的

Sec.5（第19–20页）讨论：① AndroLog/Soot 静态插桩会破坏部分应用，限制可测范围；②缺文字语义的控件难以从 HTML 理解，当前版未引入视觉补足；③参数较多，P/Q、初始增长阈值及参数间依赖仍主要凭经验；④导航功能定义与跨页面/跨入口的重复功能识别不足，仍会重复推荐。作者提出的视觉、推理与功能关联改进是后续方向，不能记成当前已实现模块。

### 我们的观察

- **覆盖收益与错误发现分开。** 全文没有缺陷检测实验或独立非崩溃 oracle；因此不能据覆盖提高推断能检测遮挡、截断、业务错误或更多 crash。
- **主证据受筛样与统计协议限制。** 只有 14 个兼容应用、单设备、人工预登录、三次取最高；不能直接与三次均值的其他论文对比，也不能由此证明所有应用上的稳定收益。
- **引导评价不是独立因果消融。** 后续自主探索贡献也计入一次引导到下次停滞的覆盖增量；47.84% 不能作为模型决策正确率或缺陷检测 precision。
- **表述与元数据应看所读版本。** 作者将数据总体称为闭源商业应用，但名单含开源应用；不同网页摘要还保留过不同成本数字。本文只采用所读 22 页版本的表3/4数据，不用外部摘要替换正文，也未核实各应用当年的发行渠道和许可证。
- **代码参与程度有限。** 使用插桩执行反馈，有助跳出仅靠屏幕的新颖性判断；它仍未解释具体未覆盖代码为何不可达。把覆盖信号升级成代码路径/条件推理，是另需检索的技术路线，不能预先认定无人研究。

## 和我们课题的关系

### 与 UX testing 的关系

可以借鉴**探索器与判定器分工、后台总结、按需调用模型、记录端到端等待时间**的方式，以控制大量页面探索和候选复核的费用。不同任务的触发信号需要重新设计：方法覆盖不增长不代表应检查或已发现文字截断、遮挡、重叠、溢出；控件树相似也不保证实际显示相同。本文没有验证这些 UX 缺陷，因此只能把它作为页面探索与资源调度的参考，不能用其覆盖数字支持显示检测效果。

### 与 GUI testing 的关系

它是“已有 GUI 探索算法 + 运行时覆盖反馈 + 选择性 LLM 指导”的代表，适合与逐步 LLM 探索方法比较**调用时机和导航执行方式**。核心阅读问题是：何时依赖旧探索器，何时切换模型；页面摘要压缩了什么；局部未点过控件为什么不等于全局未测功能；更高覆盖最终是否转化成可复现、可确认的缺陷。最后一项需要另加 oracle 与缺陷实验，本文未回答。
