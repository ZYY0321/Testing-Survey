# MobileWorld：用可控手机环境评价长流程、用户澄清与 GUI/工具混合操作

## 一页读懂

| 问题 | 本文的回答与边界 |
|---|---|
| 研究什么 | 构造更复杂、可验证结果的移动操作 benchmark，评价 agent 完成手机任务的能力；**不是评价测试 agent 发现应用故障**。 |
| 动机 | 常见环境偏短流程、单应用、完整指令；实际使用还需跨应用、问用户缺失信息、把外部工具结果接到手机操作。 |
| 新增什么 | 201 个任务及可控 Android 环境；自托管后端和定制客户端；四类状态检查；加入用户澄清与 MCP 工具调用的 planner-executor 基线。 |
| 任务怎么来 | 人工设计功能目标和混合流程；澄清任务先写完整目标再删关键信息，并确保设备里找不到答案；不是 agent 自由探索自动生成测试。 |
| 一次运行 | 恢复设备/后端初态→给目标和允许动作→看图规划→定位操作，或问模拟用户/调用工具→记录结果→独立检查最终业务状态，最多50步。 |
| 主要证据 | 主表最佳框架 GPT-5＋UI-Ins-7B 总成功率51.7%，最佳端到端模型20.9%；分任务类别揭示澄清和工具能力差异。它们是论文实验值，不是当前持续更新榜单的最强值。 |
| 重要限制 | 程序化检查不代表所有依赖都确定：附录明确外部 MCP 没有缓存/代理，仍有变化与不可用风险。部分正文/附录计数不一致，应按所在版本引用。 |

## 一段话介绍

MobileWorld 的核心不是给模型再加一个会点屏幕的角色，而是把“能否完成真实手机任务”变成较可控的评测。作者使用 Android 模拟器、开源客户端和可访问的后端：给 agent 一条跨应用目标，允许它逐步观察截图、执行 GUI 动作，在信息缺失时向持有隐藏答案的模拟用户提问，或先调用外部工具再将结果写入手机应用。评测器不只看 agent 说完成了没有，而是查询数据库、本地存储、回调记录或文本答案。它为移动测试研究提供 **环境初始化、可观察内部状态及独立检查器** 的构建参照，但没有因此得到“哪些正常应用被改坏、测试器是否报告了 bug”的缺陷发现基准。（§3–4，PDF pp.4–9）

## 关键术语与阅读前提

- **[Benchmark 与任务成功率](../glossary.md#benchmark)**：固定任务、环境、协议和评分组成的比较材料。本文 Success Rate 是任务目标达成比例，不是故障检出率。
- **AVD 与 snapshot（虚拟 Android 设备与快照）**：快照保留初始设备状态，运行前恢复；带后端应用还需恢复后端数据库/文件，不能只重启客户端。（§3.2、附录E）
- **[Grounding（目标定位）](../glossary.md#grounding)**：planner 说“点右下角发送”，executor 把描述转为截图坐标；两个模型和外部执行循环合起来才是本文基线框架。
- **MCP（Model Context Protocol，模型上下文协议）**：向 agent 描述并调用外部工具的接口，例如读取仓库提交记录。它是另一种行动渠道，不是获取手机像素的模型能力。
- **User agent（模拟用户）**：GPT-4.1 持有被删去的信息，按问题回答；它不是被测试的手机操作 agent，也不是独立 judge。
- **[Callback 与真值](../glossary.md#truth)**：在定制应用关键点记录邮件、购物车等状态，供评测程序查询。记录的范围决定它能证明什么，不自动等于真实商业交易完成。

## 动机

作者认为，现有手机任务难以覆盖三种实际条件：长流程和多应用协调、用户指令缺少必要信息、GUI 与外部工具共同使用。对闭源商业应用，身份认证和后端不可见又使评测难以重置，常依赖模型判最终结果。MobileWorld 用开源替代和自托管换取状态控制，再主动设计更长、更依赖澄清与工具的任务。（§1、§3）

“AndroidWorld 已饱和”是作者在其引用与比较条件下的动机，不能理解为任意模型、任意预算都超过90%，也不能推导移动 GUI 测试研究已成熟。本文主任务是操作成功，软件是否有 bug 是另一问题。

## 贡献

按实际新增产物归纳：

1. **Benchmark/环境构造**：人工编制跨应用、用户交互、工具混合的任务，配设备与后端初态以及程序化成功检查。
2. **评测协议**：除总成功率，还分析分任务类别的表现、步骤数、用户提问效率和工具调用情况。
3. **参考 agent 框架**：统一规划与截图定位，并把询问用户和调用 MCP 接到执行环路。
4. **能力诊断**：根据多模型运行和失败案例分析歧义识别、长记忆、工具上下文及时间状态等问题。论文没有自动生成 bug 或通用测试预言的方法贡献。

## 方法：一条任务怎样从初态走到评分

以 Figure 2 的原文例子为主线：给 agent“给 Kevin 发内容为 Hello 的邮件”，但手机联系人和邮件中没有他的地址。

1. **准备环境和隐藏信息。** 人工先写能完成的完整目标，再删去地址；复核设备没有该信息。模拟用户单独持有完整目标/地址，操作 agent 只能看到不完整目标。
2. **恢复初态。** 启动容器化 Android 环境；设备使用预设快照，自托管后端恢复对应数据库及文件状态。
3. **决定下一动作。** planner 接收目标、当前截图、动作及返回结果历史，判断应操作、询问还是调用工具。普通点按先输出目标描述，再由 UI-Ins-7B 定位。
4. **执行并回写观察。** `ask_user` 将问题送给 GPT-4.1，回答和当前图追加到历史；GUI 动作由控制器执行并重新截图；MCP 调用返回结构化内容，同样进入历史。
5. **完成或停止。** agent 可输出答案、结束状态，或达到50步上限；独立评测器按任务要求检查邮件回调中的收件人/内容等。模拟用户提供信息，评测器判目标完成，两者不是同一个角色。（§3；附录A、C–F）

这条链说明环境在许多环节可控，但任务、预期与检查逻辑仍由人构造；它不是让 agent 无目标探索并自创一整套测试。

## 核心技术详解

### 1. 三类任务如何构造

| 类型 | 原料与构造 | 主要评价能力 |
|---|---|---|
| GUI-only，116项 | 在预置联系人、邮件、消息等状态上人工设计操作/检索目标；包含跨应用流程 | 看图操作、状态记忆、检索和多步规划 |
| Agent-user interaction，45项 | 人工完整目标→删除收件地址、具体事件等关键信息→确认设备中不存在答案；模拟用户只持有规定隐藏信息 | 意识到缺信息并提出有效澄清，不能靠猜测补齐 |
| MCP-augmented，40项 | 先根据工具说明和示例输出编制工具可完成的子任务，再追加消费工具结果的手机操作 | 选择工具/参数、理解结果、与 GUI 动作衔接 |

原文混合任务例子为：先读取指定仓库最近提交，再把作者与提交信息写入手机 Mail 发送；工具拿到数据并不等于最终邮件目标完成。MCP 规格只在对应任务注入提示，不能默认 agent 在所有任务都获得全部工具。（§3.3、附录D）

### 2. 环境可控具体控制了什么

Mattermost 与 Mastodon 使用自托管服务，预置聊天/帖子/账号，保存 PostgreSQL 及媒体文件并在任务开始恢复。Mattermost 还有按需生成初始消息的辅助工具；Mastodon 客户端为连接本地 HTTP 后端作小改动。

Mail 来自 React Native 邮件客户端，作者修编译问题并添加附件、搜索与系统分享入口；发送时把收件人、主题、正文、附件写到本地回调文件。Taodian 基于 Mall4Uni，改成轻量文件 mock 后端，补登录和购物车功能，并在结账等位置记录状态。（附录E.2，pp.14–15）

因此它兼有实际开源服务和定制/模拟业务组件，不能说每个任务都在原封不动的商业 APP、真实邮件投递系统或真实交易后端上运行。对测试研究，源码和内部状态可见有助于定义真值；对部署结论，则需承认这些替代与修改的外部有效性边界。

### 3. 四种成功检查器：谁判对错

| 检查方式及任务数 | 原文例子与检查 | 能支持什么 |
|---|---|---|
| 后端数据库，95 | Mattermost 建频道：查名称、预期成员及欢迎消息；Mastodon 查回复/发帖 | 证明规定数据库状态达成，通常比最后截图或 agent 自报可靠 |
| 本地存储，74 | ADB 查飞行模式值、短信内容提供器或闹钟数据库 | 证明设备/应用内部设置符合目标，需相应权限及状态接口 |
| 文本匹配，22 | 清洗日期/时间等噪声，再匹配“会议天数”的答案；或比较距离数字 | 得分取决于匹配规则和答案时效，不等于理解任意自由文本语义 |
| 应用回调，10 | Mail 发送元数据；Taodian 结账时记录商品/数量等 | 证明被插桩事件及字段满足检查，不能越过回调范围声称完成真实外部业务 |

这些是离线评测器可以读的内部证据，不能自动假定操作模型也读取数据库或隐藏答案。可控环境中的任务成功真值也不同于“应用在某状态违反产品需求”的故障真值。（§3.2；附录F）

### 4. 可复现不等于没有动态依赖

设备和部分后端可以快照恢复，但附录J（p.17）明确：MCP 仍调用外部服务，没有响应缓存或代理，主要靠选择较稳定内容减小变化；固定 commit、缓存或容器内回放被列为后续改进。附录L.2还展示实时天气检索。因此，正文使用的完全确定性表述应理解为特定检查逻辑及本地状态控制，不能扩大为全部外部数据永不变化。

固定用户提示和 temperature=0.0 可减少输出变化，不是模型/API 永远逐字确定的证明。模拟用户提示还带特定日期，后续改环境时要同步检查设备时间、任务含义和隐藏上下文。

## 实验

### 设置、指标与分母

主文 Table 2 为201任务：单应用76、两应用100、至少三应用25，跨应用共125/201≈62.2%。最大50步；通用模型搭配固定 UI-Ins-7B 做定位；端到端模型用官方实现适配。开源模型用 vLLM 和8张H20，闭源用官方 API；用户模型为 GPT-4.1，温度0.0。（§4.2、附录C）

- **SR**：达到全部目标的任务数/纳入任务数；另按116/45/40三个任务类别报告。没有局部得分，也不是bug recall。
- **平均步骤**：公式包含成功和失败轨迹；低步骤可能因为早早失败，不能只据此称效率高。论文27.8步是其模型/协议下的执行轨迹统计，不是人工最短步骤或不随模型变化的任务固有属性。
- **平均提问**：在用户交互任务中平均调用 `ask_user` 的次数；不是全任务平均。
- **UIQ，用户交互质量**：成功的交互任务按“成功标志/提问次数”累计；分母再加入非交互任务中误触发询问的任务数，惩罚不必要询问。它不是提问文本质量的独立人工打分。
- **平均工具调用**：在 MCP 任务上统计调用次数；多调用不代表正确调用。

附录C说明，部分模型不支持工具或提问，相应类别不参与其兼容任务执行，表格用横线表示；不能把横线当成真实运行的0分，再将所有模型的分类指标拼成公平全能力排名。论文未给足全套重复次数、种子与置信区间，不补写 Pass@k 或多次平均。

### 主表结果及解释

主文 Table 3，PDF p.7，百分数：

| 模型/框架 | Overall | GUI-only | 用户交互 | MCP |
|---|---|---|---|---|
| GPT-5＋UI-Ins-7B | 51.7 | 54.0 | 62.2 | 51.6 |
| Gemini-3-Pro＋UI-Ins-7B | 46.3 | 55.6 | 24.4 | 48.6 |
| Claude-4.5-Sonnet＋UI-Ins-7B | 43.8 | 47.8 | 37.8 | 50.0 |
| Doubao-1.5-UI-TARS | 20.9 | 26.3 | 32.4 | — |
| Qwen3-VL-235A22B | 9.5 | 12.8 | 4.4 | 5.4 |

结果支持本文任务能区分跨应用推理、主动澄清与混合工具能力。框架和端到端模型差距还包括动作空间与工具支持，不能全部归因于模型参数量，或说 planner/executor 分工单独造成全部增益。

Table 4 中 GPT-5 平均27.8步、每交互任务1.11次询问、UIQ=0.40；Qwen3-VL 可有相近甚至更多 MCP 调用，但任务成功仍低，说明正确参数与内容衔接比调用次数重要。UI-TARS 的较低平均步骤伴随大量失败，不构成高效率证明。

附录G另报告去掉 `ask_user` 后交互任务均0%成功，支持这些任务确实依赖隐藏信息；这是一项动作权限消融，不等于证明整个框架每个模块均作过消融。失败案例主要为定性展示，缺少各类错误在全部失败中的完整频率，不能自行推导占比。

### 论文值与当前资源分开

论文主表的51.7%是该实验模型与设置下的最佳框架成绩。作者[仓库](https://github.com/Tongyi-MAI/MobileWorld)随后持续补充模型/轨迹和修复；截至本笔记核查，README还记载2026-04-15修复 Mattermost 快照认证过期可能导致假阴性。不能把历史论文分数称为当前最高水平，也不能把后来更新的榜单数值直接当本文原实验。此处未重跑任何版本。

## 局限

### 作者承认

Limitations（p.10）说明：模拟用户不能覆盖真人语言变化；开源替代与商业 APP 的界面/边界行为不同；201任务无法覆盖所有手机场景，仅中英文；模拟器与真机触摸/渲染延迟有差别；二元成功忽略部分完成，温度0与实际部署不同。附录J进一步承认未缓存外部MCP带来的复现风险。

### 我们根据机制与证据的观察

- 人工编制目标、预置数据和逐任务检查仍有较大工程成本；本文不是自动任务来源或自动 oracle 生成方案。
- 数据库/回调检查会提升评分稳定性，但不能单独覆盖页面可用性。例如数据库记录正确，文字仍可能截断；回调记录点过结账，也不等同完成真实付款。
- 路径、用户回应和工具输入有多种合法表达；简单文本/状态检查是否覆盖全部等价解，需要逐任务核验，不能仅凭确定性就说无评测偏差。
- 部分模型缺动作支持、运行子集不同，且正文/附录数字冲突；整体分数不能直接作为纯视觉定位模型与工具框架的同条件比较。
- 原文的固定时态、实时内容和外部服务说明，容器化本身没有消除时间/后端依赖；做测试 benchmark 应额外固定版本和记录环境失败。

## 和我们课题的关系

### 与 UX testing 的关系

本篇可提供手机页面、状态重置及独立数据检查的环境参考，但没有截断、遮挡、重叠、溢出标签，也没有比较静态模型与滑动验证。对截图候选→布局→滑动链条，业务检查可以帮助确认滑动没有误点、状态没有意外变化；它不能代替判断文本是否真正不可恢复的视觉/交互真值。自托管或定制应用便于后续改布局，但如何注入有效UX缺陷仍是需另做的研究。

### 与 GUI testing 的关系

最值得借的是“快照/后端初始化→真实交互→独立状态检查”的闭环，以及把用户、操作 agent 与评测器区分开。若改为测试器发现故障评测，应另建正常/故障版本、隐藏位置、明确违反需求的证据，并评分到达、触发、正确报告与正常误报。MobileWorld 自身没有完成这套改造；任务失败也不能一概算应用出错。它不同于 MobileWorldBench，也不是 MobileGym++。
