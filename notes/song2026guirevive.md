# GUIRevive：界面改版后，找回旧 GUI 测试真正要操作的功能

## 一页读懂

| 问题 | 本文回答 |
|---|---|
| 研究中心 | Android 应用改版导致旧测试找不到控件时，怎样修复测试脚本，并保持原来要验证的功能。修的是测试，不是应用缺陷。 |
| 旧方法的困难 | 只比控件文字、ID 或外观容易选错；目标可能藏到菜单、弹窗后或移到其他页面，必须补导航步骤。 |

## 一段话介绍

GUI 回归测试通过点击、输入等操作检查应用在更新后是否仍保持预期行为。但界面改版可能仅仅改变按钮文字、位置或入口路径，就让原来的测试脚本停止执行，尽管应用功能仍然存在。GUIRevive 研究的是这种**旧测试的维护问题**：它先确认原操作实际产生什么效果，再在新版界面上寻找功能对应控件；候选还要通过功能角色和执行效果检查，不能只因外观相似就接受。若当前页没有合适控件，模型依据原功能目标和探索历史决定下一步导航，逐步恢复路径。论文以失效原因分类、带人工真值的数据集、对比及消融实验支撑方法，但其成功率主要衡量修复目标控件的正确性，不能直接当成整个回归测试套件或业务逻辑的正确率。

## 关键术语与阅读前提

- **[过时 GUI 测试与测试修复](../glossary.md#guirevive-obsolescence)**：测试在旧版本可执行，在新版本因目标控件无法定位或操作而中断。修复可以替换当前控件定位，还可能补上导航步骤；不等于修好被测应用。
- **[控件树与定位器](../glossary.md#view-hierarchy)**：控件树记录页面元素及层次；定位器利用 text、resourceId、description、className 等属性找到目标。它们分别对应显示文字、开发者分配的 ID、无障碍说明、控件类名。属性改了，不代表功能被删除。
- **[GUI 状态与转移](../glossary.md#guirevive-goal-exploration)**：页面连同弹窗、抽屉、选项展开等状态构成可操作的界面状态；一次点击可改变状态，未必启动新的 Android Activity。本文“跨页”分类也包含打开弹窗或移除遮挡。
- **[功能保持验证](../glossary.md#guirevive-functional-validation)**：候选控件不仅要“像原来的”，还要承担同类交互角色，并产生与旧操作一致的功能效果。其自动判断依赖多模态语言模型，不是形式化等价证明。
- **[真值与成功率](../glossary.md#guirevive-obsolescence)**：真值是人工确认的新版本对应控件；成功率的分母是失效测试数，分子是工具正确找到真值控件的测试数。
- **消融实验**：只移除某个模块或上下文，再比较表现，判断它在整套系统中的作用。移除角色分类提示，不等于移除所有功能验证。

## 动机与贡献

传统修复方法有两类明显障碍。第一，控件的文字、ID 或外观随改版变化，相似度高也可能代表完全不同的功能。第二，旧测试到达的界面可能已经不再包含目标，继续在当前页匹配并不能解决问题。源码分析可以补充控件处理逻辑，但本文指出其分析代价、动态控件映射及细粒度状态建模仍有限；这些是作者对所比较方法的分析，不能推出所有白盒方法都不适用（Sec.1、5.2，第2–3、15–17页）。

Sec.1 的贡献包括：①构造 736 个失效 GUI 测试及人工真值；②实证分析失效原因，导出修复难点；③提出组合语义定位、功能验证和目标探索的 GUIRevive；④进行开源与工业评价，并公开材料。本仓库记 `benchmark, empirical, method`：实证部分有独立的抽样、分类和发现，不只是方法的常规性能实验。

## 先理解数据集：736 个测试是怎样来的

### 1. 收集应用与历史版本

作者用 GitHub API 搜索 Android 相关仓库，要求包含 Android manifest，且应用在 F-Droid 或 Google Play 发布，得到 5,085 个候选。随后按以下条件逐级筛选（Sec.3.1，第5–6页）：

1. 至少 100 stars、创建至少三年、研究前三个月有提交，剩 568 个。
2. 至少五个发布版本，剩 306 个。
3. 人工排除启动即崩溃、依赖外部硬件或其他应用、历史版本无法运行、交互过少或无主要 GUI 等情形；排除不适合稳定回归的游戏，剩 52 个。
4. 按类别和功能覆盖选 36 个，并收集其 **2020-10-01 至 2025-10-01** 的正式 APK 发布，共 668 个版本，每应用 5–49 个。

因此，668 是收集的**应用版本数**，不是独立应用数，也不是 668 对版本；36 个应用也不是从全部候选中纯随机抽样。

### 2. 生成旧版测试，再到新版重放

开源应用往往没有规模足够的公开 GUI 测试，因此作者参照 RegDroid 生成随机事件序列。对每个基准版本生成三条测试，每条 100 个事件，再在所有后续版本重放，合计 20,215 次跨版本重放。重放中无法继续定位或操作事件目标的测试被视为失效候选。

三条而非更多的理由是执行与人工标注成本；作者在五个应用上试过五条、七条，发现新增失效高度重复，但没有据此证明所有深层业务路径都已覆盖。随机生成的交互序列也不等于开发者围绕明确业务断言编写的测试。

随后排除在原版本也不能稳定重放的 flaky 测试，并去重：同一旧测试在多个后续版本因同一事件失败，只保留与基准旧版最接近的后续版本；不同基准版本生成的测试若在同一新版本指向同一失败控件，也合并。

### 3. 人工找对应控件，形成真值

两位作者独立寻找新版中能保留旧操作行为的对应控件，分歧讨论解决；无法找到对应控件的情形，例如功能已被删除，被排除。最后保留 736 个失效测试，提供旧/新 APK、测试脚本及重放信息。

**这一筛选边界很重要**：评测主要研究“功能仍有对应目标，但旧脚本失效”的可修复情形，不评价工具能否正确识别功能删除、拒绝不应修复的测试。人工修复目标不是模型自己生成的答案。

## 失效原因实证：四类问题分别需要怎样修

两位作者每轮随机取 50 个案例，检查失败事件以及新旧界面，独立标注后讨论；必要时第三人裁决。讨论前 Cohen's κ 为 0.91，这是**分类者的一致性**，不是方法准确率。一个案例可能同时有多处改动，但只按最先阻止定位或操作的主要原因归入一类（Sec.3.2，第6页）。

| 类型 | 数量 | 实际含义 | 对修复的要求 |
|---|---:|---|---|
| 定位器失效 Locator Invalidity | 297/736，40.4% | 目标仍在旧路径到达的当前页，但原 text、ID 等条件不再适用。 | 在当前页找功能相同的替代控件。 |
| 控件被遮挡 Widget Occlusion | 161/736，21.9% | 目标仍存在，却被新弹窗、覆盖层等挡住，不能直接操作。 | 先移除阻挡或改变临时状态，再定位。 |
| 移入子界面 Moved to Subpage | 139/736，18.9% | 功能被收进当前页关联的菜单、抽屉或弹窗，旧路径没有展开它。 | 找到并打开承载目标的入口。 |
| 移到其他页面 Moved to Another Page | 139/736，18.9% | 原路径仍可走，但到达页不再包含目标功能。 | 推理新的多步导航，不能停留于局部控件匹配。 |

后面三类合计 439/736，59.6%。论文将它们统称 inter-page UI changes；这并不表示 59.6% 都被移入完全不同的页面。尤其“被遮挡”在这里描述**测试可达性受阻**，不能直接当成需要向开发者报告的 UX 缺陷。

四项发现进一步解释设计依据（Sec.3.2.3，第7–8页）：

1. **目标常在附近，但不一定直接可见**。当前页 40.4%，遮挡或子界面 40.8%，合计约 81.2%。因此先局部定位，再有目标地探索邻近状态，比一开始遍历全应用更有依据。
2. **文字与图像都不足以单独判断身份**。Table 1 的属性变化率使用“有相应属性的案例”为分母，例如同页组 text 为 161/165，97.6%，不是全部 297 个同页案例中有 97.6% 改了文字。Fig.2 还表明属性缺失常见。Fig.1 中视觉相似度大于 0.9 的占 32.5%，正文写 32.3%，原文存在小幅不一致。
3. **有时难点是到达，而不是辨认**。跨状态组有 50.1% 的目标没有定位属性变化；即便 ID 完全没改，不补菜单或导航仍然找不到。这说明“更强的匹配器”不能代替可达性处理。
4. **交互角色比表面属性更稳定**。562/736（76.4%）保留相同 className；进一步结合功能角色判断，719/736（97.7%）保留角色。className 是粗粒度代理，不是功能语义等价的自动证明；角色稳定也不代表业务正确性未变。

## 方法与核心技术：定位、验证、导航反复交替

### 1. 输入、失败位置与修复产物

旧测试的每个事件包含操作类型、目标控件和可选输入数据。在新版本重放，直到第一个无法执行的事件。工具保留之前已经完成的前缀，尝试把失败事件替换为新版对应操作；必要时在它之前插入短导航序列，再接上后续原事件（Sec.2、4，第4、9页）。

原版可执行，因而工具可以重放旧操作、取得原控件截图和执行效果作为目标依据。这里的“意图”主要来自原测试交互与其效果，不是从完整外部需求文档中重新验证业务规格。实现基于 DroidBot，uiautomator2 负责设备交互、控件树与应用状态管理；没有使用被测源码来分析业务路径（第13页）。

### 2. 过滤不可交互控件，先用低成本属性规则

从 Android Accessibility Service 提取控件树后，先删除不可见元素、状态栏等系统元素、极小装饰元素（原文举小于 10 像素的例子），再根据空间重叠与绘制顺序去掉被其他元素遮住的控件。剩下的才是匹配候选，避免让模型选择看得到记录却无法点击的元素（Sec.4.1.1，第10页）。

接着提取旧控件的 text、description、resourceId。在新版当前页上，若某单项属性能唯一匹配到一个控件，便返回这个候选，进入**后续验证**。这不是“只要有任意同名元素就宣布成功”，也不是要求三个属性全部不变。规则无法给出足够确定候选时，才进入模型匹配（Sec.4.1.2，第10页）。

### 3. 多模态语义定位：看原功能，而不只比较外观

模型收到四类信息（Sec.4.1.3，第10–11页）：

- 旧版本页面截图，标出原目标。
- 原控件裁剪图，突出局部外观和文字。
- 原操作执行前后界面变化的功能效果摘要（Widget Effect Summarization，WES）。
- 新版当前页截图，给可选控件画边框并编号。

它回答哪个候选最可能承担原功能，或说明当前页没有合适目标。为减少随机输出影响，**同一输入独立询问三次**：至少两次选同一控件才接受；否则视为没有选出控件，转向探索。这里的三次投票是匹配模块设计，不是整项实验重复三轮。

遇到可滚动容器时，工具按页面高或宽的 50% 滚动，读取新出现的动态控件，把多个视图的候选合并，再经过同一定位流程；多个滚动候选之间还按功能对应关系选择。这样避免把尚未加载的列表项误认为已经不存在。正文没有完整交代滚动总次数、终止条件及所有去重细节，不补猜（Sec.4.1.4，第11页）。

### 4. 功能验证：候选能够点击，还需要证明它承担原功能

验证分两层（Sec.4.2，第11–12页）：

**先看功能角色是否一致。** 模型把旧目标和新版候选分别归为：导航型（打开页面、弹窗或子流程）、展示型（只呈现信息）、可编辑型（切换选项、输入或选值并改变状态）。角色不一致就拒绝候选。例如旧目标本身是可改变主题的选项，不能把仅仅通往主题设置页的入口当成最终修复目标，即使两者文字相近。

**再看执行效果是否一致。** 在旧版执行原操作并观察效果；在新版用相同操作类型执行候选，观察其结果。模型比较是否恢复了相同功能，例如进入对应流程、展开目标选项或改变相应状态，而不要求两个结果页结构或像素相同。两层都通过才接受，否则继续探索。

这使本文区别于只做元素重定位：它引入了一个用于**修复决策**的自动判定环节。但效果来自可观察交互及模型理解，不是完整的业务断言或数据库状态证明。即使原文提到持久状态变化，也不能据此认为系统已系统性验证所有持久化结果。

公开[提示目录 P2、P6](https://github.com/iSTARS-SMU/GUIRevive/blob/main/prompts.md)补充了判定口径：效果摘要应限于截图可见变化；导航型要求可启动同一功能流程，展示型要求同类信息可见，可编辑型要求明确的编辑控件直接可达。它并非统一要求整个业务流程已完成。这里核读提示文档，未审计全部实现代码或执行复现。

### 5. 目标探索：当前页找不到，就补通向原功能的路径

探索目标由旧操作效果摘要推导，不是“尽量访问新屏幕”。每到一个状态，模型获得当前页的可操作控件及编号、已有探索历史、原功能目标，输出“控件编号 + 操作类型”，或返回事件（Sec.4.3，第12–13页）。

每执行一步，再用操作前页面、被操作控件局部图和操作后页面生成短摘要，记录做了什么、是否跳转、哪些界面内容发生变化。摘要按时间顺序追加，供下一步判断已经试过哪些入口；优先未尝试且与目标语义相关的选项，没有合适未探索选项时回退。这里的历史是导航语义摘要，正文没有给出额外的学习训练或长期跨测试记忆机制。

新状态重新进入“定位→验证”；验证通过便形成修复，否则继续导航。默认每次修复最多 15 个探索步骤，整体测试执行加修复最多 30 分钟。预算耗尽仍找不到有效控件则失败。**没有成功候选时拒绝局部修复**是流程中的正常分支，不能为了让脚本继续而随意挑选一个控件。

## 原文案例：切换暗色主题为什么需要三种能力

Fig.3 的 **Permission Manager X** 案例贯穿方法动机（第8–9页）。旧版在主菜单直接显示 Force Dark Theme 复选框，旧 resourceId 为 `action_dark_theme`。新版变成先打开 **Settings→Theming→Dark theme 选项对话框→Dark**；最终选项的 ID 为 `android:id/text1`。

这里同时发生了目标 ID 改动、控件形式变化和路径加深。只改 ID 不够，因为目标根本不在当前页；只找带 Dark 的一行也不够，因为中间入口可能只负责打开主题选项，尚不是可编辑的目标。方法需要依据“切换暗色主题”的原效果寻找设置路径，在中间状态继续导航，直到能直接操作对应选项，再验证功能角色与效果。以上路径从原图和说明整理；原文没有公布这个案例每次模型的完整回复，不补写虚构的逐轮推理。

另外两个成功例子说明不同障碍：Activity Manager 的旧抽象图标移成菜单中的 Intent Launcher 文字项，需要跨外观匹配及展开子界面；Amaze File Manager 的覆盖状态要先使用导航箭头退出，才能重新访问原控件（Fig.5–6，第14–15页）。

失败例子同样重要：Activity Manager 的 Show disabled app indicator 开关在新版被移到不同页面，并改成 Disabled apps 按钮。系统可能误选相似开关，验证模块也可能因上下文相似而错误接受（Fig.7，第15–16页）。所以“另加一个模型验证”并未消除假阳性。

## 实验：分别读成功率、成本和证据边界

### 协议与指标

RQ1 是前面的实证分类；RQ2 比较修复效果，RQ3 分析各模块，RQ4 评价工业应用（Sec.5，第13–18页）。开源实验沿用 736 个带人工真值的失效测试；温度设为 0.8，底层模型为 GPT-4.1-mini。全方法最大探索 15 步，RQ2 每测试最多 30 分钟，包括执行与修复。正文未报告设备型号、具体 Android 系统配置，以及完整实验的独立重复次数、均值或置信区间；不能把“三次语义匹配投票”写成“三次实验取均值”。

比较对象为：**RM**（只用规则属性匹配）、**Guider**（属性与视觉启发式匹配及浅层探索）、**COSER**（外部属性与源码处理逻辑相结合，按 Activity 转移图导航）。作者适配基线到同一设置，尤其把原面向 Java 的 COSER 分析扩展至 Kotlin。故它是适配后的复现比较，不等于直接采用原论文表格数字。

三个指标的口径是：①成功率 SR，正确找到人工真值控件的失效案例比例；②Steps，**全部失效案例**平均使用的导航步数；③TU，全部失效案例平均模型 token 消耗。它们不以只成功的案例作分母，也不是新发现应用缺陷数量（第14页）。

### RQ2：对比效果

| 原失效类型 | RM | Guider | COSER | GUIRevive |
|---|---:|---:|---:|---:|
| 定位器失效（297） | 99，33.3% | 199，67.0% | 125，42.1% | 282，94.9% |
| 遮挡（161） | 0 | 23，14.3% | 39，24.2% | 134，83.2% |
| 移入子界面（139） | 0 | 2，1.4% | 9，6.5% | 120，86.3% |
| 移到其他页（139） | 0 | 15，10.8% | 26，18.7% | 100，71.9% |
| 合计（736） | 99，13.5% | 239，32.5% | 199，27.0% | **636，86.4%** |

来源 Table 2，第14页。相对 COSER 和 Guider，作者报告约 220% 和 166% 的**相对增幅**；不是提高 220 或 166 个百分点。跨其他页面仍明显更难，说明原目标定位和新路径恢复没有完全解决。

GUIRevive 的 100 个失败分为：高度相似上下文混淆 43%、模型幻觉导致匹配错误 36%、导航逐步偏离目标 21%。这不是 736 个案例中的占比，也没有分别给出“错误接受”和“预算耗尽”的完整混淆矩阵（第15页）。

### 成本：修复正确性与等待时间的取舍

Table 3（第16页）按失效类型给平均步骤/token：定位器失效 2.25 步/33.9k，遮挡 3.19/65.4k，子界面 3.58/93.8k，其他页 4.37/97.6k；总体 **3.11 步、64.1k tokens**。平均耗时 57.02 秒，推理估算约 **0.056 美元/案例**；Guider 平均 18.9 秒，COSER 632.9 秒。价格属于论文实验估算，不能当作当前固定 API 价格；token、时间和成功率要一起比较，不能仅凭平均三步就认为模型代价很小。

作者还以 Qwen-3.5-Plus 替换模型，保持其他配置，报告成功率 86.6%，GPT-4.1-mini 为 86.4%；平均步骤 3.04 对 3.10。后者与 Table 3 的 3.11 有小幅呈现差异，按来源保留。两种模型相近可支持该实验下的替换可行性，不能证明所有模型都稳健。

### RQ3：哪些模块起作用，移除后是否省成本

| 移除项 | 总成功率 | 相对完整方法下降（百分点） | 平均 token / 时间 |
|---|---:|---:|---:|
| RM：属性规则匹配 | 77.7% | 8.7 | 82.0k / 68.9秒 |
| SM：语义匹配 | 58.0% | 28.4 | 43.0k / 51.2秒 |
| RV：验证提示中的角色分类规则 | 71.3% | 15.1 | 88.7k / 77.9秒 |
| WES：原控件执行效果摘要 | 83.6% | 2.8 | 53.9k / 48.9秒 |
| PES：过去探索摘要 | 79.9% | 6.5 | 72.3k / 67.0秒 |

来源 Table 4–5，第17–18页；表中的 Δ 是绝对成功率差，中文改记“百分点”。语义匹配影响最大；验证和历史并不只是增加成本：去掉后，错误候选或重复路径反而带来更多后续探索，总 token 与耗时上升。

WES 并非在所有类别都提升：移除它时，定位器失效组从 94.9% 变成 96.0%，增加 1.1 个百分点，但遮挡组下降 7.4 个百分点。作者认为过多上下文有时引起错误联想。不能把总表概括成“所有模块对所有类别都必不可少”，也不能用这个消融声称已独立验证整套执行效果检查，因为移除 WES 主要去掉相关辅助上下文。

### RQ4：工业 93% 到底覆盖什么

合作手机厂商在近 12 个月收集 112 个应用、45 个类别的 1,642 个失效 GUI 测试，提供失败截图与控件树。由于**缺少历史 APK，无法评价跨页导航模块**，研究限制在目标预计仍位于当前页的失败。该集合报告 93% 修复成功率（Sec.5.4，第18页）。

正文没有给精确成功计数、工业案例的分类细表，以及与开源集同等详细的真值构建和重复执行协议，因此不从 93% 反算一个精确修复数量。此外，缺少旧版 APK 时原控件效果摘要、角色与执行效果对照如何取得，工业配置实际启用了哪些模块，正文未完整说明。93%应按这一同页工业设置单独理解，不能推定双版本完整验证流程已经照常运行。这个结果支持工业同页修复的适用性，不能转述为“完整多步导航在 112 个工业应用上已达 93%”，也不是发现或修好 93% 的应用 bug。

## 局限与需要保留的疑点

**作者承认的（Sec.6，第18–19页）**：36 个开源 Android 应用的代表性有限；人工检查有主观性；主要采用合成随机事件而非开发者业务测试；用“第一个不可执行事件”识别失效，可能遗漏更早发生但仍可执行的语义偏移。作者回看失败前 5–10 个事件，未发现这类提前偏移，但不能排除。开发者编写测试的系统研究仍是未来工作。

**我们的观察与待核实事项**：

- 当前真值评价关注对应控件，论文没有据此给出完整后缀事件、原断言与全部业务效果均保持的整体测试通过率。不能把“恢复正确控件”扩大为完整测试语义等价。
- 功能已删除的案例被排除；在真实维护中，工具还需要区分“应修脚本”和“需求真的变了”，当前数据不能评价这种拒绝能力。
- 功能验证仍可能与匹配共享相似上下文误判；已出现假接受案例，尚不能作为可靠的独立业务 oracle。
- 同一基准既用于失效分布归纳又用于方法评价，是围绕该分布设计的结果；工业集合又只补同页验证。还需独立应用/版本和开发者测试来检验外推，而不是据此认定设计无效。
- 正文未说明完整重复次数、随机稳定性区间、全部滚动终止规则，以及验证试操作后的所有状态回滚细节。公开代码可以进一步核查，本次没有复现，不补猜实现。
- Fig.1 高视觉相似比例图为 32.5%，正文为 32.3%；Qwen 对比段 GPT 步骤为 3.10，Table 3 为 3.11。主结果计数 636/736 与各分类相加一致，以上小差异保留并与主结论区分。

## 和我们课题的关系

### 与 UX testing 的关系

最直接的联系是**主动操作后的候选复核**：检测出一个界面异常候选后，滑动、关闭覆盖层或打开子界面，可以帮助区分真实显示问题和暂时不可见、尚未加载或操作状态不同。本文还示范把截图候选、控件树可交互性过滤、操作效果与历史摘要串成明确验证流程。

但本文的遮挡首先是旧测试目标不可操作的原因；合法弹窗或有意隐藏的菜单不一定是 UX 缺陷。其成功率也没有测截断、重叠、溢出的检测精确率。可借鉴验证组织和跨版本回归维护，不能直接当作 UX 显示 oracle 或现成缺陷数据集。

### 与 GUI testing 的关系

这是 GUI 测试链条中的**维护**，与主要追求新页面、新覆盖或新 crash 的探索生成工作不同。它保留既有目标，以新旧交互效果约束修复，证明“探索”也能用于恢复既有测试意图。研究时值得继续核查：怎样独立评价修复后的完整测试及断言、怎样识别语义真实变更、怎样结合源码与外部规格减少相似上下文的共同误判。这些是证据导出的待查问题，不是已验证创新空白。

## 原文摘要关键句（节选）

> “even when underlying functionality remains unchanged”
>
> — Abstract，第1页。

它限定了核心动机：应用功能可能未坏，失效的是旧 GUI 测试对界面的依赖。不能把修复测试当成修复应用。

## 原文摘录

> “the located widget exactly matches the ground-truth target widget”
>
> — Sec.5.1.4，第14页。

这是实验成功率的判定口径，比“能点击、能运行”严格，却也不同于已证明完整业务测试等价。两处英文原句共 15 词。
