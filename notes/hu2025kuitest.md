# KuiTest：先预测控件应有的作用，再判断点击后的界面是否符合预期

## 一页读懂

| 问题 | 本文的回答 |
|---|---|
| 测什么 | 移动应用中一次界面交互的功能响应，例如点击“待付款”是否打开待付款订单，而非退款订单。 |
| 为什么需要 | 工业脚本将操作和检查绑定到平台控件属性，换平台或更新界面后维护成本高；随机探索虽便宜，却通常只能借助崩溃信号判错。 |
| 方法新增 | 将判错拆成“预测控件功能”和“验证实际响应”，用截图、控件树、OCR及图标功能库支持模型理解。 |
| 输入 / 输出 | 输入应用、起始页或页面列表；输出交互轨迹和带解释的异常判断。不要求逐项提供业务断言，但图标库仍有人工标注。 |
| 核心证据 | 4,664个控件输入中150个注入历史功能错误，检出129个、误报52个；precision 0.71、recall 0.86，正文FPr约1.2%。 |
| 结论边界 | ICSE 2025 **SEIP工业实践论文**，不是主会Research Track。主要检查单步交互；预期由模型常识推断，并非独立业务规格真值。 |

## 一段话介绍

KuiTest研究的是 GUI 功能测试中的**判错依据**。普通探索器能点击许多按钮，却不知道点击后是否打开了正确业务页面；手工脚本能检查，却需要不断编写和维护规则。作者让模型先根据控件、页面和常识预测“这个按钮应该做什么”，执行后再比较实际响应。为减少看图误解，工具补充 OCR 文字、控件编号及人工图标库。它实际部署在美团的新平台适配和每周回归中，但检查重点是一次交互的局部响应，不是多步交易或完整业务链条的正确性。（§I–III、VI，PDF pp.1–5、9–10）

## 关键术语与阅读前提

- [Oracle与功能错误](../glossary.md#oracle)：oracle是“应发生什么”的依据。本文用模型从外观和常识推断的用户预期，比较实际页面；不以有无崩溃替代功能正确性。
- [控件树 / XML](../glossary.md#view-hierarchy)：运行时页面元素及其属性的层次结构。本文找出clickable或long-clickable为真的控件，并用视觉检测补充树里缺失的元素；不是分析业务源码。
- [OCR](../glossary.md#ocr)：识别截图文字。将识别文字分别绑定到各控件，比把整屏文字拼成一段更容易解释某个按钮。
- [SoM（Set-of-Mark）](../glossary.md#set-of-mark)：在控件周围画框并编号，提示中引用编号，避免“右边按钮”指代含糊。
- [图标功能检索](../glossary.md#icon-function-library)：给无文字图标找一个外观相似、人工标注过功能的样本，再把功能说明提供给模型；相似不等于当前业务语义必然相同。
- [Precision / recall / FPr](../glossary.md#metrics)：precision看报告中多少真有错；recall看已有错误中多少被找到；FPr看正常输入中多少被误报。正常输入很多时，FPr很低仍可能产生不少误报。

## 动机

§II（pp.2–3）给出两个工业需求。第一，应用迁移到HarmonyOS NEXT时，旧Android/iOS脚本依赖的控件树结构和属性发生变化，难以及时迁移大量判定脚本；新平台又容易暴露加载等问题。第二，持续回归里脚本通常优先覆盖核心交易，其他页面因编写与维护成本而缺少检查。作者希望在已有自动探索上附加功能oracle，给人工测试提供高风险区域提示。

作者没有要求该工具直接处理所有复杂历史状态；§II明确将快速遍历和风险提示作为实际目标。其“无规则”指不为每项被测业务预先编写响应断言，而不意味着没有人工准备、没有阈值或任何先验知识。

## 贡献

按§I（p.2）三项整理：①报告工业界规则oracle泛化与维护的经验问题；②提出用模型知识模拟用户预期，作为功能oracle；③实现KuiTest并以消融、定量数据及真实部署评价。主要归类为`method`。论文构造企业内部评测集，但未给可公开获取完整评测集的地址，本笔记不将其直接当公开benchmark贡献。

“首个无规则工具”是作者对工作的定位，未独立核验优先权。方法实际上还依赖图标库和检测模型，不能把该措辞扩展为“零人工准备、业务预期始终正确”。

## 方法

整体是**识别可操作元素 → 预测目标控件功能 → 执行一次交互 → 检查有无响应 → 比较预期与实际语义 → 保存异常和轨迹**。（Figures 2–4、§III，pp.3–5）

### 1. 找控件并建立对应的文字与编号

Android使用ADB获取控件树，取clickable或long-clickable为真的元素；同时用vision-ui视觉检测器识别截图中的交互元素，补充WebView等树信息不足情形。随后在截图上画框、分配ID，OCR识别文字并按控件关联进提示。模型收到的是带编号截图和组件级文字描述，不是只看裸图。（§III-C，p.4）

这里树中“可长按”只是元素识别条件；正文执行介绍主要描述点击，没有完整展开所有动作类型、冲突去重规则或视觉框与树节点合并算法，不为它补写统一动作规划器。

### 2. 无文字图标先检索功能库

库来自美团应用的常见无文字控件，每类由人工标注名称和功能，图像经CLIP转成向量。新图标与各库样本算余弦相似度，最高分超过阈值δ才将该功能说明添加到提示。实验用随机十页构建18类图标库；原文未明确给δ具体数值或图标库与不同评测子集的完全隔离方式。（§III-C、IV-A4，pp.4–5、7）

最终模型按控件ID预测其应有作用，例如心形按钮可能收藏当前内容。预测在操作前完成，避免直接把操作后界面本身当预期；但它仍来自模型与检索样本，而非产品规格。

### 3. 执行和判错分两路

Android通过ADB、HarmonyOS NEXT通过hdc执行交互，随后截图。先比较前后截图的像素相似程度：无可见变化就标记为无响应异常。若有变化，再将操作前预测的功能与操作后截图、文字信息提供给模型，询问实际响应是否冲突。响应判断没有放few-shot示例，作者希望保持跨业务泛化。（§III-D，p.5）

原文没有说明图像相似度阈值、界面等待时机及异步加载稳定判据。合法但无需立即视觉反馈的动作可能挑战该规则；这是我们的观察，不是论文已测出的误报分类。

### 4. 两种测试模式怎样推进与停止

**随机探索**输入应用、起始页和最大步数，默认500步；随机选择当前可交互控件并检查响应，随后留在新页面继续操作，不每次重置。达到步数停止。

**控件遍历**输入页面列表，对各页控件逐个操作并检查。每次操作后关闭重启应用，再导航回目标页面，保证下一个控件从原页面条件检查。定量实验选择此模式便于统计；正文未完整说明页面导航脚本如何生成及准备成本。（§III-E、IV-A1，pp.5–6）

最终产物是交互轨迹和模型判断，交给工程师复核。即使随机模式执行很多步，oracle仍主要逐步判断响应，不能写成其建立了跨历史的业务不变量。

## 核心技术与原文案例

Figure 7（p.9）的回归错误是：点击“待付款”，实际显示退款订单。系统先解释所点入口的功能是查看待付款订单，再执行并理解结果页面，两者冲突时报告。这个例子直接体现GUI功能判定，不能概括成“模型自由探索页面”：没有功能预期，打开任意订单页面可能被误当作导航成功。

Figures 3–4（pp.4–5）的模块关系说明，预测并非只读按钮文字：图标库为无文字图标补语义，OCR对有文字控件减少看图遗漏，编号把语义绑定到精确控件。两步拆分保留了操作前的预期，又直接给验证模块看操作后原始图像，避免先将后图压成文字时丢失颜色等细节。

Figure 6（p.9）另展示HarmonyOS NEXT上的图片加载失败、页面加载失败。这些影响可见功能或页面内容，和订单入口错跳不同；它们也不是遮挡、重叠、溢出检测。论文的“功能错误”覆盖范围较宽，阅读结果时应保留具体错误表现。

## 实验

### 数据、模型和真值

三组数据均来自美团M应用，不是多应用公开基准。（§IV-A，pp.6–7）

| 实验 | 数据与用途 |
|---|---|
| RQ1任务拆分 | 五业务线总计25个历史错误输入，另每条业务线25个正常输入，共150输入，错误占25/150。比较不拆分、两步、三步。 |
| RQ2控件功能理解 | 五业务线随机250个控件，含有文字与纯图标。两位作者人工判断预测是否符合设计，分歧第三人裁决；不是用模型自评。 |
| RQ3响应检测 | 十业务线，每线十页并注入15个历史错误输入；共100页、4664可交互控件、150错误响应。检查注入历史故障，区别于后来部署发现新缺陷。 |

定量评测用Claude-3-haiku，MacBook Pro 2.6GHz六核i7，Xiaomi14采集页面及树。部署模型与评测不同，正文没有明确列出实际部署模型，不能把全部工业成绩都归给Haiku。未明确报告重复次数、随机种子、统计显著性检验或完整耗时。（p.7）

### RQ1：为什么两步，而不是一步或三步

Table I（p.7）作者报告的Average如下：

| 拆分 | accuracy | precision | recall | prompt / completion tokens |
|---|---:|---:|---:|---:|
| 不拆分 | 0.83 | 0.65 | 0.48 | 3420 / 223 |
| 两步 | 0.93 | 0.86 | 0.72 | 5326 / 316 |
| 三步 | 0.90 | 0.83 | 0.60 | 7012 / 773 |

三步先预测功能，再单独提取操作后页面语义，最后比较两段文字；这可能丢掉图标颜色等细节。作者据此选择两步，平衡质量和token成本。这里的Average是表中汇总口径，没有给出完整混淆矩阵，不与RQ3聚合precision合并。作者使用“显著更好”的描述，但未给统计检验，不改写成有p值支撑的显著提升。

### RQ2：文字、编号和图标库分别有什么证据

Table II（p.7）把有文字控件与纯图标分开。纯模型输入的平均正确率为0.90/0.13；Img+Text为0.92/0.16；SoM+Text为0.96/0.19；完整KuiTest为0.96/0.95。图标库主要改善无文字图标，不能说它把所有控件识别从19%提高到95%。完整方法单次功能理解prompt/completion约3136/97 tokens，纯模型1655/120。

正文先写三种变体，构造说明又逐项描述多个去除步骤；应以最终Table II四种实际配置为准，而不擅自补出第五种结果或每组件完全独立的消融。

### RQ3：低FPr不等于所有报告都可信

Table III（p.8）聚合输入4664、真实注入错误150、TP129、FP52，precision=0.71、recall=0.86；正文FPr约1.2%，表中四舍五入为0.01。precision分母是报告的错误输入，recall分母是150个错误输入，FPr分母是正常输入而非全部报告。因此低FPr仍伴随52个需要人工排除的误报。

**表内汇总疑点**：Table I三步方案的五业务召回率列为0.60、1.00、1.00、0.60、0.40，Average却写0.60，原文未解释这一汇总口径；Table III逐业务FP合计为51，Aggregate列写52。本笔记保留作者聚合结果TP129/FP52，不自行选一个分项值更改，精确复算仍需原始数据。

**所读版本笔误**：§IV-D同页称“50个错误、150页”，与§IV-A1及Table III的“150错误、100页”冲突；本笔记保留构造与表格一致的后者，不把50/150混入主结果。各业务线precision从0.55至1.00，也不能只用总体数字宣称所有业务同样稳定。

### 真实部署：发现、确认与修复必须分开

- **新平台适配**：31,176次交互，报告32个此前未知错误，31个获确认；其中28个确认错误与UI加载有关。（§V-A，pp.8–9）
- **每周回归**：六个月24轮、约100k cases，报告12个GUI错误，10个确认；确认部分含四个显示错误、六个语义错误。（§V-B，p.9）
- 引言称发现41个未知错误；后文两场景分别32/31和12/10，41恰与两场景确认数合计相符。原文没有进一步明确合并口径和去重，因此不把41写作同口径的总报告数。未列修复数量，不写41个已修复。
- 工程师估计可替代约15%的脚本和人工测试工作，这是部署经验估计，不是随机对照测出的精确工时下降。（p.9）

## 局限

**作者承认（§VI，pp.9–10）**：检测能力依赖基础模型；为保证可靠性，只把单步交互作为目标，多步序列留待未来；外部应用泛化存在限制，虽不依赖专有实现，但没有跨企业大规模验证。

**我们的观察**：手工图标库和常识本身不保证应用特定语义；没有规格输入时，一些反直觉但合法设计可能被误报，一些符合常见外观的业务错误也可能漏掉。主要数据来自同一企业，缺少完整公开复现和多次运行波动；无响应规则、δ阈值及实际部署模型等配置不充分。模型oracle降低规则维护成本，不等于获得独立正确性证明。

## 和我们课题的关系

### 与 UX testing 的关系

可借鉴“先建立操作前预期，再主动交互复核”的设计，以及把控件树、截图、OCR绑定到同一目标。UX-Agent针对截断候选用布局树和滑动验证时，同样需要明确操作应造成什么变化，避免操作执行成功即认定候选消除。本文并未给出遮挡、重叠、溢出或截断的专用判定器；工业显示错误以空白和加载问题为例，不能将这些结果直接当我们的显示检测效果。

### 与 GUI testing 的关系

它主要补充常识驱动的功能oracle，可附加到随机探索和页面遍历流程。适合与需求/显式属性驱动方法比较：KuiTest减少逐项规则输入，但牺牲了业务预期的显式来源；它验证单步响应，而跨页面数据与历史约束需要额外机制。可以研究常识预期与外部规格如何交叉核验，但本篇未验证这一组合或证明其新颖性。

## 原文摘要关键句（节选）

> “KuiTest can automatically predict the effect of UI inputs and verify the post-interaction UI response.”
> — Abstract，PDF p.1。

这句明确两个任务：先预测输入效果，再验证响应，而非只有动作生成。

## 原文摘录

> “one-step interactions rather than interaction sequences”
> — §VI，PDF p.9。

该限制说明随机执行很多步，不等于oracle能够检验整段业务历史。
