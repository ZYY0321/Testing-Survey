# A11yNavigator：通过真实读屏导航发现网页控件不可达与不可激活问题

## 一页读懂

|问题|本篇的回答|
|---|---|
|研究什么|网页上的控件对视力正常、使用鼠标的人可能明显可见，但使用读屏器的人能否通过键盘找到它、找到以后能否操作？|
|旧方法不足|检查HTML和ARIA标记是否合法，不能直接证明NVDA读屏器确实能到达或激活该控件。|
|新增方法|从网页结构提取应当可交互的控件清单，分别用Tab、快捷键、向下箭头模拟读屏导航，再比较实际到达清单；激活检查则比较按键前后的无障碍状态。|
|输入与输出|输入为公开网页和运行中的NVDA；输出为某导航方式下未到达的控件，以及接受Enter/Space后未出现预期状态变化的控件记录。|
|证据|26个网站，表I合计207条问题记录、193条经人工验证，精确率93.24%；召回率98.97%仅来自6个网站的详细人工检查。|
|边界|不是LLM方法，不检查文字溢出、布局重叠；也不是自然语言目标导航或通用业务正确性判定。平均完整检查约234分钟/网站。|

## 一段话介绍

网页界面即使视觉上正常，也可能存在读屏用户找不到按钮、或者找到下拉框却无法展开的问题。A11yNavigator直接接入NVDA读屏器，在浏览器中模拟三种常见键盘导航：逐个切换可聚焦控件、按类型跳转控件、逐行读取内容。工具把实际访问的元素映射回网页结构，并与事先提取的可点击控件清单比较，定位“控件存在但在某种读屏导航中不可达”的问题；另外，它将每个候选控件置于焦点，通过Enter或Space尝试激活，检查读屏器暴露的展开、选中等状态是否改变。论文在真实网站上人工核验报告，说明直接观察辅助技术运行结果能补充静态规则检查，但其判定范围受元素抽取、身份匹配和状态变化规则限制。

## 关键术语与阅读前提

- **读屏器**：将界面文字、控件名称、角色和状态转成语音的辅助工具。本文使用Windows上的NVDA，并修改其日志模块记录运行信息；不是让LLM听语音后自行判断。见[可访问性](../glossary.md#accessibility-tree)。
- **DOM**：浏览器中的网页结构树，例如按钮、链接、输入框及其属性。**XPath**是元素在这棵树中的定位路径，供不同阶段关联“同一个控件”。见[DOM](../glossary.md#dom)与[元素定位](../glossary.md#locator)。
- **无障碍角色、名称和状态**：分别表达“这是什么控件”“它叫什么”“当前是否选中或展开”。ARIA属性由网页提供；NVDA通过无障碍接口获得对应信息。角色写错可能让视觉上像按钮的控件无法被按钮快捷键找到。
- **焦点与虚拟光标**：Tab通常移动浏览器的键盘焦点；NVDA逐行读取则移动自身的虚拟光标，不一定改变DOM焦点。因此两种方式不能用完全相同的技术获取访问位置。
- **可到达性与可激活性**：前者问某种导航方式能否找到目标，后者问对目标发出键盘操作以后是否有响应。本篇分别检测，不能把“被读到”直接当成“功能可用”。见[本篇专项术语](../glossary.md#a11ynavigator-navigation)。
- **Oracle与真值**：oracle是工具判错的规则，人工真值用于评价该规则是否正确。本文称可点击元素清单为ground truth，但这是程序抽取的运行参照，不等于已经由独立人工确认的完整缺陷真值。见[测试预言与人工核验](../glossary.md#oracle)。

## 动机

### 静态标记合规不能保证真实交互成功

原文Sec.II-C的Stack Overflow示例中，登录和注册按钮在视觉上存在，却被NVDA快捷键跳过；MakeMyTrip的页头控件在Tab导航中被跳过。IRCTC示例则不同：下拉框能被定位和读出，但Enter不能展开。前两类属于导航到达失败，后一类属于激活失败。论文指出WAVE未报告这些具体交互问题。

要注意，这并不证明静态检查整体无用。缺少标签、低对比度等问题正是静态规则的常用对象；本文补充的是辅助技术真实交互行为。

### 三种导航方式来源于用户观察

作者招募5名盲人用户，4男1女、25—64岁，均有至少10年读屏经验。在Agoda上进行每次约30分钟的远程任务观察和5分钟反思访谈，任务包含更换酒店目的地、日期、人数和搜索航班。用户陌生时可能逐行阅读，知道目标类型时使用快捷键，或者用Tab系统遍历可聚焦控件。这个小规模形成性研究支持选择三种策略，但不能代表所有读屏用户、网站和辅助技术使用习惯。

## 贡献

作者列出四项：①直接模拟读屏交互来检查动态可访问性；②实现Windows上的NVDA集成工具；③在26个网站上评价；④分析不可达和不可激活的实现原因。研究产物的核心是**方法与工具实现**。公开代码和选定网站并不自动构成具有完整缺陷真值的benchmark；论文把扩展为大规模benchmark列为未来工作。

## 方法

整体分为可点击元素提取、用户行为模拟、问题比较三个部分。可到达检测与可激活检测共享清单，但独立执行，不是必须先通过完整导航才允许激活。

### 1. 从网页提取“应当可交互”的参照清单

工具先寻找标准交互标签，如链接和按钮，以及带有相应ARIA角色的元素；再寻找绑定JavaScript事件监听器的自定义元素，例如被当作按钮使用的`div`或`span`。这使它不只依赖开发者是否使用正确的语义标签。

每个元素保存XPath、可访问名称以及id、href等属性。名称可从文字、ARIA标签、替代文本和placeholder等来源获得。工具排除隐藏、禁用、尺寸为零等元素；Sec.IV-A还说明，向下箭头检查排除缺少可访问名称及后备属性的元素，因为这类问题可由静态工具检查。

**这里没有采用截图识别“看起来可点击”的控件，也没有先用鼠标点一次来建立正确执行结果。** 可见性由结构/属性过滤实现；激活参照来自控件状态。这一区别关系到方法能发现什么以及会漏掉什么。

### 2. 三种导航分别记录实际到达的元素

|导航方式|如何移动|怎样关联到DOM元素|特别处理|
|---|---|---|---|
|Tab|发送真实Tab按键，在可聚焦控件间移动|记录NVDA名称、角色、状态和IA2UniqueID，同时执行JavaScript获取焦点元素XPath|对标签页组、单选组等复合控件补充内部箭头操作。|
|快捷键|使用链接、按钮、复选框、表单等类型快捷键跳转|记录无障碍属性并提取当前目标XPath|每个类型既向前也用Shift组合向后遍历，避免切换快捷键时漏掉当前位置之前的目标。|
|向下箭头|逐行读取交互和非交互内容|记录NVDA播报，清洗辅助描述词、合并分裂的长标签，再按文字/ARIA/title/placeholder/alt等匹配DOM，推断XPath|虚拟光标不触发普通DOM焦点变化，所以不能直接沿用Tab的焦点提取。|

三种代理各自输出标准化的XPath和无障碍属性记录。除了到达集合，还记录按键数量、到达比例和遍历时间。

### 3. 比较集合以判定某导航方式下不可达

对Tab和快捷键，工具把参照清单的XPath减去实际访问过的XPath；未访问到的目标被报告。向下箭头则必须同时使用推断的XPath与无障碍属性确认匹配，否则目标仍被视作未到达。

**判定以导航方式为单位。** 某按钮无法通过快捷键找到，但仍能逐行读到，不等于用户完全无法访问该功能；它意味着常用的高效路径受阻。论文仍将这类方式特定的不可达记录视作问题，并比较不同方式的操作负担。

### 4. 直接聚焦目标，检查键盘激活前后的状态

激活检测遍历可点击清单，先按XPath把目标置于焦点，再依据元素类型发送Enter或Space，并记录NVDA前后状态。例如下拉框应由收起变为展开，复选框应由未选中变为选中；若没有状态变化，则报告不可激活。

这一步通过程序直接聚焦，**不会证明正常用户已经能够通过键盘到达目标**。它是独立隔离“激活”问题的方法。原文没有完整交代所有元素类别对应的状态判定表、等待超时、页面恢复和重试上限；也未充分说明普通链接跳页、下载等不在当前控件上体现状态变化的情况如何统一处理。不能自行补写成完整的业务结果验证器。

### 5. 原文案例如何贯穿流程

以IRCTC的类别下拉框为例：它的标签和ARIA属性使提取器将其列为交互目标，正常导航也可以发现它；因此不是“根本没有到达”。激活模块对目标发送Enter，观察到`aria-expanded`所代表的展开状态没有改变，于是报告激活失败。作者人工核验认为该控件缺少相应键盘事件行为。该例说明“存在、被读到、响应操作”需要三个不同证据，不能只看一张截图。

## 核心技术与研究含义

### 同一测试目标需要多种可观测通路

本篇的难点不只是多发送几种按键，而是为它们分别建立可靠的位置观测：DOM焦点适用于一部分导航，虚拟光标则需要从辅助技术播报逆向匹配。误报和漏报也发生在这一关联过程。例如轮播图已更换卡片，旧XPath代表的对象不再相同；重复标签又可能把播报关联到错误的嵌套元素。由此可见，测试代理的状态识别错误也可能被误当成产品缺陷。

### 可到达与导航效率不能互相替代

逐行读取较完整，却需要更多按键。论文记录各网站按键统计，再在26个网站间取中位数：快捷键28.5次，Tab41.5次，向下箭头100.5次。逐行方式约为快捷方式3.53倍。作者因此反对用“另一种方式终究能找到”直接消除高效导航路径的问题。

这些按键数是观察特定网页结构和导航过程得到的负担指标，不是完成所有用户任务的成功率。运行时间还受按键等待和读屏日志采集影响，不能把按键减少直接解释为同比例的端到端加速。

### Oracle的外部依据来自真实辅助技术行为

本文既不要求LLM凭常识判断页面好坏，也不只凭HTML属性预测可访问性：它调用真实NVDA，观察实际可到达集合与状态转变。其优势是把判错依据落在可以重放、检查的交互上；边界是清单生成和状态模型仍可能不完整，辅助技术的观察结果也不自动等于所有用户体验的完整真值。

## 实验

### 数据、环境与人工工作

- 选择26个公开、以英语为主的网站，覆盖19类领域，参照Semrush流量与既有研究的选择方式。作者称筛选月访问量超过1000万的网站，表I的Wikipedia行仅写超过100万；表格提供的下限本身不能独立确认这一站达到前述筛选阈值，也不能反过来据此断言其实际流量低于1000万。
- 环境为Windows10 Pro、i7-7660U、16GB内存，NVDA2024.1。浏览器自动化使用Selenium，原生按键由keyboard库发送；NVDA的speech和inputCore模块被修改以输出JSON日志。
- 设计上比较正常桌面布局和400%缩放、约320 CSS像素的紧凑布局。**表I并非每站都有两行**：Craigslist、Google、MakeMyTrip、Wikipedia、YouTube仅列Desktop，不能将表格自行扩成26×2个完整配置或补造缺失结果。
- 报告核验由3位作者和1位外部评价者进行；前两位有4年以上可访问性研究经验，另外两位有约3.5年Web行业经验。核验者在Chrome无痕窗口、Windows+NVDA上重做导航与激活。
- 本文没有报告LLM配置或Token成本，因为不是LLM方法；未给出自动化实验的多次独立重复/均值与方差协议。

### RQ1：报告正确性与漏报情况

表I的统计如下，列内是问题**记录数**：

|类别|工具报告|人工判断为真|精确率|
|---|---:|---:|---:|
|Tab不可达|90|85|94.44%|
|快捷键不可达|93|86|92.47%|
|向下箭头不可达|9|7|77.78%|
|不可激活|15|15|100.00%|
|合计|207|193|93.24%|

**193/207评价“报告里有多少是真的”**，不能据此称检出了全站93.24%的问题。同一控件可能在不同导航方式或布局下重复计数；原文没有提供跨方式/视图的独立根因去重数。因此193条真记录也不能直接改写成193个唯一新缺陷或开发者已确认的修复。

召回检查更昂贵：作者从大、中、小网站中各取2个，共6站，详细人工找完整问题集合。工具漏掉ScienceDirect的两个向下箭头问题，分别位于桌面和紧凑布局，总召回报告98.97%。**这一百分比的范围是6站，不是26站全量。** 正文没有单独列出召回子集逐站真值表或总分母，不应从四舍五入百分数反推确定总数。

论文说每个网站在多导航方式下平均需要约200次按键；完整人工核验可能超过3小时。该成本解释了为何只对6站穷举召回，也意味着剩余20站的未知漏报无法由已知结果排除。

误报主要来自动态页面的元素身份变化：轮播更换卡片，或Google按钮聚焦后文案及对应节点改变，造成旧参照与新XPath不匹配。两个漏报则来自ScienceDirect重复DOM/ARIA属性使播报关联错目标。这些例子同时说明正常页面变化可以制造误报，结构匹配歧义也可以掩盖真问题。

### RQ2：与WAVE的关系

WAVE在表I合计报告1767条规则问题，A11yNavigator合计报告207条交互记录。作者强调两者针对的缺陷集合互补，而不是用207对1767证明某工具更优。**WAVE记录未接受与本文报告相同的完整人工核验，不能横比二者总体精确率或召回率。** 本篇也没有与其他动态读屏工具进行同预算、同真值的完整横评。

### RQ3：实际问题的实现模式

1. **自定义可点击区域无法聚焦**：`div`、列表项等挂了鼠标事件，却没补键盘聚焦属性。视觉上可以点，Tab和按类型快捷键可能跳过。
2. **链接标签缺少href**：开发者把链接当按钮，却丢失链接原本的键盘语义。
3. **ARIA角色不恰当或冲突**：例如页头被当成dialog，或菜单项嵌在角色清空的父元素内，干扰NVDA导航。作者通过实际观察分析这些模式；工具本身没有自动输出完整修复方案。
4. **只有可访问性标记，没有激活事件**：下拉框声明了角色和收起状态，但Enter/Space没有触发展开；还有被声明为按钮却无实际响应的对象。

原文还讨论SEO等更广泛影响，但它不是本篇GUI测试的核心实验，不据此展开额外结论。

### RQ4：执行成本

平均每网站：Tab43分钟、快捷键39分钟、向下箭头92分钟、激活检查60分钟，合计约234分钟。当前实现顺序执行。作者提出未来可以并行，但**没有报告已实现的并行加速结果**。这里的分钟是论文工具的自动检查耗时，不能与前述人工核验三小时混为同一测量。

## 局限

### 论文承认的

Sec.V强调网站选择与泛化、召回仅在6站人工穷举、人工判断主观性，以及Selenium、DOM抽取、NVDA日志的时序和XPath错误。作者采用多类别网站、不同布局、多人复查和重试逻辑缓解，但这些措施不能消除威胁。

### 我们的观察与待核查问题

- **检查对象收窄**：主要是交互元素，且向下箭头排除无名称元素；未评价正文阅读、描述准确性、完整业务任务完成或视觉布局缺陷。不能把结果外推为全面可访问性检查。
- **参照清单也可能错误**：基于标签、角色和监听器识别交互意图并不保证清单完整。隐藏属性错误的元素、复杂事件代理、自绘内容是否被覆盖，没有逐类证据。
- **局部状态oracle不等于功能oracle**：状态没变可能是等待不足、需要前置输入、页面跳转或缺少无障碍反馈；状态改变也不能证明后端操作正确。论文给出了成功案例，但没有发布完整类型级判定表和消融。
- **独立检测与完整使用路径不同**：通过XPath直接聚焦后能够激活，不说明用户正常导航能够找到它；两种失败要分别报告。
- **环境范围有限**：单一NVDA版本和Windows配置不能代表JAWS、VoiceOver或所有浏览器组合，也未展示对不同辅助技术的差分实验。
- **证据范围不对称**：26站用于报告精确率，6站用于召回，且表I有缺失紧凑布局行。页面数、站内多级探索范围和停止预算未给出充分细节，不把“26个网站”解读成全站页面爬取。
- **没有开发者确认/修复漏斗**：人工核验是真问题的证据，但不能标作开发者确认或已修复。论文未提供相应计数。

这些是方法边界和可继续核查的问题，不是“当前无人解决”的选题空白断言。

## 和我们课题的关系

### 与 UX testing 的关系

本篇直接属于交互可访问性UX测试，补充UI-Lens以外的另一种oracle：当视觉上存在的控件无法被读屏用户到达或操作时，通过实际辅助技术交互给出证据。其研究启发是让候选问题接受真实动作复核，并区分“目标被访问到”与“目标能使用”。但它不检测文字截断、遮挡、重叠、溢出，也不证明NVDA状态规则能直接迁移到这些显示问题。

### 与 GUI testing 的关系

它提供缺陷目标明确的执行/判错闭环：先定义可点击对象，再按具体用户交互通道遍历，以到达集合差与状态变化为oracle。其探索是**预定义导航方式下的控件检查**，不是自然语言任务引导的页面跳转，也没有根据UX风险自适应选择下一页面。可以作为研究“为特定oracle安排检查动作、如何验证候选”的非LLM参考。

与[A11yScan](zhang2025a11yscan.md)相比，A11yScan重点增加Android页面状态并解释规则警告；本篇直接操作Web读屏器。与[TIMESTUMP](mehralian2025timestump.md)相比，本篇关心控件是否可到达和激活，TIMESTUMP关心交互后动态内容及焦点/播报时序；三者不能都简化成“读屏检测”。与[Reca11](huq2025reca11.md)相比，本篇自行执行并采集NVDA结果，Reca11从已有用户测试转写中提取问题报告。

## 原文摘要关键句（节选）

> “whether user interface (UI) elements can be located and activated using a screen reader”

— Abstract，作者团队13页PDF，第1页。此句限定了本文核心问题是交互元素的定位和激活，不是所有UX缺陷。

## 原文摘录

> “Each detection strategy runs independently”

— Sec.IV-F，同版PDF第10页。各检测策略独立运行；不能假定激活模块必然复用一条成功的用户导航路径。
