# WebTestPilot：把自然语言需求转为跨页面可执行断言，检查 Web 功能是否正确

## 一页读懂

| 问题 | 解释 |
|---|---|
| 旧方法哪里不足 | GUI 代理能完成点击、输入和导航，不代表它能判断功能正确。若让模型直接回答“购物车是否正确”，它可能遗漏历史商品、算错金额，或者在相同输入下给出不同理由。 |
| 本文新增什么 | 按需将页面信息抽成有类型的变量，保留可回查的页面历史，再让模型生成 Python 风格断言，由程序执行这些断言。贡献还包括四个 Web 应用、100 条需求及对应人工注入故障的评测集。 |
| 输入 / 输出 | 输入自然语言测试需求以及运行中可见的截图、DOM；输出操作轨迹、前后条件断言和不一致报告。不以读取被测应用业务源码指导测试。 |
| 怎样验证 | 对比三种 GUI 代理的执行能力；缺陷检测只与具备断言能力的 PinATA 对比。另测试需求改写、模型替换、23 个复现历史故障及工业案例。 |
| 证据边界 | 主实验任务完成率 0.99、缺陷检测 precision/recall 均为 0.96，但主要来自四应用、人工构造需求与注入故障；不是开放式未知应用探索结果，也不覆盖纯显示缺陷。 |

## 一段话介绍

本文研究的是**基于需求的 Web GUI 功能测试**：测试者提供一段需求，系统既要完成对应操作，也要检查结果是否符合预期。核心例子是购物：将相机加入购物车后，不能只看到“购物车页面已打开”就通过，还要检查商品、数量、价格和原有购物车内容是否一致。WebTestPilot 把页面中的商品、购物车等信息抽成有类型的变量，利用保留的历史状态表达前后关系，再生成可执行断言。执行断言的比较过程是确定的，但需求理解、变量抽取、断言生成仍由模型完成，因此它降低了自由文字判定的不确定性，并未获得完全独立于模型的正确性保证。（§2–4，PDF pp.5–11）

## 关键术语与阅读前提

- [测试预言 oracle 与断言](../glossary.md#oracle)：预言是“应当怎样”的依据；断言是把这种依据写成可执行检查。例如“加入一件商品后，购物车商品总量增加一件”。断言失败说明观察与所表达的预期不一致，还需要排除断言本身错误。
- [前置 / 后置条件](../glossary.md#test-spec)：前置条件检查动作开始前的状态，后置条件检查动作结果。本文每步表示为“条件—动作—预期”，不是只有动作列表。
- [DOM](../glossary.md#dom)：浏览器维护的页面元素树。本文同时使用 DOM 和截图；不应把 DOM 误当应用业务源码。
- [符号化与 schema](../glossary.md#symbolic-gui-oracle)：将画面信息转成有名称、有字段、有类型约束的数据。例如商品包含标题、非负价格、正数数量；购物车包含商品列表和小计。schema 规定结构，实际价格等值仍需从页面抽取。
- [DSL（领域专用语言）](../glossary.md#symbolic-gui-oracle)：只为一类任务设计的表达方式。本文扩展 Python，提供当前状态、历史状态、查找元素、按 schema 抽取数据等接口，让模型写检查代码。
- [页面重识别](../glossary.md#page-reidentification)：识别不同时间的两个状态是否属于同一逻辑页面。购物车从空变为非空，截图变了，逻辑页面仍是购物车；这使系统能回查加入商品以前的内容。

## 动机

动作执行和结果判断是两种能力。§1（pp.2–4）指出：不生成断言的导航代理可能正确到达结尾，却没有验证中间业务行为；用自由文字保存历史的断言代理又可能在早期没有记下后续才需要的信息。例如结账时才需要核对折扣前金额，而此前摘要没有保留这个值，就无法重建计算关系。

作者将问题进一步分成两部分。第一，模型需要识别跨状态的隐含要求：选中的商品应延续到详情和购物车，删除商品后折扣应重新计算。第二，直接让模型判定页面正确性，其理由可能不一致。Figure 1 的小型说明性实验对五种模型各重复提问十次，展示判定理由变化；它不是完整的错误率或稳定性基准。

本文的解决方向不是再增加一个独立说“正确 / 错误”的代理，而是先显式表示相关数据和关系，把最终判断尽量落到可执行比较上。

## 贡献

按 §1 的作者贡献表述（p.4）整理：

1. **方法**：将模型理解与符号断言结合，让页面数据、历史依赖和隐含预期进入可执行检查。作者称其为首个神经符号 GUI 测试方法；“首个”是作者定位，本笔记未独立核验整个领域的优先权。
2. **实现**：实现 WebTestPilot，并报告中国移动合作方采用。系统实现不自动意味着它贡献了一种通用测试 harness，分类以方法为主。
3. **评测资源与实验**：构造四个开源应用的 100 条需求、参考脚本和 100 个注入故障；对比代理并在真实开发场景检验。由于数据集本身是明确新增产物，记录 `benchmark`。

## 方法

整体流程是：**需求结构化 → 推导检查条件和变量结构 → 检查前置条件 → 执行动作 → 抽取新状态并检查后置条件 → 保存历史 / 报告不一致**。不是先无目标地探索所有页面。（Figure 8，pp.8–11）

### 1. 将自然语言变成逐步规格

模型读取原始需求，输出 JSON 步骤序列。每步包含 `conditionNL`、`actionNL`、`expectationNL`，分别表示动作前条件、动作内容及动作后预期。系统可配置为补全缺失步骤，但论文讨论明确承认其评测假设需求信息完整、有序；不能据此认为任意含糊需求都能可靠补全。（§4.1，pp.8–9；§7，p.19）

### 2. 从显式要求推导隐含要求，再定义符号

每一步分两次模型推理：先提供显式条件、预期以及历史状态的文字表示，寻找数据、因果和时间依赖；再根据这些要求定义必要的数据结构并编写断言。状态中的所有元素不会提前全部抽成业务数据；模型需要购物车时，再对相关历史截图抽取购物车结构。这缓解了“早期摘要没记下、后期就永远丢失”的问题，但依然依赖保留下来的原始状态及抽取模型能力。（§4.2，p.9）

### 3. 用有类型的数据与 Python 风格 DSL 表达检查

自定义 schema 用 Pydantic 描述。Figure 3 中商品的标题为字符串，价格非负，数量可选且大于零；购物车保存商品列表。Figure 6 又展示包含小计的购物车结构，表达小计等于商品价格乘数量之和。类型约束能拦截部分格式或值域错误，不能证明页面中的价格被识别正确。（pp.6–7）

内置对象及更新关系如下（Table 1，p.11）：

| 对象 | 保存的信息 / 接口 | 用途 |
|---|---|---|
| `Session` | `history` 为按时间排序的状态列表；`state` 为当前状态 | 在同一次测试中访问过去与当前页面 |
| `State` | `page_id`、元素集合；`find(description, top_k)`；`extract(instruction, schema)` | 识别逻辑页面、查找控件、按指定结构抽业务数据 |
| `Element` | 边界坐标、父元素、子元素；`extract(...)` | 检查局部内容或空间关系 |

DSL 支持存在性、关系、时间、因果和数据完整性五种检查，也允许 Python 逻辑连接、循环和部分标准库。这里的“符号”不是数学求解器自动证明出来的真实值，而是模型给出的结构化页面观测；其价值在于让后续比较更明确、可回查、可执行。（§4.2.2，pp.9–10）

### 4. 动作定位与状态历史怎样衔接

动作定位先由 UI-Venus-7B 根据动作描述和整页截图预测大致坐标，再在该位置附近裁剪截图。系统根据元素树为可交互元素画框并编号，模型在局部图上选择精确元素及点击、输入、按键、滚动或等待等动作。这是“粗定位再精定位”，不是本论文 oracle 的全部创新。（§4.3.1，p.11）

每产生新状态，先从历史中选择 DOM 树编辑距离最小的状态作为候选，再让模型对比两个截图是否属于同一逻辑页面。同页沿用 `page_id`，否则分配新 ID；同时生成包含页面 ID、摘要与布局的文字表示并追加到历史。这使相隔较远的两次购物车访问能够关联起来，而非只比较相邻截图。（§4.3.2，p.11）

### 5. 判定、重试与最终产物

系统执行前置断言、动作和后置断言，断言持续失败时记录不一致。论文说明可以重新生成断言并重试，也可提前生成多个候选并投票；本研究设 `n=1`，因此不能把多次投票带来的可靠性当作实证结果。§4 概述提到动作重试，§4.3.3 着重描述重新生成断言；实际重试对象和故障恢复边界仍需要代码核验。本文未复现代码，保留此表述差异。（pp.8、11）

## 核心技术：原文购物案例怎样连接模块

原文 Figure 2–6（pp.5–7）的流程为：空购物车 → 主页 → 输入 camera → 搜索结果 → 第一项商品详情 → 加入购物车。三种依赖分别解决不同检查：

- **因果依赖**：输入搜索词后，搜索框内容和联想列表应随该输入变化。检查的是动作引起的页面效果。
- **数据依赖**：搜索结果选中的商品、详情页商品和购物车商品应一致。检查的是信息在不同页面之间传递后是否改变。
- **时间依赖**：第一次和最后一次购物车访问属于同一页面，后者应保留原有内容并加入新商品。检查的是跨时间的增量变化。

系统先抽取加入前的购物车、商品详情和加入后的购物车，再按商品标题查找对应项，比较数量、价格和小计。最终执行的是数据间关系，不是仅凭最后一张图询问模型“看起来对不对”。

**示例代码的证据边界**：Figure 2 的时间依赖示例前面定义 `a`、`f`，后面却引用 `b.items`；同图又有加入一件商品后要求列表长度大于一的表达。Figure 4 的索引/状态标注也与整段流程不完全一致。因此应学习其跨状态检查思想，不能把图中片段直接当经过运行验证的代码。Figure 5 的逐商品比较也不能单独保证“没有任何额外商品”，完整正确性取决于实际生成的检查集合。以上是我们对所读版本的观察，未修改作者示例来假装原文正确。

## 实验

### 数据和真值如何构造

四个应用是 BookStack、Indico、InvoiceNinja、PrestaShop，分别有 27、25、25、23 条需求，总计 100 条。作者按活跃度、成熟度、真实使用和文档可得性等条件选应用，将其打包为 Docker Compose 环境。需求先来自用户文档中的正常使用路径，再按增删改查扩展；参考脚本由人工用 Playwright 编写，每步断言构成外部评测真值。（§5.1、Table 2，pp.12–13）

故障部分先从 2,043 条已关闭且标注 Bug 的 issue 中随机抽取 10%，经两位作者开放编码、第三人裁决得到分类，再为每条需求人工实现一个 JavaScript 注入故障。四类为缺失必需控件、数据不一致、无效果动作和导航失败。**这些不是 100 个原样复现的真实缺陷**。作者刻意排除 crash 及不影响功能的纯外观/布局问题；因此不能将结果解读为通用 UX 显示缺陷检出率。（§5.1.4，p.13）

### 协议、比较对象和指标

- 动作执行对比 LaVague、NaviQAte、PinATA；缺陷检测只对比有断言能力的 PinATA。前两者没有断言，不能把它们算成检测失败的 oracle 基线。
- 每条测试启动干净应用实例、还原数据库，顺序执行避免共享状态干扰；动作数达到参考脚本长度后停止。正文没有给清晰的全套重复次数、随机种子或置信区间，不补写“重复三次”等设置。（§5.2.3，p.14）
- `TC`（任务完成）要求各步状态都满足参考脚本断言；不是只到最终页面。`CT`（正确轨迹比例）是首次失败前连续正确步骤数除以参考步骤总数。（p.14）
- 缺陷 precision = 正确失败报告 / 全部失败报告；recall = 被检出的故障状态 / 应检出的故障状态。这里在**步骤状态层面**记 TP/FP/FN，作者另人工核查断言语义，避免碰巧失败被算作检出。（pp.15–16）
- 基础模型为 GPT-4.1，动作粗定位用 UI-Venus-7B。后续替换 Qwen2.5-VL 72B、32B、7B、3B；模型替换不是拆掉符号化或页面重识别的模块消融。（pp.11、17–18）

### 主结果及解释范围

| 实验 | WebTestPilot | 比较 / 可以支持什么 |
|---|---|---|
| 主实验 TC / CT | 0.99 / 0.99 | LaVague 0.64/0.77；NaviQAte 0.54/0.70；PinATA 0.08/0.18。支持此评测协议下的执行优势，不能推断所有网站通用成功率。（Table 3，p.15） |
| 注入故障 precision / recall | 0.96 / 0.96 | PinATA 0.26/0.69；提升为 70、27 个百分点，不是相对提升 70% 和 27%。（Table 4，p.16） |
| 23 个真实历史故障复现 | 检出 22 个 | PinATA 检出 15 个。这是复现已知缺陷，区别于发现新缺陷。（p.16） |
| 每步资源 | 中位耗时 29 秒，中位 10k tokens | 对应本次模型与配置；不是 2026 年所有模型的成本结论。（p.15） |
| 小型维护试验 | 39/40 动作定位得到保留 | XPath 32/40、CSS 33/40、Playwright 29/40；测量相同控件在更新前后的重识别，不等于整个业务断言自动正确迁移。（p.15） |

主实验的 PinATA 在执行层面很弱，而检测实验对步骤断言进行比较，两种数字不能混成“同一批完整成功轨迹上的检出比较”。作者解释差距还包括整页截图、粗细两级定位和历史表示，**没有分别移除这些模块的消融**，因此不能将全部增益归因于符号化一项。

### 需求改写和模型实验

需求改写包括加入噪声、删除 10% 句子、摘要缩写、改变文体，作者假设不改变必要语义；现实中删除句子可能损失关键信息。Table 5（p.18）中 GPT-4.1 的 TC 从默认 1.00 到噪声 0.93、其余三类 0.70，跨五种输入的聚合值 0.81。不能只凭摘要写“对各种输入都稳定”。较小模型既有符号声明和 DSL 用法错误，也有运行时类型错误；作者对错误样本归因为 52%、39%、9%，这是错误类型比例，不是全部测试失败率。

**版本中的统计疑点**：Table 3 主实验 TC=0.99，Table 5 默认 GPT-4.1=1.00；Table 5 的若干默认小模型 TC 也等于 1.00，而正文又描述参数越小整体越差。正文未给足样本/重复协议来解释差别。保留各自原值，不跨表拼接推导模型排名或最小可用参数量。作者对“7B 门槛”的建议也不应视为本项目选模型的通用依据。

### 工业案例与新缺陷

中国移动无代码平台上正在开发的仓库系统：PRD 预处理成 56 个测试输入耗时 6.4 分钟，执行耗时 32.7 分钟，报告发现八个缺陷，其中五个数据绑定问题、两个 UI 问题、一个导航问题。UI 问题包括重复表单字段、查询字段名称不正确，不等同遮挡/溢出。（§6、Table 6，pp.18–19）

论文没有逐项提供“报告—开发者确认—修复”计数链，故记录为**作者报告发现八个**，不写八个已修复。正文称 PinATA 技术上可检测其中 3/8，更像能力分析，不能作为同协议实测的工业对照成绩。

## 局限

**论文承认（§7，p.19）**：参考动作路径可能低估等价实现路径；四应用、测试需求及故障不一定代表现实；假设需求自包含、完整且按顺序给出。输入解析质量是重要瓶颈。

**我们的观察**：断言执行确定并不保证抽取值、推导需求或断言语义正确；缺少模块消融与明确全套重复协议；纯显示故障被排除；少量示例代码和表间数字存在上述不一致。若采用其设计，应独立检查“符号值抽错”“关系推导错”“应用真错”三种来源，而非把所有断言失败直接认作产品缺陷。

## 和我们课题的关系

### 与 UX testing 的关系

直接可借鉴的是将视觉候选转为结构化证据、再执行检查的链路。UX-Agent 从截图发现文字截断候选，结合布局树与滑动复核时，可以借鉴“保留操作前后原始状态、按需抽取、让判定有可追查数据”的方式。本文也能写空间关系断言，但主基准主动排除纯布局外观问题；它未证明对遮挡、重叠、溢出或滑动消除候选的有效性。

### 与 GUI testing 的关系

它补上的是需求驱动测试中的 **oracle**，并配套动作执行和专门评测集。相比只追求覆盖页面，它关注跨页面业务数据与历史状态一致性。适合用来分析“测试代理完成任务”和“测试代理能发现功能错误”的区别。把它扩展到代码或后端证据、用独立数据源验证符号抽取，属于待评估研究假设，本文没有提供这些结果。
