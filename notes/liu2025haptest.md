# HapTest：为 OpenHarmony 应用提供可扩展的动态测试框架

## 一段话介绍

HapTest 研究“如何在 OpenHarmony 上搭起可复用的动态测试底座”。它把源码插桩、设备操作、页面建模、日志收集与动作策略拆开：底层负责可靠地点击和取回数据，上层策略根据页面转移图、已执行事件和覆盖信息决定下一步。论文用随机策略验证基础覆盖能力，用贪心 DFS 在商业应用里触发崩溃和卡死。它适合充当其他测试方法的执行与取证基础，但仅靠这个框架还不会判断界面是否截断，也不会理解某条业务流程应当有什么正确结果。

## 关键术语与阅读前提

- **OpenHarmony / HarmonyOS**：本文定位于 OpenHarmony 的 ArkTS 应用生态，实验设备写作 Mate60、OpenHarmony 5.0.0。不能由此推断任意鸿蒙版本、设备或旧 Android 兼容应用都能直接运行。
- **ArkTS / ArkUI**：前者是应用开发语言，后者是声明式 UI 框架。`@State` 变量变化可能更新界面；不能只把它们当成传统 JavaScript 页面处理。
- **HAP**：Harmony Ability Package，应用安装包的基本单位。
- **UIAbility / Page / Component**：本文 GUI 模型的三级结构，一个 UIAbility 可以有多个页面，页面包含多个控件。因此只覆盖全部 UIAbility 仍可能漏掉页面及其中的状态。
- **插桩**：在源码特定位置加入计数/监测逻辑，执行到那里才增加计数，不是由截图猜测调用了哪个方法。
- **PTG（Page Transition Graph，页面转移图）**：页面为节点，实际执行事件为边，保存“上个页面—事件—当前页面”。可以据此找路和过滤重复事件，不是功能语义簇。
- **DataHub**：经过整理的故障日志、应用日志、覆盖与性能数据。它是运行数据接口，不是独立需求真值。
- **RPC / hdc**：RPC 让宿主机调用设备端操作服务；hdc 是 Harmony Device Connector，承担设备连接与系统级命令等工作。

## 动机

Android 自动化测试已有随机、模型驱动和搜索策略，但平台适配不只是把 ADB 命令换个名字。OpenHarmony 有不同的 UI 组件与事件参数、以 UIAbility 为中心的 Stage Model，以及 ArkTS/ArkUI 语法与页面路由机制，需要重新支持控件识别、事件模拟、覆盖采集和导航（Sec.1–2，PDF 第1–3页）。

因此本文首先解决“能否统一观察、执行、记录并让不同策略复用这些能力”。作者没有以“LLM 不理解鸿蒙页面”为问题起点，也没有把一般非崩溃 oracle 作为核心贡献。

## 贡献

按 Sec.1（第2页），作者贡献为：①面向 ArkTS/OpenHarmony 的动态分析框架；②分层解耦架构和开放策略接口，提供 PTG、覆盖、崩溃、日志等实时数据；③商业应用实证；④开源框架，并报告插桩能力 BJC 已接入 DevEco Studio。本文自称“首个”框架属于作者的优先权主张，本笔记没有独立穷尽验证。

贡献类型主要记为 **harness（测试基础框架）**，兼有工程方法与实证评价；不能因为提供 Greedy DFS 就将其概括成全新的探索算法，也不能因为建立应用集合就自动称为完整、独立验证的 benchmark。

## 方法：一次测试如何从源码走到报告

1. **准备应用与可用信息。** 完整白盒流程从源码工程开始；CIM 插入监测代码，再编译构建。只有安装包的商业应用可以进行 GUI 探索与日志观测，但不能自动获得相同的源码级覆盖信息。
2. **选择下一步事件。** EGM 事件生成模块根据当前结构化状态，通过候选生成、过滤、评分、选择四步输出一个事件。可用状态包括 PTG、覆盖、控件—代码映射 CCM、崩溃及普通日志；不意味着每一种策略都使用全部数据。
3. **真正执行。** Executor 将点击、长按、滚动、输入或按键转换为设备端 uitest 的 RPC 请求；启动/终止应用等系统事件通过 hdc 执行。这里的 bot 不需要理解自然语言指令：策略已经产生了指定控件或坐标的结构化事件。
4. **采集后态。** 收集截图、页面树、应用日志、系统故障和插桩计数。对受沙箱限制的运行数据，论文提出在应用沙箱内启动 FTP 通道，持续拉取，避免退出后数据丢失。
5. **更新结构化数据。** DPM 解析当前页面及控件，将 `(lastPage,event,currentPage)` 加入 PTG，整理日志与覆盖数据，再反馈给策略。
6. **循环与停止。** 当探索完成或达到时间预算结束，生成覆盖、页面转移和崩溃报告。论文示例策略按运行预算循环，不以证明所有功能正确作为结束条件。

### 一个贯穿例子（教学例子，非论文真实故障）

假设记事应用首页有“新建笔记”。框架从页面树读到它可点击，生成 ClickEvent；执行器调用设备端接口点击。编辑页出现后，PTG 添加“首页—点击新建—编辑页”。如果有源码插桩，相关函数/语句计数同时增加。如果保存时系统产生未处理异常，框架收集堆栈，报告崩溃。

如果保存按钮只是被键盘遮住而应用没有崩溃，框架可以留下截图和动作证据，但本文没有提供判断“按钮被遮挡且影响操作”的自动规则。需要额外 UX oracle；不能把“没有发生页面跳转”直接标为产品缺陷。

## 核心技术详解

### 1. 覆盖到底怎样测量，需要源码吗

CIM 遍历 AST（抽象语法树），根据节点类型定位插桩点并插入计数节点，再生成修改后的程序（Sec.3.1，第3–4页；Table1）。

| 覆盖类别 | 论文列出的插桩点 | 计数入口 |
|---|---|---|
| 函数 | FunctionDeclaration、FunctionExpression、ArrowFunction、MethodDeclaration | instFunction |
| 分支 | If、Switch、While、For、ForIn、ForOf、Do、Try 等节点 | instBranch |
| 语句 | Basic Block | instRegion |

源码级覆盖依赖插桩与可数的总集合，不是安装任意闭源 App 就会自动有百分比。论文没有完整展开复杂语法下分支分母如何计数；不要直接认为它与另一工具的分支覆盖定义完全相同。

CCM 是 Component Code Mapping，即控件与源码的映射，作为策略可用信息被列出；正文没有完整说明其构建算法和准确率。因此不能推断框架能为每个商业控件精确找出全部相关方法。

### 2. 页面如何识别，PTG 如何更新

GUI 模型是 Ability → Page → Component；控件保留位置、文本、clickable、scrollable 等属性。原始 ViewTree 可能同时包含多个页面，框架按 `a.height > b.height && a.width > b.width` 的条件排序、选第一项，依据是前台页面通常占据较大屏幕区域（Sec.3.3，第5页）。

这是一种尺寸启发式，**不是语义识别当前对话框或任务页面**。当宽高不同时占优、前台弹层小于背景时，该规则是否稳健需要另外验证；正文没有给识别精度。原文把 Android Activity 描述为通常只有一个页面，是解释性简化，不能当成 Android 的严格约束。

得到页面后，加入三元组；PTG 还记录各页面已执行的事件，供去重使用。基于图可以计算可达性与最短事件路径。但正文没有完整给出页面身份相等、内容变化如何合并，以及所有回退失败的恢复规则。它与 LLMDroid/GraphDroid 的语义聚类不是同一概念。

### 3. Greedy DFS 如何选择动作、怎样回去

Sec.3.4.2（第6页）给出流程：

1. 扫描当前页面未访问的控件，根据属性产生可执行事件，例如 clickable 控件产生 ClickEvent。
2. 过滤当前页面已经执行过的事件。
3. 没有可用事件时，利用 PTG 回退到最近的尚未探索页面。
4. 以 `Score = Σ(property_i × weight_i)` 给候选事件评分，按降序排列。
5. 选择最高分事件并执行，继续循环。

这里的“贪心”是优先选当前最高分事件；“深度优先”是沿可探索方向继续，遇到死路再退回。执行的是图里记录的操作，不需要 LLM 猜“设置页”怎么走。**但原文未完整公布属性权重、同分处理和全部不可重放情况**，不能补猜成“导航一定成功”或“永远有一条返回路径”。

### 4. 这篇论文是否使用 AI

**论文评估没有使用 LLM 决策。** 第9页相关工作把高级 AI 技术描述为未来可接入方向。框架接口可以支持启发式、覆盖驱动或学习策略，不代表都已实现并评估。

另外，[当前上游 README](https://github.com/SMAT-Lab/HapTest) 已列出 `--llm`、`--policy static_guided`、`--simk` 等可选功能。本地准备副本 README 也有这些选项。它们只能说明当前实现接口的状态，不能反向写进 FSE2025 的实验协议，更不能把开启 LLM 的结果称作论文原配置复现。

### 5. 故障依据是什么，是否会检查 UX

系统通过未处理异常、POSIX 信号等生成故障日志；报告整理堆栈和环境。商业实验区分 ArkTS 崩溃、C++ 崩溃和 Freeze（无响应），并没有用 LLM 比较预期界面，也没有需求断言验证数据是否正确（Sec.3.2、4.4，第4、8页）。

Freeze 可能由主线程阻塞、输入响应延迟或生命周期超时导致，属于与体验相关的稳定性现象，但不能把它扩大成“已经支持一般 UX 缺陷检测”。论文没有详细公开 Freeze 的全部阈值、缺陷去重及人工确认协议；26 条报告不等于已核实的 26 个不同源码根因。

## 实验

### 设置、数据和预算

Sec.4.1（第6页）：10 个开源应用来自官方 Codelabs 及 GitHub/Gitee，规模约 752–5,128 LOC；另选 AppGallery 的 20 个热门商业应用。设备是 HUAWEI Mate60，系统写为 OpenHarmony 5.0.0。RQ1、RQ2 每次 10 分钟、重复 3 次；RQ3 每次 1 小时、重复 3 次。正文未清楚说明所有图表如何合并三次运行，不擅自写成均值或取最好。

**没有与 Android 工具或其他鸿蒙测试工具进行同设备、同预算的直接性能比较，也没有完整策略消融。** 因此不能由图4宣称它探索优于 LLMDroid 或其他方法。

### RQ1：基础覆盖能力

在 10 个开源应用上使用**随机探索**。指标为语句、函数、分支覆盖和 UIAbility 覆盖；UIAbility 分子是动态 PTG 中按 UIAbility 聚合后的数量，分母来自静态分析识别的 UIAbility（Sec.4.2，第6–7页）。

Fig.4 横轴是**事件执行步数**，不是分钟；四种覆盖曲线跨应用差异明显。正文概述语句/行覆盖约 40%–90%；摘要式结论框写 UIAbility 覆盖 100%，正文则说接近100%。图中最终曲线支持全部到达100%的粗粒度结果，但不支持“所有页面或代码全部覆盖”。

一个值得关注的具体坏情况是 **SwiperArkTS 的代码覆盖出现长尾平台**：Fig.4 中 UIAbility 很快达到100%，但分支覆盖最后仍约85%，后续动作增长没有明显改善。作者明确据此指出深层逻辑分支与边界条件仍需要更强探索策略。这个案例能支持“粗粒度入口覆盖掩盖深层遗漏”的研究判断，**不能声称已证明遗漏某个真实缺陷**。

### RQ2：动态 PTG 是否完整

作者用 ArkAnalyzer 得到视图树与调用图，识别 `@Entry`、`@Component`，分析 onClick 中的 `router.pushUrl`、`router.replaceUrl`、`router.back`，并跟踪间接调用，构造静态图 s-PTG。再将运行生成的 d-PTG 与其比较（Sec.4.3，第7–8页）。

为了比较，动态页面按所属 UIAbility 聚合，**实际比较粒度是 UIAbility**，不能把 Table3 的聚合转移数与原始页面转移数混用。

| Table3 示例 | 未聚合动态页面/转移 | 共享 UIAbility | 仅静态 UIAbility | 仅动态 UIAbility | 共享转移 / 仅静态 / 仅动态 |
|---|---|---|---|---|---|
| Wechat_HarmonyOS | 25 / 108 | 5 | 0 | 0 | 5 / 0 / 7 |
| MultiShopping | 25 / 88 | 2 | 0 | 4 | 2 / 0 / 15 |
| OxHornCampus | 14 / 51 | 2 | 1 | 1 | 1 / 0 / 5 |
| OhBill | 9 / 18 | 3 | 0 | 1 | 2 / 1 / 3 |
| Msea | 8 / 22 | 2 | 0 | 1 | 2 / 2 / 5 |

8/10 应用有动态独有 UIAbility，10/10 有动态独有转移；说明静态分析遗漏了一些运行关系，动态数据可补充它。**但 OxHornCampus 仍有一个静态独有 UIAbility，OhBill 和 Msea 仍有静态独有转移**，不能写成动态探索完全没有漏检。

静态图本身不是穷尽真值；动态图更丰富也不能证明完整召回率。作者对静态节点粒度的解释与前述页面文件识别之间仍有简化，复现需核对实际身份字段，不根据术语替作者填补实现。

### RQ3：商业应用稳定性问题

使用 **Greedy DFS**，没有源码插桩覆盖对比。20 个应用中 11 个有报告问题，总计26（Table4，第8页）：

| 故障类别 | 数量 |
|---|---:|
| ArkTS Crash | 13 |
| C++ Crash | 10 |
| Freeze | 3 |
| 合计 | 26 |

抖音7个（2 C++、3 ArkTS、2 Freeze），高德地图5个（3 C++、2 ArkTS），喜马拉雅3个；其他报告分布于 Bilibili、携程、微博、今日头条、大众点评、钉钉、百度、飞书。微信、淘宝、支付宝等未检出，**不等于已经证明没有缺陷**。

摘要称26个此前未报告的 crashes，但表4包含3个 Freeze，正文也改称 issues。笔记采用**26个稳定性问题**。正文没有给开发者确认数、修复数、每条最小复现路径、误报率或完备真值；不把作者“此前未知”扩大成“全部已确认并修复”。摘要称每个商业应用下载达百万，但表4飞书仅0.3M；第8页“多数超过百万”更符合表格。

### 框架扩展示例：性能分析

Sec.5（第8–9页）说明可在 `aboutToAppear`、`build` 等生命周期位置加入性能计时或监测，再复用采集模块。在 OxHornCampus 的初步观察中，ImageAnimate、ZonesComponent 资源使用较高。但没有提供完整定量对照、阈值或性能缺陷真值，属于概念与初步可行性说明，不能写成成熟性能检测准确率。所读版本5.1与5.2标题重复，不是两套独立实验。

## 局限

**作者承认（Sec.4.2、5.3，第7、9页）：** 覆盖存在长尾，深层分支与边界条件难探索；无法检测全部崩溃，应用类别/下载量与故障关系的分析可能不准确；开源样本少，平台、语言和应用快速迭代，需要持续适配。

**我们的观察：** 前台页尺寸规则缺少精度评价；源码级覆盖依赖插桩；静态图比较不是完整真值；没有强基线对照和策略消融；权重、三次重复汇总、故障去重与开发者确认未充分交代；没有一般视觉或业务 oracle。以上属于本文证据边界，不意味着后来版本必然没有改进，也不意味着整个研究领域都无人解决。

## 和我们课题的关系

### 与 UX testing 的关系

可复用的部分是鸿蒙执行、截图/控件树采集、页面图与动作证据，帮助 UX 检测器到达页面并记录触发前后。它没有直接实现文字截断、遮挡、重叠、溢出的判断，也没有用滑动检验内容可获得性。框架采集到截图，与截图中的 UX 缺陷被覆盖并识别，是两个不同结论。

可以验证的研究问题是：**UIAbility 已覆盖但关键页面状态未覆盖时，UX 缺陷是否仍漏触发？** 应拿已知缺陷的具体状态和可重放动作证明，而不是只报入口覆盖率。SwiperArkTS 的平台现象是动机证据，不是已有 UX bad case。

### 与 GUI testing 的关系

它为探索、执行、充分性度量和报告提供基础设施。与 LLMDroid 的区别是本文没有“停滞后请 LLM 选择功能目标”的论文方法；与 GraphDroid 的区别是 PTG 不等于按语义组织的状态簇。可把不同策略接到同一执行和采集层做公平对照，但必须固定版本、事件集合、预算及初态，另行设计 oracle。
