# DroidFixBench：把真实与注入的 Android GUI 缺陷做成可执行基准，检验代码修复的边界

## 一页读懂

| 问题 | 本文的回答 |
|---|---|
| 旧方法哪里不够 | 普通代码修复基准很少覆盖手机界面中的事件回调、页面跳转和显示状态；已有手机 bug 数据又常缺可构建版本、精确定位、修复及可执行测试。 |
| 本文新增什么 | 构建 DroidFixBench：50 个真实缺陷和 46 个应用源码变异缺陷，配套定位、修复、可构建版本、描述和 GUI 测试；用五类修复工具做实证，分析 379 个失败补丁。 |
| 输入与输出 | 数据构造输入是正常/历史 Android 源码与 bug 报告，输出可运行的故障实例及配套修复/测试真值；原论文的被测工具收到已知缺陷信息，输出代码补丁，**不是让 GUI agent 自主发现 bug**。 |
| 怎样验证注入有效 | 在页面相关类改源码，重新编译，再在模拟器操作触发；不能构建或复现的候选被替换/排除，作者复核实际行为、预期及测试。自动变异后仍需要人工。 |
| 主要结果 | 合成集 OpenHands 的 39/46 个补丁语义正确；真实集为 6/50。全部工具合起来为 30/50 个真实 bug 找到至少一个通过测试的补丁，但“通过测试”不保证真正修好。 |
| 对测试研究的价值 | 是正常应用故意改坏、并检验可达/可观察性的直接移动端先例；还能学习真实＋合成分组与回归检查。不能据此说已有完整自主故障发现 benchmark。 |

## 一段话介绍

这篇 ISSTA 2026 研究论文问：擅长改普通代码的工具，遇到手机 GUI bug 时还能修好吗？作者先解决评测材料不齐的问题：把真实问题恢复成能编译、能操作、能检查的应用版本，又在正常应用内部制造可复现变异，然后为每个缺陷准备修复和 GUI 测试。修复工具可以看到 bug 描述、出错代码和失败信息，输出补丁；研究者替换代码、构建并运行测试，最后人工核对补丁是否真正符合修复语义。最值得借鉴的不是新的测试 agent，而是**把一条缺陷变成可信可执行评测实例所需的整套证据**。结果也说明只用简单合成错误会高估能力，测试通过与语义正确应分开。（§1、§4–5，PDF pp.2–3、8–19）

## 关键术语与阅读前提

- **[自动程序修复 APR](../glossary.md#repair)**：输入已知 bug 及代码等上下文，生成代码修改；不同于自主探索发现未知 bug。本篇主要测前者。
- **UI-centric（以界面交互为中心）**：程序由点击、长按等事件驱动，页面、回调、状态和业务逻辑相互影响，不等同于所有缺陷都只是外观问题。
- **[变异与故障注入](../glossary.md#mutation-testing)**：故意修改原实现，制造需要测试揭示的偏差。本篇真正改 Android Java 源码，不只是拦截 agent 点击或编辑一张截图。
- **Activity / Fragment**：Android 页面和可复用界面片段等组件；此处作为定位页面相关变异的程序范围。见 [Activity](../glossary.md#activity)。
- **Plausible patch（通过测试的候选补丁）**：应用能构建且通过所给测试；**Correct patch（语义正确补丁）**还需人工核对是否等价于正确修复。测试通过是有限证据，见 [oracle/真值](../glossary.md#truth)。
- **Overfitting patch（迎合测试的补丁）**：只让给定断言成立，没普遍修复，例如把变量直接设成测试里期望的零；属于通过测试但不正确的一部分。
- **Cohen’s Kappa**：两人标注一致性指标，不能读成缺陷检测准确率或修复成功率。

## 动机

修复评测不只是提供一个 bug 文本。工具要修改故障版本、重新构建，再运行能揭示 bug 的测试，才能区分补丁的成败。手机历史版本常因依赖或构建系统变化无法编译；能重现的问题也可能缺精确定位与回归测试。因此，原有移动 bug 集不自动成为修复基准。（§1、§3.3，pp.2、7）

同时，GUI 错误涉及不同抽象层：看似“长按跳错页”，根因可能是长按和点击回调冲突，正确修复还要管理弹窗显示期间的状态。作者以这种界面事件、代码和状态的联系解释为什么不能直接把普通代码修复成绩推广到手机应用。（§2，pp.3–5）

## 贡献

按作者 §1（p.3）归纳：

1. **Benchmark**：DroidFixBench，96 个可执行缺陷及定位、修复、描述和 GUI 测试。
2. **实证研究**：比较 D4C、ChatRepair、OpenHands、NTR、RewardRepair 在真实/合成 UI 缺陷上的修复表现。
3. **失败分析**：对 379 个不正确补丁开放编码，归纳九类问题。
4. **公开工件**：数据、工具适配、生成补丁与分析材料。它没有提出一种新的全链路 GUI 测试 agent，也没有提出新的通用变异算子族；源码变异使用已有 MDroid+。

## 方法：从应用变成基准，再交给修复工具

整体是两条构造路线汇合：**真实 bug 的故障/修复版本恢复**，以及**正常应用源码变异**；两者均经过构建、复现和测试核验。之后用五种工具生成补丁，先运行测试，再人工检查语义。最终产物是数据和工具失效分析，不是测试探索策略。（§4，pp.8–14）

### 1. 真实缺陷怎样得到

来源有三组：已有 80 条移动缺陷定位报告、五个较新应用的历史 issue，以及 FBO4A 报告集。对第一组，最初仅 15 条的故障代码可直接或稍改依赖后构建；处理旧 Gradle/依赖后增加 27 条，共 42 条，再因无法复现排除七条，得到 35 条。（§4.1.1，pp.8–9）

较新应用限定 Java、F-Droid 且同时上架 Google Play、最近更新在 2025；每类按评分和可构建性选择。GPSLogger、URLCheck、SkyTube、HarmonicHN、PSLab 的 30 条候选经过构建、修复提交、复现、Java 修改和测试可编写性筛选，剩 13 条。最后从 FBO4A 再得到两条，合计 **35＋13＋2＝50 个真实 bug，覆盖 23 个应用**。五个新应用已在这个覆盖范围内，不能再加成 28 个。（pp.9–10）

仅改 XML/Gradle 的报告被排除，一部分复杂复现也因难写测试被排除。因此这套可执行集有明确筛选偏向，不代表所有手机 GUI 故障。

### 2. 正常应用怎样被故意改坏

MDroid+ 支持 38 种算子；本研究仅挑页面相关 Activity/Fragment 等类的候选。每次选 Java 方法修改，尝试构建并在 Pixel 2 / Android 9 触发；失败就换变异，某类始终无法构建或复现则剔除。最后十类算子留下 46 个实例。（§4.1.2、Table 2，p.11）

| 变异作用 | 原文的具体操作及后果范围 |
|---|---|
| 去掉响应 | BuggyGUIListener 删除监听器中的动作；可产生操作后没有预期效果的情况，实际后果仍依上下文复现 |
| 隐藏组件 | ViewComponentNotVisible 改变组件可见性，形成 UI 可观察差异；不是图片涂抹 |
| 增加 UI 延迟 | 在界面创建或监听线程加入等待，诱发响应迟缓 |
| 改页面跳转/传值 | 改 Intent 的目标、值或键，或使 Intent 为空；可影响导航、输出，也可能崩溃 |
| 改控件引用 | 改查找控件的 ID 或让结果为空；并非每个候选都能构建且产生有效故障 |

两名作者独立复现和分类，另制作、复核实际/预期行为与步骤；最终合成集含 **19 崩溃、8 输出、2 导航、9 外观、8 延迟**。全部单 Java 文件/单方法修改。作者说明这套合成集的筛选和测试制作同样耗费多人月，不能从“使用自动变异工具”推断为全自动 benchmark 生成。（p.11）

### 3. 测试和真值由谁提供

每个 bug 准备两条 GUI 测试：一条复现并检查目标行为，一条检查相关功能，以发现修复引入的新问题；测试由作者编写和交叉复核。故障/修复提交及必要修改作为语义参照。被测修复工具不是先独立推断整个应用正确需求，再自行决定 bug 在哪。（§4.1.1，p.9）

因此，换成“评价 GUI agent 自主发现”的任务时，必须把故障位置、复现答案与修复保留给评测器，而不是照搬原工具输入。两类任务可以复用数据资产，但信息边界不同。

### 4. 修复与评价怎样运行

工具读缺陷代码、报告或失败信息，按各自机制生成补丁；替换到故障版本，编译并运行两条测试。不能构建/测试失败属于不通过；测试全过后，再由两位作者按公开规则核对修复语义，不一致经讨论解决。输出补丁级统计、缺陷级覆盖和失败分类。（§4.2–4.4，pp.12–14）

## 核心技术：为什么运行测试仍不够

### 原文案例：长按链接错误触发点击

Harmonic 的 issue 114 中，长按新闻评论里的链接本应弹出分享菜单，却同时打开浏览器。修复在菜单显示时暂时关闭点击行为，菜单关闭后再恢复。它需要理解长按/点击事件以及弹窗生命周期，不是单看链接按钮的位置。五个被测工具都没为此给出通过测试的补丁。（§2.3、Fig.1，p.5）

### 原文反例：修到测试通过却没有修对

PSLab 的数值问题需要根据滑块位置计算并四舍五入，但补丁直接赋值零，因为给定测试恰好断言零。它通过该输入上的检查，却没有实现正确关系。（§5.2，p.16）

另一个延迟例子中，测试检查界面在三秒内显示；部分补丁仅缩短人工加入的等待而未消除不合理等待，作者将其列为迎合测试。这里的语义标准强于“在三秒内”，也说明阈值断言没有完全表达正确行为，不能只把测试通过当可靠真值。（§5.1，p.15；后一句是本笔记的分析）

这与 oracle 研究直接相关：评测器有代码和修复参照，才能发现断言遗漏。若只用同一个模型生成缺陷、写断言并判定有效，可能形成循环自证。

## 实验

### 数据、预算与比较条件

真实集的类别为 12 崩溃、25 输出、9 外观、4 导航，共 50；合成集前述五类，共 46。真实修复可能涉及多方法，合成修复全部单方法，二者难度来源不同。（§4.1，pp.10–11）

| 工具 | 使用模型/机制 | 本研究的候选预算 |
|---|---|---|
| D4C | GPT-4，一次提示生成函数修复 | 每 bug 十个候选 |
| ChatRepair | GPT-3.5-turbo-0301，测试反馈迭代 | 合成最多 200 次、真实最多 100 次内部尝试；统计最终每 bug 一个候选 |
| OpenHands | Qwen2.5-Coder，按给定缺陷信息适配修复 | 每 bug 一个候选；不把本文当其完整仓库探索评测 |
| NTR | CodeLlama，模板指导 | 最多取前十；实际合成 445、真实 492 个候选 |
| RewardRepair | 作者预训练模型 | 每 bug 十个候选 |

作者沿用各工具设置，模型和候选预算并不统一。因此补丁比例不是统一 Pass@1 排名，结果也不代表截至 2026 年最新商业 agent 的能力上限。全部补丁在 Pixel 2 / Android 9 模拟器上用 GUI 测试验证，单条测试约两分半；未披露一套统一的独立重复/随机种子协议。（§4.2–4.4，pp.12–14）

### 补丁级结果：分母是生成的补丁

下表取正式 Table 3/4（pp.15–16），其中“正确”是测试通过且人工核对语义正确；“通过”包含未真正修对的候选。

| 工具 | 合成：通过/全部 | 合成：正确/全部 | 真实：通过/全部 | 真实：正确/全部 |
|---|---|---|---|---|
| D4C | 258/460（56.09%） | 234/460（50.87%） | 100/500（20.00%） | 40/500（8.00%） |
| ChatRepair | 38/46（82.61%） | 31/46（67.39%） | 17/50（34.00%） | 4/50（8.00%） |
| OpenHands | 40/46（86.96%） | 39/46（84.78%） | 10/50（20.00%） | 6/50（12.00%） |
| NTR | 103/445（23.15%） | 77/445（17.30%） | 27/492（5.49%） | 3/492（0.61%） |
| RewardRepair | 18/460（3.91%） | 8/460（1.74%） | 15/500（3.00%） | 0/500 |

证据支持这套实验中简单合成缺陷更易修、通过与正确有差距；不能把 D4C 的 100 个通过补丁说成修好了 100 个 bug，也不能用这些修复分数表示 GUI 测试器检出率。

### 缺陷级与失败分析

以“至少有一个通过测试的补丁”为标准，所有工具的并集覆盖 43/46 个合成 bug、30/50 个真实 bug；D4C 覆盖 19 个真实 bug。这里统计的是有限测试下可接受修复，不是这些 bug 全部语义修复正确。（§5.1–5.2，pp.15–17）

失败分析从 184 个通过但不正确、2,423 个不通过补丁中分别抽 117 和 262 个，共 379；先共同制定编码表，再双人标注。九大类包括 GUI、Activity/Intent、API/库、线程、Java 语法、对象使用、业务逻辑、补丁输出及其他问题。正文将 159/379（约 41.95%）归为 UI 相关，典型问题包括虚构控件 ID、Activity 和 API。（§4.3.3、§5.3、Fig.5，pp.13、17–19）

这不是模块消融，也不能将“建议提供更多 GUI 上下文”当成已经验证的改进；§6 提供的是未来研究建议。引言使用“近三分之一”，与正文 159/379 的明确计数不一致，本笔记保留正文分子/分母，不把近似说法另造结果。

## 局限

### 作者承认的

§7（p.20）指出人工语义核验、错误分类和测试编写带主观性；用双人复核、讨论和一致性系数缓解。五个工具与 96 个缺陷仍限制外部有效性，开发者领域知识未必被全部测试表达。

### 根据实验观察到的

- **选择偏差**：Java、能构建、能复现、能写测试是筛选条件；复杂复现以及仅 XML 修改被排除，不能推广到 Compose、混合渲染或 HarmonyOS。
- **简单合成可能过易**：全部单方法修改，真实集则有 23 个多方法 bug；两组差异不宜仅解释为“真实”二字。
- **预算与模型异构**：各工具候选机会、输入信息、基础模型不同，论文主要说明实用边界，不能隔离某个框架设计的净收益。
- **通过不等于正确**：两条测试仍会遗漏过拟合。对发现评测，也要分别验证应用故障、触发过程和报告，不能把任何失败当正确发现。
- **自动化范围有限**：变异工具自动改源码，编译适配、复现、测试和报告仍投入多人月；没有证明全自动沿流程注入并生成可靠真值。

## 和我们课题的关系

### 与 UX testing 的关系

它提供真实运行程序中的外观、导航、响应延迟等缺陷构造先例，适合讨论如何为截图候选→布局→滑动验证准备可交互正例。它没有专门研究文字截断，也不能将组件不可见变异直接当成“滚动后仍不可恢复”的真值。对正常滚动露边等负例，应另补可解释的标注和交互证据。

### 与 GUI testing 的关系

最直接用途是学习 benchmark 的构造质量：正常/故障版本、触发步骤、修复和 GUI 测试怎样共同支撑一个缺陷实例。若改成自主发现任务，需隐藏定位/复现答案，定义初态与探索预算，同时加入正常对照；按到达、触发、识别和误报拆开统计。这些是可迁移设计建议，不是本文已完成的发现实验。

> “bugs that arise in UI-centric programs, such as mobile apps.”
> — Abstract，正式排版 PDF p.1。

论文研究的是界面事件驱动程序中的代码缺陷，不局限于视觉排版错误。

> “If the project did not build”
> — §4.1.2，PDF p.11。

该条件后续还检查能否复现；源码发生修改只是候选，不能构建或复现就换样本。

> “multiple person months”
> — §4.1.2，PDF p.11。
