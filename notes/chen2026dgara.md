# D-GARA：用可交互中断和状态规则，评价 Android agent 遇到异常后的任务恢复

## 一页读懂

| 问题 | 本文的回答 |
|---|---|
| 旧方法哪里不够 | 把异常截图插进静态轨迹后，下一步又给标准截图，测不到真实偏航；只相信模型说 done，也会把提前结束算成功。 |
| 本文新增什么 | 运行中按界面条件触发异常、根据 agent 选择执行后续跳转，再用独立界面状态规则判断任务完成的框架；实例化为 D-GARA-152。 |
| 输入与输出 | 输入用户任务、应用环境、触发规则、异常模板和目标状态规则；agent 实际操作 Android，输出轨迹、正常/中断成功率与条件鲁棒成功率。 |
| 怎样造异常 | 独立 APK 呈现参数化弹窗，ADB 执行接受/拒绝后的系统动作；可强制停止应用等。不是将目标应用源码自动变异。 |
| 怎样验证 | 正式稿列七应用、152 任务，五模型，比较正常/中断条件，另比较单/双按钮路径、截图与截图＋界面结构输入。 |
| 主要结果 | Gemini2.5-flash 正常成功率 80.26%，中断后 68.42%；AgentCPM-GUI-8B 为 59.87%→26.97%。相应 RSR 为 73.77% 和 39.56%，分母只含各模型正常时成功的任务。 |
| 核心边界 | 测 agent 维持任务完成的能力，不测测试器是否发现产品故障；正常权限、更新提示也不必然是应用缺陷。 |

## 一段话介绍

D-GARA 让手机任务在执行时真正遇到中断，而不是仅让模型判断一张预制图片。框架先读当前截图和 XML 控件树，若页面文字满足预设条件，就显示一个可操作弹窗；模型选择后，还会执行相应后续行为，例如跳到设置或停止应用。恢复后 agent 继续原任务，独立检查器根据界面元素和属性判定是否到达目标，而不只相信 agent 自己宣称完成。作者用这套机制构造 D-GARA-152，说明普通任务成功、点击定位和遇中断后恢复是可以分开测量的能力。它为受控移动环境设计提供方法参照，但没有要求 agent 提交 bug 位置或故障报告。（§1、§3–5，PDF pp.1–7）

## 关键术语与阅读前提

- **[XML 控件树](../glossary.md#view-hierarchy)**：运行中界面元素、文字和属性的结构表示。不是目标应用业务源码；D-GARA 用它匹配注入页面和目标状态。
- **[测试预言与评测真值](../glossary.md#truth)**：这里的规则主要回答任务是否完成，例如点赞控件已显示相应状态，不回答应用所有业务逻辑是否正确。
- **[Grounding（控件定位）](../glossary.md#grounding)**：把动作意图落到目标元素或坐标。本文部分实验由 XML 提供坐标，因此不全是纯视觉操作。
- **SR（Success Rate）**：全部任务中成功的比例；正常和中断两种环境分别计算。
- **RSR（Robust Success Rate）**：在该模型正常环境能成功的任务中，受中断后仍成功的比例。它依赖同任务配对，**不是两个总成功率相除**。
- **[反事实配对](../glossary.md#baseline)**：同一任务在有/无中断条件下比较；需要控制初始状态与运行条件，才能把差异较可靠地归到中断。

## 动机

静态轨迹的下一帧通常来自预设正确路径。即使模型错误处理弹窗，之后还可能重新收到标准页面，因此无法观察真实后果。真实手机上，接受更新可能带到安装页，拒绝权限可能使应用退出；处理完中断还需要把目标和当前状态重新对齐。（§1–2，PDF pp.1–3）

另一方面，任务结束也不能依赖模型输出 done：小模型可能做完后不结束，大模型可能还没做完就宣称成功。作者因此采用最终界面状态的独立检查，允许中间绕路和回退。这是执行完成的评价设计，不是断言每一步业务行为都正确。（§3.3，PDF pp.4–5）

## 贡献

按作者 §1 三项主张及全文实际产物整理：

1. 将条件触发、交互中断、后续系统动作、任务状态验证接成动态评测框架。
2. 收集并标注 D-GARA-152，涵盖多应用任务和五类中断，可扩充新模板及规则。
3. 用正常/中断对照及 RSR 分析模型鲁棒性，并检验交互选项和定位信息的影响。

贡献类型为 `harness / benchmark / empirical`。这里的 harness 是论文明确设计的运行与评测框架，不是因“公开了代码”而附加的标签。它不是新训练的 GUI 模型，也未自动生成全部任务和检查规则。

## 方法：从一次任务到成功判定

1. **人工准备配置。** 指定应用、任务、异常触发条件、异常内容及后续操作；另准备目标界面条件。DataCollector 保存人完成代表任务后的截图/控件树，设计者从中选稳定属性写成功规则。（§4.3）
2. **读取当前界面。** 取手机截图及 XML 控件树，轻量规则引擎检查当前文字是否满足关键词条件。
3. **触发中断。** 满足条件才启动独立 APK 中的模板。比如四个关键词中命中至少三个，触发定位权限对话框；这里的“语义”主要是人工关键词及阈值，不是模型自动理解全部业务上下文。
4. **执行真实分支。** 模型操作弹窗，框架依据选择派发 ADB 后续动作；接受可跳设置页，拒绝可停止应用。之后重新获取实际状态，agent 继续原目标。
5. **逐步核验终态。** 每次动作后检查稳定界面是否满足目标规则；agent 输出 done 时立即验证，若不满足就结束并计失败。自动成功结果再经人工复核。（图 2、§3–4，PDF pp.3–5）

输出是动作轨迹和任务结果。框架本身不要求报告中断为产品 bug，也没有以原始正常路线作为唯一正确动作序列。

## 核心技术详解

### 触发条件、弹窗和后续动作是三个可分离部分

触发器检查当前控件树中的关键词集合及匹配阈值；异常配置还指定目标 Activity、要呈现的内容和后续处理。作者把这部分放在外部配置中，以便增添场景而不改核心执行逻辑。（§3.2，PDF pp.3–4）

独立 APK 由 Android Studio 设计通用对话框布局，运行时从配置填入文字和选项。它将中断逻辑与被测应用隔离，减少不同系统原生对话框差异。代价是模拟呈现不等于系统底层真实发生相同故障；例如显示低电量提示，不自动证明真实电池状态也已改变。是否还有相应系统动作，需要按每个配置分别核验。（§4.2，PDF p.5）

| 类别 | 作者列的例子 | 正确理解 |
|---|---|---|
| 系统资源 | 低电量、温度/限频警告 | 可以控制提示；不能只由模板文字推定已模拟完整资源机制 |
| 系统网络 | Wi-Fi 断开、移动数据切换 | 要区分呈现提示和实际修改网络状态 |
| 应用故障 | 崩溃、冻结 | 论文案例通过外部强制停止模拟异常，不是自动找到应用内部崩溃根因 |
| 权限控制 | 运行时权限提示 | 可能是正常产品行为，评价的是 agent 的处理 |
| UX 中断 | 更新、反馈表单 | 此处 UX 指流程中断，不是裁剪、重叠、溢出检测 |

### 两阶段中断为什么比“覆盖一张图”强

第一阶段让 agent 面对可操作的前台窗口；第二阶段把选择兑现为后续状态。图 2/Listing 1 的高德导航案例：当前页命中“驾车、附近、公交地铁、我的”相关条件，出现定位权限提示；接受后跳设置，拒绝后终止应用，再由 agent 自己找回广州塔驾车导航任务。关键是操作改变了未来的真实页面，下一帧不强行恢复黄金轨迹。（PDF pp.3–4）

但这仍是研究者定义的分支语义，不能据此推定真实高德所有版本都拒绝权限即退出，或这些行为本身有产品缺陷。

### 目标规则在哪里来，又保证了多少正确性

设计者先手动完成代表性任务，收集终态；再从 XML 中抽取可复用条件，比如指定点赞控件的 `content-desc` 包含已点赞。相同应用同类目标可以复用规则。每步都会检查，最终条件满足则可以接受绕路、回退或中途错误。（§3.3–4.3，PDF pp.4–5）

规则比模型自报 done 更独立，但仅证明写入条件成立。如果条件只覆盖点赞状态，而没有充分限定正确视频或账户，就未必覆盖完整用户需求。正式稿未逐项公开论证所有目标规则的充分性；人工复核是额外保障，不能从“读 XML”推出无误真值。

### 原文案例：崩溃恢复后仍相信过期历史

京东任务要求搜索指定图书、查看详情并加购。框架在输入后强制停止京东，GPT-4o 能识别应用退出并重新打开；但返回搜索页后，它根据历史认为关键词还在，直接点搜索，忽略当前输入框已变成推荐词。这样“重启成功”仍不能算“任务恢复成功”。这直接说明历史动作是否发生过，与当前业务状态是否仍成立必须分开。（§5.4、图 4，PDF p.7）

## 实验

### 数据与协议

正式 §4 写 D-GARA-152 含 **七应用、152 个任务**，偏向高使用率复杂应用，不均匀分布于电商、社交、内容、导航和旅行；每任务配一个或多个中断。任务由人工定义，成功规则也经人工设计/复核。它不是 152 个自然缺陷，亦不表示每任务都覆盖五类中断。（PDF p.5）

**计数疑点：** 同页应用类别的举例可数到八个名称；作者主页正文也写八应用，而主页比较表与正式总述写七。这里采用正式主述七应用，不悄悄把额外例子算成第八个实验应用。精确应用名单及各类任务数需要工件进一步对齐。

正式八页没有充分展开完整模型快照、温度、每任务步数预算、重复次数/随机种子、任务重置及置信区间；不自行补成 Pass@1 或 Pass@3。作者主页命令中的默认 15 步是使用说明，不据此断言论文全部实验都采用相同步数。各模型输入方式还受 §5.3 的坐标实验限制。

### SR 和 RSR 要分别读

SR 是全部任务成功比例。RSR 的分子是“正常与中断条件均成功”的任务数，分母是“正常成功”的任务数；不能以 WithInt 总成功数直接作为分子。

例如，以下是教学示例而非论文数字：十项中正常成功六项，受中断后其中三项仍成功，另有两项原本失败但这次成功；SR-WithInt 是 5/10，RSR 是 3/6，而不是 5/6。不同模型的 RSR 分母任务集合不同，因此它有助排除原能力，但并非完全相同难度子集上的统一排名。（§4.4，PDF p.5）

### 主结果

| 模型 | SR 正常 | SR 有中断 | RSR |
|---|---|---|---|
| Gemini2.5-flash | 80.26% | 68.42% | 73.77% |
| GPT-4o | 69.08% | 60.53% | 66.67% |
| Qwen2.5-VL-7B | 69.08% | 46.05% | 53.33% |
| UI-TARS-1.5-72B | 50.66% | 39.47% | 48.05% |
| AgentCPM-GUI-8B | 59.87% | 26.97% | 39.56% |

Table 1（PDF p.6）。五个模型的总体成功率均下降；AgentCPM 下降 32.90 **个百分点**。正式正文称平均下降超过 17.5%，依据本表算术平均是约 17.50 个百分点，不应混成相对百分比。受中断仍有相当任务成功，因此不能把作者的概括强化成所有模型都完全不能处理异常。

### 绕开提示与真正处理复杂分支

当更新提示有“关闭”按钮时，agent 可直接跳过；作者增加只留复杂选项的设置，例如必须安装后再回原任务。Qwen2.5-VL-7B 的 RSR 从双按钮 96.15% 降到单按钮 41.27%，AgentCPM 从 82.35% 降到 9.30%。（Table 2，PDF p.6）

这支持异常的后续路径难度很重要，不证明所有闭合弹窗都是缺陷修复。该表没有充分列出子集规模、配对和重复协议，不能把 96.15% 当成全 152 任务的总鲁棒性。

### 对照输入信息：XML 帮了多少

| 模型/输入 | SR 正常 | SR 有中断 |
|---|---|---|
| AgentCPM，截图＋XML | 59.87% | 26.97% |
| AgentCPM，仅截图 | 56.58% | 19.74% |
| Gemini2.5，截图＋XML | 80.26% | 68.42% |
| Gemini2.5，仅截图 | 45.33% | 41.33% |

Table 3（PDF p.7）。截图＋XML 设置下，模型根据截图选择动作，但坐标直接取 XML；移除结构后 Gemini 正常成绩下降 34.93 个百分点，说明定位是重要因素。它不是只改了“能否看某段文字”的纯感知消融，不宜把全部差距归因模型更懂业务或更会恢复。

## 局限

**作者明确写到的边界：** 成功取决于最终界面，不要求每个中间动作都正确；自动核验可能不足，全部自动验证结果还经人工复核，未来才考虑更多模型参与验证。（§3.3）正式稿没有独立 Limitations 节，不能替作者伪造其承认了哪些完整性问题。

**我们的观察：** 规则与任务准备仍需人工；真实在线应用、账户、网络、版本变化影响复现；独立 APK 中断与真实系统故障可能不同；七/八应用计数、缺少完整预算和重复协议限制公平比较。RSR 的条件子集随模型而变；最终 UI 规则的充分性也需额外检查。该实验未评价真实缺陷定位、正常场景误报或 bug 报告精确率。

## 和我们课题的关系

### 与 UX testing 的关系

当前以截图找截断候选、布局和滑动复核的流程，可以借这种条件触发，在指定页面加入弹窗、跳转或执行中断，检查验证器是否仍能区分正常显示与真实不可恢复截断。尤其需要防止重启后沿用旧容器/旧输入状态。这里能学的是受控异常及恢复协议，不能把 D-GARA 的“UX Disruption”直接说成它已经检测视觉布局缺陷，也不能以任务成功率替代截断检测成绩。

### 与 GUI testing 的关系

最直接价值是“在合适的页面注入可交互异常，并用独立目标规则观察后果”的框架。若改造成发现故障的 benchmark，还需定义哪种行为违反需求、正常负例、触发真值及 agent 报告匹配。目标应用仍正常、外围框架强制停止它的样本，应保留为外部注入，不能当应用内部源码缺陷自动生成的证据。
