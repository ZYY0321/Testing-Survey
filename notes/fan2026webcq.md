# WebCQ：用深度强化学习协调多个浏览器，减少大型网站 GUI 测试中的重复探索

## 一页读懂

| 问题 | 本文的具体回答 |
|---|---|
| 测试目标 | 自动生成网页交互，在固定时间内探索更多状态、执行更多不同动作，并触发浏览器日志中的失败。 |
| 旧方法哪里不够 | 表格型强化学习为状态与动作保存数值，网站复杂后表和通信负担增长；多个浏览器独立学习又容易重复探索。 |

## 一段话介绍

一个网站有大量可以点击和填写的元素，多开几个浏览器不一定能有效增加测试范围：它们可能反复走相同路径，交流探索经验也会产生开销。WebCQ 让多个浏览器各自执行动作，同时把探索结果集中训练。每个浏览器不再保存不断扩大的状态—动作数值表，而使用神经网络，结合页面结构、按钮文字与历史访问次数估计下一步的探索价值。集中训练利用 QTRAN 协调这些估计；执行时每个 agent 根据自己看到的页面选择动作。论文主要证明这种组织方式在大型商业网站上的探索与长期吞吐量优势，错误信号沿用浏览器严重日志，而非独立检查业务需求。

## 关键术语与阅读前提

- **[DOM](../glossary.md#dom)**：浏览器中的网页元素树，包含标签及其嵌套结构。读取 DOM 不等于读取前后端业务源码，也不等于只看截图。
- **[强化学习](../glossary.md#learning)**：根据执行动作后的奖励学习下一步选择。本文奖励主要来自新页面和未执行动作，不来自“业务行为正确”。
- **[DQN](../glossary.md#deep-q-network)**：用神经网络估计在某状态下做某动作能获得多少未来奖励。此处是训练专门的策略网络，不是向大语言模型提问。
- **[集中训练、分散执行（CTDE）](../glossary.md#ctde)**：训练时汇集多个浏览器的经验，执行时各自根据本地页面决策。多个 agent 是多个浏览器学习进程，不是分别扮演规划员、测试员的 LLM 角色。
- **QTRAN**：本文采用的既有合作多智能体学习算法，用联合价值与各 agent 的局部价值之间的约束组织训练。本文贡献在于把它适配到异步网页测试，不能把 QTRAN 本身写成本文原创算法。
- **状态数与覆盖率不同**：本文统计访问过多少“URL加元素集合”组合；没有得到网站所有可能状态的总数，因此不能称其覆盖了某个百分比的完整功能空间。

## 动机

表格型 Q-learning 为观察到的状态—动作组合保存分值。当网页数量、动态元素与候选动作快速增长时，这类表会扩大；多个 agent 共享表中经验的成本也随之增加。完全不通信又会浪费并行资源，因为各个浏览器可能学到相同路径。作者还指出，以元素定位符表示动作难以表达按钮语义及探索价值（Sec.1，第1–2页）。

WebCQ 的问题定位因此包括两个部分：如何把越来越多的状态/动作压缩为可学习的表示，以及如何用有限通信支持多个浏览器协作。它没有把“理解用户自然语言需求”设为前提，也不是一篇 GUI 显示错误检测论文。

## 贡献

按 Sec.1（第2页）的作者条目：①将多 agent 网页测试形式化为分散式部分可观测决策问题，并把 QTRAN 适配为异步执行下的集中训练；②提出并评价 WebCQ 的探索、失败触发及扩展性；③公开源码与实验数据。我们记录主要贡献为 `method`；释放代码不是自动贡献新 benchmark 或测试 harness 的理由。

## 方法：每个浏览器执行，多个浏览器共同学习

1. 每个 agent 打开独立浏览器，获取当前页面的 DOM 和候选交互。
2. 把页面结构编码成固定长度的状态向量，为每个候选动作构造文字与探索历史特征。将“状态向量+一个动作向量”送入该 agent 的网络，估计每个动作的价值。
3. 以一定概率随机探索，否则选估值最高动作；用对应元素 XPath 和动作类型通过 Selenium 执行，记录页面转换。
4. 各浏览器异步执行。当每个 agent 都至少产生一次新转换时，控制器汇集各自最近转换，计算奖励并存入全局经验池；样本足够后更新联合网络及各 agent 网络。
5. 重复至时间预算用尽，统计探索状态、不同动作和严重日志。全文没有把“收集到严重日志”设为停止整个测试的条件，也没有规定功能验证全部完成的终止判据。

论文没有逐项展开输入文本的生成策略、每种控件失败后的恢复流程或登录业务的完整准备协议。不能为凑完整链路补写 LLM 生成表单、需求推导断言或自动最短复现脚本等模块。

## 核心技术详解

### 状态向量：压缩页面树的结构

作者预定义常见 HTML 标签列表，为每种标签计算它在 DOM 树中的平均深度，缺失标签填0；再增一维概括未列入标签（Sec.4.2.1，第4页）。原文 Fig.3 的标签顺序为 `div, button, input, other`，两个 div 平均深度1.5，两个 button平均2.5，没有input，other为1，因此向量是 `[1.5, 2.5, 0, 1]`。

这样网络输入维度固定，不必把每个新 URL 变成新的一维，适用于同 URL 下页面内容变化的应用。但平均深度会舍弃不少细节；两个不同页面也可能产生相同结构摘要。论文没有将其证明为无损抽象。还应区分：**学习网络的输入表示是标签深度向量；实验统计状态数则使用“URL+元素集合”**，两者不是同一个定义。

### 动作向量：不仅标记“哪个按钮”，还记录探索价值

每个可执行 UI 事件有三部分特征（Sec.4.2.2，第4页）：

- **文字语义**：预训练 GloVe 词向量计算按钮文字与 accept/confirm/submit/ok/yes/next 等预设正向词的余弦相似度，取最高分。作者假设这些动作常推进流程；这是启发式，不表示按钮业务行为必然正确。
- **动作执行次数**：记录重复程度，让策略能够识别已经尝试很多次的操作。
- **后继状态潜力**：10维向量统计后继页面中各类执行次数的动作数量，例如从未执行的动作有多少。未知后继页面填零。这个特征需要已有执行经验，不能解释为提前知道未访问页面内容。

这些特征随着探索更新，不是训练前一次生成。原文用于说明10维直方图的文字称页面有10个动作，但紧接着列4个未执行、6个执行一次、1个执行超过8次，对应示例向量总数为11；此处是原文示例计数不一致，不把“10个”写入确定机制。

### 动态动作空间：逐个评估当前候选，而非固定输出按钮编号

不同网页的候选动作数量不同，标准固定输出维度的 DQN 不容易直接适配。WebCQ 对每个候选动作与当前状态拼接，输入同一个网络得到一个 Q 值，再在当前候选中选择（Sec.4.2.3，第4–5页）。网络看到的动作向量用于学习；真正执行仍映射回动作类型和目标元素 XPath，不能直接把语义向量当点击坐标。

探索概率 ε 初始0.9，在预算前半段线性降低至0.3，后半段保持0.3：早期更多随机尝试，后期更多依据已学估计。即使后期仍有随机动作，因此报告必须保留重复试验与波动。

### QTRAN 与轻量同步：协作不等于完全没有等待

每个 agent 的局部网络估计自身动作价值，集中模块把所有局部状态向量拼接为联合状态。QTRAN 用联合奖励、联合动作价值及局部价值间的损失约束更新网络；其中时间差误差学习未来收益，另外两项约束用于使分散选择与联合优化相容（Sec.2.2–4.3，第3–6页）。

原始 QTRAN 面向同步共享环境。网页加载速度不一致，逐步等待最慢浏览器会浪费时间。WebCQ 用每个 agent 的 `done` 信号记录是否已有新转换：快的浏览器可以继续前进，直到所有 agent 都有新数据；最后满足条件的线程获取全局锁，触发集中训练，再清空信号。学习期间其他 agent 会等待，训练前汇集的是各自最近转换，而非同一物理时刻发生的联合动作（Algorithm1，第6页）。因此“异步执行”不能改写成“所有阶段完全无阻塞”或“多用户共同完成一个业务事务”。

### 奖励与错误信号是两件事

局部奖励为 `(页面相似度奖励+动作次数奖励)×(1+时间补偿)`。与历史页面差异更大可得到更高奖励；首次动作奖励较大、重复动作逐渐减弱；时间补偿随已用预算比例增加，缓解后期奖励稀疏。联合奖励是所有 agent 局部奖励之和（Sec.4.3.2，第5页）。

页面相似度采用 APIMiner 度量，奖励阈值与权重经过先导试验选择。奖励中**没有业务规格断言或用户体验评分**。失败统计另外读取浏览器控制台，只保留 SEVERE 日志，将数字等动态内容规范化后去重（Sec.6.1.1，第7页）。它可以触发资源加载、脚本或权限等错误日志，不能单凭日志推断所有功能错误或视觉缺陷。

原文案例是在 Gap 商品页收集到图片加载失败的 PhotoCarousel 错误，来自两个不同商品页（第8页）。它用于说明日志失败类别，不是作者通过截图独立识别了图片遮挡。把此方法用于 UX 链路时，仍需额外的候选检测和主动验证。

## 实验

### 数据、环境与指标

8个商业网站是 EatingWell、ESPN、FoxNews、GameRant、GameSpot、Gap、GitHub、Smadex，覆盖多个类别。作者基于 MARG 的数据选择状态较丰富的网站，排除较小状态空间网站；受英文 GloVe 限制，排除非英文内容较多的 YouTube/IKEA，并从热门网站补选4个（Sec.5.4，第7页）。这不是8个固定版本、带完整 bug 真值的开源基准。

执行采用 Selenium-Python、Python线程控制器、PyTorch2.3.1，策略网络为4个全连接层的 DenseNet式连接网络。Ubuntu22.04、Chrome117；32核64线程、128GB内存、2张 Quadro RTX6000、千兆网络。学习率0.001、折扣因子0.5；基线保留原论文超参数，非所有超参数逐项完全相同（Sec.5.2–5.5，第6–7页）。

三个统计指标都没有“所有可能行为”的真值分母：①探索过的 URL+元素集合状态数量；②不同 UI 事件数量；③规范化去重后的严重日志数量。本文没有测代码覆盖率、断言正确率、业务任务完成率或显示缺陷检测精确率。

### RQ1：同样预算能探索多少

基线为 MARG 的分布式 Q-learning 版本，以及5个独立 WebExplor进程合并结果；不是以单进程 WebExplor 对比5个 WebCQ。**全部5个agent，每网站3小时，重复6次；表中为均值**（Table3，第8页）。

| 8站点的平均计数 | WebExplor5 | MARG5 | WebCQ5 |
|---|---:|---:|---:|
| 探索状态 | 51.2 | 734.1 | 978.8 |
| 不同动作 | 72.8 | 858.2 | 1220.6 |
| 严重日志失败 | 22.7 | 42.6 | 44.4 |

作者报告相对MARG，状态多33.3%、不同动作多42.2%；这里不是完整状态覆盖率提高33.3个百分点。WebCQ 在7/8站点状态数更高，在6/8站点严重日志数更高，不是每个站点所有指标均领先。Mann–Whitney U检验与 Vargha–Delaney A12 效应量见Table5（第9页）：相对MARG，状态和不同动作在各5个网站显著改善；严重日志数量在8个网站相对MARG均未达到 `p<0.05`，包括Smadex的p=0.1275；该站的0.0301属于无通信消融行，不能串行引用。不能把探索收益普遍显著推广为失败数量也普遍显著。

Table4把日志分为渲染/UI、资源加载、API/异步请求、运行时/应用逻辑、安全/认证和其他。各站点占比再平均，运行时/逻辑31.2%、资源加载21.5%、安全/认证21.7%；这些是**日志类别占比**，不是已确认漏洞或 UX bug 占比。未报告新缺陷被开发者确认/修复的数量，不能称其发现44.4个新 bug。

### RQ2：通信以及QTRAN分别贡献什么

两个消融都仍使用深度强化学习和相同状态/动作表示：①不通信，各自独立训练；②用MARG式经验共享替代QTRAN。平均状态分别769.9与806.7，完整方法978.8；不同动作1000.4与1006.1，完整1220.6；严重日志39.7与41.6，完整44.4。作者报告状态分别提升27.1%与21.3%（第9页）。

结果支持适配的协作训练比简单并行或较弱共享更有效；没有单独消融所有动作特征、奖励项与同步机制，所以不能把总提升准确分摊给每一个设计。

### RQ3/4：时间更长、agent更多是否仍有效

长期实验只在状态丰富的 Gap 网站，5个agent、20小时、重复6次；Fig.5展示每小时执行动作均值及标准差。WebCQ 的动作吞吐量总体高于 MARG，但它自己也随时间下降，并非无限扩展不退化（第9–10页）。

数量实验同样只在Gap，分别3/5/8/12个agent，各3小时、重复6次。Table6总动作均值从2955.67增至6914.83；每agent动作却从985.22降至576.24，作者报告下降41.5%。这些是**总执行动作**，不是Table3的不同动作。Fig.6显示多agent下的探索收益及分布，但不支持“增加4倍agent得到4倍收益”。只有单站的长时间与数量实验，不能直接外推所有网站或资源配置。

## 局限

**作者承认的（Sec.7，第10–11页）**：只测8个网站、偏大型商业站点，泛化有限；先导试验选出的超参数可能不适合全部网站；随机初始化、随机探索与样本抽取引入波动，通过6次重复和统计分析缓解。Sec.9提出以后比较VDN/QMIX等算法，并研究并行交互与非确定执行顺序下的失败复现。

**我们的观察**：①英文词向量限制多语言界面；②严重日志既可能是网站业务错误，也可能与资源、第三方服务或访问环境有关，缺少开发者确认及独立功能真值；③DOM结构摘要丢失视觉与部分语义，不能承担显示错误oracle；④长期及agent数实验仅Gap，且吞吐量不是直接分解测出的纯通信耗时；⑤未和最新LLM探索方法同场比较，不能据本文称其优于所有2026年GUI测试方法。论文的优势主张应限定为文中RL/MARL比较和所选场景。

## 和我们课题的关系

### 与 UX testing 的关系

可以借鉴它把“页面探索速度”“不同交互数量”和“检测到的错误”分开评价，以及多执行器避免冗余探索的设计。但DOM深度和浏览器日志不直接检测文字截断、遮挡、重叠或溢出；若接入截图候选、布局树复核与主动滑动链路，必须另保留缺陷判定器和验证记录，不能以新状态奖励代替 UX 正确性。

### 与 GUI testing 的关系

补充非LLM路线的并行测试生成及可扩展执行。与功能流/需求驱动方法相比，它主要追求探索广度，不显式组织业务目标或生成规格断言。这有助于把综述中的“怎样到达更多状态”与“到达后依据什么认定错误”分别比较。后续可以核查语义导向奖励与UX主动验证是否兼容，但本文没有证明这一组合或相关创新性。
