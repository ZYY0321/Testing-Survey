# Trong 综述：LLM 在 GUI 测试流程里承担什么工作

这篇作为流程补充，放在 [Yu](yu2025guisurvey.md) 和 [GPTDroid](liu2024gptdroid.md) 后读。它不发布新的最强测试器。术语见 [术语表](../glossary.md)，判定/维护机制见 [field](../field.md)。

## 先区分操作能力与测试能力

假设模型收到“删除任务 A”，成功打开菜单并删除。这个结果说明它可能具备执行该任务的能力。测试需求如果是“删除后重新打开仍不恢复”，还要重新打开并检查；在“只隐藏、未真正删除”的错误应用上，系统还应给出失败证据。

因此 GUI 测试可以复用通用操作 Agent 的定位与规划，但不能直接用“正常应用上的操作成功率”替代“软件缺陷检出能力”。这是我们阅读本文数据集和指标时最重要的检查。

## 五个阶段分别产出什么

以下是本项目的教学拆解，不是作者新建的实验应用：

1. **设计**：从要求形成测试场景，写出前置条件和预期，例如已有 A，删除后 A 不恢复。
2. **脚本生成**：把场景变成可执行操作与检查。代码应包含定位、等待、操作和断言，不只是动作列表。
3. **执行**：在真实 GUI 上操作并取得观察。点错、加载超时、环境失败要留证据。
4. **Oracle**：比较实际与预期；有依据地说通过/失败。模型若自称完成，不等于独立判断正确。
5. **维护**：新版本的菜单改了，更新操作实现并保留原检查；需求真变了则显式更新预期。

同一系统可承担多个阶段；多角色协作也可拆分。需要按阶段评价成果，不能凭角色数决定方法先进程度。

## 一个失败该归哪里

| 观察 | 先检查什么 | 能否直接当应用 bug |
|---|---|---|
| 模型输出不存在的按钮 ID | 上下文、定位与命令生成 | 不能，可能是测试器错误 |
| 页面尚在加载，操作没生效 | 就绪条件和等待 | 不能，先核对时序 |
| 删除后 A 重现且违反明确要求 | 执行证据、需求和持久化结果 | 是可核验的功能缺陷候选 |
| 模型说“A 已删除”，但没有观察/断言 | 判定依据是否缺失 | 不能只凭自评确认 |

上述表是我们的阅读框架。本文的架构/benchmark 介绍用于找线索，具体效果必须回到原始论文；不采用未核验的成本百分比当项目结论。

## 架构分析具体看什么：不是按模型名称排榜

原文 Result 的架构部分（第 13–20 页）先看系统取得什么信息、怎样决策，再看记忆与自治程度。输入可含 GUI 截图、DOM/控件结构、需求/说明和历史记录；不同信息服务不同问题：图像看实际渲染，结构帮助定位，需求提供预期，历史保持长流程。

模型可能只按固定提示翻译步骤，也可能在“观察→决策→执行→反馈”中持续规划；可以是单 Agent，也可按规划、执行、复核等角色分工。论文还区分短期历史、长期记忆，以及选择/摘要等上下文压缩。它们解决的是信息组织与执行策略，不凭名称就保证更有效。

自编例子：把全部 DOM 原样输入，可能淹没有用的按钮；仅保留按钮名又可能丢掉父容器区别。上下文筛选需要在信息量与含义保持之间取舍。这个问题与是否叫多 Agent 无关，也不是在本篇中通过统一实验得出了最优输入。

作者的 L1–L4 分类表示从人工主导、遇例外需指导、结束后需复核，到仅初始设目标的自治程度。**自治程度高不等于判定更准确**；L3 结束后复核与执行中时时指导也不是同一种人工成本。跨文献统计只描述集合分布，不能作架构因果结论。

## 五个阶段的技术内容：输入怎样变成研究产物

以下依据原文第 20–30 页的生命周期分析，补以自编 GUI 例子解释。综述里出现的技术是原始工作线索；未逐篇核验其效果，不复制“达到某百分比”作统一性能结论。

### 1. 设计：从需求或当前界面形成测试场景

**输入和两条路线。** 需求规格、用户故事、旧测试、历史 bug 报告与当前 UI 提供不同起点。有规格时，可先获取全局业务背景，再按功能生成场景；仅有 UI 时，可边观察边探索、构造功能目标，但缺少独立需求依据的风险更高。

**具体处理。** 需求驱动路线将抽象要求拆成前置条件、操作和预期，使用多轮/链式提示保留上下文。旧测试或 bug 历史可提供回归目标；检索到的例子/知识用于补背景，而不是任意替换需求。作者还讨论把边界和状态变化纳入设计，不能只生成正常路径。

自编例子：“不能保存空标题”需要场景区分空输入与有效输入，且给出错误提示/保存状态的预期。只看页面“有输入框”生成任意字符，无法保证覆盖这条要求。

**产物与评测。** 产物是场景/用例，不一定已经是可运行脚本。应检查覆盖哪些需求、是否可操作、是否有冗余、是否获得人工真实认可。文字和旧用例相似不等于真实发现 bug。

原文：Test design phase，第 20–22 页，Figure 10。

### 2. 脚本生成：将场景落实为定位、动作和断言

**输入差异决定处理。** 已结构化的场景给定步骤/预期，模型主要将它映射到具体框架命令；只有高层用户故事时，需先规划中间“测试骨架”，再生成代码。页面结构/截图提供真实控件位置，旧脚本和示例提供框架表达。

**技术路线。** 综述讨论场景→脚本翻译、先规划再编码、视觉/结构驱动动态生成，以及迁移旧脚本。它们都要连接业务意图与具体定位器。仅把框架语法写对，不能证明步骤与断言仍符合需求。

自编例子：“删除任务”要生成定位菜单、选择正确 A、确认、等待和检查的实现。凭空生成一个不存在的 ID 会导致执行失败；只输出点击而不检查结果则丢了测试目的。

**人工作用与产物。** 人可能提供账号、数据与业务约束，检查生成逻辑或改代码。产物是脚本及其检查。评价应分语法、执行、意图/断言正确和人工修订成本；不能将人工修过后的成功率当纯自动生成能力。

原文：Test script generation phase，第 22–24 页，Figure 11。

### 3. 执行：三种目标不同的交互模式

**已有产物驱动。** 输入是既有场景、脚本或路径，执行层将步骤映射到控件。主要问题是可靠落实既定流程，重复性和前置状态很重要。

**高层意图直接驱动。** 输入如“删除任务 A”，模型结合当前 UI 临时分解动作并反馈调整。它可以适应中间变化，但每轮决策有成本，且需要核对是否擅自改了原测试目标。

**开放探索。** 没有给定的具体业务任务，系统根据页面可操作信息选择新状态/功能。重点是探索覆盖与触发错误；若只以 crash 观测为终点，不能顺势称为验收了深层功能要求。

三条路线可以共享执行接口、状态观察、记忆、等待与恢复。自编例子中，同样点击删除，可能是执行固定回归脚本、完成用户指定任务，或探索器的临时选择，评价目标不同。

**评测。** 任务完成、路径与人工轨迹相似、执行错误、覆盖、时间与调用成本分别回答不同问题。与专家路径不同也未必错，动作相似也未必验证结果；具体判据要查原任务。

原文：Test execution phase，第 24–26 页，Figure 12。

### 4. Oracle：静态检查与动态模型验证

**静态路线。** 在生成脚本时把预期固定为断言，执行时检查可见元素/内容/状态。其优点是规则明确、便于重复；定位或显示正常变化可能使检查失效，过弱断言则会漏掉真实错误。

**动态路线。** 给模型需求/检查点、动作轨迹及视觉/结构观察，让它对当前或多步行为给出判断。作者讨论需求验证点、原测试抽象和前后状态比较，并举 AUITestAgent 等作为线索；这里未将所有相关系统独立验证为功能检测器。

自编例子：看见“保存成功”图标只能支持某种可见状态。验证保存数据正确，需要根据需求检查记录/后续状态，必要时使用允许的非视觉观察。下一步能继续操作，也不总证明上一步全部业务逻辑正确。

**解释与证据。** 正确的通过/失败标签可能来自错误理由。比如任务 A 本来不存在，模型报告“删除失败”的理由是找不到 A，就需要重新检查初始条件；系统不能仅凭最终标签碰巧一致而说理解了逻辑。作者因此讨论同时检查判断与理由/步骤的指标及人工审计。

**产物。** 不只有一个布尔值，还应有相关截图、步骤、条件和解释供核对。独立真值来源、误报漏报和模型自评偏差，是研究难点。

原文：Test oracle phase，第 27–28 页，Figure 13。

### 5. 维护：从控件对应走向测试意图复用

**传统对应路线。** 匹配新旧控件的文字、结构或向量表示（将语义编码为数值特征）。适合较直接的对应，但一个旧步骤在新应用可能需要多个动作，逐元素一一映射就不够。

**抽象→具体化路线。** 先从源脚本提取业务目的和必要检查，再在目标 UI 找新的实现路径。综述举 LLMigrate 等说明这种思路；源测试成为导航和意图依据，而非逐行照抄。

自编例子：源版本点行内删除，新版本需要打开菜单、点删除、确认。抽象层保留“删除 A 并检查持久化”，具体层改变操作。两个层次一起维护，才能避免仅修按钮而漏断言。

**反馈与长期复用。** 执行不变或出错时，更新信息、回退/重规划可以帮助绕开无效路径，但回退能力要看具体系统。作者还讨论案例库：取旧案例、适配、修订、核验后保留以供以后复用。储存错误脚本会污染下一次迁移，因此案例质量仍需检查。

**产物与评测。** 新版脚本/轨迹、保留的意图/检查以及人工修改量。成功执行、终态相符、检查有效与编辑减少是不同证据；不能让模型“修复”到接受错误行为。

原文：Test maintenance phase，第 29–30 页，Figure 14。

## 这篇怎样看 benchmark：先辨认测的能力

Dataset and benchmark（第 31–39 页）把公共评测、内部应用和真实运行环境分开，也区分缺陷发现/复现、任务完成、控件定位。对本项目有用的读法是：问每组输入、真值和指标到底对应什么能力。

已知 GUI crash 集合给缺陷触发目标；任务完成集合给指定最终状态；控件定位集合给语言目标与位置标注。这些评价各有用处，但不能统一当软件 bug 检测率。内部/在线环境贴近使用，却可能缺完整独立真值或不便复现。原文 Table 6 的具体数值与引用还需原始来源核对，后面保留本轮发现的版本差异。

## 讨论提出什么后续问题

Discussion 的可靠性、上下文、交互和成本问题连接上述各阶段。研究难点包括模型/提示变化下重复性、复杂状态与输入、动态 UI 与受限动作、频繁推理开销。

作者的后续议题包括：明确业务前置/多角色状态；把探索结果沉淀成可反复运行的脚本以接入持续测试；用需求及其他证据验证界面外的逻辑；维护从意图到脚本的可追溯关系。这里保留与 GUI 测试直接相关部分，不展开一般行业/法规议论。这些是作者的议题，不是我们已经确认的 2026 创新空白。

## 实验与证据边界

本文的实验性质是文献统计与结果综合，不是重跑所有方法。数据集讨论（第 31–39 页）区分缺陷发现/复现、任务完成和控件定位等目标；我们必须继续核实每篇原始研究。

三个指标在本项目中的区别（我们的工作解释）：

- 定位正确：知道按钮在哪里，是执行能力。
- 任务完成：把指定操作做完，是流程能力。
- 缺陷检测正确：判明被测程序违反要求，才是测试判定证据。

“操作完成”不能独自证明“能发现隐藏的软件缺陷”；正例能走通，也不证明测试会在错误版本失败。
