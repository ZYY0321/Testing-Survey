# GPTDroid：让 LLM 连贯探索 Android 应用

**本文先讲清楚方法，再保留原文数字和核对依据。** 不认识的英文词可查 [术语表](../field.md#gui-terms)；输入结构与截图的区别见 [layout](../field.md#layout)，判定机制见 [oracle](../field.md#oracle)。

## 先把作者要解决的问题讲明白

一个自动 GUI 测试器至少要做两件事：选择下一步操作，以及判断操作后有没有错误。GPTDroid 主要改进前者：让工具更容易完成连贯流程、到达更深的路径，最终通过覆盖和崩溃发现来评测。

例如创建任务需要先输入标题、再选日期、最后保存。一个只看当前可点击按钮的探索器，可能填到一半就返回；一个只记“保存点过”却不记创建进度的工具，也可能在相同位置循环。作者希望借 LLM 理解控件文字和操作目标，再用功能记忆保持全局进度。这里的任务例子为教学构造，不是论文原始实验案例。

问题不是“LLM 能不能输出一个 click”，而是：**模型收到什么界面信息，怎样将输出执行成真实动作，怎样记得已经尝试过哪些功能？** Section 2 的三项设计分别回应这些问题。

## 从一轮交互看输入、模型和执行器

假设当前在任务编辑页，工具从控件树取得标题框、日期项、保存按钮的信息。它不是直接发截图给模型，而是将这些结构信息整理成可读文字。

| 环节 | 系统拿到/产出什么 | 谁负责 |
|---|---|---|
| 观察 | 当前 Activity、控件文字/ID/类型、粗位置和邻近文本 | 界面信息提取模块 |
| 组织问题 | 应用信息、当前可操作项、功能进度、近期历史、输出要求 | Prompt/记忆模块 |
| 决策 | 填什么文字、选哪个控件、做什么动作 | gpt-3.5-turbo |
| 执行 | 把模型回答解析成 Android 操作 | 命令生成与 ADB 执行模块 |
| 反馈 | 操作后新页面，或目标不存在等失败信息 | 执行/观察模块，反馈给下一轮 |

LLM 本身没有“手指”。它输出动作描述，执行器才真正点击/输入。也不是回答一次就完成全部测试，而是反复观察、决策、执行和更新。

```mermaid
flowchart LR
    U[Android 当前界面结构] --> T[整理成文字上下文]
    M[功能与近期历史记忆] --> T
    T --> L[LLM 选择动作]
    L --> P[解析动作并执行]
    P --> U
    U --> M
```

图按论文方法绘制为阅读辅助，不是原论文图像，也没有新增一个功能判定模块。

## 功能记忆具体解决什么

“近期历史”可记录刚才点过哪些页面/控件，但短窗口可能忘掉更早的探索；“功能记忆”记录创建、删除等语义进度，帮助下一轮保持目标。这不是模型自动训练出的永久知识，而是系统组织并继续提供的上下文。

以下是自编的示意记录，不是原文 prompt：

| 时刻 | 观察与动作 | 记忆需要反映什么 |
|---|---|---|
| 进入编辑页 | 看见标题框与保存按钮 | 正在尝试创建任务 |
| 填写标题 | 输入了任务名，仍未提交 | 流程尚未完成，避免跳去无关页面 |
| 点击保存 | 返回列表、看见新任务 | 创建流程已经尝试过，更新相关页面/功能进度 |
| 继续探索 | 决定删除或编辑等新路径 | 结合已探索功能，减少无意义重复 |

原方法允许模型给功能完成标记，这个标记用于探索规划。**它不代表系统已独立证明数据库保存正确。** 如果列表看起来成功但重启后数据丢失，只用本篇 crash 终点可能漏掉它。必须有额外需求与检查才能验证持久化。

## 实验为什么分覆盖、旧 bug、新 bug 和消融

- **覆盖实验**：看工具有没有到达更多组件/代码，是探索能力的代理指标。
- **已知 crash 实验**：应用里已有可追溯崩溃，检查工具能否触发。它比只数点击更接近缺陷发现，但只覆盖这些已知 crash。
- **新 crash 验证**：在所选应用中找原来未报告的问题，向开发者提交并区分确认状态。提交不等于已修复。
- **消融**：在同一新方法中移除上下文或记忆，观察结果变化；它回答这些设计在当前设置下是否有帮助。

这些实验共同支持“此方法在该设置下探索和发现 crash 更有效”，不支持“所有平台/现代模型/全部功能错误都更强”。后文数字保留应用集合、运行预算和版本信息，避免仅凭摘要读成更广结论。

## 一段话介绍：主要贡献是什么

GPTDroid 改进的是“怎样探索应用”。它把页面与控件信息转成文字，询问 LLM 下一步操作，执行后继续反馈，并维护“探索过哪些功能”的记忆。语义与记忆有助于执行连贯的多步骤行为，而不是在某页反复点击。作者以覆盖和崩溃发现验证效果。

这是直接的 Android GUI testing 方法，不是只测用户偏好的 UX 研究，也不只是按指定任务操作手机的通用 agent。但本轮实验的缺陷是 **crash**，没有证明它能通用判断不崩溃的业务逻辑错误。

## 动机

依据：Section 1，第 1–2 页。

作者认为概率/模型方法可能产生与真实用户差异大的行为，覆盖受限；学习型方法又面临数据需求、泛化和动态交互困难。因此尝试借助预训练 LLM 的语义知识生成更连贯的交互。

## 方法详解：三个核心设计怎样接起来

依据：v1 §2.1–2.4，第 3–6 页，Tables 1–4 与 Figure 2。前面的交互图说明整体，本节展开具体信息与规则。

### 1. GUI 上下文提取：从应用和控件树取得三个层次的信息

**应用级信息：给模型全局线索。** 读应用名和声明的 Activity 名称，帮助知道这是哪类应用、可能有哪些页面。它不是正式需求规格，也不是完整功能清单。名称本身如果含义不清，模型仍可能误解。

**页面级信息：说明现在在哪里。** 记录当前 Activity、页面上有哪些控件及粗位置。作者从控件 text 或 resource-id 中取第一个非空值表示页面元素；按从上到下、从左到右整理位置，并区分页面上部/下部。这样不是把一堆坐标原样交给模型，而是提供它能读懂的位置描述。

**控件级信息：让模型知道能做什么。** 控件文字按 text、hint-text、resource-id 顺序取第一个非空项，并带 class（控件类型）、clickable（可点击属性）。文字为空时，还加入父节点或兄弟节点的文本，减少只见匿名节点的问题。注意页面列表表示与控件细节的取值规则不完全相同。

自编例子：一个输入框没有 text，hint 是“任务标题”，旁边按钮文字是“保存”。只给资源 ID 可能难读；给提示、类型和邻近文字，模型更容易决定先填标题再保存。若全部都是无意义标识，语义能力仍无从发挥。

作者将属性名按下划线和 Camel Case（驼峰命名）拆分。例如将一个连写的“保存任务”标识拆成可读词，是语言输入预处理，**没有训练新的控件识别网络**。全部来源仍是文本结构而非 screenshot 输入。

### 2. GUI Prompt：把信息组成可重复使用的问题

作者让五位标注者编写并试用提示，检查动作在整个测试过程是否合理，再通过卡片分类（将候选提示分组）和讨论形成模式。核心不是“随便问一句测试这个 App”，而是固定组织几类信息。

Table 2 的六类模式为：应用信息、当前页面信息、控件细节、一般操作询问、文本输入询问、失败反馈。一般操作与输入分开，是因为文本框往往需要填写多个相关值并提交，而按钮/滚动属于另一类动作。

组合后有三个使用场景：

- **Start Prompt**：测试开始用一次，加入应用名和全部 Activity 名称，提供全局视角。
- **Test Prompt**：正常迭代时描述当前页面和可操作控件，询问下一步。不是每轮都重复完整应用声明。
- **Feedback Prompt**：例如回答指向当前不存在的控件，反馈这个问题、重新给可操作项，再询问动作。

当页面有 EditText（文本输入框）时，按表中规则使用输入询问；其他情况主要询问一般动作。这里“提示选择”是一种手工规则设计，不是另一个学习出来的策略模型。

**反馈能解决什么。** 如果模型推荐点击“任务详情”，但当前页没有该项，重新告知当前可操作项能让它换选择。它不因此自动判断应用有 bug，也没有证明任意执行异常都能恢复。本文明确的反馈机制主要是错误目标的再询问。

### 3. 命令生成：让语言回答能真正执行

自由语言可能有多种表达，例如“现在把标题写进去，然后提交”。执行器需要的是动作类型、目标元素和参数，因此作者用输出模板与少量示例约束回答，并解析成 Android 操作。

它定义五种常见操作：点击、双击、长按、滚动、输入。前四类主要需要动作与目标；输入类需要控件/文字内容，并可附提交操作。这让模型能一次给出相关输入和后续动作，仍不等于任意复杂手势都可表达。

教学示意（不是复制原文模板）：

| 自由描述的含义 | 执行前需要明确的内容 |
|---|---|
| 点保存 | 动作=点击；目标=当前页的保存控件 |
| 填标题后保存 | 输入目标=标题框；内容=任务名；后续动作=点击保存 |
| 往下看 | 动作=滚动；具体目标/参数需按实现支持表达 |

模型回答先要通过解析和目标映射，然后 ADB 才向设备发操作。模型说完成和设备实际完成，不能合成一个未经观察的事实。

### 4. 功能感知记忆：不只保存聊天，还维护探索记录

作者在引言定义两个困境：

- **Local dilemma（局部困境）**：只依赖近期交互，会忘记较早探索，缺少全局进度。
- **Low-level dilemma（低层困境）**：只看控件/Activity，难看出多个动作共同完成的业务功能。

它用以下结构回应，而不是简单“把所有历史原样复制回模型”。

**功能进度。** 初始功能线索来自应用描述与 Activity 名称，然后询问模型当前在测什么功能、是否完成，并继续细化。记录功能名、探索次数与状态。功能列表不是独立人工真值，YES 也不证明功能实现正确。

**序列记忆器。** 保存已测功能、Activity 路径/访问次数、当前页控件及访问次数。执行操作后依据控件 text/resource-id、ActivityName 等找到对应记录并更新；不是通过截图进行身份匹配。这样能提供“哪个控件重复点过、从哪里转到哪里”的信息。名称相同是否对应不同数据状态，论文没有给完整的独立状态真值验证。

**记忆提示。** 每轮从记录器取出三组内容：已探索功能、已覆盖 Activity、最近 k 步页面与操作。相邻相同 Activity 的序列被整理并更新访问数；近期部分保留控件访问和离开页面的动作，默认 k=5。它保留粗粒度全局进度，又提供细粒度近期上下文。

自编例子：仅记最近五步，可能忘了十分钟前已完成创建；只记“创建完成”，又可能不知道当前标题框是否已经填了。两类信息一起输入，有助于保持当前流程并减少旧功能重复。是否实现这个收益，由后面的消融实验检验，不能仅凭设计直觉保证。

### 5. 外循环、内循环和判定之间的关系

外循环围绕当前页面：取结构 → 形成问题 → LLM 给动作 → 解析执行 → 观察反馈。内循环围绕探索历史：记录实际操作/路径 → 取得模型功能进度 → 组织记忆 → 参与下一轮决策。Figure 2 用嵌套循环表示这种配合，并不是两个独立对抗 Agent。

**最终检查范围。** 本轮效果实验统计 crash，以及覆盖和时间。找不到目标是测试执行问题，不能自动计为应用 bug。功能状态主要帮助决策，没有在方法里变成独立需求驱动的非崩溃 oracle。

**实现与结束条件。** 系统用 VirtualBox/pyvbox 管理 Android-x86，UIAutomator 取结构，ADB 发操作，模型是 gpt-3.5-turbo。效果评测每工具每应用 60 分钟；模型标记某功能完成不代替总预算，也不证明全部测试结束。Prompt 设计集合为被效果筛选排除但本工具可运行的 101 应用，和最后 93 应用不同；人工模板设计属于开发成本。

### 环境、预算与重复

- Ubuntu 18.04，AMD 64-core；Android 7.1 x86 模拟器、2GB RAM，固定存储配置。
- 为登录和外部文件等准备脚本/数据，每次重置；不能解读为工具独立解决了所有登录前置条件。
- 每工具每应用 60 分钟，运行 3 次，**保留最高结果，不是三次均值**。文中的平均覆盖是应用集合聚合，与“重复运行均值”不同。
- 核心工具 10 个：Monkey、DroidBot、TimeMachine、WCTester、Stoat、Ape、Fastbot、ComboDroid、Humanoid、Q-testing。
- 另 5 个增强配置：DroidBot+QTypist、Ape+QTypist、Stoat+Toller、WCTester+Vet、Ape+Vet。是 15 个比较配置，不应说 15 个完全不同的核心算法。

这些工具名暂时不需要逐个掌握。Section 3.2 的比较设计是：先比较不同探索路线的核心工具，再给部分工具加辅助机制，避免只比较较弱的原配置。QTypist 帮助生成有效文本输入，Toller 提供 Android 运行基础设施增强，Vet 帮助识别探索陷阱。Ape+QTypist 表示把输入辅助和 Ape 探索器结合，不是把两者的结果简单相加；本文没有独立阅读全文核验所有辅助工具实现。

### 指标

- Activity coverage：访问了多少 activity，占应用声明 activity 的比例。一个 activity 内可能有多种界面/业务状态，不能视为全功能覆盖。
- Code coverage：执行到代码的比例；须按论文的采集口径比较，不用 activity 覆盖替代。
- 崩溃缺陷数：对不同已知/新缺陷计数，不能用触发次数代替独立 bug 数。
- 时间趋势：在预算内覆盖与已知 bug 累积变化；不是 2026 年模型的最新速度或费用。

Section 4.2，第 9 页：223 应用中发现 135 个崩溃，涉及 115 应用；其中 53 个为新报告，涉及 41 应用。53 个中：20 已修复、15 已确认、18 未回应。35 表示修复与确认之和，**不是全部修复**。

三个用于真实性比较的基线为 TimeMachine、Stoat+Toller、Humanoid；作者报告它们检测到这批新 bug 中的 9 个。不要延伸为与所有 15 配置的全面对比。

作者观察到 17 个 bug 需要多次输入/复合操作，11 个需要从主 activity 走超过 20 步，至少 28 个涉及主业务逻辑。**业务逻辑场景中的崩溃仍是 crash**，不因此改成非崩溃功能错误检测。

## 消融：为什么认为两个组件有用

依据：Section 3.3.3、Table 7、Figures 5–6，第 8–9 页。

| 配置 | Activity / code coverage | 作者要说明什么 |
|---|---|---|
| 完整方法 | 0.75 / 0.66 | 基准 |
| 移除 GUI 上下文 prompting | 0.17 / 0.14 | 信息呈现有影响；替换为较原始层级与控件名称 |
| 移除功能感知记忆 | 0.34 / 0.28 | 进度与历史有影响 |

记忆组件消融和 k 值实验支持在该设置下保留全局功能/近期历史的价值。它没有证明 k=5 是所有模型和应用的最优值。信息格式和信息量一起变化，不能从覆盖下降精确断言每种机制的独立因果贡献。

## 原文的四项案例分析：不只看覆盖表

依据：§5、Figure 7，第 9–10 页。这是作者解释效果的定性观察，不是四项能力各自有独立大规模正确率实验。

**长业务链。** SmartMeter 的“删除设备”先要找到候选设备、添加并填写信息、启动、关闭，再长按并从弹出菜单删除，才触发相关 crash。关键是前面的状态准备，不能直接从空页面点一个删除按钮。作者借此说明功能记忆对跨页面依赖有帮助；本文没有独立检查真实设备/开发者报告。

**功能优先级。** Moni 示例中，某些基线先进入设置并容易在其中循环，GPTDroid 先探索新增收入这种核心功能。这个例子说明语义选择可能不同于按位置探索；不能推成系统已有可靠的全应用“功能重要性评分”。

**有效文本输入。** 模型结合字段语义生成内容，也可协调多个相关输入。对需要日期、地点等约束的表单，这比无意义字符串更有机会越过校验。作者用此解释探索可达性，不意味着所有业务约束和负例都被覆盖。

**复合动作。** 健身记录示例需要输入名称、选日期、调整组数/次数再提交。模板/解析把多个动作落实到控件。它说明混合基本动作可以完成复合流程，不意味着动作空间新增了所有拖动/多指操作。

对本项目，四项观察分别落在“跨页依赖、路径选择、数据约束、动作落地”。以后比较新论文时，可以问它实质改进了哪一项、相应实验怎么证明，而不只比模型名称。

## 局限

**作者讨论（Section 3.3.1，第 8 页）：** 无意义的控件文本/ID 不利于理解；依赖复杂数据或外部连接的流程、复杂手势等仍需完善。不能把基本长按支持等同于任意拖动/多指手势支持。

**我们的观察：**

- 主要终点是覆盖和崩溃，没有非崩溃功能 oracle 的准确率/误报漏报验证。
- 旧 Android 7.1、x86 和应用过滤限制泛化，不能推断现代系统/iOS/Web 效果。
- 3 次取最高可能高估日常一次运行效果；没有足够重复分布支撑稳定性结论。
- 模型未记录完整 snapshot 和足够采样配置；费用/token 等未系统报告，难以按当前模型直接复现预算。
- 语义记忆是否错误、遗漏或把错误实现当预期，缺少独立真值评测。
- 所读版本存在数字疑点；正式版正文尚未对照。真实性验证与效果集合可能重叠。
- 以上属于我们的证据边界，不冒充作者写了专门的 Threats to Validity 小节。

## 和我们课题的关系

先用本篇理解 LLM 如何参与 GUI 探索，再补 2025–2026 原始工作判断现状。最值得学习的叙事是：已有方法的具体困难 → 文本上下文和功能记忆两项设计 → 覆盖/缺陷验证 → 消融 → 新 bug 佐证。

可进一步考察的**问题假设**：怎样让功能记忆与独立需求/oracle 相连；怎样把探索轨迹变成可重放、含断言的回归测试；怎样更公平比较探索收益与模型调用成本。它们尚不是已查明的创新空白，不能直接据本篇立题。
