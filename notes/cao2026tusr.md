# TUSR：按完整测试意图修复因 Android 应用更新而失效的 GUI 脚本

## 一页读懂

| 问题 | 本文的回答 |
|---|---|
| 修复什么 | 同一 Android 应用更新后，旧 GUI 测试脚本中的控件定位和操作顺序不再适用。目标是在新版本保留原测试意图，不是修复应用程序代码。 |
| 旧方法为何不足 | 逐个为旧操作寻找新操作，难以处理“原来两步现在三步”“原来多步现在只需一步”的交互逻辑变化。 |
| 核心新增 | 把连续、共同完成一个测试意图的操作组成 Test Unit（TU，测试单元），以单元为整体重新生成操作；结合规则纠正切分和失败反思记忆。 |
| 输入与输出 | 输入旧脚本、可运行的旧版与新版应用；旧版回放采集截图和 XML 控件树。输出在新版执行并保留原意图的修复脚本。无需应用源码。 |
| 主要证据 | COSER 数据集：20 应用、262 脚本、3,485 个原始操作；TUSR 正确修复 232 脚本、3,311 操作。LLM 方法运行三次取最好，不是平均表现。 |
| 关键边界 | 运行时是否完成由 LLM 判断，实验中的正确性由人工核查原意图。功能被删除时不一定有可保留的对应路径；本文不提供显示缺陷或功能正确性的通用 oracle。 |

## 一段话介绍

应用更新后，旧测试脚本可能无法继续点击原来的控件，即使原来要测的功能仍然存在。TUSR 研究如何维护这些脚本：先在旧版回放脚本，理解若干相邻操作共同要完成的事情，再在新版围绕这个意图生成新的操作顺序。它允许一个旧操作对应多个新操作，也允许省略旧版必需而新版多余的导航。实验显示，在指定的跨版本 Android 脚本数据集上，这种以测试单元为基础的修复比逐操作修复更有效；相应代价是模型调用、动态探索时间，以及对模型意图判断的依赖。最值得研究的内容是修复粒度如何从“控件/操作”提升为“意图明确的一段交互”，以及如何证明修复后仍在测原来的事情。

## 关键术语与阅读前提

- **GUI 测试脚本**：记录点击、输入、返回等操作的可执行序列，用于重复测试界面流程；[脚本测试](../glossary.md#scripted-testing)与单次让 Agent 完成用户任务有所不同。
- **控件与定位器**：[控件](../glossary.md#widget)是按钮、输入框等界面元素；[定位器](../glossary.md#locator)用 `resource-id`、文字、无障碍描述等属性找到具体控件。属性改变会让定位失败，但“定位恢复”还不等于测试意图恢复。
- **XML 控件树**：界面元素及其属性、层级的结构化表示，见[控件树](../glossary.md#view-hierarchy)。本文使用截图与控件树，不读取功能实现源码；按作者定义属于[黑盒](../glossary.md#black-box)修复。
- **Test Unit / TU（测试单元）**：旧脚本中一段连续、共同完成单一测试意图的操作，详见[测试单元](../glossary.md#tusr-test-unit)。它不是“单元测试”，后者通常测试函数或组件。
- **原意图保持**：新版操作不仅要执行成功，还要完成与旧版相同的测试目的，见[修复意图保持](../glossary.md#tusr-intention-preservation)。模型的完成标志与实验人工真值是两个层次。
- **反思记忆**：保留失败原因及下一次如何调整的建议，避免反复走同一路径；本文区分单元级和应用级，见[双层修复记忆](../glossary.md#tusr-reflective-memory)。这里是提示中的外部记忆，不是更新模型参数。

## 动机：界面改版可能改变整段流程，而非只改变一个按钮

旧脚本的一个操作可写成三部分：定位器、事件类型、必要时的输入值。例如，找到协议下拉框并点击，然后选择 telnet。逐操作修复擅长回答“原按钮换成了哪一个按钮”，却难以回答“原来这个入口消失后，完成这件事要先去哪一页”。如果机械地为每个旧操作都生成对应操作，还可能多做已经不需要的步骤，导致后续状态错误。`back` 这类不依赖具体控件的操作也有上下文意图，简单重放同样可能出错（Sec.1，第2–3页）。

作者讨论的 COSER 使用源码分析，能在部分范围内补导航、识别功能关联，但仍逐操作修复，而且依赖源码、Java 和支持的分析模式。TUSR 的设计目标是在不具备这些条件时，从一段 GUI 交互的整体目的出发适应改版；这不意味着源码对修复没有价值，后文确实出现只有 COSER 能解决的情况。

## 贡献

作者列出的三项贡献为（Sec.1，第3页）：

1. 提出基于测试单元的脚本修复框架，结合多模态模型切分、规则纠正、带反思记忆的提示来修复。
2. 公开 TUSR 工具及实验数据，入口为[作者代码仓库](https://github.com/Vallxy/TUSR)。数据来自已有 COSER 数据集；不能因此将本文标成提出新 benchmark。
3. 在 20 个 Android 应用上，与黑盒、白盒和 LLM 测试迁移方法比较，验证框架与组件作用。

核心贡献类型记为 **method**。实现、数据公开和常规实验支撑方法，不额外标成 harness 或独立 empirical 贡献。

## 方法：先理解旧测试，再在新界面中逐步实现意图

### 1. 将旧脚本切成连续的测试单元

在旧版应用上执行旧脚本，为每个操作收集执行前后的截图和 XML 控件树。若操作面向控件，利用 `resource-id`、`content-desc`、文字及控件类别理解对象；对于只有图形、缺乏文字的控件，先让模型从视觉信息描述其外观和功能，再结合事件、输入值及前后界面概括本次操作意图（Sec.3.2.1，第7页）。

切分按脚本顺序进行，而不是一次任意重排整个脚本。模型每次收到 TU 定义、当前操作描述/事件/控件、前后截图，以及当前已经积累的 TU 操作列表；输出“当前操作是否属于这个 TU”及理由（Table 1，第6页）。属于就继续合并，不属于则形成新的单元边界。如此保留旧脚本顺序，同时让相邻操作共同表达测试目的。

定义上的 TU 是最小、独立、不可再有意义地拆分的连续子序列。但“最小”并不自动产生唯一答案：一次勾选后又取消勾选，可以理解成一个复合意图或两个意图。作者因此使用人工标注及部分重叠指标评价，而没有把每个边界都当成客观唯一真值。

### 2. 用三条规则纠正模型的切分

这是明确的边界调整，不能概括成“加规则提高准确率”后省略（Sec.3.2.2，第7–9页，规则框在第8页）。

| 规则 | 如何调整 | 为何这样做 |
|---|---|---|
| 导航纠正 | 同一个 TU 中，非导航操作之后出现导航操作，就在导航处切开；如果某个 TU 全是导航，则合并进后一个 TU。 | Android 标准溢出菜单、抽屉等主要用来进入功能，单独打开入口通常没有构成完整功能测试。 |
| 模态对话框合并 | 如果一个 TU 全部是模态框内的确认/取消操作，把它合并进前一个 TU。 | 确认或取消通常完成此前动作，而不是独立的测试目的。检测依据包括控件语义，例如 OK、Confirm、Cancel。 |
| 输入隔离 | 把事件类型为 `input` 或 `clear` 的每个操作分别独立为 TU，保留两侧其他片段。 | 若连续编辑被合在一起，模型可能只设置最终值，跳过“先输入、清空、再修改”的测试过程。 |

最后一条说明“最终界面相同”不一定足够：测试有时就是为了覆盖中间编辑过程。上述规则是作者依据 Android 特征设计的启发式约束，不是对所有界面、所有测试意图成立的语义定理。第8页公式确实将每个输入/清空操作单独隔离，不能只写成“每组至多保留一个输入”。

### 3. 按 TU 在新版动态生成下一步操作

进入修复阶段，模型收到原 TU 的操作描述、当前新版截图、过滤后的控件列表、可执行事件，以及相关反思记忆（Sec.3.3.1，Tables 2–3，第9–11页）。纯布局元素被删除以减少提示长度，其余控件保留语义属性并编号。模型选择控件时输出编号，不必复述完整属性集。

可用事件包括点击、长按、返回、清空、输入、回车、向上/下滚动。提示按四步组织：观察当前屏幕；比较已经执行的操作与原 TU；判断整体意图是否完成；未完成则只生成**下一条**操作。动作执行后再获取新界面继续判断，因此不是在首次观察后生成一长段脚本就盲目重放。

输出包含原 TU、观察、推理说明、`Completeness`、事件、控件编号、输入和操作描述。`Completeness=yes` 要求模型判断原意图已满足，且至少已经执行一条动作；仅仅初始界面看似符合目标也不能按提示直接零操作完成。论文展示了脚本式驱动接口，但未在正文完整交代全部执行器封装，不将其擅自补写成某套确定的自动化平台。

### 4. 失败后回到 TU 起点，带着记忆重试

每次 TU 尝试的生成动作预算经验性地设为**原 TU 长度的三倍**；超过预算仍未完成，就认为本轮失败，恢复到当前 TU 修复前的 GUI 状态，再反思并重试（Sec.3.1、3.3.2，第6、10–11页）。正文没有明确给出全局最大重试次数、重置怎样恢复所有应用数据、各基线是否采用相同动作上限，因此不能补造具体数值。

**单元级记忆**记录失败尝试、失败原因和可执行调整建议。反思提示传入原 TU、失败后的最终截图、已经尝试的动作序列；要求识别哪一步导致失败，并建议尽量少的修改。下一次修复将这些内容加回提示。论文模板中的例子是：目标按钮不可见，前次错误地搜索了菜单，下次应先返回或补滚动，而非再次重复原探索。

**应用级记忆**用 GUI 状态转换图记录操作经验。节点由 XML 识别状态，边是操作；每个状态额外存已观察到的无效操作，例如选择不存在的元素、在不可滚动屏幕滑动。再次到相同状态时，把对应禁忌带入提示。这种错误可通过规则发现；它与“整个 TU 的功能意图是否完成”不是同一种判定。单元级记忆指导本单元重试，应用级记忆可帮助之后修复时避免重复操作错误；原文没有证明它是可跨任意应用直接迁移的经验库。

### 5. 用 ConnectBot 原文案例串起来

原文 Fig.1、Listings 1–2（第4–5页）给出 ConnectBot 的同一意图：**将连接协议选为 telnet**。

- 旧版 1.8.6：主页面直接点击协议下拉框 W1，再点 telnet 项 W2；共两步。
- 新版 1.9.8：主页面已经没有对应下拉框，需要先点击 Add host 按钮 W3，进入主机创建页面，再点当前协议字段 W4，最后点 telnet 项 W5；共三步。
- 逐操作匹配第一步时，主页面上没有可直接替换 W1 的控件。TUSR 将旧两步作为同一 TU，推断整体目标是协议选择，因此能先生成 Add host 这个旧脚本里没有的动作，再完成剩余步骤。

此例支持“多步意图有助于补必要导航”，不是模型根据源码找到路径。作者还指出，即使把逐操作方法直接放到新建主机页面，控件外观/结构变化仍会使 METER、GUIDER 失败；COSER 对该实现片段的分析也超出其范围。原文未把这一个例子展示成反思记忆多轮成功的完整日志，不能给它追加一段虚构重试过程。

## 完成判定、意图保持与 oracle 边界

要区分三个问题。**动作能不能执行**，可由元素存在性、操作合法性及执行结果提供反馈；**TU 是否应该结束**，由 LLM 根据原意图、历史与当前界面设置完成标志；**整段修复是否正确**，在实验中由人工对照旧版测试目的判断。后两项不能互相替代。

本文没有提出独立于修复模型的运行时功能 oracle，也没有系统评价旧脚本断言是否正确迁移、错误产品行为是否会被修复器误适应。完成一个脚本，不足以证明被测应用没有功能错误；生成了可运行的替代流程，也不足以保证原测试覆盖和中间状态全部保留。输入隔离规则正是局部防止意图丢失的一种手段，但不能据此宣称通用的等价性证明。

## 实验：测的是修复正确性，而非新发现多少产品缺陷

### 数据、环境及人工真值

使用已有 COSER 数据集，20 个真实 Android 应用、262 个测试脚本、3,485 个原始动作（Table 4，第12页），包括 AnkiDroid、AntennaPod、ConnectBot、KeePassDroid 等。每个应用提供旧版与新版。该数据集没有覆盖任意现代 Android 平台：正文实验环境为 API level 25 模拟器；PC 为 Ryzen 9 5950X、64GB RAM、RTX 3050。默认模型 GPT-5，替代模型 GLM-4.5V；没有做 GUI 领域微调。

切分真值由两名有一年以上移动测试经验的研究生独立标注，再讨论统一；边界标注在讨论前 Cohen’s κ=0.78。修复正确性由三名有一年移动测试研究经验的学生核查：一人先判断每个修复动作/脚本是否保持旧版执行时的原测试意图，另两人独立检查并写理由，分歧讨论解决（Sec.4.2，第12–14页）。论文未给这一阶段的独立一致性系数。

LLM 方法 ITeM、TUSR **各运行三次、报告最好一次**（Sec.5，第18页）。没有报告三次均值/标准差或置信区间，不能把结果解释成随机一次运行的期望表现。正文也没有给基线统一超时、全部提示参数或精确模型快照。

### RQ1：测试单元能否被合理切出来

在 3,485 个动作上生成 1,822 个 TU，长度 1–14。切分完整度为“人工真值单元中，被模型完整复现的比例”；切分正确度为“模型产出单元中，与人工真值完整一致的比例”。这两项要求单元的边界完全相同。m-IoU 则对每个人工单元，找模型单元中区间重叠比例最大者，再平均，以容纳切分粒度差别（Sec.4.2–4.3.1，第13–14页）。

| 切分方式 | 完整度 | 正确度 | m-IoU |
|---|---:|---:|---:|
| 仅 LLM | 0.54 | 0.60 | 0.73 |
| LLM + 三条纠正规则 | 0.78 | 0.80 | 0.87 |

规则带来的是这三个指标各增加 0.24、0.20、0.14，不是“模型切分完全正确”。作者承认可合理多解；OpenBikeSharing 被进一步拆分的案例经标注者讨论也认为合理。该讨论中动作数与数据表不一致，见下文。

### RQ2–3：修复了多少，花了多长时间

五个基线各自代表不同信息来源：METER 用视觉匹配；GUIDER 结合结构与视觉；ExtRep 先探索建立转换模型、搜索替代分支；COSER 用源码构建转换图和控件功能语义；ITeM 原本做跨应用测试迁移，本文将它作为 LLM 逐动作基线。前四者不是同一类算法，不能合称“随机探索基线”。

Table 6（第15页）的总计为：

| 方法 | 正确脚本 / 262 | 正确原动作 / 3,485 | 总修复时间（分钟） |
|---|---:|---:|---:|
| METER | 85（32.44%） | 1,598（45.85%） | 679.6 |
| ExtRep | 30（11.45%） | 490（14.06%） | 9,863.1 |
| ITeM | 140（53.44%） | 2,381（68.32%） | 3,245.2 |
| GUIDER | 161（61.45%） | 2,326（66.74%） | 648.9 |
| COSER | 215（82.06%） | 3,121（89.56%） | 555.5 |
| TUSR | 232（88.55%） | 3,311（95.01%） | 1,377.4 |

百分比按表内计数与统一分母复算。动作指标的分母是旧数据集的 3,485 个动作，并不是新版最终生成动作总数；多对多修复的具体动作级匹配记账细节未完整给出，不能把 3,311 当成输出脚本动作条数。

TUSR 的优势主要是成功率，时间不是最优：总时间约为 METER 的 2.03 倍、GUIDER 的 2.12 倍、COSER 的 2.48 倍，为 ITeM 的约 42.44%。作者认为自动化可减少人工维护，但没有直接计量与人工修复工时的对照实验。

全部方法共同能修的有 323 个原动作，只有 TUSR 能修的有 154 个；只有 COSER 能修的有 28 个。TUSR 未修复的 174 个中，57 个 COSER 可以修，117 个所有比较方法都不能修（Fig.3、Sec.4.3.2，第15–16页）。这说明总体领先不等于替代所有白盒能力。

### RQ4–5：优势来自哪些组件、是否依赖模型

| 配置 | 正确脚本 | 正确原动作 |
|---|---:|---:|
| 完整 TUSR / GPT-5 | 232 | 3,311 |
| 移除 TU 切分，回到逐动作修复 | 92 | 2,231 |
| 移除反思记忆 | 212 | 2,858 |
| 完整 TUSR / GLM-4.5V | 214 | 3,009 |

移除 TU 后脚本少 140 个、动作少 1,080 个；移除记忆后脚本少 20 个、动作少 453 个。结果支持“修复粒度”和“失败经验”都有作用，但没有单独拆开 TU 级/应用级记忆或比较不同反思触发阈值。正文未给独立移除 CoT 的消融，不能声称 CoT 的单独贡献已经被验证。

GLM-4.5V 仍能工作，说明不完全绑定 GPT-5；这只是两个模型在同一数据集上的证据，不能推论任意模型都能达到相同效果。其动作百分比在原表存在错误，保留计数为主。

### RQ6：token 与费用

Sec.4.3.6（第17–18页）报告总输入 31,064,723 tokens、输出 5,596,630 tokens；同时称平均每个生成修复动作约输入 4,000、输出 500 tokens，GPT-5 每次修复尝试约 0.01 美元，每应用总费用 0.42–17.72 美元。

这些是作者当次实验记录，不能用作当前模型报价。正文没有充分给出总 token 对应哪些阶段、三次运行如何计入、生成动作总数和“尝试”的明确分母，所以不能从上述数字推导每个成功脚本的可靠平均成本，也不能把最高单应用费用当成全数据集总费用。

### 原文数字/表述不一致：保留计数，不静默修正

1. 正文与结论称相对最强黑盒脚本/动作修复提高“27%”。Table 6 的脚本最佳黑盒为 GUIDER 161 个，动作最佳黑盒为 ITeM 2,381 个。按计数，232 对 161 的相对提升是 44.10%，对应成功率差 27.10 **个百分点**；3,311 对 2,381 的相对提升是 39.06%，成功率差 26.69 个百分点。因此“27%”更接近两项四舍五入的百分点差，不直接沿用为相对提升。相对白盒 COSER 则增加 17 脚本、190 动作，约 +6.49 / +5.45 个百分点，亦保留原始计数。
2. Table 8 的 GLM-4.5V 写 3,009（89%）；3,009/3,485=86.34%，不是 89%。按计数与 GPT-5 比，动作率差约 8.67 个百分点，也不等于正文所说“6%”。
3. Sec.4.3.3 写 4.2–259.8 分钟“每脚本”，但它们对应 Table 6 不同应用行的修复总时间。按表格只记录为应用行数值，不当单脚本耗时范围。
4. Table 6 的 TUSR 各应用脚本成功数逐行相加为 **233**，但 Total 行及正文写 **232**；动作列逐行相加与总计 3,311 一致。本文主结果沿用作者反复报告的 232，同时保留这项一例差异，不能以行和擅自替换作者总计。
5. Table 4 的 OpenBikeSharing 是 5 脚本、29 动作；Sec.4.3.1 的同应用解释却写 34 动作。总数据集规模按 Table 4 及全文反复使用的 3,485 记录。Table 6 中该应用 TUSR 为 5 脚本成功但 27/29 动作成功，提示多对多修复下脚本与动作记账可能不同；正文未充分解释，不能自行改成 29。

## 局限

### 作者承认的

- **功能删除**：174 个失败动作中，作者归因 33% 为功能移除。TUSR 可能仍搜索不存在的功能或生成冗余操作；可靠决定“应该删掉这个 TU”需要额外动态/静态证据，不能仅凭探索失败判断（Sec.4.3.2，第14–16页）。
- **GUI 误解**：其余 67% 归因通用模型误解界面，影响控件选择、TU 对应和后续流程。作者提出未来微调或结合代码知识，不是本文已经实现的能力。
- **与源码语义互补**：显著外观变化而功能语义不变、以及功能删除等情况下，COSER 可利用代码获得 TUSR 没有的证据（Sec.4.3.2、6.1，第16、19页）。
- **随机性与代表性**：三次取最好缓解失败但不展示波动；20 个应用不足以代表所有真实 Android 应用，工业协作评估留待未来（Sec.5，第18页）。

### 我们根据正文观察到的

- 完成判定与下一步都来自同一个模型推理流程；没有独立 oracle 约束“修到能跑但测错目标”的风险。人工评价支持该数据集正确性，不等于生产中每次自动修复都可免核查。
- TU 的独立性主要是设计假设，恢复到 GUI 状态未必恢复登录态、数据库或外部副作用；正文没有给出充分的恢复一致性验证。
- 相同最终界面可能对应不同中间操作覆盖。输入隔离是有价值的防线，但还需要检查断言、异常流程与被删路径是否被不当绕过；此为后续评测问题，不声称作者已证明没有问题。
- 三次最好值、人工一致性范围、动作记账和多处百分比问题限制精确横比。后续复现宜保存每次结果、明确语义成功条件及编辑距离/新动作数，而非只复用摘要百分比。

## 和我们课题的关系

### 与 UX testing 的关系

对 UX-Agent 的直接可借鉴点是**保留主动验证动作的意图和中间过程**。例如，某段验证需要先发现截断候选、再滚动观察文本是否可展开，那么应用改版后应维护这整个验证过程，而不是只让最终页面“看起来正常”。输入隔离规则也提醒：不能为了完成终态而跳过本来要检验的操作。不过 TUSR 没有检测遮挡、重叠、溢出或文字截断，也没有提供这些问题的判定规则；它对 UX testing 的作用是维护可重复验证流程，不能充当显示缺陷 oracle。这个应用场景是我们的迁移设想，不是原文实验结果。

### 与 GUI testing 的关系

本篇补上的是 **GUI 测试维护**：旧脚本在版本演化后如何保持测试意图。它与提高自由探索覆盖率的工作不同，拥有明确的历史测试目标；与通用 GUI 任务 Agent 共享感知和执行技术，但评价对象是修复脚本对旧测试目的的保留。值得与代码辅助修复对照，研究模型能恢复哪些跨页面语义、哪些仍需要源码或显式规格；是否应安全拒绝修复或删除 TU，则需要独立证据，不能把猜测写成已验证选题空白。
