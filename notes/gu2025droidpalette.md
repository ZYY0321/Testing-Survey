# DroidPalette：根据同页配色和运行效果，修复 Android 颜色可访问性问题

## 一段话介绍

一个按钮虽然存在并且能点击，前景与背景颜色过近仍可能让用户看不清。修复时既要提高对比，也要知道该改哪个属性：输入框正文颜色和提示文字颜色不是同一个设置，改错属性不会改变实际问题。DroidPalette先从真实修复中归纳选色习惯，再结合同页控件、颜色库和亮度调整选择替代色；随后分析Android框架与依赖库支持哪些颜色属性，逐项修改XML并运行检查，输出有效补丁。所读作者稿中，497个报告有331个通过同一检查器的修复验证；另有用户偏好与维护者反馈。但一个检查器不再报警，不等于业务功能、主题切换和所有用户体验都正确。它应作为颜色oracle与修复验证的相邻工作，不是本项目定向探索的主要基线。

## 关键术语与阅读前提

- **颜色对比度**：前景文字或图形与背景的明暗可辨认程度，不是只比较两种颜色的RGB差。本文以普通文字4.5:1、大文字及所研究非文字元素3:1作为选色约束；这里记录论文实验准则，不表示所有视觉元素均适用同一阈值。
- **颜色检测、选色、补丁应用**：分别回答“哪里不够清晰”“换成什么”“修改哪个配置才能生效”。三个阶段的成功率不能互相替代，见[颜色修复与闭环验证](../glossary.md#droidpalette-color-repair)。
- **XML及资源引用**：Android界面元素的配置可写在布局文件，也可通过父节点、style、drawable等资源间接决定。仅找到截图位置，还不足以定位可修改属性。
- **静态切片**：从与颜色属性解析有关的代码出发，追踪相关处理逻辑。本文利用ConfDroid的方法整理框架/第三方库可设置的颜色属性，不是只靠固定五个控件规则。
- **运行验证与oracle**：修改配置后重新运行，观察目标颜色是否改变并复检低对比报告；这属于特定属性效果验证，不是完整业务正确性证明。

## 动机与贡献

原文§I–III（第1–4页）有两类案例。OneBusAway的进度条颜色与背景接近，需要修改与进度条着色有关的属性；VPC输入框则是提示文字对比不足，改`textColor`不能替代`textColorHint`。这些案例说明：提出一个可读颜色，与真正改变对应视觉内容是两个难点。

先前Iris主要从跨应用颜色库与固定规则产生补丁；作者认为这会受到颜色库缺项、控件类型和属性覆盖的限制。直接模型生成也可能选原色、生成无效属性或重复不稳定。

作者§I提出三项贡献：真实修复策略的实证研究、自动修复方法DroidPalette、在应用及用户/开发者层面评价。核心记为 **empirical + method**，不因为发布应用文件就自动宣称贡献统一GUI benchmark。方法本身不用LLM，GPT-4o是对照。

## 方法与核心技术

### 1. 从真实补丁提炼选色策略

作者以GitHub中“color fix”及语言、热度条件检索，1629个候选经人工筛选得到63项目202个相关PR。两位作者先独立分析101项建立分类，再迭代处理剩余101项，分歧讨论至一致（§IV，第4–5页）。

三类策略为：

| 策略 | 数量与作用 |
|---|---|
| T1 取同页已有颜色 | 150项，保持同页面风格；其下同位置对齐129项、相似属性104项可交叉，不能相加为233独立问题。 |
| T2 调整原色明度 | 34项，在基本保留色相的同时提高对比。 |
| T3 引入新颜色 | 18项，同页找不到合适颜色时使用新配色。 |

这些是筛选样本中的开发者做法，不是所有Android项目的普遍概率。184/202来自T1与T2合计；不能把91.09%都说成取同页相似控件颜色。

### 2. 选择同时满足可读性和页面协调的颜色

输入Xbot报告、页面截图、前景/背景颜色和控件树。候选来自同页控件前景色及Iris颜色库；库内按评分取前5项。评分综合目标与其他控件的树中距离、属性集合相似度，以及颜色对比和HSL色相/饱和度/明度差（§V-A，第5–6页）。

直观上，距离近、属性相近的控件更可能共享风格；但这只是评分依据，不是业务上必须同色的规格。属性相似用集合交并比，树中距离越远权重越小。

对每个候选随机微调明度：初始步幅1%，改善则扩大步幅，不改善则反向并重置；各方向不再改善时停止。明度低至10%或高至90%边界的候选会按原文规则排除，以避免丢失原色特征。最终在满足对比约束的候选里取最高分，不将“风格分高”直接代替对比要求。

### 3. 找到能够真正改变目标颜色的属性

候选XML位置包括目标控件定义节点、其父节点和被引用的其他资源。定位先结合运行控件ID与文字；再从Android框架及依赖库中提取可用于该节点、接受颜色值的属性（§V-B，第6–7页）。

系统逐一赋值并运行，只有实际能改变目标颜色并通过验证时才输出补丁。例如输入提示应改提示颜色，而非正文颜色。每个补丁只尝试一个修复属性；没有在实证数据中见到需多属性并不等于现实中没有。

### 4. 验证闭环及其不能保证的内容

主要实验将补丁应用到APK后再次运行Xbot，不再报告原问题就算修复成功（§VI-A，第7页）。颜色候选、属性生效和复检形成闭环，但它可能继承原检查器的范围与误差。

这不是图像变化即成功，也不是完整回归验证。主题、系统动态配色、其他页面共享资源及交互功能可能受到影响。论文后续维护者反馈就显示，符合当前页面颜色标准的修改仍可能不适配深浅主题或Material You。

## 实验

### 样本、对照与协议

| 项目 | 实际设置 |
|---|---|
| 效果数据 | F-Droid初650应用，按GitHub超过10星等条件保留105应用；Xbot产生497报告：普通文字340、大文字73、非文字84。 |
| 成功定义 | 修后Xbot不再报告原低对比问题；不是497个都经维护者确认的独立根因缺陷。 |
| 对照 | Iris与GPT-4o。模型收到问题报告、相应XML和截图。 |
| 模型重复 | GPT-4o运行3次，并要求稳定输出能消除问题的结果；不是三次最好，也未将所有方法结果写成多次均值。 |
| 未充分报告 | 完整设备/版本、统一运行预算、端到端耗时和模型费用未在实验设置中清楚给出；不自行补猜。用户问卷截图以Pixel5显示分辨率校准，不据此推定所有测试都在Pixel5。 |

### RQ1：自动修复端到端是否有效

表I、第9页，主结果：

| 方法 | 修复数/497 | 比例 |
|---|---:|---:|
| DroidPalette | 331 | 66.60% |
| Iris | 198 | 39.84% |
| GPT-4o | 129 | 25.96% |

DroidPalette分别修复245/340普通文字、51/73大文字、35/84非文字问题；非文字效果较低。它比Iris多133条，相差约26.76个百分点，不能将其写成新增133个已确认产品缺陷。

失败166条中存在运行代码控制颜色且无可用XML属性的情形。例如EnforceDoze的对话框按钮需通过Java对象修改，单改XML不能完成。这与设置相关显示问题中动态生成页面的局限相呼应。

### RQ2：选色与属性生成分开测，暴露真正瓶颈

颜色阶段允许研究者人工把算法选出的颜色应用到正确XML，再检查对比：DroidPalette有效497/497，Iris457/497，GPT-4o344/497。**497/497是选色阶段效果，不是自动完整修复率。**

属性阶段则让各方法推荐可生效属性，填入随机颜色验证能否改变并消除低对比：DroidPalette331/497、Iris230/497、GPT-4o192/497。这说明本设置下自动应用属性是更明显瓶颈，阶段评测又包含不同人工条件，不能把两个阶段比例随意相乘。

### RQ3：通过检查器后，人是否接受

问卷选择10个各工具结果不同、对比较低的报告；截图随机排序，以五点量表评价，最终55份有效问卷，其中43人自报视觉障碍、12人没有。参与者限50岁以上、英语地区，包含响应质量过滤（§VI-E，第9–10页）。这不是对所有497问题或一般用户的随机评估。

论文的304、214、142等数字是跨问题的偏好计数，可以并列，不能称为304位不同用户。仅凭截图进行偏好判断，也不能代替在真实设备和辅助设置中完成任务的结果。

开发者评价另挑近期更新、且工具能修复目标页全部颜色问题的13个应用提交PR。表II、第11页给出 **4合并、4确认、1拒绝、4待回复**；作者“8份正面反馈”是前两项之和，不是8份均合并。

organicmaps反馈需要进一步适配明暗主题；disky拒绝补丁，因为未考虑Material You按系统配置动态配色。两者说明标准对比、截图偏好与产品接受是不同证据层次。

## 局限

### 作者明确说明

- §V-B：只改一个颜色属性，可能不足以处理需协同多属性的情形。
- §VI：Java/Kotlin运行代码控制的颜色及多主题/动态配色适配仍受限。
- §VII：50岁以上参与者并不充分代表所有色觉或视力障碍人群；截图问卷与真实设备使用可能有差距。

### 我们的观察

1. 输入已是Xbot报告，因此未评价整个应用的缺陷发现召回或UX驱动探索效率。
2. 同一检查器产生问题并确认修复，存在对检查器的依赖；没有系统性的全业务回归或共享资源副作用检查。
3. 同页风格与颜色关系是经验，不是独立需求。即便视觉结果被多数问卷偏好，也不证明满足全部用户、主题和品牌要求。
4. 原始PR检索、热度筛选、可修复页面选择均有取样条件；不能将202个实证补丁和497个检测报告合并为699个同性质已确认缺陷。

## 和我们课题的关系

### 与 UX testing 的关系

补充颜色可读性与修复后验证，尤其有助于区分**检测规则通过、实际视觉改变、用户偏好、维护者接受**。对遮挡、重叠、溢出，它只能提供闭环评价思路，没有实现这些类型的统一oracle。它的修复主要改代码配置，不是通过滑动恢复可见性。

### 与 GUI testing 的关系

主任务是产品修复 `repair`，依赖现成GUI报告和实际运行验证，不是脚本维护 `maintain` 或导航生成。可作为“结构/代码与视觉反馈结合”的相邻参考，避免将模型自然语言建议直接等同验证完成；不作为自然语言定向探索的核心比较对象。
