# FuncDroid：通过功能之间的状态与数据联系，发现单独测试一个功能时容易遗漏的错误

## 一段话介绍

移动应用的功能往往共享数据：设置页删除一个提醒，应该影响另一个页面是否允许重新创建它。FuncDroid 研究的就是这类跨功能交互测试。它把操作轨迹整理成“功能节点”和“带状态条件的功能连接”，再从两个角度生成测试：一类检验功能划分与连接条件是否准确，另一类改变操作方式或共享数据，寻找条件满足却行为异常的情形。执行结果既用于报告缺陷，也用于修改图。它的重点是**组织有状态的测试过程**，而不是提出新的图像布局检测器或形式化正确性证明器。

## 关键术语与阅读前提

- **功能与页面不同**：本文的功能是完成一个用户任务、且不能再分成独立子任务的单元。同一页面可参与不同功能，一个功能也可跨多个页面。这个划分是待验证的假设，不是作者预先人工给出的标准答案。
- **[功能流图 FFG](../glossary.md#functional-flow-graph)**：节点记录功能目标、有关状态变量和操作轨迹；边记录先后两个功能的轨迹及使后一个轨迹可执行的条件。区别于只记录页面跳转的图。
- **状态变量与条件**：例如 `alarm` 表示提醒是否已经添加。本文由界面及轨迹推断这些语义变量，没有说明读取程序内存中的同名变量。
- **[变形关系](../glossary.md#metamorphic)**：不必直接知道所有具体输出，而是改变输入/历史后检查应当保持的关系。例如删除提醒后，应能再次添加同样的提醒。关系是否适用于当前业务仍需判断。
- **长时视角 LTV 与短时视角 STV**：前者优先提高后续测试所依赖的图质量，后者优先利用当前图发现错误；不是两种神经网络记忆长度。
- **[Activity 覆盖率](../glossary.md#activity)**：访问的 Android Activity 占应用全部 Activity 的比例。Activity 是应用界面组件，不等于每个视觉页面或每条功能路径。

## 动机

作者认为，现有功能感知方法虽然能理解页面语义，却容易把功能表示为线性操作片段，并分别探索各个功能。这会遗漏两个层次：一是功能边界可能划错；二是功能间通过数据和历史产生的依赖没有进入测试计划。即使两个页面都访问过，也不说明关键状态组合被执行过（Sec.1–2，PDF第2–4页）。

原文 Blood Pressure 应用的例子有两个错误。先在 BMI 页面设置08:00的 BMI 提醒，再去设置页查看提醒列表，列表却把它显示为血糖提醒。继续从提醒列表删除该提醒，再到血糖页面重新添加08:00提醒，应用提示时间重复。后一个错误必须保留“曾创建、已经删除、又从另一个入口创建”的历史；只检查新增和删除两个功能各自能否完成会漏检（Fig.1，第4页）。这是功能状态错误，不是文字遮挡或按钮溢出的 UX 错误。

## 贡献

按作者 Sec.1 的三个条目（第3页）：①设计明确表示功能及其相互流转的 FFG；②提出迭代构建、利用 FFG 的跨功能 GUI 测试方法；③实现 FuncDroid，并在开源与商业应用上评价。本文的主要贡献类型记为 `method`。使用 Themis 以及收集商业应用，不自动等于提出新 benchmark；作者自称首个系统模型，也不应转述为我们独立验证过的优先权结论。

## 方法：从界面轨迹到测试，再把结果写回图

1. **初始化**：先轻量探索应用，采集轨迹。多模态模型分析截图、控件树及文字，为页面推断目标和相关状态变量；比较目标的语义向量相似度，把连续动作归入候选功能。跨功能的相邻片段连边，初始条件设为 `True`，仅代表“观察到曾经先后执行”，不代表在所有状态都可执行。
2. **生成场景**：LTV 检验功能是否完整、是否可再拆分，以及边的条件是否需要细化；STV 改变已有操作或共享数据，探测现有功能连接的异常。
3. **执行场景**：场景保存 `type / strategy / object / guidance`，即视角、具体策略、目标节点或边、自然语言执行指导。模型从主页出发，参考 FFG 导航，把指导逐步转换成控件动作。动作因控件不存在、禁用或状态不符而失败时，记录失败，并根据实时截图和 FFG 尝试恢复或替代动作。论文未完整给出底层执行库与每个动作的重试上限。
4. **检查并报告**：非崩溃检查使用常见错误知识库增强的多模态模型，推断预期；结合最终截图、控件树、测试轨迹与系统日志比较实际结果，生成结构化报告。执行失败也可能只是图不准确或导航问题，不能自动作为产品 bug。
5. **更新并循环**：新的轨迹用于创建/合并/拆分功能，以及修改连接条件。实验在60分钟预算结束，不是达到“全功能验证完成”才停止；正文未给独立的完备性停止准则。

## 核心技术详解

### FFG 到底存什么

功能节点是 `(goal, vars, traces)`：`goal` 是用户任务目标；`vars` 包括界面属性、数据实体与系统环境设置；`traces` 是实现该功能的一个或多个控件操作序列。边是从功能 `n` 到 `n′` 的 `(π, φ, π′)`：先执行轨迹 `π`，当状态满足条件 `φ` 时，能够执行后续轨迹 `π′`。同一对功能可有不同轨迹或不同条件的连接（Sec.3.1，第5页）。

这种表示把“去过提醒列表”细化为“做过某种操作以后，在什么状态能继续做什么”。它不等于真实程序的完整状态机；其中目标、变量、条件都来自运行观察与模型推理，需要不断试验校正。

### LTV：用执行来检验模型假设

功能**完整性检查**寻找目标所需、但当前轨迹中缺失的操作；功能**独立性检查**比较各轨迹目标并聚类，如果一个功能中实际包含不同用户子任务，就分别尝试执行以判断是否应拆分。在原例中，导航功能尚未探索血糖按钮，补测后发现新的“血糖编辑”功能（Fig.4，第8页）。不是所有补测都会修改旧节点，也可能新增节点。

条件检查使用三类策略（第9页）：①**划分**：把“若干条件之一成立”的情况分组测试，观察各组是否通向不同结果；②**最小违反**：一次让一个必要条件不成立、其他条件保持，检验该条件是否真的必要；③**不变性检查**：完成一次功能流后，用中间操作返回，再重复原操作，观察看似相同条件下是否出现不同结果。原例发现血糖提醒不能重复添加，把最初过宽的 `True` 细化为“尚未添加提醒”。

条件采用析取范式，即若干“并且”条件组之间再以“或者”连接。这是组织条件的形式；正文没有交代完整的求解器实现、语义相似度阈值、聚类参数或条件推断准确率。不能把这种形式化记号误当作已验证的源码逻辑。

### STV：围绕条件变化，而非只重复访问页面

**单流变形**在一个功能内部改变建立条件的方式，例如先隐藏/显示动态控件、交换语义允许独立填写的表单顺序、切换不必需的开关。目标是仍然满足原条件，再检查后续功能是否仍能执行；顺序不影响业务是需要判断的前提。

**跨流变形**寻找当前图中没有直接连接、但 `vars` 有交集的功能，改变共享实体。例如一个功能删除提醒，另一个功能尝试重新创建；还包括修改实体属性、产生或消耗共享资源。原文 Fig.6 的“添加提醒→从管理页删除→重新添加”触发了时间重复错误（第10–11页）。这说明测试的是数据一致性，不只是页面间导航是否顺畅。

### 图怎样更新，为什么不能把所有差异都当错误

功能更新包括新增目标、把同目标同数据的轨迹并入节点，以及把包含不同独立目标的节点拆分。连接更新根据条件和结果是否相同进行：新条件更强且通向不同结果时，为该条件新增连接，同时从旧边中排除它；较弱条件仍通向同一结果时放宽旧条件；不可相互蕴含但结果相同时用“或”合并（Sec.3.2.3，第12–13页）。

因此“后续动作不再可执行”可能意味着图漏掉了合法前提，而不一定是程序错误。本文仍需要独立于图更新的缺陷判断模块。不过这个模块的预期来自模型与常见缺陷知识，而不是经过验证的需求断言。笔记据此把本篇主要归为测试生成，不能当作解决独立 oracle 的代表。

## 实验

### 设置与分母

RQ1/2 使用 Themis 原有20个开源应用的72个带崩溃版本，去除无法启动/注册的版本，保留**50个版本及各自对应的50个崩溃**。版本数不是不同应用数，额外发现的非崩溃问题也不是那50个已知崩溃之一。RQ3 使用52个商业应用，覆盖13类；排除反复启动崩溃、不兼容某工具，以及无法绕开或脚本化登录的应用（第13页）。

基线是 DroidBot、Fastbot、Humanoid 各加 LLMDroid 增强，以及 GPTDroid、VisionDroid 各加 MemoDroid。比较的不是五个原始未增强工具。全部模型后端统一 GPT-4o；Ubuntu24.04主机64核；开源应用在 Android7.1模拟器，商业应用在 Android15模拟器。预置外部文件，必要时人工注册账号、编写登录脚本并重置账户数据。**每个工具每应用60分钟，重复3次报告最好成绩**（第13–14页）。没有报告均值、方差、显著性检验或完整 API 费用；最高成绩不代表通常一次运行表现。

### RQ1：覆盖与错误检测

| 指标（Table1，第14页） | FuncDroid | 最好基线 VD+MD |
|---|---:|---:|
| 平均 Activity 覆盖率 | 0.55 | 0.43 |
| 平均代码覆盖率 | 0.40 | 0.38 |
| 崩溃错误数 | 49 | 25 |
| 非崩溃错误数 | 13 | 5 |
| 总错误数 | 62 | 30 |

作者报告 Activity 相对提升约28%、代码约5%，总错误数约107%；这些不是百分点。正文同页把最好基线的崩溃数写为24，并说49相对24提高96%，而表中是25且总数30=25+5。**这里保留表中计数，另记录正文冲突，不替作者修正文稿**。正文还说发现基准中的全部错误，但49不能写成50/50全部已知崩溃复现。非崩溃结果没有给出完整精确率/召回率或独立人工标注协议，不能由13例推断一般判定准确性。

Fig.9（第15页）显示覆盖和错误曲线，作者称约20分钟达到最好基线60分钟的水平。这是该预算和取最好协议下的效率证据，不是通用三倍加速保证。正文未清楚定义代码覆盖的具体单位与采集方案，不能自行将0.40称为分支覆盖率。

### RQ2：消融验证各部分有什么用

Table2（第16页）的完整方法平均105条功能流、62个错误。去掉功能边界细化得到71条流/48个错误；去掉条件细化89/50；去掉整个LTV65/43。去掉单流变形97/46，去掉跨流变形101/49，去掉整个STV94/39；两视角都去掉58/27。

结果支持两类作用不同：LTV对发现和细化连接数量影响更大，STV在已有图上变化状态可明显增加缺陷，即使新增流不多。**流数不是有固定真值分母的覆盖率**；更多模型边不自动证明边更准确。论文未报告功能边界和条件的独立人工准确性标注。

### RQ3：商业应用与确认状态

52个商业应用中报告18个新非崩溃问题，Table3列18个应用条目；两个增强基线分别发现其中4和6个，前者均包含于后者。18个报告中**2个修复、2个确认、3个无可用反馈渠道，其余11个等待回应**（第17页）。不能合写成4个修复或18个确认；没有被拒绝也不能视为确认。Fig.1的血压应用例子是此类非崩溃跨功能错误的机制说明。

## 局限

**作者明确写出的边界/未来工作**：Sec.6（第18–19页）提出扩展到 iOS/HarmonyOS，增强非崩溃错误知识库。正文没有独立 Threats to Validity 章节；不能把下列观察冒充作者承认的限制。

**我们的观察**：模型生成的目标、变量及条件缺少独立准确率；判定预期依赖模型与模式知识，不能保证满足应用真实需求。图更新规则虽明确，但阈值、初始探索预算、LTV/STV调度与失败重试细节不足。取3次最好、缺少费用与波动数据、商业应用登录筛选会限定外推范围。实际交互主要使用截图/控件树，而代码覆盖只用于实验评价，不能因此说方法是源码白盒测试。

## 和我们课题的关系

### 与 UX testing 的关系

它可以提供“完成某功能后再改变页面/数据”的有目的探索，比只访问更多截图更适合产生状态相关 UX 候选。对截图候选、布局树复核、主动滑动验证链路，可以借鉴“显式记录条件→改变状态→检查是否仍成立”的组织方式。本文没有检测遮挡、重叠、溢出或文字截断的独立方法，也没有证明滑动后问题消失就意味着候选不是 bug。

### 与 GUI testing 的关系

主要补测试生成与跨功能探索，用 FFG 把共享数据、先后历史和可执行条件连接起来；既有 crash 检测，又有模型判定的非崩溃检测。与需求驱动 oracle 论文比较时，应分别问“更容易触发问题”和“更可靠地认定问题”，不能用同一个错误总数掩盖两者差异。可继续核查的研究问题是：如何为图的条件与跨功能不变性提供外部需求证据；这不是本文已证实的空白。
