# iPBT：把人工描述的 Android 功能属性转成可执行检查代码

## 一页读懂

| 问题 | 解释 |
|---|---|
| 旧方法哪里不足 | 基于属性的 GUI 测试可以反复检查功能规则，但测试者必须懂框架 API、编写前后条件，并手动查找控件标识。规则本身容易描述，准确转成可执行代码却费时。 |
| 本文新增什么 | 先用截图、控件树和页面上下文生成控件语义注释，再让语言模型根据结构化自然语言规则、控件信息和框架示例生成 Kea 属性代码。 |
| 输入 / 输出 | 输入由人提供的“前置条件—交互—预期结果”，以及预先收集的应用界面信息；输出可由 Kea 执行的属性代码。它不负责自动发现应测试哪些未知功能规则。 |
| 怎样验证 | 八应用、124 条已有属性，两种生成模型均正确生成 118 条；移除语义注释显著下降；另有十人编写实验和 1,180 条改写实验。 |
| 最重要的边界 | 95.2% 是**属性代码生成正确率**，不是 GUI 缺陷检出率。评测提供已知到达路径以确保采集相关控件，不表示自动探索已解决。 |

## 一段话介绍

iPBT 解决 GUI 功能测试里一个具体的人工瓶颈：测试者知道“点击文件夹应进入文件夹”，但把这句话变成测试代码时，需要找到对应控件、调用正确 API、写清检查条件。系统先给控件补上功能含义，例如把含糊的 `qa` 标识解释为“复习卡片的问题文本”，再将测试者写的规则转换为 Kea 框架代码。测试运行与输入生成继续交给原有框架。因此，这篇工作的重点是**可执行属性编写**，不是重新设计手机探索代理，也不是让模型自由观察页面后直接判断所有错误。（§1、3、5，PDF pp.1–8、17）

## 关键术语与阅读前提

- [基于属性的测试（PBT）](../glossary.md#property-based-gui)：先写对一类状态都应成立的规则，再让框架生成多种操作序列寻找违反规则的情况。规则例子不是固定点击某个文件夹，而是“遇到可打开的文件夹，点击后路径应包含该文件夹名”。
- **可执行属性**：本文用三部分 `⟨P, I, Q⟩` 表示：`P` 是何时可检查的前置条件，`I` 是执行功能的操作序列，`Q` 是操作后应成立的断言。它不仅是一句布尔表达式，也包含 GUI 操作。（[前后条件](../glossary.md#test-spec)、[预言与断言](../glossary.md#oracle)）
- **控件语义落地（UI semantic grounding）**：把“搜索按钮”“文件名”等用户用语对应到可操作的具体控件标识。这里的输出可以是 `resource_id` 或文本，不只指屏幕坐标。（[grounding](../glossary.md#grounding)、[定位器](../glossary.md#locator)）
- [增强控件上下文](../glossary.md#enriched-widget-context)：原有属性加上模型生成的语义标签和功能描述。它辅助写代码，不是开发者提供的业务真值。
- **上下文学习 / 少样本示例**：在提示里放两个输入及正确输出示范，模型据此生成相同形式的代码；本研究不微调模型。（[提示与示例](../glossary.md#prompt)）
- **Kea**：既有 Android 属性测试框架；本文生成它能执行的代码，未替换其输入生成和执行机制。与 [Kea 原论文笔记](xiong2024kea.md) 的关系是“减少编写成本”，不是同一篇工作。

## 动机

原文 Figure 1（pp.1–2）以 Amaze 文件管理器为例：点击 Download 文件夹，应进入目录并更新路径，而不是出现打开普通文件的对话框。测试者容易描述预期，却需要手动确定列表项标识 `line`、搜索按钮标识 `Search`、路径控件标识 `path`，再写枚举项目、选目录、点击及结果检查。

仅把自然语言丢给模型并不足够。真实应用常把控件命名为 `button1` 或 `qa`，单看标识无法确定作用；同一应用里还可能存在多个外观或功能接近的控件。传统规则转换也难枚举所有“打开目录 / 进入文件夹”的说法。作者因此把“先理解界面控件”与“再写框架代码”拆成两阶段，避免把生成任务简化为纯文本翻译。（§1、3.1，pp.2–5）

## 贡献

按 §1（p.3）作者贡献归纳：

1. **概念**：使用轻量结构化自然语言降低 Android PBT 属性编写门槛，让测试者表达功能意图。
2. **方法与实现**：iPBT 包含控件语义注释和可执行属性合成两个阶段，结合视觉与结构信息以及框架示例。
3. **数据与实证材料**：在既有 Kea 属性上新增 124 条人工自然语言描述、1,180 条模型改写，并给出生成、消融和用户实验。原有 124 个历史缺陷不是本篇首次发现的缺陷。

## 方法

完整流程是：**收集截图和控件树 → 为控件补语义 → 人写结构化规则 → 将规则、控件信息、框架 API 和示例组成提示 → 输出属性代码 → 交 Kea 执行**。（Figure 2、§3，pp.4–8）

### 阶段一：收集界面数据并解释控件

数据可以来自人工交互、自动探索或应用提供方。实验中使用自动探索并额外执行已知路径，不代表方法只能人工采集。

| 信息层次 | 实际字段与来源 | 在生成中的作用 |
|---|---|---|
| 页面信息 | 应用名来自 AndroidManifest；Activity 名来自运行时布局；ADB 截图中用红框标出目标控件 | 判断所属功能和控件在整页中的位置 |
| 控件信息 | 按边界裁剪的局部图；控件树中的 `text`、`resource_id`、`content_description`、`class` | 给出可定位标识、文本、可访问性说明与类型 |
| 模型新增信息 | `semantic label`：简洁角色名；`functionality`：用途描述 | 将自然语言中的角色与具体控件对应起来 |

例如 Figure 2 的 AnkiDroid 预览页中，目标控件的文本只是 Test，资源名是 `qa`，类型是 `android.view.View`。给模型整页图、局部图、AnkiDroid 应用名及 Previewer 页面上下文后，模型补出“问题文本显示区”和“向用户展示用于复习的问题文本”等语义，供后续规则中的“问题文本”匹配。（pp.4–6）

注释提示包含角色、任务、两个示例、输入、格式约束五部分。示例来自不参与评测的 SimpleNote。语义注释由 GPT-4o mini 完成；不能将后续 DeepSeek-V3 结果理解为完整流程只用了开源模型。（Table 1，p.6；§4，p.8）

### 阶段二：把规则合成 Kea 属性

用户输入有两个文本段：`Precondition` 对应 `P`；`Function Body` 同时包含操作 `I` 和预期 `Q`。因此 iPBT 的自然语言是有约束的规格接口，不是从任意聊天片段中恢复所有需求。

合成提示有六部分（Table 2，p.7）：①测试代码生成角色；②框架支持的控件查找、点击、长按、读文本、检查存在、返回等 API；③前阶段得到的增强控件上下文；④两个“属性描述—可执行代码”示例；⑤本次属性描述；⑥只输出 Python 代码的约束。框架 API 从 Kea 文档和源码人工整理，示例仍来自独立的 SimpleNote 应用。（pp.7–8）

模型据此输出前置条件、交互和后置断言。论文提出 API 列表可以替换成其他框架，但实际评测是 Kea；可迁移是一种设计可能性，不是已经验证多个执行框架的结果。

### 执行、状态和 oracle 的来源

iPBT 本身不维护新的在线探索记忆，也没有报告生成失败后自动执行反馈修复循环。控件上下文是前期收集的数据，规则是人工提供的预期，代码生成模型负责落地，Kea 负责进入状态、生成输入与检查属性。断言为可执行代码，不代表意图完全正确：若人把长按写成点击，或模型把“选中的卡片”解释成“正在浏览的卡片”，代码仍会偏离原测试意图。

系统读取 Manifest、Activity 名、控件树等信息，但不分析业务源码控制流；不应把“输出测试代码”误写为“白盒分析被测程序”。

## 核心技术与原文案例：为何注释重要，何时仍然失败

在 Amaze 示例中，规则要求枚举列表项，选择名称不含点号的项目，点击，再断言路径包含项目名称。这里模型必须同时完成三件事：将“项目名称”匹配到列表控件，调用正确的枚举和点击 API，保留变量供后置断言使用。已有 PBT 框架能够多次执行这样的规则；iPBT 新增的是从描述到这段规则代码的转换。（Figure 1、Table 2，pp.2、7）

这个例子本身也有边界：用“不含点号”判断目录是所给示例中的启发式，不是 Android 文件系统的可靠定义；原图第 10 行使用 `file_name` 而前面定义 `directory_name`，属于所读版本的变量名不一致。笔记保留其机制，不将图中代码当可直接执行的程序。

语义注释有用但并非真值。原文 Figure 3（p.10）显示：同应用里相似功能控件会匹配错误；AnkiDroid 的注释把“当前选中卡片的编号”解释成“当前正在浏览卡片的编号”，细小的语义差别就会选错控件。

在改写实验中作者给出四类失败（Figures 7–8，pp.15–16）：

- **控件错配**：想点击更多选项，却生成设置按钮标识。
- **逻辑不完整**：OmniNotes 属性缺少“笔记标题存在”的前置检查，进入不满足条件的状态后访问该控件会抛出异常，容易把测试代码问题误认产品问题。
- **冗余逻辑**：多生成一步打开通知页，改变页面后原断言失败。
- **语义偏差**：要求点击压缩文件却生成长按，改变交互语义。

这些失败解释了为什么“代码能运行 / 能触发某个故障”不能单独作为属性正确的标准，也说明 GUI 测试中的 oracle 质量依赖于精确的前置条件和控件语义。

## 实验

### 数据、采集和正确性标准

数据基于 Kea 的八个开源 Android 应用、124 条可执行属性，每条对应一个历史真实功能缺陷。应用覆盖 OmniNotes、Markor、SimpleTask、Amaze、ActivityDiary、AntennaPod、AnkiDroid 和 Transistor。作者先安装对应 APK、到达前置状态并执行原属性，再由一位作者写自然语言描述、其他作者讨论修订。因此这些输入**从已有正确代码反向整理而来**，不等于现实需求文档中随机抽取的 124 条全新意图。（§4，pp.8–9）

界面采集用扩展随机策略的 DroidBot 每应用探索三小时，**再执行数据集提供的 main path**，确保属性相关控件都被采到。论文有意把“探索不到相关页面”和“代码生成失败”分开研究；95.2% 因而以已获得相关界面信息为条件。（p.9）

正确性不仅看是否触发历史故障，还由两位作者独立核对：前后条件的子句和逻辑运算、操作及目标控件、分支是否符合参考属性；允许用不同标识定位同一控件。Cohen’s κ=0.96 是两位评估者的一致性，不是检测准确率。分歧讨论解决。（p.9）

### RQ1：原始描述的生成正确性与模块消融

两种代码生成模型是 GPT-4o、DeepSeek-V3，均设置 temperature=0，依次对 124 个提示生成代码；正文未说明完整多轮重复和方差。temperature=0 也不能当作 API 服务绝对可复现的保证。语义注释模块仍用 GPT-4o mini。（pp.8、10）

| 设置 | GPT-4o | DeepSeek-V3 |
|---|---|---|
| 完整 iPBT | 118/124 = 95.2% | 118/124 = 95.2% |
| 去掉控件功能注释 | 93/124 = 75.0% | 96/124 = 77.4% |
| 作者报告绝对差 | 20.2 个百分点 | 17.8 个百分点 |

六个失败均表现为控件标识错误：五个与同应用内相似功能控件有关，一个来自含糊注释。该消融支持“语义注释对属性生成有帮助”，但没有分别移除截图、页面名称、裁剪图、示例或模型类型，不能声称每个提示成分的独立贡献都被证明。（§4.1，p.10）

### RQ2：用户编写成本

十位软工研究生参与者均至少四年编程经验且熟悉 Python，并非完全不会编程的用户。六个任务按属性复杂度分低中高，每级选两个不同应用属性；用视频提供到达状态、执行功能、验证结果的信息。参与者分两组交错编写自然语言和代码，每个人不为同一属性写两种形式，合计 60 次任务：每种形式 30 次。实验先提供教程，之后另有约 45 分钟的热身练习，正式环境关闭代码补全。（§4.2、Table 3，pp.11–12）

- 人工描述平均编写时间 272.7 秒，手写可执行属性 625.7 秒，作者报告减少 56%。计时包含写作、必要文档查阅、自查，不应默认把前期三小时探索、控件注释生成或全部模型推理时间都计入。（p.12）
- 两种模型均得到 29/30 个正确属性；人工代码为 26/30。模型方案唯一错误来自用户把长按写成点击。去掉注释后 GPT-4o 为 24/30，DeepSeek-V3 为 16/30。（Table 4，p.13）
- 原始 124 个输入的自然语言平均 211.3 字符，代码平均 555.0 字符。字符数度量书写长度，不能直接等同全部认知成本。（Figure 5，p.13）

原文 p.12 将对照条件写成 manual writing property descriptions，与实验设计和表格不符；本笔记按明确的设计记录为**手写可执行属性**，并保留此版本笔误说明。

### RQ3：语义相近的不同表达是否稳定

仅选择 RQ1 已成功生成的 **118 条**，每条先用 Llama-3.1-405B 生成 100 个改写候选，再根据 BLEU / Self-BLEU 的词面差异贪心选择十个，共 1,180 条。因此它们是条件化的改写样本，不是额外 1,180 个独立属性，也没有重新包含原始六个难例。（§4.3，p.14）

GPT-4o 正确 1,034/1,180（87.6%），DeepSeek-V3 正确 1,032/1,180（87.5%）；共同成功 956 条、仅 GPT-4o 成功 78 条、仅 DeepSeek 成功 76 条、共同失败 70 条。移除功能注释后分别为 833（70.6%）、822（69.7%），作者报告下降 17.0、17.8 个百分点。（Figures 6–8，pp.15–16）

GPT-4o 的 146 个失败中，控件错配 69、逻辑不完整 39、语义偏差 27、冗余逻辑 11；DeepSeek 的 148 个失败对应 84、30、25、9。比例的分母是**失败的生成结果**，不是全部改写。BLEU 主要衡量文字相似度，不能证明改写完全保持所有隐含约束；作者讨论也承认改写可能丢失约束。（pp.14–17）

### 未做的实验

本文没有将 iPBT 与其他自动探索器做同预算的新缺陷发现对比，没有报告“新发现—开发者确认—修复”的缺陷数量，也没有证明 118 条正确属性会给任意最新应用带来 95.2% 检出率。结果最直接支持的是既定属性的代码转换正确性和有限用户任务中的编写成本降低。

## 局限

**论文承认（§5，pp.16–17）**：八应用、124 条属性代表性有限；探索可能遗漏控件；由专家整理的描述不一定代表实践者输入；只测两种生成模型；存在模型训练数据暴露顾虑。作者认为描述未公开且模型训练早于 Kea 数据发布，风险较低；本笔记未独立核验训练数据。Web 或其他框架扩展只是讨论。

**我们的观察**：已知 main path 让评测隔离了探索问题，实际使用还需衡量采集成本和未知路径；规则由参考代码整理，和从产品需求首次建立 oracle 的困难不同；语义注释可以自带错误，生成代码仍需意图复核。无注释消融能支持整体模块作用，但不能证明整个系统在所有复杂 GUI 上泛化。

## 和我们课题的关系

### 与 UX testing 的关系

可以借鉴其“给控件补语义，再把候选规则落到具体控件”的阶段划分，帮助将截图中的文字截断候选与布局树控件匹配，并减少错误操作目标。其失败分析也提示：验证动作是点击还是长按、目标是选中项还是当前显示项，都必须明确。本文没有研究遮挡、重叠、溢出检测或滑动消除候选；要应用到 UX-Agent，需要另设计显示属性及主动验证的真实正确性评测。

### 与 GUI testing 的关系

它位于**人类测试意图到可执行 oracle / 属性之间**，直接服务功能测试，而非通用手机任务代理。与 Kea 配套时，前者负责生成属性代码，后者负责反复探索与执行；与自动推断属性的方法相比，iPBT 保留人工选择规则作为规格来源。适合用于比较“发现测试规则”“把规则编成代码”“执行规则寻找违反”三个不同研究贡献。
