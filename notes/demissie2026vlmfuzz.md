# VLM-Fuzz：用按需视觉推理补强多入口递归 GUI 探索

## 一页读懂

| 问题 | 正式期刊版的回答 |
|---|---|
| 旧方法哪里不够 | 普通遍历难为表单生成有意义的数据，弹窗出现后容易遗漏原页控件，从主入口出发也无法覆盖某些外部 Intent 入口。逐步让模型控制全部动作则昂贵且可能忽略隐藏交互。 |
| 本文新增什么 | 将组件多入口启动、按控件复杂度分配时间、递归 DFS 与局部动作记录结合；含文本输入框时调用 VLM 生成数据和动作顺序，其余交互由启发式处理。 |
| 输入与输出 | 输入 APK 和总测试预算；读取 Manifest、运行时控件树与带编号截图；输出动作/转移轨迹及 crash 日志。 |

## 一段话介绍

VLM-Fuzz 用传统搜索组织整个 Android 测试过程，让视觉语言模型只解决输入和局部操作语义。它先从 Manifest 获得 Activity、Service、Receiver 和 Intent 入口，逐个启动可访问组件，按初始控件数量和菜单复杂度分配预算。运行时通过无障碍服务读取控件树；遇到含文本框的页面时，给 GPT-4o 一张带编号截图，请它生成合理输入与动作序列；不含文本框或模型遗漏的控件则由启发式处理。页面变化后递归探索，记录到达路径并回放，以继续尝试被导航或弹窗打断的剩余动作。正式版在 59 个应用上达到平均 46.5% 行覆盖，对 APE 的 44.4% 提升 2.1 个百分点；80 个商店应用中，作者过滤非真实用户可达异常后得到 12 个应用的 52 个独立 crash。它的贡献在于探索和事件生成，没有让模型判断“业务结果是否正确”。

## 关键术语与前提

通用概念可参照[术语表](../glossary.md)。

- **DFS（Depth-First Search，深度优先搜索）**：沿当前分支深入，之后回到分叉处继续其他路径。GUI 中需要真实重放动作才能回到先前状态，不能只移动图中的指针。
- **Multi-entry（多入口）**：不仅从桌面启动图标进入，还根据 Manifest 的 Intent 声明启动公开组件，包括深链、其他应用调用与系统广播入口。
- **Manifest**：APK 中描述组件、权限和入口的配置文件。读取它不是源码控制流分析；本文没有用业务源码或覆盖反馈决定下一步。
- **Intent / intent-filter**：Android 的组件调用消息及组件声明可处理消息的条件。消息的 action、data、extras 决定启动方式和参数。
- **Activity 与 GUI state**：一个 Activity 可含多个页面状态，弹窗、菜单、列表变化都可能在同一个 Activity 内发生。只按 Activity 去重会遗漏局部状态。
- **Transient state（暂态）**：弹窗、对话框、下拉菜单等附着在宿主 Activity 上的局部界面。本文单独处理，避免它们耗尽宿主访问次数。
- **VLM（视觉语言模型）**：同时读截图和文本的模型；本文用于输入与动作生成，不负责 crash 判定。
- **Coverage（覆盖率）**：执行过的类、方法或代码行占总量的比例。测量需插桩，但工具运行本身不要求源码；测量代码覆盖不等于用覆盖指导搜索。

## 动机和贡献

作者列出三个难点：理解复杂动态界面、产生有效输入/事件、协调前后探索以免重复。BookCatalogue 是贯穿例子：初始空书架只有菜单入口；添加书籍需要作者、标题或 ISBN 等有效内容；点击菜单项会离开当前弹窗，剩余选项容易被漏掉。

作者列出算法、与 APE/DeepGUI 的比较、VLM 消融、真实应用 crash 验证和工具公开等贡献。按本仓库分类，核心贡献为 **method**；实验是支持算法的证据，使用 AndroTest/Themis 不等于提出新 benchmark。

## 方法

### 1. 多入口准备与预算分配

工具用 AAPT 解析 APK 的 Manifest，得到组件及其 intent-filter，再尝试启动组件并通过自制无障碍服务获取控件树。组件 `i` 的预算权重为：

`score_i = w_i + 4 × m_i`，`budget_i = total_budget × score_i / Σ score_j`。

`w` 是交互控件数，`m` 是菜单可达控件数。菜单权重 4 是经验值，用于给可能展开额外功能的入口更多时间。这个“复杂度”是初始可见结构的代理，不是实际路径复杂度或代码风险的证明。

### 2. 递归探索与按需模型调用

系统记录当前组件、已访问组件栈和控件—动作清单。组件切换、新控件出现、弹窗覆盖都触发新状态分析。递归访问同一组件设阈值 `τ=2`，用于在 60 分钟预算内限制循环；论文指出更长预算和更高阈值还可能提高覆盖，因此“完整遍历”是策略目标，不是无限状态空间的穷尽保证。

本文将**存在至少一个文本输入框**作为调用视觉模型的“复杂页面”规则。模型收到带编号的交互控件截图、可用动作 API 和单个示例，输出有序动作及文本。例如图书查询先输入作者和书名，再点击搜索。执行后比较控件实际文字和生成文本，若类型限制拒绝输入则换值。模型没有覆盖的控件由后备启发式继续处理；后备文本生成仍可调用文本 LLM，失败才随机填值。因此“非视觉模型分支”不必然意味着完全没有任何 LLM。

### 3. 非视觉交互规则

无文本输入页按点击、滚动、菜单的顺序处理。点击控件先分为中性、正向（Save/Open）、负向（Exit/Cancel），各组内打乱；可能离开页面的按钮放后面。同一行中的 Yes/No/Cancel 等也推迟执行。控件同时支持点击和长按时两者都加入待执行队列；点击带来新状态后，长按仍保留为未探索。

检测到进度指示器后最多等 60 秒，避免把加载时的静止当成终态。局部探索后主动尝试 Menu，并旋转后恢复屏幕，以发现截图上没有直接提示的交互。工具还按声明生成系统广播，支持文档整理出的 187 类广播消息。这些事件扩大的是输入空间，并非独立的正确性检查。

### 4. 弹窗、下拉框和回放

系统先判断 Activity 是否变化；若未变，则比较前后交互控件集合。新布局边界与屏幕边缘的间距超过 150 像素时，启发式判为弹窗。暂态转换不计入宿主 Activity 的访问次数，避免几个对话框就耗尽 `τ`。

- 普通弹窗尽量探索全部动作；关闭后检查宿主是否改变，再决定分析新状态或继续原动作队列。
- Spinner 下拉选择只随机点一个选项后返回宿主，不反复重开遍历所有取值。它控制循环，也主动放弃了部分组合。
- 状态保存为控件集合与属性 `s=(W,P)`，边保存动作。离开页面后回放原路径（排除最后一个离开动作），尝试回到分叉前完成剩余动作；回放失败则结束该局部探索。

这是具体的传统测试机制：模型帮助生成语义输入，搜索栈、动作队列、状态分类与回放负责覆盖组织。

### 5. 实现与测试判据

Python 控制端与 Java 无障碍服务配合，ADB 执行动作。测试本身不依赖源码修改或应用插桩；支持点击、长按、滚动、输入、菜单、切应用、旋转及 Intent，尚缺完整拖动、缩放和多点触控。crash 从 logcat、轨迹和截图人工复核；模型不提供非崩溃 oracle。

## 实验与证据

### RQ1：覆盖是否提高

AndroTest 66 个应用中，7 个因 DeepGUI 兼容或崩溃问题排除，剩余 59 个。每工具/应用 60 分钟、重复 5 次取均值。VLM-Fuzz/APE 使用 Android 9，DeepGUI 使用 Android 2.3.3；每 60 秒用 Emma 取覆盖。不同系统版本是比较限制。插桩用于评估，未用作搜索反馈。

| 均值 | DeepGUI | APE | VLM-Fuzz | 相对 APE 的绝对差 |
|---|---:|---:|---:|---:|
| 类覆盖 | 57.8% | 59.5% | 68.5% | +9.0 个百分点 |
| 方法覆盖 | 48.0% | 49.5% | 53.2% | +3.7 个百分点 |
| 行覆盖 | 43.7% | 44.4% | 46.5% | +2.1 个百分点 |

论文将这些差写作“relative improvements”，但它们等于百分比相减的**百分点**；例如行覆盖通常相对增幅应为 `2.1/44.4≈4.7%`。与 APE 的三项差异都达到论文设定的 `p<0.05`；与 DeepGUI 的行覆盖 `p=0.072`，不能称三项全面显著。

### RQ2：模型与多入口各贡献多少

59 个应用中有 13 个完全没有调用 VLM，其中 9 个行覆盖仍高于 APE，说明传统搜索部分本身有效。对其余 46 个随机取 5 个做视觉消融，完整/去视觉分支的行覆盖分别为 21/7.2、53.8/45.8、59.8/57.2、35.8/33.8、35.2/35.2。作者称提升 5.28%，按表平均差也是 **5.28 个百分点**；样本仅 5 个，不能推出所有应用统一受益。

正式版另外把 VLM-Fuzz 限制为主入口启动：59 个中 28 个行覆盖高于 APE、27 个低于、4 个相等；均值 45.9% 对 45.1%，类覆盖均为 61.5%。这些数来自单入口实验，与主实验 APE 的 44.4% 不完全相同，不能直接相减估计多入口的净贡献。结果说明除多入口外仍有探索收益，但没有逐一移除预算、暂态判断等机制的消融。

### RQ3：商店 crash 与后续验证

80 个 2024 年更新的商店应用中，50 个发生异常终止。两名作者排除模拟器防护触发、私有组件缺少必要参数等不可对应正常使用的异常后，在 12 个应用得到 **52 个独立 crash、23 类异常**。APE 只在这 12 个已由 VLM-Fuzz 找到问题的应用上重跑，得到 14 个 crash，重叠 4 个；这不是对全 80 个应用的无偏横评，APE 可能在其余应用发现自己的独有问题。

作者已向开发者发送日志，但没有提供全部获确认的状态。8 个月后在 2025 年 6 月的新版本上复验：一个应用无新版，排除其 9 个 crash；其余原始 43 个中，10 个仍能复现，33 个未复现，另发现 19 个新 crash。**未复现不等于开发者确认修复**，可能还受版本、数据或外部服务影响。

### Themis：已知缺陷与未记录异常

正式版新增 Themis：79 个 APK 全部测试，但验证脚本仅检查 55 个预期 crash 签名；官方复现脚本在 79 个里仅成功 9 个，暴露控件定位、权限和后端失效。VLM-Fuzz 与 APE 各触发 3 个已记录缺陷，重叠 2 个。另报告 140 对 11 个未记录 crash（重叠 5 个），作者认为多入口绕过失效主页依赖是重要原因。这些历史 APK 的未记录异常不能自动等价为当前最新版开发者确认的新缺陷。

## 局限

**作者承认的限制**（Sections 3.6、4.5–4.7）：动作类型不全；私有模型漂移与费用可扩展性；特定业务知识和时限（例如识谱游戏）仍困难；Android 数据不能代表 iOS；多入口也给对比带来可达范围优势。

**我们的观察**：

1. 仅以有文本框识别复杂页面，会漏掉纯图标、自绘、手势和没有输入框的复杂状态。
2. 固定 150 像素弹窗阈值、菜单权重 4、访问阈值 2 是经验规则，缺少跨设备敏感性实验。
3. 入口直达与实际用户可达路径不同，需继续区分正常公开入口、权限绕过、参数缺失和真实业务缺陷。
4. 新版复验不等于确认修复；“62/80 个 bug 可被正常用户触发”的正文分母与主要 crash 表口径未解释清楚，不能拿它作可靠精确率。
5. 代码覆盖提高不能证明功能或显示正确；没有非崩溃 Precision/Recall，也没有现代多模态 GUI 测试器的统一横评。
6. 正式版仍有统计文字与表格不一致：覆盖差误称相对增幅，属性缺失表与正文也有冲突。主结论优先引用分项原始值和明确计数。

## 和我们课题的关系

### 与 UX testing 的关系

VLM-Fuzz 可以扩大 UX 检查的上游状态范围：从 Manifest 找到不同公开入口，用普通遍历低成本触达控件，在表单卡住时调用模型，再通过回放回到被弹窗打断的页面。进度等待和暂态区分能帮助 UX-Agent 在稳定画面上执行主动滑动验证。

它没有检测截断、遮挡、重叠或溢出。若接入 UX 检查，应在每个稳定状态额外保存截图、完整布局与几何关系，并注意“Spinner 只选一个”“访问两次就停止”等规则可能漏掉特定数据或滚动位置的显示问题。不能直接把其覆盖提升当成 UX 缺陷检出提升。

### 与 GUI testing 的关系

本篇属于**混合测试生成与探索**。与让模型自由探索的 GUI Agent 相比，递归搜索承担状态管理、回放和预算，模型局限在输入语义与局部动作组合；这是传统 GUI testing 与模型能力结合的具体例子。它读 Manifest 和运行时结构，但没有源码控制流、符号路径或在线覆盖反馈；因此适合标为“不要求源码的结构与视觉辅助探索”，不应归入源码驱动路径分析。

与 GraphDroid 的分级执行思路有共性，但分流规则不同：GraphDroid 按意图步数，VLM-Fuzz 按有无文本输入框。两篇可用于比较“什么时候值得调用模型”，仍需另外配上 Kea、PropGen、差分或 UX 几何 oracle 才能判定非崩溃错误。
