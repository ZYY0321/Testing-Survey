## 一段话介绍

没有报告bug可能来自三个完全不同的失败：Agent未到目标状态；到达后操作不对或不足以暴露异常；异常已出现却没有识别。GUITestScape使每次运行从可恢复环境开始，并提供应用相关正确性条款。GUIJudge先在长轨迹中选出相关证据，再按显示/交互两类分别验证，最后检查Agent是否报告同一个异常。它用预期条款代替有限缺陷答案的逐条匹配，从而能评价轨迹中出现的新异常。

## 关键术语

- **Scenario，场景**：应用数据、系统设置等准备好的初态，可在每轮前恢复。
- **Test basis，测试依据**：来自应用设计和业务资料的正确性条款。它规定应发生什么，不规定唯一点击路径。
- **Open-set，开放集合**：按条款判实际观察，而非只接受预先列出的508个缺陷描述。
- **Reach / Trigger / Detect**：到达前置状态／动作确实暴露交互缺陷／Agent正确识别报告。静态显示缺陷的Trigger标为不适用。
- **轨迹**：依时间记录的截图、动作、状态和报告，判交互错误需要动作及其后果。

## 贡献

一是将真实报告实例化为可复位、带依据、多入口的交互测试场景；二是GUIJudge的证据检索和分类验证流程；三是用过程指标诊断现有模型，并将验证器接回Agent以改善检测。任务生成、边界输入设计与覆盖规划作为上游输入，未作为本基准的主要评价对象。

## 方法与核心技术

### 1. 从报告建立缺陷分类与可重复场景（§3）

作者从公开issue与bug报告收集真实Android问题，显示类细分Content Rendering（CR，内容渲染）和Element Layout（EL，元素布局）；交互类细分Operation No Response（ONR，无响应）、Navigation Logic Error（NLE，导航逻辑错误）、Unexpected Task Result（UTR，结果不符）。

将问题所需应用数据、系统设置等打包成可恢复场景。每轮恢复前置条件，使比较不受上一轮数据遗留影响。508个缺陷汇入82场景，同一场景支持多个任务，总384个；任务可以以不同入口和指导粒度接近同一风险功能。显示约47%、交互约53%。

### 2. 建立场景级正确性条款（§3.2.2，附录A）

B包含多条应用相关准则，每条c有前置条件、触发条件和预期证据。导航任务提供要测试的功能意图，条款提供如何判断结果的依据；两者职责不同。任务不泄露具体缺陷和标准动作序列，允许Agent探索不同路径。

### 3. 第一阶段：选择条款并检索轨迹（§4.3.1，算法1）

输入τ、ρ、g、B。Retriever先基于任务和观察选择适用条款c*，再从整条轨迹定位满足前置条件的步骤。找到则Reach=true；找不到则停止在暴露前。接着沿时间向后找对应动作/事件与结果状态，形成候选片段。

算法中的语义匹配由模型完成，不是树哈希相等。附录表10的具体检索提示输入关键点、当前截图和XML，强调判断是否进入相关页面或功能，不要求精确像素、文本与预设答案一致；只有明显无关App、页面、错误页、启动页或缺少核心内容时判不匹配。输出JSON `matched`和`reason`。候选片段交给验证器，检索本身只建立上下文证据。

### 4. 第二阶段A：显示验证器逐状态检查（§4.3.2，表11）

输入一张截图及页面XML摘要，XML辅助解释结构，主要依据已经可见的内容。提示将缺陷限制为清晰、可描述、可定位的异常：CR包含破图、空白、乱码、null/None/undefined、文字被遮挡裁切；EL包含同类元素错位、尺寸异常、重叠、越出容器和异常空槽。

输出包含`has_defect`以及每个异常的`type`、`evidence`、`location_hint`、`reason`。位置是粗描述，不是精确坐标框；证据应写实际可见事实，并优先说明对象与同类元素或边界的关系。此流程没有追加滑动来核实内容可恢复性。

算法将显示Trigger置为⊥（不适用）。状态被验证为违背所选条款后，再与ρ核对步骤和缺陷描述；二者一致才计Detect=true。

### 5. 第二阶段B：交互验证器累积历史并检查当前转移（表12）

每个候选片段先清空历史H，再按时序加入动作和状态。对当前步输入任务候选、历史实际观察、thought/action/target/hit、pre-state/post-state和前后两张截图。`hit`表示动作是否命中目标，是排除执行错误的重要输入。

提示分别检查无响应、导航错误、任务结果不符，并明确：只归因当前步；历史问题仅作上下文；点错、输入不符、漏步骤或未到目标通常属于Agent错误。只有合理动作已经命中执行而App结果仍异常，才确认交互缺陷。输出JSON包含类别、当前步号、原因、实际效果。

验证出缺陷则Trigger=true，再核对ρ是否报告这个异常，决定Detect。历史H使多步结果具有上下文，而当前步约束避免把早先异常反复归给后续所有动作。

### 6. 过程输出怎样形成诊断

```text
恢复场景 → Agent执行并记录完整轨迹/报告
→ 按任务选正确性条款 → 检索相关片段
→ 状态验证（显示）或转移验证（交互）
→ 比较Agent报告 → 输出Reach / Trigger / Detect
```

例（自编）：进入语言设置并选择中文，界面仍为英文。未进入设置是Reach失败；点错选项属执行问题；确实切换后仍英文是UTR已触发；若Agent说切换成功而不报告，则Trigger成功、Detect失败。这个分解能说明改进应该落在导航、动作还是判错。

## 实验与结果

### 人工真值如何建立

附录C.1用真实Agent运行轨迹建立参照集，两位有Android测试经验者独立按任务、条款、轨迹和报告标Reach/Trigger/Detect，不看GUIJudge预测。裁决前原始一致率98.51%/97.03%/95.05%，Cohen κ为0.9545/0.9391/0.9010；分歧讨论后形成最终标签。

### 表1：评测器可靠性与消融（百分数）

| 方法 | 阶段 | Overall Recall | Overall F1 |
|---|---|---:|---:|
| GUIJudge | Reach | 100.00 | 97.87 |
| GUIJudge | Trigger | 100.00 | 97.12 |
| GUIJudge | Detect | 97.12 | 93.95 |
| 去掉轨迹检索 | Detect | 76.92 | 74.23 |
| 去掉分类验证器 | Detect | 80.77 | 87.05 |
| GUITester评测器 | Detect | 73.21 | 81.19 |
| Rule-based | Detect | 69.64 | 80.41 |

原表对五种缺陷逐类列分；GUITester及规则评测器不支持显示类，比较时需看适用列。原表同时在显示列展示Trigger数值，而§4.2/算法明确显示Trigger不适用，此处保留定义与表格呈现差异，不给静态异常补造触发动作。

RQ2用统一评价器比较Agent，最强模型最终检测Recall57.02%，显示缺陷是显著瓶颈；97.12%是Judge相对人工参照的表现，57.02%是Agent探索发现表现，二者任务与分母不同。RQ3将验证器嵌入执行流程，报告无需重训即可改善最终检测。

附录C.2说明信息访问区别：RQ1/2评分器有完整轨迹、报告、任务及场景依据；RQ3执行时验证器只有任务指令、GUI观察和动作历史。因此执行增强结果不能解释为直接向Agent提供预置缺陷答案。

## 局限与研究用途

正确性依据和场景准备仍需人工；检索匹配可能过宽或遗漏关键时刻；显示提示仅看已见内容，正常滚动露边仍需具体规则或操作补证。检索与验证器错误应分别检查。源码/数据包可获取性本轮未确认，未运行环境。

对显示检测可借：保留截图、树摘要、对象位置、动作命中和前后状态；明确区分候选、确认与Agent报告。对树复核研究，需要另行定义字段语义、裁切容器与字形证据，本篇提供的是评价框架与模型验证提示。
