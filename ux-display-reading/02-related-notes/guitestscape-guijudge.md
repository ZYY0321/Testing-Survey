# GUITestScape 与 GUIJudge：把“没找到 bug”拆成不同失败原因

**所读版本**：arXiv:2605.29532v2，2026-10-29。预印本；不将正式会议录用状态视为已核实。本文为原创中文解释，不是译文。核查范围为公开 HTML 方法、主要实验及附录结构，状态 `extracted / selective`；未运行基准。

## 先理解它解决什么

GUI 测试 Agent 没有报告错误，至少有三种可能：没有走到目标页面；走到了但没有执行暴露错误的操作；错误已经出现但没有识别。只统计最终找到多少 bug，会把这三类能力混在一起。GUITestScape 提供可重复的测试场景，GUIJudge 则分析已有测试轨迹和报告，判断失败发生在哪个阶段。它首先是**评测资源与评测器**，不是一个专门解决文字截断的检测算法。

论文将缺陷分成显示与交互两大类。显示类包括内容渲染异常、元素布局异常；交互类包括操作无响应、导航逻辑错误、任务结果不符。不要把这些类别全部称为视觉 UX 缺陷：按钮没响应与文本显示不全，证据要求不同。

## 输入是什么，预期从哪里来

每个评测案例不仅有应用和缺陷，还包含可恢复的初始环境、应用相关的测试依据，以及多个导航任务。测试依据（test basis）写清在什么条件下、什么操作或事件发生后，应当观察到什么；它来自应用的开发者材料。评测不是让模型只凭常识猜应用本应怎么工作。

同一案例的不同任务可以从不同入口接近风险区域。因此导航路径没有唯一答案；评分应检查真实证据，而不是要求 Agent 机械重放某条标准路径。可恢复环境则用于控制应用数据、系统设置等前置条件，使不同测试运行有可比性。

公开版本报告：61 个 Android 应用、508 个预置缺陷，组织为 82 个可恢复场景和 384 个导航任务。应用、缺陷、场景、任务不是一一对应，不能把 508 写成截图数或应用数。

## GUIJudge 怎样工作

第一步检索证据。长轨迹里大量步骤与目标无关，评测器先选择适用的正确性条款，再提取对应状态或动作片段。进入正确上下文支持 Reach 判断；检索到片段本身还不等于证实缺陷。

第二步分类型验证。显示验证器检查界面状态是否违反适用条款；交互验证器检查动作与后续状态之间的关系。最后还要核对 Agent 的报告是否与已验证证据一致，避免把“模型说有问题”当成确实检测成功。

**容易误读的地方**：正文把 Trigger 单独用于交互缺陷。不能为了统一流程，给每张有问题的静态截图强行编造一个 Trigger 动作。表格对各类别统一呈现阶段结果，也不能改变正文的任务定义。

## 用一个例子理解（自编）

设一个报名应用规定：调整字号后，确认页面仍应让用户读取完整注意事项。Agent 在首页徘徊，是没有 Reach；已进入确认页并看到裁切文字，却只说“报名成功”，是异常已呈现但没有 Detect。若研究任务另要求在该页主动切换大字号再检查，则还应单独记录设置是否成功，不过这是新的实验设计，不能说原文已有专门的截断触发协议。

评测器也不能看到某句文本在截图里不完整，就推断其余文字不可获得。正常滚动、点开详情、业务省略等都可能改变正确性解释。对截断任务，需要具体说明读取要求、可接受入口与可恢复内容，而不是仅把通用 GUIJudge 接上去。

## 实验怎样读

论文分别评价评测器与人类标注的一致性、现有 Agent 的探索测试能力，以及把验证器接入 Agent 后的变化。评测器 Detect 召回率报告为 97.12%，这一数字是**评测器识别测试结果的表现**，不是 Agent 在全应用中自动找出 97.12% 缺陷，更不是文字截断召回率。表格中 Agent 的最终发现能力与评测器可靠性使用不同实验对象，不能混成排名。

消融实验去掉轨迹检索或类型专用验证器后表现下降，支持“先找对证据、再按证据类型判错”这一设计。它并未证明仅采用多 Agent 角色划分就能提高检测，也没有给出 HarmonyOS 截断数据上的结论。

## 对截断与 UX 树研究的用途

最值得借鉴的是评测拆分：候选页面是否到达、干预是否生效、异常是否出现、报告是否准确应分别记录。这样可以发现一次滚动失败究竟来自执行器点错位置，还是检测器错误理解了裁切。

但该论文不是“截图与控件树字段如何对应真实裁切”的机制研究，也没有定义 `bounds`、祖先裁切、实际字形边界的关系。用树复核截断时仍需独立标注结构证据。评测器的开放集合设计也不等于不需要正确性依据：应用相关条款依然是关键输入。
