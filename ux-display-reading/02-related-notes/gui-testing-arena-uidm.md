# GUI Testing Arena 与 UIDefectMocker：先分清三种数据

**版本与证据**：GUI Testing Arena: A Unified Benchmark for Advancing Autonomous GUI Testing Agent，arXiv:2412.18426v1，2024-12-24。本文核查公开方法、数据构造章节和官方仓库，`selective / extracted`，不等于完成复现。UIDefectMocker 是相关工具，不能将工具、论文和数据集视为同一资产。

## 它想评价什么

论文把 GUI 自动测试拆成测试意图生成、任务执行、缺陷检测三个子任务。生成“检查下单流程”的意图，准确点击完成流程，判断结果存在错误，是不同能力。它提供统一表示和评测框架，而不是专门的文字裁切 oracle。

作者使用操作前状态、动作、操作后状态的三元组表达证据；静态显示问题允许空操作。这有助于保存“在哪个状态、做了什么、发生什么”，但数据结构本身不会告诉人应用正确结果是什么。

## 三类数据的区别决定用途

| 数据来源 | 发生在什么地方 | 可以支持什么 | 不能直接推断什么 |
|---|---|---|---|
| 真实应用缺陷 | 原有程序运行 | 真实问题与复现路径研究 | 未经复现不能确认每条报告仍有效 |
| 程序注入缺陷 | 源码或 APK 改动后运行 | 可控触发、交互与结构采集 | 人工注入不自动代表自然缺陷分布 |
| 合成缺陷 | 已有截图或轨迹后处理 | 图像检测训练、可控视觉测试 | 原程序和树已同步发生相同错误 |

论文三类数据共同出现，不能看到其中有可执行注入，就把所有合成截图称为运行时 bug。

## UIDefectMocker 究竟能拿来干什么

官方仓库提供显示缺陷模拟工具，利用截图与 XML 布局信息确定元素等区域，再构造图像异常。公开的是工具代码，仓库带 MIT 许可；没有在本次工作中运行并核对每种注入器。

最重要的边界是：**读取 XML 定位图像编辑区域，不等于修改应用布局树**。输入时树可能准确描述原始页面；生成后图片中某段文字被遮去，原树仍可能描述完整显示的正常程序。因而该工具对视觉基线有用，对“截图与真实树一致的裁切数据”只能作为候选构造思路，不能直接当成完成品。

## 自编例子：同一外观，两种数据资格

原界面有一个 200 像素宽的姓名框。方案 A 在图片右侧盖一块背景色，让最后几个字消失；方案 B 修改真实程序，使固定宽度容器裁切溢出的文本，然后运行并采集树。

两张图可能看起来相同，但 A 没有真实触发页面，滑动也不可能改变这张静态图；B 可以研究祖先容器、滚动能力与内容恢复。若测试方法要读取树、执行操作验证可恢复性，就必须把 A 与 B 分开评估。这个区分来自任务证据要求，不表示合成图像一概无效。

## 实验读法与限制

原文按三个子任务分别报告指标，并将缺陷与正常样本的召回分开，防止总回答“没有错误”的模型获得误导性的印象。其 2024 年模型表现只反映当时配置；不宜用来评价 2026 年最强模型或当作 UI-Lens 同协议成绩。

对截断研究，更值得查看原文 §3 的构造方法与附录缺陷示例，而非逐项比较旧模型分数。需要进一步检查具体合成算子是否造成边缘伪影、是否改变文字语义、训练与测试是否泄漏同源页面。以上是使用数据时的审查问题，不是本次已证实全部存在的错误。
