# 相关工作：桌面智能体的"受阻"与观察/执行通道选择

本文为"AX 树残缺导致智能体受阻，模型能否察觉并切换通道"这条线做会前相关工作调研。AX 树指操作系统辅助功能接口（accessibility API）暴露出的界面元素树，macOS 上叫 AX，Windows 上叫 UIA，Linux 上叫 AT-SPI，网页上对应 DOM 或浏览器的 accessibility tree。"通道"指智能体可用的观察方式与执行方式：读 AX 树、看截图、按 AX 元素操作、按坐标点击、键盘快捷键、AppleScript 脚本、shell 命令，以及应用 API 或 MCP 工具。

**核实口径。** 下列 37 篇每篇都打开过 arXiv 页面（或 arXiv HTML 全文）以及会议或期刊的官方页面（OpenReview、ACL Anthology、NeurIPS/ICML/ICLR 论文集、ACM DL、AAAI）中至少一个，核对了标题、第一作者单位、编号或 DOI、发表场合。没有找到官方录用页面的，写"arXiv 预印本"加月份；只有第三方或作者仓库声称录用的，列入第 4 节存疑清单。"阅读深度"一栏写明：**仅读摘要**，或**摘要加正文关键词检索**（按关键词在 HTML 全文里定位到相关段落和表格，没有通读）。没有一篇做过复现。AnTrap 与 D-GARA 已有全文笔记（[AnTrap 笔记](../notes/gan2026antrap.md)、[D-GARA 笔记](../notes/chen2026dgara.md)），这里只在对比中引用，不计入 37 篇。

检索日期为 2026-11-02。arXiv 编号以 26 开头的是 2026 年的论文，其中几篇（HCU、HybridCUA、"Screenshots or Tools?"）发布于近两个月，后续可能有修订。

## 1. 一页结论

### 已经被做过的部分

1. **"AX 树不完整"本身已是公认事实，并已有粗粒度统计。** Screen2AX 统计了 99 个热门 macOS 应用，只有约 36% 提供完整的辅助功能信息，约 18% 完全没有；随机抽的冷门应用里完整的只有约 33%。UFO2 在 WindowsAgentArena 上把超过 62% 的失败归为"控件检测失败"，原因是 LibreOffice 等第三方应用不遵守 UIA 规范。OSWorld 和 UGround 也明确写到 AX 树并非所有软件都支持、噪声大、不完整。所以"AX 树残缺"不能当成我们的新发现，第一层的价值只能在更细的分类上：按窗口、按控件类型、按故障类型（控件缺失、角色错、状态值缺失、空容器、观察窗口绑错），并覆盖国产和自绘界面应用。
2. **截图、结构树、两者结合的对比已在主流基准上做过，结论是"组合通常最好、但因模型而异"。** OSWorld（GPT-4V 只看截图 5.26%，截图加 AX 树 12.17%）、VisualWebArena、WindowsAgentArena（UIA 加像素检测器比只用像素检测器高 15% 到 57%）都给出了这一结论。更进一步，"Do GUI Agents Believe Their Eyes?" 专门测了"像素和结构树说法不一致时模型信谁"：模型看图本身能看对，但遇到冲突时有 30% 到 75% 的情况跟着结构树走，面对过期的结构树最多 88% 跟着旧值走。这直接覆盖了"AX 树出错时模型会被误导"这一判断。
3. **"GUI 操作与代码、API、命令行混用"已是热门方向，而且已有工作专门训练"何时切换"。** 系统层面有 UFO2、CoAct-1、Agent S3；训练层面有 ComputerRL、UltraCUA、ToolCUA、HybridCUA；基准有 MCPWorld、OSWorld-MCP、MAS-Bench、MacAgentBench。最接近我们第二、三层的是 2026-10-30 发布的 HCU（Microsoft Research），它把"程序、AX、GUI"三个通道并列交给模型自选，在 macOS 上有原生实现，并在正文里讨论了"自绘内容没有 AX 元素、AX 覆盖不全时用截图补"。"模型不会用好多通道"也已被量化：OSWorld-MCP 中工具调用率最高只有 33.3%；"Screenshots or Tools?" 发现推理模型在可用工具的任务里只有 23.9% 真的调用了工具；HybridCUA 发现直接给现有模型开放 shell，四个模型在 OSWorld 上反而掉 2.5 到 11.5 个百分点。
4. **运行中异常、受阻、错误恢复的评测和训练已经很多。** 注入式鲁棒性评测有 AnTrap、D-GARA、GUI-Robust、GhostEI-Bench、弹窗攻击；"察觉自己出错"的度量有 RoTS 的错误察觉率（Error-Awareness Rate）和 VeriGUI 的失败识别基准；"察觉不确定时换一种做法"的形式在 OS-Kairos 中出现过（换成向人求助）。

### 还没被做过的空白（在本次检索范围内）

1. **没有工作把"通道坏了"作为切换的条件。** 现有混合通道工作切换的理由都是效率或能力：工具步数少、脚本更稳、GUI 序列太长。它们在 OSWorld、WindowsAgentArena、OSWorld-MCP 上按总成功率和步数报告，没有按"默认通道是否可用"分层。HCU 虽然讨论了 AX 覆盖不全，但只作为设计考虑和个例（GIMP 中输入框的新值没出现在 AX 反馈里，模型截图确认后继续用 AX），没有构造受阻任务、没有按 AX 故障类型统计切换行为。依据：CoAct-1、UltraCUA、ToolCUA、HybridCUA、HCU、OSWorld-MCP。
2. **现有鲁棒性基准的"受阻"几乎都是研究者从外部注入的干扰，不是应用自带的辅助功能缺陷，而且集中在 Android 和网页。** AnTrap 注入弹窗、遮挡、坐标偏移、动作丢弃；D-GARA 用独立 APK 弹出中断；GUI-Robust 收集登录页、验证码、广告和网络断开；GhostEI-Bench 和弹窗攻击注入欺骗性界面元素。"应用自身 AX 残缺、在真实 macOS 桌面应用中自然出现"的受阻，没有被系统构造成配对任务。依据：AnTrap、D-GARA、GUI-Robust、GhostEI-Bench、Attacking VLM Computer Agents via Pop-ups。
3. **没有工作把"当前窗口 AX 是否可用"的诊断作为运行时输入，并比较强弱模型从中获益的差异。** 最接近的三篇都不是这件事："Do GUI Agents Believe Their Eyes?" 的一致性门控检测的是像素与结构冲突，且没有比较强弱模型收益；UFO2 观察到 GPT-4o 主要靠 API 从控件检测失败中恢复、o1 更多用 API 走捷径，提示模型强弱与通道用法有关，但不是诊断实验；OS-Kairos 预测每步置信度以决定是否求助人，切换对象是人而不是另一个执行通道。
4. **AX 质量的自动检查与跨应用泛化是空白。** Screen2AX 走的是"从截图重建 AX 树"的补全路线，UFO2 把 UIA 和视觉检测结果合并去重，二者都没有输出"这个窗口的 AX 可不可信"的判断，也没有在未见过的应用上评估这种判断。依据：Screen2AX、UFO2、HCU（只是"标出缺失信息、允许模型自己要截图"）。
5. **训练"聪明选通道"的数据都以效率为监督，没有以通道失效为监督。** ToolCUA 把 GUI 轨迹中可替换的片段改写成工具调用，HybridCUA 把 GUI 轨迹改写成等价 shell 命令，UltraCUA 从文档和代码抽工具，奖励都是成功率加路径效率。没有工作构造"默认通道不可用、必须换通道"的训练数据。另外这些训练工作都在 Ubuntu 的 OSWorld 上，macOS 只有 HCU 附录的 28 题和 MacAgentBench。依据：ToolCUA、HybridCUA、UltraCUA、ComputerRL、HCU、MacAgentBench。

**一个需要正面回应的风险：** HCU 和我们的第二、三层在"通道集合"上高度重合（程序、AX、GUI，macOS 原生实现）。我们必须讲清区别：HCU 的问题是"给模型统一接口、让它自选"，评测的是总分和成本；我们的问题是"默认通道坏了时，模型能否察觉并换到能走通的通道"，评测对象是受阻条件下的察觉与切换。

## 3. 逐篇条目

### 3.1 观察模态对比与 AX 树可靠性（12 篇）

#### OSWorld
- **标题：** OSWorld: Benchmarking Multimodal Agents for Open-Ended Tasks in Real Computer Environments
- **第一作者单位：** The University of Hong Kong
- **编号与场合：** arXiv:2404.07972；NeurIPS 2024 Datasets and Benchmarks Track，DOI 10.52202/079017-1650
- **链接：** https://arxiv.org/abs/2404.07972 ；https://papers.nips.cc/paper_files/paper/2024/hash/5d413e48f84dc61244b6be550f1cd8f5-Abstract-Datasets_and_Benchmarks_Track.html
- **阅读深度：** 摘要加正文关键词检索（§4.2 结果段与 Table 5）
- **做了什么：** 在真实虚拟机里构造 369 个 Ubuntu 任务和 43 个 Windows 任务，每题有初始化配置和执行式判分脚本。系统比较了四种输入：只给 AX 树、只给截图、截图加 AX 树、Set-of-Mark（在截图上给可交互元素画框编号）。GPT-4V 只看截图为 5.26%，截图加 AX 树为 12.17%；纯文本模型只读 AX 树时 GPT-4 为 12.24%；人类为 72.36%。作者写到 AX 树"并非所有软件都支持"，并且叶子节点就可能有上万个 token。
- **和我们的关系：** 它是"截图与 AX 树组合通常更好"这一结论的源头之一，也是后续几乎所有混合通道工作的评测平台。区别：它按模型平均报告，不区分哪些窗口 AX 可用、哪些不可用；我们要回答的正是"AX 不可用的那些窗口里发生了什么"。

#### VisualWebArena
- **标题：** VisualWebArena: Evaluating Multimodal Agents on Realistic Visual Web Tasks
- **第一作者单位：** Carnegie Mellon University
- **编号与场合：** arXiv:2401.13649；ACL 2024（arXiv 评论栏标注 Accepted to ACL 2024）
- **链接：** https://arxiv.org/abs/2401.13649
- **阅读深度：** 摘要加正文关键词检索（§5 结果段）
- **做了什么：** 910 个需要看图的网页任务，比较纯文本模型读 AX 树、AX 树加图片说明、截图加 AX 树、截图加 Set-of-Mark。GPT-4V 从截图加 AX 树的 15.05% 提到 Set-of-Mark 的 16.37%；在图片密集的分类广告和论坛网站上提升更大，作者解释为 AX 树不足以区分空间上挨得很近的元素。人类为 88.7%。
- **和我们的关系：** 说明"AX 树信息不足时需要视觉补充"在网页上早已被观察到。区别：网页 AX 树由浏览器根据 DOM 生成，质量远比桌面国产应用稳定；它没有研究 AX 树错误或缺失的情形。

#### Windows Agent Arena
- **标题：** Windows Agent Arena: Evaluating Multi-Modal OS Agents at Scale
- **第一作者单位：** Microsoft
- **编号与场合：** arXiv:2409.08264；ICML 2025（PMLR v267, pp.4874–4910）
- **链接：** https://arxiv.org/abs/2409.08264 ；https://proceedings.mlr.press/v267/bonatti25a.html
- **阅读深度：** 摘要加正文关键词检索（§4 结果段、Table 4、附录 UIA 树说明）
- **做了什么：** 把 OSWorld 框架移植到 Windows，150 多个任务，提出智能体 Navi。屏幕解析比较了 UIA 树、开源像素检测器、OmniParser 及其组合。最好配置（UIA 加 OmniParser，GPT-4V-1106）为 19.5%，人类 74.5%。在像素检测器上加 UIA 标记，OmniParser 提升 57%，开源检测器提升 52%，专有像素模型提升 15%（原文写 boosts by，从数值看应为相对提升）。作者也指出查询 UIA 树可能要几秒到几分钟。
- **和我们的关系：** 给出了"结构树与像素检测互补"在 Windows 桌面上的量化证据，也提示 AX 查询本身可能慢到不可用。区别：没有按应用或控件统计 UIA 失效，也不测模型何时该放弃 UIA。

#### macOSWorld
- **标题：** macOSWorld: A Multilingual Interactive Benchmark for GUI Agents
- **第一作者单位：** Show Lab, National University of Singapore
- **编号与场合：** arXiv:2506.04135；NeurIPS 2025（poster）
- **链接：** https://arxiv.org/abs/2506.04135 ；https://openreview.net/forum?id=YJxGJP8feU
- **阅读深度：** 摘要加正文关键词检索（实验设置与附录 SoM 消融）
- **做了什么：** 第一个 macOS 交互式基准，202 个任务、30 个应用（28 个 macOS 独占），五种语言，并有欺骗性弹窗的安全子集。评测六个智能体，专有电脑使用智能体超过 30%，开源轻量模型低于 5%。所有主实验只给最近 3 张截图，不给 AX 树；只有 GPT-4o 的 SoM 消融用 OmniParser v2 生成标注，成功率大约翻倍。两个最强模型在欺骗性弹窗上被骗率约 70%。
- **和我们的关系：** 同为 macOS，但它完全绕开 AX 树，用纯截图评测，因此无法揭示 AX 残缺带来的问题。我们的应用（WPS、剪映、Blender 等）也不在其以苹果自带应用为主的任务集里。

#### UGround
- **标题：** Navigating the Digital World as Humans Do: Universal Visual Grounding for GUI Agents
- **第一作者单位：** The Ohio State University
- **编号与场合：** arXiv:2410.05243；ICLR 2025 Oral（arXiv 评论栏）
- **链接：** https://arxiv.org/abs/2410.05243
- **阅读深度：** 仅读摘要
- **做了什么：** 主张智能体完全用视觉感知、直接做像素级操作，理由是 HTML 和 AX 树"常带来噪声、不完整和额外计算开销"。构造了 130 万张截图、1000 万个元素的视觉定位数据，训练 UGround；在六个基准上，只用视觉的智能体超过了使用额外文本输入的现有智能体，定位准确率最多高 20 个百分点。
- **和我们的关系：** 代表"放弃 AX、全走视觉"的路线，是我们必须回应的对立观点。我们的论点应是：AX 在可用时省 token、精确、能直接执行，问题不在于用不用 AX，而在于何时它不可用、能否及时察觉。

#### Screen2AX

#### Hybrid Computer Use（HCU）

- **标题：** Don't Act Blindly: Robust GUI Automation via Action-Effect Verification and Self-Correction
- **第一作者单位：** Beijing University of Technology（百度实习期间完成）
- **编号与场合：** arXiv:2604.05477；ACL 2026 Long Papers，pp.28924–28941，DOI 10.18653/v1/2026.acl-long.1335
- **链接：** https://aclanthology.org/2026.acl-long.1335/
- **阅读深度：** 摘要加正文关键词检索（问题定义与效率分析段）
- **做了什么：** 指出现有智能体默认环境响应是确定的、不检查上一步是否成功，在网络延迟、渲染延迟和系统中断下会出现未察觉的动作失败、重复无效动作和误差累积。提出"思考、验证、动作、预期"循环：每步预测动作的预期效果，下一步用画面验证预期是否实现，失败时转入诊断和恢复。用合成失败轨迹做稳健 SFT，再用非对称验证奖励做 GRPO；基于 AndroidControl-High 构造失败识别与纠正基准。3B 与 7B 模型减少了"失败循环"，7B 模型每条轨迹的 token 数甚至低于 3B 基座，因为更早跳出循环。
- **和我们的关系：** 是"循环检测"方向最直接的工作，"重复无效动作"正是我们观察到的受阻表现（在坏掉的 AX 上反复点击）。区别：恢复手段仍限于同一 GUI 通道内重试或改动作，不换通道；失败来源是合成的环境噪声。

#### RoTS（Recovering Policy-Induced Errors）
- **标题：** Recovering Policy-Induced Errors: Benchmarking and Trajectory Synthesis for Robust GUI Agents
- **第一作者单位：** Alibaba Cloud Computing
- **编号与场合：** arXiv:2605.29447；ICML 2026 Spotlight，PMLR v306
- **链接：** https://proceedings.mlr.press/v306/bu26b.html ；https://arxiv.org/abs/2605.29447
- **阅读深度：** 摘要加正文关键词检索（基准定义与 Table 2 结果段）
- **做了什么：** 评测与数据两方面。GUI-RobustEval 有 1,216 个可执行用例，覆盖 11 类错误、4 种错误深度：给一段含错误的前缀轨迹，把环境重置到错误发生后第几步，让智能体接管完成任务；报告"错误察觉率"和"出错后成功率"。RoTS 用树状在线合成：在成功分支的脆弱状态处分叉发现新错误，在失败分支从错误状态重放并合成恢复步骤，共 80 万条数据。RoTS-7B 与 32B 的察觉率为 51.9% 与 58.8%，平均出错后成功率为 34.2% 与 40.3%；32B 在 OSWorld 上 47.4%。作者发现察觉与恢复正相关但不等价，GPT 5.1 和 Jedi-7B 加 GPT 5.1 察觉率相近（约 34%），恢复成功率差别很大。
- **和我们的关系：** "察觉率与恢复成功率分开报告"正是我们第二层需要的指标设计，可直接借鉴；"把环境重置到出错后的状态再让模型接管"也可用于构造受阻任务。区别：错误由模型自己造成，环境通道是健康的。
