# 方向分析：四个方向，范文怎么写，我们的假设是什么，先验证什么

> 类型：核心 ｜ 归属：2026-10-30 起的论文方向 ｜ 状态：维护中；每个假设验证完，在对应行后面补结论

范文的数字都来自本仓库的精读笔记（`../notes/` 下，逐页读过原文）。实验编号对应 [待跑的实验.md](待跑的实验.md)。

## 先看全貌

| 方向 | 范文 | 我们一句话 | 最先要验证的假设 | 先跑 |
|---|---|---|---|---|
| SE1 视觉问题检测（截断 + 开合） | ReFLAIR（FSE 2026） | 先让模型给候选，再滑一下、折一下复核 | 只看截图的大模型会误判，交互复核能明显减少误判 | SE1-a、SE1-b |
| 方向一（SE2）以 UX 问题为目标的探索 | GraphDroid（ASE 2026） | 不拼覆盖率，比同样预算下找到多少不同 UX 问题 | UX 问题集中在某几类状态，而现有工具很少走到这些状态 | SE2-a、SE2-b |
| 方向二 从轨迹长出功能状态图 | PropGen（ASE 2026） | 按功能认页面，自动长出 spec，用它衡量真实覆盖 | 按布局认页面和真实功能对不上，而且会高估覆盖 | G-a |
| AI 篇 结构树和画面对不上（布局树可靠性是三条线共用的基础，见 AX-1） | arXiv 2607.04334（2026） | 原生 App 里天然的不一致，加上省调用的通道选择 | 不一致常见、出现在动作目标上的比例适中、能提前预判 | AX-1、AX-4 |

四个方向的关系：SE1 提供判定器；方向一用这个判定器数"找到多少问题"；方向二的功能状态图给方向一当记忆；AI 篇单独成篇，同时给 SE1 加一节"布局树什么时候不可信"。

**怎么读下面每一节**：先看范文从上到下每一部分写了什么；再看"对标我们"那张表；最后看"假设"。假设分两种，动机假设（为什么要做，背景和空白）和贡献假设（做出来会怎样）。每个假设后面写了要什么证据、哪个实验去拿、什么结果出来就放弃。**在实验跑出来之前，所有动机和贡献都只是假设，不能写进摘要。**

## 一、SE1 视觉问题检测：范文 ReFLAIR

*ReFLAIR: Detecting Responsive Layout Reflow Issues using Multimodal Generative AI*，FSE 2026，UC Irvine。笔记 [`../notes/he2026reflair.md`](../notes/he2026reflair.md)。

### 范文从上到下

| 部分 | 它写了什么 |
|---|---|
| 动机 | 网页从宽屏变窄屏，导航收进菜单、内容移到视口外，这是正常设计；但也可能真的把功能弄丢了。只看两张截图分不清。用一个真实案例开场：Mailinator 宽屏有 7 个导航项，窄屏菜单打开后只有 5 个，FAQ、API 真的丢了 |
| 空白 | 固定截图或 DOM 规则只能判当前状态；正常折叠和真丢失都会让控件从截图里消失，要交互才能区分 |
| 贡献（3 条） | ① 方法：结构提取、实际点击、语义匹配、目标驱动探索连成一条流程；② 和 5 个已有工具、2 个大模型直接判的基线比，加消融；③ 换网页领域、换模型、换视口看适用边界，开源代码和数据 |
| 方法 | 宽窄两版提取控件 → 点击记录效果 → 初次匹配 → 没匹配上的成为候选 → 滚动、让模型生成展开菜单的代码 → 重新匹配 → 还找不到才报缺失 |
| 实验设置 | 24 个网页主集，每页 3 次；扩展到 36 页；真值是作者人工交互标注、另一作者核对；GPT-4.1，temperature 0 |
| 结果怎么呈现 | 主表：precision 80.49%、recall 95.31%，对比 GenA11y 60.00%/8.45%、GPT-4.1 结构化提示 57.82%/39.91%。消融表：去掉探索后 precision 降 40.08%（误报大增），recall 反而略升。成本表：每页 $1.18、顺序跑 3.23 小时。失败案例图：轮播、滚动吸附 |
| 一句话卖点 | 探索不只用来走更多页面，也可以为判错找反证 |

### 对标我们

| 部分 | 范文 | 我们 |
|---|---|---|
| 动机案例 | 窄屏菜单里 FAQ、API 丢了 | 截断：文字被切，滑一下能不能露出来；开合：展开后弹层没了、内容被等比放大挤出首屏 |
| 平台 | 网页离线副本，有 DOM、能程序化滚动 | 鸿蒙原生 ArkUI 真机，只有布局树，没有 DOM；开合是物理配置变化，会触发窗口重建、状态丢失，ReFLAIR 只改宽度 |
| 交互 | 滚动、展开菜单 | 滑动（截断）、折叠再展开（开合） |
| 真值 | 作者人工交互标注 | 截断已有测试集（华为数据不能公开，论文要用重新收的）；开合要人工复核 |
| 不能当新意的 | — | "从静态判到动态复核"，ReFLAIR 已经做了。新意只能落在原生多形态设备、开合这种配置变化、以及截断三分类（合法隐藏、可滑出、真截断）的定义上 |

### 我们的假设

| 编号 | 假设 | 类型 | 要什么证据 | 实验 | 放弃条件 |
|---|---|---|---|---|---|
| H1-1 | 只看截图分不清"真截断（缺陷）"和"假截断（合法隐藏、能滑出来）"；有些看起来能滑的截断其实是真问题，加布局树也看不出来；交互复核能纠正这些误判 | 动机 | 同一批按"真截断 / 能滑出 / 合法隐藏"分层、特意多放"看似能滑其实有问题"的样本，比三档：只看截图判"是不是缺陷"、加布局树、再加滑动复核 | SE1-b | 只看截图在"真截断 vs 能滑出"上 precision、recall 都 ≥ 0.9。（10-30 更正：之前把放弃条件写成"只看截图判有没有截断就很准"，那测的是更容易的问题，不对。用户观察到判"是不是缺陷"只看图和加布局树都不行；AX-1 试跑也发现树里的文字永远是完整原文） |
| H1-2 | 开合问题在 Top App 里普遍，可以分成几类（10-30 用户判断：开合可能截两张图就直接看得出来，方法上没什么可做的，重点在普遍性和分类） | 动机 | GPT 判 fail 的准确率（849 组里判 fail 266 组，人工还没复核）；按类别的分布 | SE1-a | 人工复核后 GPT 判 fail 的准确率 < 0.6，说明现有标签不能用，要先重标 |
| H1-3 | 命令切屏（hidumper）和真手折出的问题一致 | 动机（有效性） | 30 个确认的问题用手真折复现 | SE1-c | 一致率 < 0.7，说明采集方式本身有问题，论文要改用真折 |
| H1-4 | 我们的方法在两种缺陷上都比基线好，而且成本可接受 | 贡献 | SE1-b 的三档对比加 OwlEye/Nighthawk 类检测器；每页耗时、恢复现场成功率 | SE1-b | 交互复核相对"加布局树"提升不到 10 个百分点 |
| H1-5 | 能找到被开发者确认的真问题 | 贡献 | 报给开发者或华为的问题数和确认数 | 跑完 SE1-b 后再做 | — |

## 二、方向一（SE2）以 UX 问题为目标的探索：范文 GraphDroid

> 2026-10-30 用户判断：我们在这上面不突出。截断、开合都没有什么预兆，能找到它们基本约等于覆盖率更高。H2-1 就是在检验"有没有预兆"，离线一天能做完；不成立的话这个方向不做。

*GraphDroid: Asynchronous LLM-Based Mobile App GUI Testing via History-Aware Exploration and Hybrid Intent Fulfillment*，ASE 2026，港科大、南科大。笔记 [`../notes/li2026graphdroid.md`](../notes/li2026graphdroid.md)。对照 FuncDroid（[`../notes/he2026funcdroid.md`](../notes/he2026funcdroid.md)）。

### 范文从上到下

| 部分 | 它写了什么 |
|---|---|
| 动机 | 很多功能要一串操作才能完成（填标题、日期、选颜色、保存）。传统遍历缺功能语义；纯大模型方法有三个毛病：只记最近几步、等模型时设备停着、每一步都调模型 |
| 空白 | 就是上面三个毛病，每个对应一个设计 |
| 贡献（3 条） | ① 方法框架：状态簇记忆、异步意图生成、简单和复杂意图分开执行；② 41 个 App 加 Themis 基准，和 6 个工具比；③ 开源 |
| 方法 | 冷启动深度优先 → 相似页面合并（相似度 > 0.95）→ 谱聚类成 2–20 个状态的簇 → 每簇异步让模型生成没覆盖的意图 → 去重 → 一步的交给遍历，多步的交给 UI-TARS |
| 实验设置 | 41 个 App，6 个基线，每个 2 小时、跑 3 次；统一用 GPT-4.1 和 UI-TARS-1.5 |
| 结果怎么呈现 | 每个设计主张对应一个 RQ：RQ1 覆盖（Activity 36.94% 对 LLMDroid 28.36%）；RQ2 缺陷（19 个，其中 13 个崩溃）；RQ3 意图从哪来（82.3% 来自 5 步以前的历史，直接支持"要保留完整历史"）；RQ4 时间和费用（$1.41 每 App，DroidAgent $11.97）；RQ5–6 参数和消融（每去掉一个组件都变差） |
| 一句话卖点 | 历史怎么组织、模型什么时候调、谁来执行，三件事决定覆盖、速度和成本 |

**它的弱点正好是我们的切口**（笔记"我们观察到的问题"）：
- 没有非崩溃判定器，6 个非崩溃问题是人看日志和截图找出来的；
- 10 个商业 App 上 Activity 覆盖只有 10.01%；
- 相似度 > 0.95 就合并页面，细小显示差异会被合掉，论文没测这对 UX 缺陷的影响。

### 对标我们

| 部分 | 范文 | 我们 |
|---|---|---|
| 目标 | 覆盖更多功能和代码 | 同样预算下找到更多不同的 UX 问题 |
| 主指标 | Activity 覆盖、代码覆盖、崩溃数 | 每小时不重复的 UX 问题数、功能 + 状态覆盖（商业 App 拿不到代码覆盖） |
| 判定器 | 崩溃日志加人工 | SE1 的开合、截断判定器 |
| 平台 | Android | 鸿蒙真机商业 App |
| 基线怎么比 | 同预算跑覆盖 | 别人的工具不会做开合测试，要把它们走到的页面都用**同一个判定器**测一遍，才公平 |

关于"75% 还有提升空间吗"：75% 是 GPTDroid 自己选的应用；LLM-Explorer 同批对比里只有 28.62%；那张表里人手动测也只有 66.74%。activity 覆盖率已经接近人的水平，再拼这个指标，审稿人不会觉得有意义。我们的空间在"走到的状态里有没有 UX 问题"。

### 我们的假设

| 编号 | 假设 | 类型 | 要什么证据 | 实验 | 放弃条件 |
|---|---|---|---|---|---|
| H2-1 | UX 问题集中在少数几类状态（弹层打开、输入框有字、筛选面板打开、列表填满） | 动机 | 已有的开合标签按状态类型分组算 fail 率（要先有 SE1-a 的人工复核） | SE2-a（离线，不用手机） | 各类状态的 fail 率差不多。说明不存在"去哪更容易出问题"，方向一的立足点没了 |
| H2-2 | 覆盖导向的工具很少走到这些状态 | 动机（空白） | 在鸿蒙上跑 FuncDroid、HmTest，统计它们到达的状态里这几类占多少，再用同一个判定器测 | SE2-b | 它们到达这些状态的比例和我们差不多 |
| H2-3 | 我们的探索在同样预算下找到更多不同的 UX 问题 | 贡献 | 同 App、同预算、同判定器的正面对比；消融（去掉功能命名、停滞恢复、带子目标的 CUA） | SE2-b 之后 | 不比基线多，或多出来的都是同一类问题 |

注意：之前"GPT 挑控件到新页面 9%、随机 16%"不能当证据（大模型只在卡住时调用）。要比大模型和规则，必须在同样的状态下比。

## 三、方向二 从轨迹长出功能状态图：范文 PropGen

*PropGen: Automated Property Generation for Property-Based Testing of Mobile Apps*，ASE 2026，华东师大、SMU。笔记 [`../notes/xiong2026propgen.md`](../notes/xiong2026propgen.md)。对照 ProphetAgent（FSE 2025 Industry，先建带语义的聚类转移图，再把自然语言用例合成脚本）。

### 范文从上到下

| 部分 | 它写了什么 |
|---|---|
| 动机 | 自动探索只能靠崩溃判错。Kea 用人写的"前置条件、交互、后置条件"性质能查功能缺陷，但性质要人写；直接让大模型根据应用简介写，会编出不存在的功能和控件 |
| 核心假设（原文） | 先在真实应用里把功能成功执行一遍，再从轨迹归纳性质，比凭常识猜更可靠 |
| 贡献（3 条） | ① 从运行证据生成性质的方法；② 用失败轨迹修正写得不准的性质；③ 12 个 App 上评功能发现、性质有效性、修正和缺陷发现 |
| 方法 | 提出功能假设并绑定到具体控件 → 执行 → 成功轨迹整理成行为证据（前态、动作、后态、变化）→ 先写自然语言性质再翻成代码 → 跑测试 → 人判是真缺陷还是性质不准 → 对照两条轨迹局部修正 |
| 实验设置 | 12 个开源 Android App；每个 3 小时生成、6 小时测试；两名非作者研究生独立标注，κ 0.81–0.91 |
| 结果怎么呈现 | 一个极端对比撑起整篇：从运行证据生成的性质 912/985（92.6%）有效，只读应用简介生成的 0/240 有效。然后功能发现 94.4% 有效、修正 118/127 成功、25 个新功能缺陷，和 4 个工具互补而不是全面替代 |
| 一句话卖点 | "光靠大模型不够，必须有运行时的行为证据" |

### 对标我们

| 部分 | 范文 | 我们 |
|---|---|---|
| 从轨迹里长出什么 | 可执行的功能性质 | 按"功能 + 状态"组织的页面图，也就是自动 spec |
| 拿什么当标准答案 | 人工标注性质有效性 | mobilegym-mock 里人工整理的 spec（唯品会 46 页），喜马拉雅也有 spec |
| 极端对比 | 只读简介生成 0% 有效 | 按布局模板数算覆盖：唯品会一轮 35 个模板，按 spec 只走到 10/46 个功能页面 |
| 已有积累 | — | 用户毕设 Fairy 的 App Map Learner：跟踪页面变化和引起变化的动作，建 App 知识图谱 |
| 和别人的区别要说清 | — | ProphetAgent、FuncDroid、PG-Agent、UI-KOBE 都建带语义的图。我们能不重复的只有：**拿人工 spec 当标准答案，评"图对不对"**，以及"按页面数算覆盖会高估多少"。没人评过自己的图和真实功能差多少 |

这个方向单独成篇的风险最大：建图已经很拥挤。更稳的用法是两种：一是写成评测方法类的软工文章（"按布局认页面会高估覆盖"）；二是当方向一的记忆模块。要看 G-a 的结果再定。

### 我们的假设

| 编号 | 假设 | 类型 | 要什么证据 | 实验 | 放弃条件 |
|---|---|---|---|---|---|
| H3-1 | 按布局或截图相似度认页面，会把一个功能拆成多个节点、把不同功能合成一个，不只是唯品会这样 | 动机 | 3 个 App 各 200 步，人工给每一步标功能页面名，和布局模板、GraphDroid 式的 0.95 合并、VLM 功能命名比较 | G-a | 另外两个 App 上布局模板和人工功能基本一一对应，说明唯品会只是个例 |
| H3-2 | 按页面数算的覆盖会明显高估按 spec 算的真实覆盖 | 动机 | 同上数据，算"模板数 ÷ 估计总页面"和"spec 覆盖率"的差距 | G-a | 差距 < 10 个百分点 |
| H3-3 | 从轨迹自动长出的功能图和人工 spec 足够接近，可以代替人工 spec 衡量覆盖 | 贡献 | 自动功能图对 spec 页面的召回、错合并率 | G-a 之后 | 召回 < 0.7 |

## 四、AI 篇 结构树和画面对不上：范文 arXiv 2607.04334

*Do GUI Agents Believe Their Eyes? Diagnosing State-Belief Reliance on Pixels versus Structure*，2026-07 arXiv，深圳大学。原文读过（arXiv 2607.04334）。

### 范文从上到下

| 部分 | 它写了什么 |
|---|---|
| 动机 | GUI 智能体同时读截图和结构树（DOM 或无障碍树）。现有 benchmark 只评任务成没成，不问"模型的判断是从哪个通道来的" |
| 空白 | 能看对，不等于会信对：模型单看图能答对，但结构树一冲突就跟着结构走 |
| 贡献（4 条） | ① 定义一个新指标 Perception-Fusion Gap（看对了、但冲突时信了结构的比例），加裁图复核的严格版；② 735 个探针的 benchmark，225 个是 38 个网站上天然的不一致，双人标注 κ 0.86；③ 发现各家模型都偏信结构，并用白盒消融找到原因；④ 量了后果（第一步信错，多步任务几乎必败）并比较了四种缓解办法 |
| 方法 | 成对干预：每次只改一个通道（只改结构、只改图），用确定性的选择题打分，不用模型当判官 |
| 实验组织 | 五步：确认现象 → 验证指标测的是想测的东西 → 在天然不一致上复现 → 白盒找原因 → 追到真实动作和多步任务，比较缓解办法 |
| 排除浅层解释的对照 | 反向对照（结构是对的、图被模糊）：模型这时会信结构，说明不是"一律偏信结构"而是融合失调；人类基线：人只有 0.03 跟着错误结构走 |
| 结果怎么呈现 | 跟随过期结构最高 0.88；自我恢复至多 0.03；缓解对比表：提示词几乎没用，证书检查拒掉 59–77% 的动作，一致性门控有效但每个动作多调 1.8–5.5 次 |
| 一句话卖点 | 未来的智能体不仅要知道界面状态，还要知道这个判断来自哪个通道 |

**AI 顶会这类文章靠什么中**：一个清楚的新指标，一组排除浅层解释的对照，以及量出来的后果。对照本仓库 [`../reviews/`](../reviews/README.md) 的录用规律：Spotlight 是"开放资源加一个新认识"；被拒的常见理由是"已有流程换了个名字"，比如又一个价值模型。

### 对标我们

| 部分 | 范文 | 我们 |
|---|---|---|
| 不一致从哪来 | 人工改网页文字值，38 个网站的天然不一致，旧的 Rico 手机数据 | 鸿蒙真机商业 App 的天然不一致；开合这种可控的配置变化；macOS CUA 真实失败（对话框看不见、复选框读不到状态） |
| 不一致的种类 | 主要是文字值被改 | 幽灵节点、漏掉的控件、状态读错、框错位 |
| 多步任务 | MiniWoB++，最多 6 步 | 真实 CUA 任务，带程序化打分；公开的 AndroidWorld 或 OSWorld |
| 缓解办法 | 每步都核验，最贵 | 只在可能出错的步骤核验，比"成功率 × 额外调用次数" |
| 风险 | — | "预测这一步要不要核验"容易被说成又一个价值模型，必须讲成有代价的通道选择，并和它的门控在同一基座上比 |

| 编号 | 假设 | 类型 | 要什么证据 | 实验 | 放弃条件 |
