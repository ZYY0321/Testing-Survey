# 移动端探索与 UX testing：论文借鉴、方法候选与实验依据

日期：2026-10-28。依据：10 月 27 日会议文字记录、已确认的五篇论文、现有项目代码和归档。本文是研究设计分析，没有新增实验结果；候选方法尚不构成已证实的贡献或领域空白。

**本周有两条主线：A，生成有测试价值的探索轨迹与用例；B，提高已有 UX 截断检测的可靠性。** C/G 中的故障构造、正常对照和评分机制，为这两条线服务，暂不另立一篇 benchmark 论文。五篇原文研读资料各自承担不同作用，无需把它们拼成一个大系统。

## 2. 五篇论文分别怎样把问题写成贡献

### 2.1 GraphDroid：从预算浪费出发，逐项证明设计必要性

**论文事实。** 传统探索快但缺少多步功能语义；纯 LLM 方法又有历史不足、等待生成、每步调用费用高的问题。GraphDroid 先建立 UI 转移图，将相关历史状态聚簇；模型异步提出未覆盖意图，简单意图交给启发式遍历，复杂意图交给 GUI agent。输出首先是更丰富的状态与执行轨迹，不是独立的 UX 真值。[P1，§1–3，图 3，表 1–7]

实验围绕设计逐层展开：41 个应用、六个基线，每应用两小时、三次运行；29 个可插桩应用统计方法级代码覆盖。再检查意图来源、完成率、时间费用和六组消融。例如同步生成使每动作时间从 5.33 秒变成 8.21 秒；完整历史支持大量非近期状态的意图。这些证据分别解释“为什么需要异步”和“为什么需要历史”，而不只报告总覆盖提升。

**对 A 的含义。** 学姐已有启发式 demo 的问题是重复页面、覆盖和效率，不能仅凭这一描述决定加哪种图。若重复主要来自列表内容变化，优先改状态抽象；若卡在多步输入，优先补语义意图执行；若模型等待占满预算，异步才有直接依据。机制必须对应轨迹中可定位的损失。

**不能照搬的结论。** GraphDroid 主实验的 19 个问题包含 13 个 crash 和 6 个非 crash；后者依赖研究者结合非致命日志、轨迹和截图判断。它没有自动解决一般非崩溃 oracle。因此，A 若主张“更会发现体验缺陷”，还须独立评价判错，而不能把覆盖提升直接当检出提升。[P1，§3.3]

### 2.2 OS-Genesis：把数据来源次序反过来，但仍需证明数据有用

**论文事实。** 先编任务再执行容易编出环境不支持的目标。OS-Genesis 先规则探索，保存前态、动作和后态，再由模型生成局部指令及高层目标；随后按高层目标重新执行，收集完整轨迹。轨迹奖励模型根据任务、低层历史及最后三个状态截图打 1–5 分，按分数加权采样进行监督训练，不是只保留成功轨迹，也不是以此做在线强化学习。[P2，§3–4，算法 1，附录 C/F]

论文用训练后模型在 AndroidWorld 等环境中的表现、数据多样性和奖励消融来证明构造价值。Qwen2-VL-7B 的 AndroidWorld 成功率由 Self-Instruct 数据组的 9.82% 提高到 17.41%；同表 GPT-4o/M3A 为 23.70%。这些数字回答训练数据是否有用，不回答软件缺陷是否找到。[P2，表 1]

**对 A 的含义。** 反向生成可以作为候选意图来源：先观察到进入收藏页，再形成“收藏后应能在收藏列表找到对象”的候选测试。但前半句是观察，后半句是待核实预期。若正常 APP 已有收藏失败 bug，照抄当前结果反而会学成错误规则。因此还要记录预期来自需求、可信正常版本、适用的变形关系，还是模型假设，并分别统计可靠性。

它与 GraphDroid 是两个可选切入点：前者改善训练样本来源，后者改善在线测试预算分配。可以共享交互记录，论文主张却不必同时承担训练小模型和实现整套在线探索器。

### 2.3 OS-Oracle：错误分类、合成训练与独立评价形成三段证据

**论文事实。** 给定目标、历史、截图与候选动作，critic 判断这一步是否有助于目标。系统改写正常轨迹中的动作及上下文，形成四类负例：操作失败、低效恢复、错误结束时机和定位错误。模型生成解释后进行 SFT 与一致性强化训练；独立的 OS-Critic Bench 则由模型提出动作、人工判断合理性，并允许不同于参考轨迹的合法动作。[P3，正式版 §3–5]

关键不只是“好坏成对”。最终任务成功不代表每一步都对，任务失败也不代表每一步都错；训练负例的规则标签和独立评测的人工标签必须分开。正式版 benchmark 共 738 个动作情境，手机 438 个；不是 738 个 APP 缺陷。手机版 Accuracy/F1 为 70.78%/74.30%。在线接入 UI-TARS 的 AndroidWorld 主文为 31.6%→33.2%，补充同项写成 33.6%，本文不合并二者。[P3，表 1、图 3、补充表 5]

**对 A 的两种借法。** 一是用操作有效性判断排除“测试器自己没点对”；二是把测试价值不同的轨迹做成有解释的数据。第二种尚是会议提出的可能方向：需要先定义“好”是触达目标条件、触发异常还是正确报告，而不是把长轨迹或任务成功简单标成好。若要沿 AI 数据论文叙事，还必须证明数据比等量普通轨迹更有学习价值；数据数量和人工定义四类标签本身不够。

**对 B 的有限帮助。** “滑动指向正确容器”与“该容器的内容真的被截断”是两个标签。一个合理的验证动作可能仍因网络、手势阈值或状态变化而失败；一个被 critic 拒绝的动作也不说明应用有错。动作验证最多补齐证据链中的一环。

**译稿版本提示。** 全文译稿依据明确 CC-BY 的作者 v1；正式版更新单列，本文研究分析采用已核对的正式主文及补充。两版的部分训练参数和消融数字不同，不能交叉引用。

### 2.4 ReFLAIR：探索的作用是寻找反证，降低错误报告

**论文事实。** 宽屏中可用的信息或功能，在窄屏第一眼不见了，可能只是进了菜单。ReFLAIR 提取 DOM 与截图中的信息项/操作项，实际点击记录效果，跨布局匹配；未匹配项驱动滚动或菜单展开，再匹配并撤销已找到项的缺失报告。Mailinator 案例中，展开菜单后出现的选项不再算缺失，仍找不到的 FAQ/API 才保留为问题。[P4，§2–3，图 1–3]

它已包含“候选异常→定向探索→重新判定”。24 个网页的主集 Precision/Recall 为 80.49%/95.31%；去掉探索，报告可信度明显下降。论文以信息/功能对应关系界定正确性，远强于只问截图看起来是否异常；但参照仍是另一布局，不能发现两边共同错误。[P4，§4，表 2、4]

**对 B 的差异压力。** 我们已有截图、布局和滑动，三模块组合不足以构成清楚创新。移动场景可研究的具体条件是：结构绑定不可靠、嵌套容器、手势未生效、吸附/轮播、恢复失败时，怎样避免把“证据不足”升级成“确定截断”。这需要方法与分层实验，而非只换平台重跑。

**成本也属于问题。** ReFLAIR 主实验顺序耗时平均 3.23 小时/网页；39.05 分钟是并行化估算。若采用候选驱动验证，需同时证明哪些动作增加了判断信息、哪些只是反复等待。其 DOM/XPath/alt 和浏览器滚动接口不能直接移植到 HarmonyOS。[P4，§4.2，表 3]

### 2.5 EP-Detector：先定义会伤害体验的干预，再决定怎样测试

**论文事实。** EP-Detector 不要求自然语言任务，而是选择页面控件，恢复起点，施加近似手势、位置偏移或卡顿下重复点击，比较页面/资源状态。三类风险来自操作主体、控件布局和执行环境。其基本思想是：标准动作能成功，并不能排除合理操作偏差触发另一种不良结果。[P5，§II–V]

53 个应用上共报告 5,818 条 EPA，5,136 条由志愿者按论文指标确认，精确率 88.28%；这些不是 5,136 个开发者确认的独立根因。没有完整 EPA 真值，页面覆盖也不能当缺陷召回。平均每应用 6.3 小时，导航占约 65.1%，说明局部对照测试的成本常在恢复相同起点。[P5，表 III–IV]

**对 B 的价值。** 可以把“同一候选区域在不同受控条件下的表现”组织成测试，而不依赖一次截图判断。例如同一列表在容器内上滑与页面外上滑，验证目标内容是否真正响应。这种对照用于诊断证据可靠性；位置变化导致结果不同本身并非必然 bug，单击/长按有意设计成不同功能就完全正常。

**对 A 的价值。** 发现页面之后还可以系统地产生条件变体：字体/窗口、内容长度、键盘、手势和时序。但不是把所有条件做笛卡尔积；每个变体应对应明确缺陷假设和可检查预期。

## 3. A 线：怎样从“逛更多页面”变成“产出更有用的测试”

### 3.1 起点、目标与独立预期

会议 02:04:28–02:05:51 描述了一个无模型的启发式 demo，约 20 分钟访问约 20 个不重复页面，也有重复和覆盖不足。这是口头资源说明，尚未取得该 demo 的具体代码、配置和轨迹，不能当作已复现实验。

**A 的候选目标：在固定预算内，生成覆盖不同功能条件、可重放、具有明确检查依据的移动测试。** 页面只是观测单位，测试至少包含以下字段：

| 字段 | 具体含义，以“收藏条目”为例 |
|---|---|
| 前置条件与状态来源 | 已登录；对象尚未收藏；说明条件来自实际观测、测试夹具还是需求，避免把隐藏假设当事实。 |
| 测试意图与执行证据 | 收藏指定对象并查看收藏列表；记录实际点击、输入及前后截图，保留目标对象身份。 |
| 条件变化 | 空列表/已有收藏，短/长标题，收藏后撤销再收藏。变体按缺陷假设选取。 |
| 检查与依据 | 例如“列表出现同一对象”，依据已确认功能约定；若只有模型推测，标成待核实，不能作为独立真值。 |
| 重放与结果 | 从保存的初态再走一遍，分别记录不可到达、动作无效、检查失败和真实缺陷候选。 |

预期可以来自需求或可信正常实现，也可以来自经过适用性校验的关系，例如“字体变化后必要文字仍可获得”。一次观察只能证明曾发生某个结果；它不能证明该结果符合需求。[P2、P3；S3]

### 3.2 三条方法候选及各自需要的证据

**候选 A-1：保留功能条件的状态抽象，减少无效重访。**

仅按图片去重，推荐列表换商品可能被当成新页；仅按页面名合并，又可能抹掉登录、空/非空、键盘和错误提示等重要分叉。可把“相对稳定的结构/功能身份”和“与测试相关的条件”分开记录；重访目标从“截图没见过”改为“该功能的这个条件尚未测试”。它借 GraphDroid 的历史组织和 FuncDroid 的条件视角，但具体抽象规则需由失败案例决定。[P1；S1]

必要证据不是图里节点更多，而是：人工小样本标注下，哪些合并/拆分正确；同预算下是否减少重复动作、保留更多有效条件；去掉条件表示后漏了哪些可复现问题。若只是合并更粗导致看起来更少重复，却漏掉空列表 bug，这个方案不成立。

**候选 A-2：从真实转移提出意图，再围绕未验证条件补测试。**

先观察收藏按钮确实改变局部状态，再合成收藏相关意图；重放确认可执行后，生成有依据的边界变化。与 OS-Genesis 的区别应落在“形成测试与揭示问题”，而不是重复反向生成过程。与 PropGen/FuncDroid 的区别也必须另外核对，不能以加前后条件作为全新贡献。[P2；S1、S7]

可以比较三种同预算来源：从首页直接生成目标、真实转移反向生成、反向生成再补条件。分别统计无效目标、可重放比例、经独立判断有效的检查、发现的唯一缺陷。若只增加了语言多样性，没有新条件或检出收益，就不足以支撑测试论文。

**候选 A-3：面向测试价值的轨迹数据，而非直接做全局 UX 风险预测。**

由正常轨迹及受控变化形成训练样本，但把标签拆开：到达了什么条件、是否触发异常、动作是否正确、是否正确报告。借 OS-Oracle 的负例设计与独立评测，训练探索策略、局部验证器或轨迹排序器；先选择一个学习目标即可。[P3]

难点是低成本标签：随机漏点按钮可能只造成操作失败，不能算发现缺陷的负轨迹；成功绕开故障完成任务也未必是好测试。可控应用提供隐藏的触发条件和对象身份，适合生成这类标签，但训练/评测应用和变异模板要分离。

会议中“能找 UX bug 的轨迹是好轨迹”是待定义方向，双方也讨论了全局 UX 风险不容易定向（01:54:49–01:56）。较窄的定义更可检验：同一候选区域下，哪种验证动作更能区分正常露边与真实截断。它可以成为 A/B 的连接点，尚不能直接推成全应用风险预测器。

### 3.3 “任务来自哪里”与“故障已知”并不矛盾

已有预设任务的 benchmark 可以评价执行器；它不必同时解决任务生成。因此不能仅以存在人工任务认定竞品逻辑不成立。真正需要明确的是**我们要测哪一环自动化**。[P2、P3；S4]

评测方知道注入位置，是为了建立隐藏真值；被测探索器可以完全不知道。只要没有把触发路径、变异名称和答案暴露给它，就仍可测自主发现。相反，给定“检查收藏后是否出现条目”主要测定向测试，给出坏截图只测看见后判错；三种设置应分开命名和报告，不能共同称为自由探索。

### 3.4 回归测试中的“未来 bug”应怎样定义

可检验的目标不是预言未来开发者会改坏哪一行，而是：**在正常版本上生成的测试，能否在未参与生成的后续故障版本上揭示行为破坏。** 先用正常版生成并冻结测试，再引入隐藏变异或使用可核实的历史故障版本，比较哪些测试能捕捉新增问题、哪些只是路径变了。若先看故障位置再定向生成，测到的是针对已知问题补测试，不能证明对未知回归有效。[P2；S1、S3，衍生实验设计]

例如“收藏后列表中存在同一对象”的检查，可保护后续版本的收藏保持关系；但换布局、改文案并不必然违反它。需要将功能预期与脆弱坐标/文字定位分开，否则会把合法改版当回归。初态中的账号、已有内容、日期和商店状态也应单独记录：先在固定环境检验可重放性，再主动改变有关条件检验分叉，不能把所有环境变化都消掉后宣称解决了动态环境测试。

## 4. B 线：验证动作成立以后，才判断截断是否真实

### 4.1 当前已有的基线和具体问题

本机实现位于 `D:/Projects/UX-testing/UX-Agent`。已检查的代码支持 image/layout/slide；当前流程由人到达同类页面，随后截图提候选、结构复核、必要时主动滑动，并保留 ok/bad/unknown。这已经是可用研究起点，但不能写成全应用自主探索成果。[R1]

`ux-detection.ts` 的 `recomputeOverall` 会将保留的 `slide_result=confirmed` 汇总为 bad；注释明确写到“负例误标且滑动也没动，会变成 bad”。`slide-verify.ts` 的部分路径以探测区是否变化区分 scrollable/confirmed，同时处理抓图和恢复失败。项目说明也要求人工确认是否滑对。**这证明存在需要检验的判定风险，不证明它在当前数据上发生得最多。**[R1，代码约第 554–582 行；R2]

### 4.2 同一种“没动”，至少对应四种不同原因

| 观察 | 可能解释 | 还需什么证据 |
|---|---|---|
| 候选文字没有露出更多 | 真正固定裁切；或者目标是正常省略显示 | 预期是否要求完整内容可获得；是否存在详情、展开、辅助文本等合法入口。 |
| 目标框和页面均没动 | 手势未生效、方向错误、已在边界、非滚动控件 | 目标容器绑定、动作落点/方向/时长、边界或替代动作对照。 |
| 页面动了，候选没动 | 滑动的是外层页面，候选在固定区/另一个容器 | 容器与内容对应关系，目标邻近稳定内容的位移。 |
| 候选变了或消失 | 滚动成功；也可能换页、弹窗或动态内容刷新 | 同一页面/对象身份，前后内容匹配，时序与遮罩状态。 |

因此，“探测区有无像素变化”不足以唯一解释动作，也不足以唯一解释缺陷。ReFLAIR 通过目标匹配和补充交互处理部分问题；EP-Detector 展示恢复同一状态后做局部对照；OS-Oracle 说明动作合理性需要单独标签。三者共同支持拆分证据链，但没有替我们证明某种具体算法一定有效。[P3–P5]

### 4.3 一个可检验的方法骨架：目标绑定、动作诊断、内容判断

以下为衍生设计，不是论文已有结论。

**第一步，确定候选是什么、属于哪个容器。** 保留候选图框、文本/图标身份、结构树匹配置信与候选容器集合。树与截图不在同一现场状态时，不强行绑定；嵌套列表有多个可能容器时，应保留歧义。它针对的是目标归属错误，不能靠模型最后说一句“我确认了”代替。

**第二步，诊断这次探测实际作用于哪里。** 执行预算内的定向动作，比较目标附近内容、容器内部和外围锚点。内部移动而外围稳定，可支持目标容器响应；只有整页移动，则需重新定位。完全没动时，尝试一个有解释的方向/落点对照，或确认当前位置是否边界。对照次数必须有上限，防止无限交互。

**第三步，判断内容是否可获得。** 目标内容完整显露可以撤销“不可恢复截断”；只移位但仍看不到缺失部分不算已消解；没有有效探测证据时保留 unknown。若产品允许省略且提供详情，应按既定 UX 规则作为正常例外，而非机械要求同屏显示完整文字。

**第四步，恢复并保留证据。** 恢复失败不直接证明 APP 有错；它使后续测试的起点不可靠。报告应分开保存候选、有效探测、内容前后对应、最终判断和失败原因。项目已有 restore_failed 机制，这部分属于增强其证据和状态管理，不能当作从零新增。

一个具体例子：横向卡片右边只显示半张。若在外层页面上滑，整页滚动而卡片不变，旧判断可能仍保留为缺陷；新流程先定位横向容器并左滑，若该卡片随后完整出现，判为正常露边。若对照版可正常出现，而故障版由于容器宽度/溢出设置使必要内容始终不可获得，才形成带依据的正例。若无法确认容器响应，输出 unknown，而不是靠“滑过了”认定故障。

### 4.4 这里可能形成的贡献及其反例

可检验主张是：**针对移动端嵌套容器与无效手势引起的证据混淆，显式验证探测作用范围和内容对应，能够在受限动作预算下减少正常界面的截断误报，同时保持真实问题的识别能力。**

该主张与 ReFLAIR 的区别要体现在上述移动困难及实测结果；与普通动作 critic 的区别在于判断探测是否提供了足够的产品缺陷证据。若有效动作诊断无收益，或降低误报只是因为把难例全部弃为 unknown，就不能算成立。后者必须通过覆盖率—风险曲线和 unknown 分布揭示。

字体/窗口变化、内容长度和键盘可作为受控触发条件；它们是否进入最终方法，取决于是否对应当前截断范围和可获得真值。将支付、网络与所有 UX 风险同时纳入会迅速扩大边界，本周不把它们纳入 B 主张。

## 5. 数据与故障构造：服务 AB 的证据，而非先追数量

### 5.1 资源必须按实际证据分层

| 资源 | 已知内容 | 尚不能假定 |
|---|---|---|
| UX-Agent 归档 | 299 个混合条目：222 图像、77 XML 参考；图像子集为 140 正、82 负，含不同设备。 | 不是 299 张独立图片；并非全部属于当前截断范围；部分 XML 与问题截图不同状态，不能直接作为配对真值。归档还有质量问题，未全量复核。 |
| 已有 UX 方法 | 截图候选＋布局＋滑动，人工到达页面，存在现场日志。 | 还没有本轮统一协议下的完整性能与组件增益；程序 confirmed 不是人工真值。 |
| 学姐启发式探索 demo | 会议描述已有无模型版本。 | 未收到具体实现与轨迹，不把它写成已本地验证的 baseline。 |
| 学姐的纯前端复刻 APP | 会议 02:14–02:16 确认多套可编辑前端，描述文件含组件、参考图和跳转等信息。 | 描述文件不是运行时的一一对应真值；改描述不会自动改 APP。未逐个核实代码路径、构建、状态重置和持久化。也不假定有真实后台。 |
| 公开 MobileGym++ | 与最初 OpenMobile-2 链接对应的候选环境，和团队复刻资源分别记录。 | 环境能执行用户任务，不等于已具备我们所需的截断注入、容器真值或故障发现评分。 |
| 既有 55 任务轨迹 | 有 Android 执行、请求响应、独立 Judge 和失败分析可复用。 | 是 Qwen 适配基线、非随机子集、每任务一次；不能充当本次 A/B 的完整效果实验。 |

以上归档事实来自现有资源盘点 [R3]；会议新增资源仍以文字说明为证据。本轮没有连接设备、调用检测模型或验证全部 APP。

### 5.2 最小有效数据单位应是什么

**B 的单位：同一页面、同一目标和同一初态下的一组可比较实例。** 至少记录正常版/故障版、目标对象、触发条件、预期依据、候选前图、验证动作、后图、可恢复性、动作是否有效、缺陷标签及复核状态。正常露边、合法省略、滑错容器、动态变化等难负例必须存在。它们决定方法究竟学会判错，还是只记住某种坏图样式。[P4、P5；S5]

**A 的单位：不泄漏目标的探索运行，以及其产出的测试。** 隐藏记录可到达状态、触发条件和唯一缺陷；操作器只看到允许的 APP 界面/结构与统一初态。生成后的测试另测重放、检查有效性。若给了目标缺陷或复现路径，则归入定向测试，不与无目标探索混算。

### 5.3 注入必须通过的检查

| 检查 | 对移动截断/交互故障的具体含义 |
|---|---|
| 能构建、能到达 | 修改后仍可启动并到达目标功能。到不了不算目标截断被测到。 |
| 真正激活 | 指定窗口、长内容或动作序列确实触发变化；没有触发的 mutant 不计有效正例。 |
| 确实违反预期 | 将“正常需要滚动”的内容误当裁切、将有意省略误当缺陷，都不是有效故障。 |
| 修改范围受控 | 正常/故障版本仅改变目标机制，排除额外遮罩、数据丢失等同时造成另一种失败。 |
| 真值与测试器独立 | 用源码改动、正常/故障配对重放和人工核验建立标签，不由被测 UX 模型自己认证。 |
| 避免模板泄漏 | 训练/调参与测试按应用家族、页面模板和变异类型划分；同页只改几字的样本不能随机跨集合。 |

例如，将内部可滚动容器误设为隐藏溢出、将关键标签固定为不足宽度，可以产生候选缺陷；但需要证明用户没有其他合规获取方式。把按钮回调置空可以产生交互故障，却不属于当前文字/组件/图标截断标签；它可以服务 A，不强行扩入 B。纯截图编辑只验证静态检测，不足以评价主动滑动。

这些检查借用了正常/故障对照、可执行资产和独立评价的已有思想 [S3、S6]。改代码注入本身已有工作，不能据此宣称首次自动造 bug。该批样本最终是否值得独立成为 benchmark 贡献，取决于是否产生了现有评测看不到的能力差异。

## 6. 实验怎样对应论文主张

### 6.1 A 线实验矩阵

| 要验证的主张 | 对照与产物 | 主要指标与失败解释 |
|---|---|---|
| 同预算探索更有效 | 启发式 demo；结构/图驱动策略；能够落地的语义探索近邻；使用同一执行器的本方法。 | 唯一状态/功能条件、重复动作比例、到达曲线、时间/调用费用。状态抽象需固定或独立复核，不能用自己图的节点数给自己评分。 |
| 生成的是可靠测试 | 相同应用/条件下比较首页生成、反向生成及完整方法；独立重放并抽样人工核对。 | 有效意图、重放成功、有效检查各自分母；虚构功能、前置条件缺失、执行错误和检查错误分开。 |
| 真的提高故障揭示 | 正常/故障版本，无目标提示；隐藏触发路径，记录每个唯一缺陷的证据。 | 到达、激活、正确报告分别统计；正常误报；首次检出时间。不用生成用例数量或任务成功率代替。 |
| 设计组件有必要 | 去掉条件、长期历史、反向生成或预算调度中的实际创新项。 | 组件是否改变对应中间环节，进而改变最终检出；不要求把未采用的所有候选都实现一遍。 |
| 若主打数据训练 | 相同模型、训练预算和样本量，比较普通轨迹、简单合成、所构造数据；独立应用测试。 | 学习收益、各类错误、数据量曲线、构造与标注成本。只做一次 SFT 优于底座无法证明数据构造独有价值。 |

GraphDroid 可借其覆盖/成本和消融组织，FuncDroid 可借其已知缺陷与商业应用验证，但两者重复协议不同：前者通常三次均值，后者三次取最好，不能拼成统一排名。候选基线若无法复现，应说明实现/适配范围并设置同执行器对照，不声称严格复现论文数值。[P1；S1]

### 6.2 B 线实验矩阵

| 要验证的主张 | 对照设置 | 为什么需要 |
|---|---|---|
| 主动证据优于只看图 | 直接模型、当前 image、image+layout、当前完整 slide、本方法；尽量保持同一候选源。 | 排除单纯换更强模型或候选召回变化造成的增益。另补端到端结果，避免只在完美候选上评价。 |
| 动作有效性诊断降低误报 | 在嵌套容器、边界、错向、遮罩、动态变化等分组中，去掉动作诊断或内容对应。 | 总 F1 可能掩盖目标机制；需要看到“滑错却确认”等错误是否真的减少。 |
| unknown 是合理拒判 | 报告全量 P/R、unknown 比例及标签分布；绘制不同阈值下覆盖率与已判样本错误率。 | 不得删除 unknown 后只报好看的准确率。unknown 中的真缺陷仍是未检出，正常样本也不能自动算正确。 |
| 注入结果可迁移 | 合成开发集、未见模板/应用的合成测试、独立真实案例分别报告。 | 随机拆分同模板会高估泛化；合成集再大也不能直接证明真实 HarmonyOS 有效。 |
| 代价可接受 | 动作数、恢复成功率、额外延迟/模型调用；同预算下比较。 | ReFLAIR、EP-Detector 都有明显运行开销。更多尝试带来的准确率提升应与时间一起解释。 |

需要两种真值：产品是否有截断，以及验证动作是否有效。前者用明确 UX 规则、配对页面和人工复核；后者看目标、容器、动作及实际变化。若用相同模型既造标签又评分，必须另有独立复核样本。[P3–P5]

其中精确率（Precision）是所报缺陷中有多少正确，召回率（Recall）是全部有效真缺陷中有多少被正确发现；正常误报率则以正常实例为分母。真实缺陷被输出为 unknown，仍属于未检出；正常实例被输出为 unknown 也不能算已正确通过。报告 F1 时同时列出这两个基础指标，避免一个合并分数掩盖取舍。

### 6.3 计数与公平性必须先固定

1. **按缺陷计，不按重复报告计。** 有源码、注入 ID 或确认依据时按根因去重；根因未知的真实 UX 样本，预先定义对象/现象匹配规则，并说明这是现象计数。相同问题的不同截图可以保留为场景，不能冒充多个独立根因。
2. **把失败原因对齐。** 有 bug 的 APP 上，Agent 自己点错后报 fail，不能计作正确发现。借鉴 S4 的失败位置思想，报告应指向隐藏真值对应的对象、条件与观察。
3. **固定可见信息与初态。** 截图-only 与截图＋结构是不同设置；纯前端复制应用和原生 HarmonyOS 也分别报告。登录、数据、网络/时钟等条件可控到什么程度须说明。
4. **记录随机性与预算。** 随机/LLM 探索以独立重复和区间描述波动；次数依据可承担预算预先确定，不沿用“取最好”来掩盖不稳定。真实环境失败单列，保留原轨迹。
5. **总体检出率与条件检出率并列。** 未到达、未激活、看见后漏报是不同失败。以全部有效隐藏缺陷为总体分母；以实际激活缺陷为条件分母，不能只报后者。

这不是所有会议都要求同一套指标，而是为了使本文两个主张能被证据检验。GraphDroid、ReFLAIR 与 EP-Detector 的应用数、异常定义和人工确认方式差异很大，数值不作横向强弱排序。

## 7. 论文叙事的几种成立方式

### 7.1 A 可以有方法故事，也可以有数据故事

**软工方法叙事：** 现有探索在某类状态条件上反复浪费预算或遗漏测试 → 以可观察失败建立问题 → 针对性组织状态、生成意图并执行 → 同预算证明更多有效条件和唯一缺陷。GraphDroid 的设计—消融对应、FuncDroid 的状态联系可作参照。核心终点是测试有效性，不是语言描述更丰富。

**AI 数据叙事：** 某种缺乏独立标签的测试能力难以学习 → 构造有解释且能验证的轨迹/动作数据 → 控制数据量和训练预算 → 在独立移动评测及下游测试中验证收益。OS-Genesis 和 OS-Oracle 给出两种不同数据来源。只有明确学习目标、训练证据和外部评价时，这个叙事才完整；“整理一批好坏轨迹”仍缺关键部分。

两者都可以发表方法或数据结论，但当前没有证据说明哪条已经具备创新。先以已有 demo 的真实失败类型决定主张，再选最少必要组件，比同时承担全部模块更容易检验。

### 7.2 B 的主张应从误判机制开始

现有方法已经有主动滑动，ReFLAIR 也证明探索可降低误报。B 更具体的故事是：**错误地理解验证动作，会把正常可恢复显示报成真实截断；只有确认目标归属、实际响应和内容可获得性，交互才构成判错证据。**

EP-Detector 提供受控动作比较的写法，ReFLAIR 提供寻找反证的闭环，UI-Lens 提供正常例外和移动显示评测。我们的候选贡献若成立，应同时表现为更少机制相关误报、可解释的 unknown、未见应用上的有效性与可接受成本。仅补大量注入截图和主表成绩，还不能说明方法为何需要。

### 7.3 效果一般时，仍可形成什么有依据的认识

ASOT 的价值之一是区分自动产生的改进建议、真缺陷、定位错误和时间采样问题，而不是用总报告数包装成功。若 A/B 的平均增益有限，但能通过受控实验稳定证明“某类动作/观察缺失会导致某类误判”，可以形成扎实的能力分析；是否足以单独成稿，还取决于发现是否普遍、机制是否新、证据是否超出少量案例。[S2]

跨会议借鉴的是论证方式，不是固定模板：SE 方法稿常将真实应用、缺陷与工程成本作为终点；这里选中的 ACL/CVPR 数据/模型稿更强调样本来源、训练效用和独立基准。不能据几篇论文概括所有 AI 顶会只看训练，也不能默认 SE 只看代码覆盖。
